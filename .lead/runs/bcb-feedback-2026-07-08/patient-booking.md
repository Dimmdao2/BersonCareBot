## Booking Page UX

TaskDB: `#543`.

Источник:

- На странице записи у клиента адрес не должен содержать `new`.
- Выбор дня в расписании показывать сеткой месячного календаря с отметкой "Сегодня".
- Прошедшие даты недоступны.
- Месяц можно листать вперед, если там есть записи.
- Выбранный день закрашивается, под календарем показываются слоты.

Критерии:

- Проверить текущие маршруты `/book/*` и `/app/patient/booking/*`, не ломать legacy redirects.
- UI выбора даты должен быть календарной сеткой, а не только списком/сегментом.
- Доступность дат определяется фактическими слотами, а не только календарным месяцем.

## Consecutive Multi-Slot Booking

TaskDB: `#543`.

Источник:

- В списке слотов выбранного дня нужна мультизапись последовательных слотов.
- После выбора одного времени соседний слот остается доступен.
- При выборе двух подряд можно выбрать следующий, пока есть непрерывные слоты без разрыва.
- Остальные слоты становятся недоступными.

Критерии:

- Мультивыбор допускает только непрерывную цепочку слотов.
- Нельзя выбрать слоты с разрывом, пересечением или разными ресурсами/услугами без явного продуктового решения.
- Перед созданием записи нужно определить, создается одна длинная запись или несколько последовательных записей. Это продуктовый выбор; если не подтверждено, первый автопроход должен оформить вариант и вынести вопрос.

## Book Another Person

TaskDB: `#543`.

Источник:

- Если залогиненный клиент вводит чужое ФИО или по телефону видно, что это другой человек, нужно дать выбор: "записываете себя" или "другого человека".
- ФИО другого человека не должно менять учетку записывающего.
- В записи должно быть видно, кто придет, и кто записал; записавший кликабелен для связи.
- На приеме должна быть возможность создать учетку для пришедшего человека.

Критерии:

- Не перетирать `platform_user` текущего аккаунта чужим ФИО.
- Нужна модель "booking actor" vs "attendee/client". Если существующая модель не поддерживает это явно, задача требует проектирования.
- Учитывать privacy/PII и дальнейший merge, чтобы родственники/друзья не склеивались с пациентом.
- Для ночного автопрохода: сначала аудит текущей модели `patient-booking` и `appointment_records`, затем минимальный план миграции/полей.
