## ВЕРДИКТ: PASS

проверена инъекцией настоящего пролома. Ни одного BLOCKER-условия из брифа не сработало.

## 1. Проба доказывает обещание, а не радуется нулю — ПОДТВЕРЖДЕНО (тест)

Ловушка пустоты реализована сильнее, чем `pg_class.reltuples`: перед утверждением «A не видит
чужого» проба **привилегированной ролью** (`sudo -n -u postgres`, суперпользователь → BYPASSRLS)
читает фактическое содержимое и берёт до двух образцов `organization_id` на таблицу. Таблица без
строк чужой организации не засчитывается пройденной, а уходит в перечень непроверенных с причиной.

Независимая сверка, что доказывать было что:

```
$ sudo -n -u postgres psql -X -A -t -d bcb_webapp_dev -c "SELECT count(*) FILTER (WHERE organization_id
    <> 'd0000000-0000-4000-8000-000000000004'), count(*) FROM public.be_appointments;"
394|406
```

То есть в момент зелёного прогона суперпользователь видел 394 чужие строки там, где арендная роль
под контекстом клиники A увидела ноль. Утверждение нетривиально.

Итог прогона (`RUN_TENANT_ISOLATION_WALL_DB=1 node --test …`): **77 таблиц из 117** доказано на
`bcb_webapp_dev`, **26 из 117** на `bersoncarebot_test`. Оба прогона зелёные.

## 2. Инъекция настоящего пролома — ПОДТВЕРЖДЕНО (тест)

Стена ослаблена на живой базе, прогон, стена восстановлена:

```
$ sudo -n -u postgres psql -d bcb_webapp_dev -c "CREATE POLICY zzz_audit_fault_injection
    ON public.be_appointments AS PERMISSIVE FOR SELECT TO app_staff USING (true);"
$ RUN_TENANT_ISOLATION_WALL_DB=1 node --test deploy/postgres/privileges/tenant-isolation-wall.devDbProof.test.mjs
$ sudo -n -u postgres psql -d bcb_webapp_dev -c "DROP POLICY zzz_audit_fault_injection ON public.be_appointments;"
```

Проба покраснела и **назвала таблицу, чужую организацию и число строк**, а не выдала голое число:

```
not ok 1 - клиника видит только свои строки
  СТЕНА АРЕНДАТОРА ПРОТЕКЛА на базе bcb_webapp_dev.
  Контекст клиники d0000000-…-0004 (актор 1ff9e592-…) вернул строки других организаций:
    • public.be_appointments: a0000000-0000-4000-8000-000000000001 x394
  проверено таблиц: 77 из 117 объявленных под стеной клиники.
```

Побочно доказано, что `SET LOCAL SESSION AUTHORIZATION` из-под postgres реально роняет
BYPASSRLS: без инъекции те же 394 строки невидимы, с инъекцией — видны.


Механизм правильный и однородный с репозиторием; неточна формулировка.

# НАХОДКИ

## F1 · 32 таблицы под стеной клиники не входят в предмет проверки и не видны в перечне непроверенных

Предметы отбираются условием `table.org === true && TENANT_WALLS.has(table.wall)`
(`tenant-isolation-wall.devDbProof.test.mjs:72`). Флаг `org` в декларации и живая схема расходятся.

Достижимый сценарий: в декларации 218 ACTIVE-таблиц; под стенами арендатора (`clinic`,
`clinic+patient`, `reference-org-copy`, `platform-role+clinic`, `parent`) стоит 169, из них проба
берёт 117. Оставшиеся 52 отсеиваются по `org !== true` **до** переписи — поэтому они не попадают ни
в «доказано», ни в «не проверено». Из этих 52 **32 имеют живую колонку `organization_id` И открыты
`app_staff` на SELECT**, то есть проверяемы ровно тем же способом:

```
$ sudo -n -u postgres psql -X -A -t -d bersoncarebot_test -c "SELECT s.t FROM (VALUES …) AS s(t)
   WHERE has_table_privilege('app_staff', to_regclass(s.t),'SELECT')
     AND EXISTS (SELECT 1 FROM pg_attribute a WHERE a.attrelid=to_regclass(s.t)
                  AND a.attname='organization_id' AND a.attnum>0 AND NOT a.attisdropped);"
32 строки, среди них: be_payments, be_payment_intents, be_refunds, be_patient_packages,
be_patient_timeline_events, support_conversations, support_conversation_messages, symptom_entries,
be_booking_form_submissions, system_settings, user_phone_history
```

Из них уже сегодня были бы доказуемы (лежат строки ≥2 организаций): **8 на `bcb_webapp_dev`**
(`support_conversations`, `support_conversation_messages`, `be_patient_timeline_events`,
`be_appointment_cancellations`, `be_appointment_history_events`, `saas_organization_trials`,
`saas_org_entitlement_overrides`, `system_settings`) и **2 на `bersoncarebot_test`**
(`be_patient_packages`, `be_package_usages`).

**Утечки здесь нет** — проверено отдельно: все 32 несут permissive-политику `app_staff` по
`current_org_id()` и `relrowsecurity/relforcerowsecurity = true/true`. Это дыра в ПОКРЫТИИ и в
ЧЕСТНОСТИ отчёта, а не пролом.

Последствие: строка «доказано на 26 таблицах из 117 объявленных под стеной клиники» занижает
знаменатель — читатель не узнает, что переписка пациентов и платежи вне предмета вовсе. Обещание
«таблица, добавленная в декларацию завтра, попадает под проверку сама» держится только для тех,
кому кто-то руками проставил `org: true`.

## F2 · Отказ гейта по внутренней причине оставляет TEST лежать, и остановить его нечем

Место врезки (`deploy/host/deploy-test.sh:187-197`) — после сверки прав и до `systemctl restart`.
Но по порядку скрипта проба стоит **после** необратимых шагов, а не до них:

```
deploy-test.sh:126  systemctl stop … (все 5 юнитов)   ← WRITERS_STOPPED=1
deploy-test.sh:135  GENERATOR --shared-role-baseline  (DDL прав)
deploy-test.sh:140  migrate-local.mjs                 (миграции схемы — НЕОБРАТИМО)
deploy-test.sh:142  migrate-integrator-local.mjs      (НЕОБРАТИМО)
deploy-test.sh:158  reconcile-access.mjs
deploy-test.sh:196  ← НОВЫЙ ГЕЙТ
deploy-test.sh:199  systemctl restart …
```

`fail` в этой точке уходит в `cleanup()`, который печатает «TEST writers remain stopped after failed
migration/deploy» и выходит: миграции применены, службы стоят, среда лежит до ручного разбора. Для
настоящей утечки это правильно. Проблема в том, что проба падает и **по причинам, не связанным со
стеной**, и тогда цена та же:

- `assert.notEqual(exercised.length, 0)` (строка 257) — «ДОКАЗЫВАТЬ НЕЧЕГО»: срабатывает, если в базе
  нет второй клиники со строками. Это условие **данных**, не кода. На `bersoncarebot_test` сейчас
  3 организации, гейт зелёный — но чистка фикстур или узкий сид роняют выкатку;
- `assert.notEqual(candidates.length, 0)` (строка 192) — нет ни одного действующего сотрудника;
- `assert.ok(login)` (строка 214) — у порта нет staff-capability;
- отказ `sudo -n -u postgres psql` (строка 113 бросает) — права локального сокета.

Плюс **нигде нет таймаута**: `spawnSync` (строки 97-99) вызывается без `timeout`, `statement_timeout`
не ставится. Один прогон читает `count(*)`/`string_agg` по 77 таблицам в одной транзакции (на dev —
587 мс). Заблокированная или разросшаяся база подвешивает выкатку **навсегда, со стоящими службами**,
и никакой сторож её не снимет.

Достижимый сценарий целиком: выкатка на TEST после чистки демо-данных до одной клиники → проба
падает со словами «доказывать нечего» → `fail` → пять юнитов остаются остановленными, база уже
мигрирована. Владелец видит лежащий TEST и сообщение, которое не про поломку кода.

## F3 · На красном прогоне «покрытия нет» перечень непроверенных молчит — ровно там, где он нужнее всего

`assert.notEqual(proven.length, 0)` стоит на строке 286, а печать перечня — на строках 291-295.
Второй коммит поднял перечень выше вердикта об утечке, но не выше этой проверки.

Доказано инъекцией (точечный, полностью откатанный REVOKE, после прогона `GRANT` вернул право):

```
$ sudo -n -u postgres psql -d bcb_webapp_dev -c "REVOKE EXECUTE ON FUNCTION
    app.require_accepted_context(name,name,app.port_context_class,text,bytea,regprocedure) FROM app_staff;"
$ RUN_TENANT_ISOLATION_WALL_DB=1 node --test …/tenant-isolation-wall.devDbProof.test.mjs
  строк «не проверено» напечатано: 0
  error: 'доказывать нечего: ни одна из 79 наполненных таблиц не читается по staff-пути на базе bcb_webapp_dev'
$ … GRANT EXECUTE … TO app_staff;   # восстановлено, проба снова 77/117 зелёная
```

Последствие: в прогоне, где покрытие обвалилось ПОЛНОСТЬЮ, человек получает одно число и ни одной
таблицы, ни одного SQLSTATE — хотя причина (`42501 permission denied for function
require_accepted_context`) собрана в `refused[].failure` и просто не печатается. Это тот же класс,
который чинил коммит `a752393b9`, оставшийся в соседней ветке.

Побочно: в этом прогоне тесты 2 и 3 остались ЗЕЛЁНЫМИ (тест 3 доволен, потому что всё отказало с
42501). Полный обвал прав арендной роли выглядит как «2 из 3 зелено».

## F4 · Заявление «в `pnpm run ci` не входит» неверно (низкая цена)

Глоб `deploy/postgres/privileges/*.test.mjs` забирает файл; он входит в `pnpm run ci` и там
