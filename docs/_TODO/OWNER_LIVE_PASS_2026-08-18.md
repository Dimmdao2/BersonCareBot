      **Что происходит по факту.** Живой прогон на DEV под ролью владельца клиники
      (`dev:clinic-admin`, организация «DEV Demo Clinic»): `POST /api/admin/booking-engine/branches`
      → `403 {"ok":false,"error":"entitlement_required","mechanic":"branches"}`. На экране «Локации»
      красным выводился **машинный код `entitlement_required`** — это и было «(ошибка)».
      Под твоим врачебным аккаунтом («Точка Здоровья») тот же запрос отвечает `200`: у этой
      организации тариф «ПОЛНЫЙ ДОСТУП - РАЗРАБОТЧИК» плюс персональный override `branches`.

      **Почему 403.** «Филиалы» — механика класса «запас»
      (`modules/org-entitlements/types.ts:78`). Для такого класса механика включена ТОЛЬКО при явно
      заданной числовой квоте в тарифе (`modules/org-entitlements/service.ts:338-340`); отсутствие
      квоты = «доступа нет», а не «без ограничений». Дальше `requireEntitlementForMutation(ctx,
      'branches')` в `app/api/admin/booking-engine/branches/route.ts:32` отказывает.
      Замер по `/api/admin/commercial` 18.08: квота `branches` задана **только** в тарифе «ПОЛНЫЙ
      ДОСТУП - РАЗРАБОТЧИК». У активных тарифов **«СТАРТ», «ПРОФИ», «КЛИНИКА» и «DEV Trial»
      `quotas` пустой** — значит ни одна клиника на них не может завести **ни одной** локации
      (и по той же причине — ни квоты пациентов, ни объёма файлов). Провижининг новой организации
      физическую локацию не создаёт (`modules/organization-provisioning/service.ts` — филиалов не
      трогает), так что клиника после регистрации остаётся вообще без локации.

      **Что починено кодом** (это отказ объяснить, а не разрешить):
      `app-layer/guards/requireEntitlement.ts` — `requireEntitlementForMutation` теперь отдаёт то же
      человеческое объяснение, что уже отдают read-адаптер и отказы Server Actions, вместо голого
      кода. Живой прогон на исправленной сборке: на экране «Локации» вместо `entitlement_required`
      теперь «Невозможно выполнить действие: этот раздел не входит в ваш тариф. Чтобы выполнить
      действие, включите этот раздел в тарифе клиники.» Поведенческие тесты:
      `app-layer/guards/requireEntitlementReadOnlyRefusesWrites.test.ts` (отказ несёт объяснение) и
      `app/app/settings/BookingSoloLocationsSection.ui.test.tsx` (созданная локация появляется в
      списке без перезагрузки; отказ показывается текстом, а не кодом).

      **РЕШЕНИЕ ВЛАДЕЛЬЦА 18.08 (дословно):** «если в тарифе не указано число, механика считается
      выключенной, а не безлимитной — ЭТО БРЕД. Механика выключена если не включена ее галочка. ЕСЛИ
      ГАЛОЧКА ВКЛЮЧЕНА — НАХУЯ ЕЕ ВЫКЛЮЧАТЬ ТУТ ЖЕ СОСЕДНИМ ФЛАГОМ???? ТАМ НЕ НАДО ВООБЩЕ СТАВИТЬ
      ВАРИАНТ ВЫКЛЮЧЕН — ЛИБО ЛИМИТ ЛИБО БЕЗ ЛИМИТА для всех таких механик с лимитом».

      Обе прежние развилки (дописать квоту данными / освободить первую локацию) СНЯТЫ: владелец
      правит не эти тарифы, а саму модель. Действующее правило — **у механики с лимитом состояния
      «выключено» нет**: тариф выбирает либо число, либо «без лимита». Пустое значение больше не
      имеет права означать «доступа нет».

      Замер 18.08, из-за чего это и всплыло: `branches`, `patient_count`, `files` **вообще
      отсутствуют** в `mechanics` тарифа (там только булевы механики: promo, booking, courses,
      warmups, …) — они выражены исключительно числом в `quotas`. У «СТАРТ», «ПРОФИ», «КЛИНИКА»
      `quotas = {}`, у «ПОЛНЫЙ ДОСТУП - РАЗРАБОТЧИК» — `{"kind":"unlimited"}`. То есть «галочки»,
      про которую говорит владелец, для этого класса не существует; включить механику нечем.

      **Последствие правила, названное владельцу заранее:** как только пустое станет означать «без
      лимита», «СТАРТ»/«ПРОФИ»/«КЛИНИКА» перестанут ограничивать не только филиалы, но и число
      пациентов и объём файлов — до тех пор, пока владелец не впишет туда числа в конструкторе.
