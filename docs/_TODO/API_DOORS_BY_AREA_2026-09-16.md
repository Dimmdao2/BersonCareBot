## Решение владельца 16.09: дверь тарифа перестаёт быть опциональной

Владелец, дословно: **«у нас же есть уже не-обходимый порт доступа в БД. Почему не проверять это там?»**
и **«но вообще именно так и надо сделать как ты сказал - нет поля - нет доступа»**.

### Что показал разбор А2

Аудит 176 докторских маршрутов нашёл 51 запись, проходящую мимо проверки тарифа. Причина НЕ в том,
что портов много, а в том, что **защита опциональная**:

- решение «позволяет ли тариф» принимается в ОДНОМ месте — `checkEntitlement`
  (`apps/webapp/src/app-layer/guards/requireEntitlement.ts`); второй реализации нет;
- карта «какой обработчик какой механикой защищён» тоже одна —
  `apps/webapp/src/app-layer/entitlements/protectedActionRegistry.ts`, и её сверяет с кодом
  `apps/webapp/scripts/check-s4-entitlement-coverage.ts`;
- но дверь ВПИСЫВАЕТСЯ строкой в каждый обработчик
  (`rg -n "requireEntitlementForMutation\(" apps/webapp/src --glob '!**/*.test.*' | wc -l` → 126),
  и сверка покрытия видит только тех, кто УЖЕ объявлен в реестре. Не вписал строку и не завёл запись —
  проверять нечего, всё зелено.

### Почему не на уровне порта БД

Порт БД видит SQL и принципала, но не видит механику операции. Соответствие «таблица → механика» не
однозначно: в одну таблицу пишет и закрытый путь, и намеренно разрешённый — удаление ради
освобождения исчерпанной квоты, расход уже купленного абонемента, обязательный журнал доступа.
Правило на уровне SQL либо перекроет разрешённое, либо потребует помечать каждую операцию механикой —
то есть то же объявление, только в худшем месте, и отказ дойдёт до человека как `42501`, а не фразой
о тарифе.

**При этом непроходимый порт у нас УЖЕ есть и заказан владельцем 01.08** —
`apps/webapp/src/app-layer/entitlements/mechanicWriteClearance.ts`: дверь, приняв решение, оставляет
метку на асинхронном продолжении, а функция записи отказывается выполняться без метки для своей
механики. Это конструкция, а не сканер исходников: её нельзя обмануть форматированием или
переименованием. Дыра в том, что метку спрашивают не все записи:
`rg -c "assertMechanicWriteClearance" apps/webapp/src/app-layer/di/buildAppDeps.ts` → 25.

### Этапы

- [ ] **А5. Компилятор заставляет объявить (слой 1, «нет поля — нет доступа»).** У
      `requireDoctorWorkspaceApiContext` появляется ОБЯЗАТЕЛЬНОЕ поле намерения: пишет такую-то
      механику / кабинетная запись без механики / не пишет вовсе. Новый маршрут не собирается, пока
      автор не ответит. Существующие вызовы (`rg -c "requireDoctorWorkspaceApiContext(" …` — 139)
      проходятся разово, значение берётся из реестра защищённых действий, а не выдумывается.
      Объявленная запись сама зовёт общую дверь — руками её больше не вписывают.
- [ ] **А6. Отказ живёт в ГЛАВНОМ порте БД (слой 2) — уточнение владельца 16.09.** Дословно:
      «я имел ввиду порт БД вообще - главный». Проверка ставится не в функции записи (их десятки), а
      в обёртке транзакции единственного исполнителя `getDrizzle()`
      (`apps/webapp/src/app-layer/db/drizzle.ts:373`): принципал сотрудника + запись + НЕТ метки
      намерения → отказ. Метку ставит дверь из А5. Это сильнее размазанной проверки: новый маршрут,
      новый сервис и новый скрипт упрутся в тот же порт.
      **Порт не придумывает ответ — он требует, чтобы ответ был дан.** Механику и разрешённость он
      знать не может (в одну таблицу пишет и закрытый путь, и намеренно разрешённый), поэтому его
      роль — отказать записи без объявленного намерения.
      Три замера/решения ДО реализации:
      1. правда ли каждая запись идёт через `db.transaction()` — конвенция это утверждает
         (комментарий в `drizzle.ts:271-273`), но проверки на неё нет; запись мимо транзакции в
         горло не попадёт;
      2. фоновые записи (кроны, интегратор, медиа-воркер, миграции) не имеют ни двери, ни
         обработчика — им нужна своя метка «системная работа», иначе порт их зарежет; список
         конечный и перечислимый;
      3. отказ обязан дойти до человека ФРАЗОЙ: порт бросает типизированную ошибку, слой API
         превращает её в отказ с названием механики — иначе на экране окажется `42501`.

      **Замер ведущего 16.09 — где именно ставить проверку.** Первый замер («правда ли каждая запись
      идёт через транзакцию») дал ОТРИЦАТЕЛЬНЫЙ ответ, и это меняет точку установки:

      ```bash
      rg -l "\.(insert|update|delete)\(" apps/webapp/src --glob '!**/*.test.*' | wc -l   # 200 файлов
      rg -n "\.(insert|update|delete)\(" apps/webapp/src --glob '!**/*.test.*' | wc -l   # 693 строки
      # из 200 файлов упоминание транзакции есть только в 41
      rg -n "getPool\(\)" apps/webapp/src --glob '!**/*.test.*' | grep -vc "app-layer/db/drizzle.ts"  # 74
      ```

      То есть конвенция «каждая мутация внутри `db.transaction()`» (комментарий `drizzle.ts:271-273`)
      как минимум не подтверждается по файлам, а кроме drizzle-пути есть ещё **74 места, берущие
      сырой пул** и пишущие текстовым SQL мимо билдеров.

      **Но горло всё равно есть, и оно двойное, обе половины — по одной функции:**

      - `getDrizzle()` — `apps/webapp/src/app-layer/db/drizzle.ts:373`, уже обёртка: она оборачивает
        `select`/`execute`/транзакции принципалом. Точно так же оборачиваются входы записи
        `insert`/`update`/`delete` — и тогда транзакция перестаёт быть условием;
      - `getPool()` — `apps/webapp/src/infra/db/client.ts:67`, единственная фабрика соединения
        (единственное `new Pool(` — `webappPoolProvider.ts:293`, и оно вызывается из неё).
        Обёртка `query` закрывает все 74 сырых пути.

      Всё, что пишет в базу, проходит через одну из этих двух функций. Значит проверка в них —
      действительно непроходимая, а не «почти».

      **Замер ведущего 16.09 по вопросу владельца «а у фоновых воркеров дверь какая?» — метку им
      заводить НЕ надо.** У фоновых работ дверь есть, и они уже сами себя объявляют:

      - `verifyInternalJobBearer` — собственные фоновые задания вебаппа, 17 маршрутов `api/internal/**`;
      - `verifyIntegratorSignature` — подписанные вызовы интегратора в вебапп, 15 маршрутов;
      - каждый такой маршрут первым действием делает
        `enterWithDbInfraPrincipal({ source: 'api/internal/<путь>:POST' })`, то есть входит с
        принципалом `infra` и названным источником;
      - весь список обязательных заданий уже сведён в ОДИН типизированный манифест
        `apps/webapp/src/modules/operator-health/backgroundJobManifest.ts` (маршрут, метод, принципал,
        расписание, таймаут, среда); крон-шаблоны, реестр здоровья и `run-internal-job.sh` — его
        проекции, а выкладка сверяет манифест с реально установленным расписанием.

      Принципалы типизированы в `packages/db-principal`: `staff`, `patient`, `organization`,
      `clinicBilling`, `integrator`, `platform`, `bootstrap`, `infra`. Поэтому правило порта короткое
      и не требует нового вида метки:

      - `staff` + запись → требуется объявленное намерение из А5, иначе отказ;
      - `infra`, `integrator`, `platform`, `bootstrap` → тариф клиники к ним не относится, запись идёт;
      - `patient` → тарифа у пациента нет, отдельный разговор.

      **Из-за этого меняется задача режима наблюдения.** Он нужен не чтобы собрать список фоновых
      писателей — манифест их уже перечислил, — а чтобы найти записи, приходящие ВООБЩЕ БЕЗ
      принципала. Если такие есть, это дыра важнее тарифной: мимо принципала проходит и разграничение
      арендаторов.
