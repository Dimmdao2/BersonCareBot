# D15b/7a Ш9 — субъектные колонки покинули акторский корень

Дата: 2026-08-22. Ветка: `wt/d15b7a-step9-20260822`.

## Итог

`height_cm`, `weight_kg`, `gender`, `birth_date` перенесены из `public.platform_users` в существующий
клинический профиль `public.doctor_patient_support`. Врачебные чтение и запись теперь используют один
носитель; FIO-зеркало больше не копирует дату рождения в `user_identity`. Миграция переносит значения,
проверяет равенство четырёх счётчиков и только затем удаляет колонки акторского корня.

Новая таблица не создана. `doctor_patient_support` выбран потому, что это уже одна строка профиля на пациента
(`uq_doctor_patient_support_patient`), класс P, `organization_id`, `ENABLE + FORCE RLS`, staff current-clinic
стена и patient self/current-clinic чтение. `user_identity` не выбран: Ш6 уже закрепил его как акторский
self-service профиль, а не клинический субъект.

## 1. Замер DEV до переезда

Команда и результат:

```bash
sudo -n -u postgres psql -X -h /var/run/postgresql -p 5432 -d bcb_webapp_dev \
  -v ON_ERROR_STOP=1 -A -F '|' -t -c \
  "SELECT count(*) AS rows, count(height_cm) AS height_cm,
          count(weight_kg) AS weight_kg, count(gender) AS gender,
          count(birth_date) AS birth_date
     FROM public.platform_users;
   SELECT role,
          count(*) FILTER (WHERE height_cm IS NOT NULL OR weight_kg IS NOT NULL
                            OR gender IS NOT NULL OR birth_date IS NOT NULL)
     FROM public.platform_users
    GROUP BY role
   HAVING count(*) FILTER (WHERE height_cm IS NOT NULL OR weight_kg IS NOT NULL
                            OR gender IS NOT NULL OR birth_date IS NOT NULL) > 0;"
```

Результат: `304|0|0|1|0`, носитель: `client|1`. То есть до переезда непусты:
`height_cm=0`, `weight_kg=0`, `gender=1`, `birth_date=0`; значение принадлежит клиенту.

Выбор таблицы проверен командой:


## 3. Миграция и сохранность данных

Миграция: `20260822T200000_patient_demographics_leave_the_actor_root.sql`.

- создаёт четыре nullable-колонки и gender-check в существующей таблице;
- отказывает, если клинические значения обнаружены у не-client актора или два старых birth-date зеркала
  расходятся;
- переносит все ненулевые значения, сохраняя существующий `organization_id`, иначе выбирая active, затем
  invited enrollment;
- сверяет четыре независимых счётчика до/после и только потом удаляет старые колонки;
- не содержит `GRANT`, `REVOKE`, `CREATE/ALTER POLICY`.

Rollback-only DEV preflight:

```bash
bash deploy/host/migrate-dev.sh --preflight
```

Результат: EXIT=0, `pending=2 total=48`, `ROLLBACK`, `migrate-dev preflight: PASS`. Сообщение самой
миграции: `height_cm=0, weight_kg=0, gender=1, birth_date=0`. Это одновременно выполненный перенос и
сверка `до == после` в кандидатной транзакции; DEV после команды не изменён. `--execute` не запускался.

A→B cutover получил отдельный явный transform из `cutover_source_public.platform_users` в
`public.doctor_patient_support` и ту же четырёхсчётчиковую остановку при потере данных.

## 4. Права

Права изменены только в декларации и сгенерированных reconcile-артефактах. Миграция прав не выдаёт и
политик не создаёт.

Появившиеся права:

1. `app_staff`: column `INSERT` на `doctor_patient_support` расширен `birth_date`, `gender`, `height_cm`,
   `weight_kg` и `id`. `id` необходим: Drizzle на INSERT перечисляет defaulted UUID-колонку.
2. `app_staff`: column `UPDATE` расширен ровно четырьмя демографическими колонками.
3. `app_seam_phone_binding_owner`: column `SELECT(patient_user_id,height_cm,weight_kg,gender,birth_date)`
   для проверки, что merge-source не пуст.
4. Для нового relation-surface того же named root генератор добавляет его стандартные restrictive
   owner-gate и permissive seam-business policy на `doctor_patient_support`.

Новых table-level grants нет. Существующие table-level `SELECT` для `app_staff` и `app_patient` не
расширялись; их прежняя tenant/patient RLS-стена применяется к новым полям. Одновременно удалены больше не
нужные column grants старых `platform_users`/`user_identity.birth_date` поверхностей.

```bash

```

Результат: оба `privileges` и оба `org-allowlist` артефакта DEV/TEST совпадают побайтно.
