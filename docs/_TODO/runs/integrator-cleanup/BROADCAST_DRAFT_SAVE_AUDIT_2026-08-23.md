## 2. Клинику подменить нельзя — PASS

`app.current_org_id()` — принятый контекст, не аргумент клиента: организация попадает в claims из серверного
staff-принципала (`apps/webapp/src/infra/db/portContextRuntime.ts:394`), а не из данных запроса.

Проверил то, чего автор не проверял, — можно ли вообще ПРИНЯТЬ чужую клинику. Проба (rollback-only, DEV):
актор `10d0d77d…` (клиника `26aca960…`) заявляет в `app.begin_port_context` клинику `a0000000-…-0001`:

```
ERROR: port context organization claim is not an active membership of the actor
CONTEXT: app_ext.assert_port_context_claim → app.install_port_context → app.begin_port_context
foreign_org_claim_sqlstate=42501
```

То есть подмена отбивается ДО всякого RLS, на приёме контекста. Плюс независимо от этого `WITH CHECK` арендной
политики отбивает чужой литерал — воспроизвёл прогоном теста автора (`foreign_probe=42501`). Две стены, обе живые.

## 3. Обновление существующего черновика — FAIL

`ON CONFLICT (doctor_user_id) DO UPDATE` в `pgBroadcastDrafts.ts:59-68` **не содержит `organization_id`** — и
содержать не может, `UPDATE`-гранта на эту колонку нет. Политика `rev10_saas_org_dormant_p0_8_3` объявлена
`FOR ALL`, поэтому её `USING` применяется к УЖЕ ЛЕЖАЩЕЙ строке: если та не принадлежит текущей клинике, upsert
падает целиком.

Живая проба на `bcb_webapp_dev` (кандидатный грант + строка-фикстура ставятся внутри транзакции, вся транзакция
`ROLLBACK`; production-shape `INSERT` — с `app.current_org_id()`, как в коде):

| Что уже лежит в `broadcast_drafts` | Результат сохранения |
|---|---|
| строки нет | `sqlstate=00000`, строка записана |
| `organization_id` = своя клиника | `sqlstate=00000`, строка обновлена |
| `organization_id` = `NULL` | **`42501` `new row violates row-level security policy (USING expression)`** |
| `organization_id` = чужая клиника | **`42501`**, тот же текст |

Постпроверка после всех проб: `rows=0`, `has_column_privilege(...,'organization_id','INSERT')=false` — в базе
не осталось ни строк, ни прав.

Отдельно проверил, что отказ ещё и НЕМОЙ. Строка с `NULL organization_id` не видна форме чтения `loadDraft`
(`SELECT … WHERE doctor_user_id = $1` под тем же staff-контекстом): `E_loadDraft_rows=0`. Врач открывает
рассылку, видит пустой черновик, набирает текст заново, жмёт «Сохранить черновик» — и получает тот самый `500`.
И так каждый раз: из интерфейса состояние не разруливается вообще никак.

**Достижимость — два независимых пути, ни один не закрыт схемой:**

1. **Легаси-строка.** `organization_id` — `is_nullable=YES`, без `DEFAULT`, без `NOT NULL`
   (`information_schema.columns` на DEV; в эталонном снимке прода
   `deploy/postgres/generated/prod-to-target/schema-pre.sql:23533` — то же самое). Бэкфилла в текущем дереве
   нет: миграция `0165_p0_4_p8b_broadcast_drafts_org.sql` в репозитории отсутствует (`find`/`grep` по
   `apps/**/*.sql`, `deploy/postgres/**` — пусто), её спецификация
   (`docs/_TODO/SAAS_FOUNDATION/scope-derivation/p0-4-batches.tsv:7`) сама допускает недозаполнение
   («…**otherwise** current single org»). Прежний код колонку не писал НИКОГДА, поэтому любая строка, созданная
   после бэкфилла, несёт `NULL`.
2. **Двойное членство, без всякого легаси.** Ключ конфликта — `broadcast_drafts_doctor_user_id_key UNIQUE
   (doctor_user_id)` (`schema-post.sql:564`), то есть ОДИН черновик на врача на всю платформу, при том что сама
   строка арендная. Врач, состоящий в двух клиниках, сохраняет черновик в клинике A, переходит в B — и там
   черновик и невидим, и несохраняем, навсегда.

**Что это значит для галочки владельца.** На TEST и на DEV таблица сейчас **пуста** (`SELECT count(*)` = `0` в
`bersoncarebot_test` и `bcb_webapp_dev`), врачей с двумя активными членствами на DEV нет — значит строка обхода
`2026-08-23_TEST_FULL_WALK.md:198` при живом клике **позеленеет**. Дефект приезжает вместе с правкой и вскроется
там, где строки уже есть, либо как только у врача появится вторая клиника. Прод отсюда не измеряю — не трогаю.

Правку не делал (бриф запрещает). Направление для воркера, не скоуп от аудитора: `organization_id` в `DO UPDATE`
писать нечем без `UPDATE`-гранта, поэтому решение — либо `WHERE`-ветка/предварительное удаление чужой строки,
либо ключ конфликта `(doctor_user_id, organization_id)`, либо `NOT NULL` + бэкфилл. Выбор — за владельцем/лидом.

## 4. Чтение своего черновика — PASS, чужого не течёт

- После успешного сохранения строка читается обратно тем же врачом: `readback_rows=1` в обеих зелёных пробах.
- Другому врачу той же клиники строка на уровне БД доступна — политика арендная, а не персональная
  (`organization_id = app.current_org_id()`), что совпадает с решением «staff — org-wide, вариант A».
  На уровне продукта утечки нет: `loadDraft` фильтрует `WHERE doctor_user_id = $1`, то есть композер грузит
  только собственный черновик врача. Расхождения с решением владельца не нашёл.
- Единственный дефект чтения — невидимость легаси-строки, это п.3, отдельной находкой не считаю.

## 5. Тест автора — инъекции честные, но ветка upsert не покрыта

Прогнал сам, все три конфигурации:

```bash
RUN_BROADCAST_DRAFT_SAVE_DB=1 node --test deploy/postgres/privileges/broadcast-draft-save.devDbProof.test.mjs
# 3/3 pass
BROADCAST_DRAFT_SAVE_FAULT=omit-org …          # not ok 1: expected 00000…, actual 42501… (pass 2 / fail 1)
BROADCAST_DRAFT_SAVE_FAULT=weaken-org-policy … # not ok 2: expected 42501…, actual 00000… (pass 2 / fail 1)
```

Обе инъекции валят **свой** тест и **по своей причине** — расхождение ровно в ожидаемом `sqlstate`, не «упало
что-нибудь». Ослабления не вижу, п.5 PASS.

Но у теста две слепые зоны, и первая объясняет, почему п.3 прошёл мимо автора:

1. **`broadcast-draft-save.devDbProof.test.mjs:132`** — `DELETE FROM public.broadcast_drafts WHERE
   doctor_user_id = …` выполняется ПЕРЕД каждой пробой. Поэтому исполняется всегда только чистый `INSERT`, а
   `ON CONFLICT DO UPDATE` — мёртвый текст в тесте. Ровно та ветка, через которую идёт всякое второе
   сохранение, не проверена ни разу.
2. **`insertSql` (строки 97–119) подставляет литеральный uuid**, а не `app.current_org_id()`. Production-код
   вызывает функцию; тест — нет. Замена `app.current_org_id()` на значение из запроса оставила бы тест зелёным,
   то есть главный инвариант п.2 этим тестом не удерживается (его удерживает `assert_port_context_claim`, см. п.2).
