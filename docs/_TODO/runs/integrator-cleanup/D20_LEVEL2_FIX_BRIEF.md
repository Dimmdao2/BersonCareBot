# D20 уровень 2 · закрыть находки аудита F1–F7 (тест не ловит названную потерю)
(run: worker-d20-level2-fix)

**Аудит:** `docs/_TODO/runs/integrator-cleanup/D20_LEVEL2_AUDIT.md` — прочитать целиком, там по каждой
находке файл, строка и предлагаемая правка. **Твоя работа — закрыть F1–F7 и доказать поломкой.**

Каждая находка означает одно: тест зелёный, а названная картой потеря проходит мимо. Это не стилистика,
это дыра ровно того класса, ради которого уровень 2 написан.

## Что закрыть

- **F1 (дороже всех).** `notificationDeliveryAttempts.test.ts` — ни один из шести тестов не проверяет
  `status`. Запись пропуска со `status:'success'` оставит всё зелёным, а журнал скажет «канал сработал»
  ровно тогда, когда человек ничего не получил. В обоих тестах пропуска ожидать `status: 'skipped'`.
- **F2.** `outgoingDeliveryWorker.finalize.test.ts` — ветка повторной постановки не исполняется ни разу
  (обе фикстуры исчерпали попытки). Добавить случай `attemptCount: 1, maxAttempts: 6`: обработка падает,
  финализация жива → ожидать повтор, а не мёртвую полку.
- **F3.** `processAcceptedIncomingEvent.test.ts` — ожидание не требует `err`. Убери причину из кода, и
  единственный след потери станет «что-то упало». Добавить ожидание причины.
- **F4.** Там же — бросок из `handleIncomingEvent` не покрыт: все три теста роняют только отправку
  намерения. Добавить тест на бросок из исполнения действия, ожидание — сегодняшнее фактическое поведение.
- **F5.** `dedup.test.ts` — `null` в отпечатке не покрыт, хотя тип его разрешает. Отпечаток с `null`-полем
  обязан отличаться от отпечатка без этого поля, иначе второе сообщение молча уйдёт в дубликаты.
- **F6.** `eventGateway.test.ts` — все шесть тестов зовут шлюз БЕЗ `options`, а единственный продовый
  вызов передаёт обёртку с принципалом арендатора. Тест обязан требовать, чтобы обёртка была вызвана и
  обернула исполнение: иначе в проде обработка побежит без принципала, а тесты будут зелёные.
- **F7 (легче остальных).** `deliveryTargetsPort.test.ts` — привязка из одних пробелов не покрыта.

## Как доказывать (гейт приёмки)

По каждой находке: **внести поломку, описанную в аудите как «зелёный при …», и показать, что теперь тест
краснеет.** В отчёте по каждой: файл и строка поломки, вывод прогона, подтверждение снятия поломки.
Правка, для которой нет такой пары, не принимается.

## Границы

- Продуктовый код **не менять**. Все семь находок — про тесты. Если окажется, что закрыть находку без
  правки кода нельзя (например поведения просто нет), это строка в отчёт с точной причиной, а не тихая
  правка кода.
- Не расширять область: остальные тесты уровня 2 не переписывать, уровни 0/1/3 не трогать.
- Не изобретать требований: чего нет в аудите и карте — строка в «развилках», вопросом владельцу.
