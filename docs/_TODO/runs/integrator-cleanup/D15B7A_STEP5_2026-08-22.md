## 1. Что сделано

### 1.1 Обратный резолвер сравнивает вид (`contract.sql`)

`app_ext.resolve_variant_a_physical(uuid, text)` — вид вошёл в ПРЕДИКАТ поиска:

```sql
  SELECT physical_user_id INTO physical_id FROM app_ext.variant_a_identity_refs
   WHERE opaque_ref = p_opaque_ref AND ref_kind = p_expected_ref_kind;
  IF physical_id IS NULL THEN RAISE EXCEPTION USING ERRCODE='42501', MESSAGE='accepted opaque identity context required'; END IF;
```

Изменена ровно одна строка тела (добавлено ` AND ref_kind = p_expected_ref_kind`) — это и есть откат
шага. OID, владелец (`app_seam_identity_lookup_owner`), сигнатура, возврат, `VOLATILE`,
`SECURITY DEFINER`, `search_path` и гейт — дословно прежние; `CREATE OR REPLACE`.

Почему предикат, а не второй statement со сравнением: `opaque_ref` UNIQUE, поэтому «найти по ссылке и
сверить вид» и «найти по паре» отвечают одинаково, но у предиката ОДИН выход на оба отказа — а схема
просит, чтобы несовпадение вида поднимало `42501` **точно так же, как неизвестная ссылка**. Нового
класса ошибки и нового текста нет: по отказу нельзя узнать, что предъявленное значение вообще чья-то
живая ссылка. Замерено: текст отказа по виду и текст отказа по выдуманной ссылке совпадают побайтно
(проба 1 ниже сравнивает их строкой, а не глазами).

Закрытый список видов остался в CHECK карты, на стороне ВЫДАЧИ: неизвестный вид здесь не находит
строки и получает тот же `42501`, что и правильный ответ на выдуманный третий вид.

### 1.2 Вызывающие называют вид явно (`contract.sql`)

| функция | поле | было | стало |
|---|---|---|---|
| `app_ext.assert_port_context_claim` | `p_actor_ref` | `resolve_variant_a_physical(ref)` | `…(ref, 'actor')` |
| `app_ext.assert_port_context_claim` | `p_subject_ref` | `resolve_variant_a_physical(ref)` | `…(ref, 'subject')` |
| `app.current_actor_user_id` | `actor_ref` | `resolve_variant_a_physical(ref)` | `…(ref, 'actor')` |
| `app.current_patient_user_id` | `subject_ref` | `resolve_variant_a_physical(ref)` | `…(ref, 'subject')` |

**Два нижних ряда — не расширение скоупа, а условие работоспособности шага, и это названо в самом
контракте до меня** (комментарий совместимой сигнатуры, редакция Ш3): «`app.current_actor_user_id`,
`app.current_patient_user_id` and `app_ext.assert_port_context_claim` all resolve a reference without
naming a kind **until step 5**». Проверка вида без этой правки ломает продукт: `current_patient_user_id`
читает `subject_ref`, однопараметрический делегат назвал бы там `'actor'`, а после Ш4 приложение кладёт
в это поле СУБЪЕКТНУЮ ссылку — значит КАЖДОЕ чтение пациента отвечало бы `42501` при зелёном reconcile.
Ловится пробой 2 ниже.

Совместимая однопараметрическая сигнатура НЕ тронута и живёт до Ш7 (граница брифа). Внутри базы у неё
больше нет вызывающих; EXECUTE у неё сохранён — снятие гранта было бы правкой прав, которых этот шаг не
меняет. Обходом проверки она не является: собственного тела у неё нет, она называет вид `'actor'`, и
сравнивает его тот самый один резолвер. Комментарий у сигнатуры приведён в соответствие с фактом.

### 1.3 Прав это не меняет — замер, а не утверждение

Новых отношений и колонок нет; `ref_kind` уже был объявлен в `relationSurfaces` обеих затронутых
функций (declaration.ts:6580 — там прямо написано, что Ш5 сделает эту колонку предметом проверки).
`declaration.ts` не правился. Артефакты побайтно прежние:

```
node --experimental-strip-types deploy/postgres/privileges/generate-cli.mjs --check                      # exit 0, 4 артефакта совпадают побайтно
node --experimental-strip-types deploy/postgres/privileges/generate-cli.mjs --db bcb_webapp_dev --check --port-context-only   # exit 0
```

В контракте ни одного нового `GRANT`/`REVOKE` (AGENTS.md §1); миграций шаг не добавляет вовсе.

4. **вход тремя учётками владельца** — по учётке на пробу, класс берётся из роли, а не из адреса:

   откат шага (` AND ref_kind = p_expected_ref_kind`), отвечает «принято». Инъекция живёт ВНУТРИ пробы,

   осталась байкой в отчёте.

**Полный `contract.sql` против живого каталога DEV в откаченной транзакции** (тот же порядок и те же
psql-переменные, что у reconcile — `--env-login-variables`, `BEGIN` … `ROLLBACK` вместо `COMMIT`):
прошёл целиком, exit `0`, ни одной ошибки.

`bash deploy/host/migrate-dev.sh --preflight` в этом worktree выполнить нельзя (`FATAL: DEV API env

выше, который проверяет ровно тот текст, что этот шаг меняет.

### 2.1 Пробы, которые пришлось привести в соответствие

`42501` по виду задел четыре существующих файла — каждый предъявлял ссылку не того вида:

- `variant-a-identity-ref-kind-argument…` — тест «Ш3: обратный резолвер ПРИНИМАЕТ вид и ещё НЕ
  сравнивает его» ПЕРЕВЁРНУТ в «Ш5: СРАВНИВАЕТ»; его собственный комментарий называл Ш5 шагом, который
  его отменит;
- `variant-a-identity-ref-kind-derivation…` — `resolve_variant_a_physical(actor_ref)` /
  `(subject_ref)` теперь называют свой вид;
- `public-booking-write-walls…` — принятый контекст пациента нёс ОДНУ ссылку в обоих полях; теперь
  `subject_ref` получает субъектную, чеканимую тем же резолвером, что зовёт приложение, внутри той же
  откаченной транзакции. Локальные `subjectRef` переименованы в `actorRef` — это акторская ссылка, и до
  Ш4 имя было верным, а после перестало;
- `port-context-tenant-claim…` — у `claim()` появилась опция `subjectKindOf`, вызов обёрнут в
  `BEGIN … ROLLBACK`, фикстуры пинают `ref_kind='actor'` (на DEV уже 27 акторских и 27 субъектных строк,
  «любая строка человека» перестала быть однозначным ответом).

Все фикстуры, читающие карту, теперь называют вид явно — иначе они молча брали бы субъектную строку в
поле актора.
