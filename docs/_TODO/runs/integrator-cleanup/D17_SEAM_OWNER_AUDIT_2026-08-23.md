## Б1. Грант на `user_channel_preferences` не нужен вообще

До правки у `app_seam_delivery_scope_owner` был колоночный `SELECT` ровно на пять колонок:
`platform_user_id, channel_code, is_enabled_for_messages, is_enabled_for_notifications, is_preferred_for_auth`.
Тело корня читает ровно эти пять и никаких других — ни `SELECT *`, ни бесколоночного обращения.
Разрыва здесь не было.

Замер (текущий каталог DEV = состояние до правки):

```
BEGIN; SET LOCAL ROLE app_seam_delivery_scope_owner;
SELECT count(*) FROM (SELECT platform_user_id, channel_code, is_enabled_for_messages,
  is_enabled_for_notifications, is_preferred_for_auth FROM public.user_channel_preferences) s;
→ 122        -- читается без единого табличного гранта
```

Правка меняет колоночный грант на `GRANT SELECT ON TABLE`, то есть открывает владельцу шва (а с ним всем
16 его definer-корням) всю таблицу вместо пяти согласованных колонок. Это чистое расширение без причины.

## Б2. Грант на `user_contacts` шире необходимого; обоснование в отчёте неверно

Настоящий разрыв — две **колонки**: тело читает `email_contact.confirmed_at` и `email_contact.is_primary`
в `LEFT JOIN`, а грант до правки нёс только `contact_kind, platform_user_id, value_normalized`.

Контролируемый опыт, один rollback-only прогон, три состояния прав:

```
A_prefix_state_as_in_catalog     :: 42501 | permission denied for table user_contacts
B_columns_only_minimal           :: OK {"ok": true, …}     -- добавлены ТОЛЬКО две колонки
C_landed_fix                     :: OK {"ok": true, …}     -- приземлённый табличный грант
```

Состояние **B** — это `GRANT SELECT ("confirmed_at","is_primary")` и ничего больше: корень отдаёт данные.
Табличный грант не требуется.

Отдельно проверена ветка по телефону, где отчёт видит причину табличного гранта («корень … выполняет
`count(*)`»):

```
B_columns_only__phone_branch_count_star :: OK {"ok": true, …, "platformUserId": "d0000000-…-008"}
SET LOCAL ROLE app_seam_delivery_scope_owner; SELECT count(*) FROM public.user_contacts; → 338
```

`count(*)` под одними колоночными грантами исполняется. Обоснование в отчёте фактически неверно:
PostgreSQL требует табличную привилегию только когда запрос не ссылается ни на одну колонку отношения, а
здесь ссылается на три.

Цена расширения измерена:

```
колоночное состояние: SELECT source_origin FROM public.user_contacts → ERROR: permission denied for table user_contacts
после табличного гранта: source_origin_readable=direct
```

То есть 16 definer-корней `app_seam_delivery_scope_owner` получают чтение всех колонок `user_contacts`
(`id`, `created_at`, `updated_at`, `source_origin`) и всей `user_channel_preferences` — колонок, которых
не читает ни один их корень. Для таблицы контактных данных это не мелочь.

## Б3. Инъекция в `seam-owner-delivery-target.devDbProof.test.mjs` не доказывает заявленного

Тест зелёный (1/1, прогнал), но его отзыв — `REVOKE SELECT ON TABLE … FROM app_seam_delivery_scope_owner` —
сносит вместе с табличным грантом и колоночные:

```
before:             channel_code,is_enabled_for_messages,is_enabled_for_notifications,is_preferred_for_auth,platform_user_id
after grant+revoke: <none>
```

Поэтому `42501` после отзыва означает «прав не осталось никаких», а не «нужен именно табличный грант».
Б1 и Б2 показывают, что различие принципиальное: колоночного набора хватает. Инъекция обязана
восстанавливать прежний колоночный грант и краснеть только на недостающих колонках — иначе она
подтверждает любое право, каким бы широким оно ни было.

## Б4. Перепись занижает: `min(access_status)` прячет разрывы по корням

Арифметика сходится: своим кодом из декларации получаю 43 владельца, 1389 строк уровня «корень×отношение×
операция», 631 после свёртки — те же числа, что печатает скрипт. Каталог DEV подтверждает 43 роли швов и
43 владельца definer-корней.

Но свёртка `rolled` группирует по `(owner, relation, operation, requires_table)` и берёт
`min(access_status)` по всем корням группы. Корни одного владельца объявляют **разные** наборы колонок на
одном отношении — таких групп 184 из 631. Разрыв у одного корня заслоняется удовлетворённым статусом
соседнего. Дополнительно: `partial` — алфавитно последний из шести статусов, поэтому `min()` не вернёт его
никогда, если в группе есть хоть один другой статус; ровно тот статус, который скрипт завёл для «грант есть,
но не покрывает», структурно недостижим в свёрточной строке.

Проверка по корням, без свёртки, на том же каталоге:

```
function-level rows checked = 1389
function-level GAPs         = 3
  app_seam_delivery_scope_owner  | public.user_channel_preferences | SELECT | app.read_integrator_delivery_target_snapshot
  app_seam_delivery_scope_owner  | public.user_contacts            | SELECT | app.read_integrator_delivery_target_snapshot
  app_seam_identity_lookup_owner | public.user_channel_bindings    | SELECT | app.pre_session_get_default_auth_otp_channel
```

Третий разрыв: `app.pre_session_get_default_auth_otp_channel` читает `binding.created_at`, а колоночный
грант владельца на `user_channel_bindings` в каталоге DEV — только `user_id, channel_code, external_id,
display_handle`. Это путь входа по телефону (выбор канала OTP по умолчанию), он краснеет `42501` на каждом
пользователе без строки в `user_phone_history`.

Продуктовой правки этот разрыв не требует: сгенерированный артефакт — и на этом коммите, и на его
родителе — грант на `created_at` уже несёт (`privileges.bcb_webapp_dev.sql:19557`), то есть на DEV просто
не догнан reconcile. Но заявление отчёта «перепись нашла ровно два неполных требования» описывает каталог,
а в каталоге их три. Перепись, которой закрывают класс, обязана считать по корням.

Отдельная граница метода, которую отчёт не называет: перепись сверяет **декларацию с каталогом**. Класс,
который и породил D17, — расхождение **тела с декларацией**; его эта перепись не ловит по построению, чем
бы её ни чинили. Мой встречный проход по телам живого каталога (`pg_get_functiondef` → отношения → права
владельца) отношений, читаемых вовсе без права, не нашёл — но он огрубляет до «есть хоть одна колонка».

Мелочь для протокола: в каталоге DEV есть один definer-корень владельца шва, которого нет в
`declaration.portContext.functions` вовсе — `app.email_auth_start_challenge(uuid,text,text,bigint,text,text,
text,text,uuid,text,text)` (объявлена 6-аргументная). Похоже на объект соседней ветки на DEV; в поле
переписи он не попадает ни в каком виде.

## Стена арендатора цела (проверено поведением)

В теле организация берётся из принятого контекста (`v_org := app.current_org_id()`), аргумент только
сверяется, дальше проверка членства идёт по `v_org`, не по аргументу. Поведение под обоими состояниями прав:

```
cross_org_user     :: OK {"ok": false, "code": "delivery_target_outside_organization"}
arg_org_mismatch   :: 42501 | accepted port context required
```

Расширенный `SELECT` этого не меняет: сверка идёт до чтения и по контексту. Достижимость роли проверена
по каталогу независимо — все 43 роли `app_seam_*_owner` без `LOGIN`, `SUPERUSER`, `BYPASSRLS` и `INHERIT`,
и в `pg_auth_members` нет ни одного ребра ни в одну сторону: ни владелец шва не член чего-либо, ни в него
никто не входит. `FORCE ROW LEVEL SECURITY` на обеих таблицах в артефакте сохранён.

Итог: Б1–Б2 — это регресс наименьшей привилегии внутри шва (радиус поражения definer-корней), а не пробой
стены арендатора.

## Почему «код читает — права нет» не поймал ни один гейт

Гейт «тело против декларации» есть — `compareFunctionSurfaces` в `function-body-surface.mjs`, его гонит
`function-census.test.mjs`. Он сверяет **отношения и операции**. Слова `columns` в этом модуле нет ни разу:
`surface.columns` — то, что становится реальным `GRANT` — с телом не сверяется никогда.

`relation-access.test.mjs` колонки проверяет, но против списков, выписанных руками в самом тесте, то есть
это детектор изменений декларации, а не вывод из тела. Деплой ассертит «каталог == декларация», поэтому
неверная декларация выкатывается зелёной.

Доказано инъекцией: вернул в декларации список колонок `user_contacts` ровно к доправочному
(`platform_user_id, contact_kind, value_normalized`) — то состояние, которое дало живой `42501` на TEST, —
и прогнал гейт:

```
node --test deploy/postgres/privileges/function-census.test.mjs → 14/14 pass
```

Гейт слеп к этому классу. (Декларация возвращена, `git diff` по файлу пуст.)

Канон это уже описывает: `AGENTS.md`, «Перед приземлением миграции — разбор её прав», пункт 3 — «какие права
этой роли нужны, чтобы тело **исполнилось**», и там же: «пайплайн сверяет „объявлено == лежит в базе“ и
молчит о том, достаточно ли объявленного… падает только на первом живом вызове». Правило есть, механики под
него нет.

Чтобы завтра краснело до выкатки, нужны две вещи, обе дешёвые:

1. **Колоночное плечо лексического экстрактора.** Метка `evidence: 'pg16-function-body-lexical-upper-bound'`
   уже обещает, что источник — тело; сегодня из тела выводятся только операции. Достроить вывод колонок и
   потребовать «объявленные ⊇ выведенные из тела», как уже сделано для операций.
2. **Перепись по корням вместо свёртки** (Б4) — она ловит расхождение декларации с каталогом и сегодня
   молча теряет часть разрывов.

Точный бэкстоп, если понадобится сверх этого: DEV-смоук, вызывающий каждый definer-корень под правами
только его владельца. Тест из этой ветки — ровно такой формы, но покрывает 1 корень из 388.
