## Измеренный дефект

`0356` перевела 15 SECURITY DEFINER функций на владельца `app_owner`, чтобы вход по почте видел
`platform_users` под FORCE RLS. Но два closure-оверлея выполняются **после** миграций:

- `organization-member-invites-rls.sql`
- `specialist-signup-public-bootstrap-rls.sql`

Они делают `DROP + CREATE` восьми из этих пятнадцати функций и назначают владельца через динамическую
переменную «текущий владелец таблицы» — то есть возвращают роль мигратора. Подтверждено живым SQL на TEST:
восемь функций снова принадлежат `bersoncarebot_test`, который не член `app_identity_bootstrap`, и читают ноль
строк из `platform_users`.

Итог: **каждая выкатка TEST заново ломает вход по почте**, а миграция `0356` при этом числится применённой.
Молча: ни ошибки, ни красного гейта — человек видит «код отправлен» и не получает письма.

## Работа

1. **Сначала перепись.** Пройти ВСЕ closure-оверлеи, выполняющиеся после миграций, и выписать каждый, кто
   делает `DROP+CREATE` или `ALTER … OWNER` для функций схемы `app`. Список с файлами и строками — половина
   ценности задачи: сегодня совпало два, завтра совпадёт третий.
2. **Починить причину, а не восемь функций.** Владелец функции не должен выводиться из «текущего владельца
   таблицы» — это и есть механизм отката. Выбрать одно правило (например: оверлей, пересоздающий функцию схемы
   `app`, обязан явно назначить `app_owner`), применить его ко всем найденным местам и обосновать выбор.
3. **Закрыть класс проверкой.** Добавить в закрывающие гейты деплоя проверку, что после всех оверлеев ни одна
   функция схемы `app`, которую миграции назначили `app_owner`, не принадлежит роли мигратора. Гейт должен падать
   красным — сегодня этот откат не ловил никто.
4. Не менять тела функций и не ослаблять политики RLS.
