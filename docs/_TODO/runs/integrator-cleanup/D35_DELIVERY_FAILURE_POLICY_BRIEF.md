# D35 — политика отказа доставки: классификация, инцидент, короткая лестница для служебных ответов
(run: worker-d35-failure-policy)

## Решение принято, вопроса владельцу нет

Владелец 31.07: инженерные решения принимает лид по мировой практике, владельцу их не носить. Практика
собрана в `docs/_TODO/runs/integrator-cleanup/D20_FORKS_RESEARCH.md`, §1 — **прочитать целиком, там источники**.
Решение владельца по существу одно и оно уже дано: **«доставляем в любом случае»** (опоздавший служебный
ответ лучше тишины).

**Действующая политика — принята, реализуется:**

1. **Постоянный отказ** (бот заблокирован человеком, жёсткий отскок почты, протухшая подписка на пуш):
   ретрая нет, инцидента-тревоги нет, канал помечается. Это нормальное состояние, а не деградация.
2. **Временный отказ** живого канала: ретрай по лестнице; **исчерпание попыток → инцидент оператора**.
3. **Служебный ответ человеку** («вопрос принят», «тип не поддерживается» и подобные реплики бота на
   входящее сообщение) — **своя короткая лестница и свой предел**: цель уложиться в минуты, а не в часы.
   Сегодня такие ответы идут по общей лестнице `[60, 300, 900, 3600]` секунд
   (`infra/delivery/deliveryContract.ts:27`), то есть подтверждение приёма может прийти через час — это
   бессмысленно. Предложить короткую лестницу и малый предел попыток, обосновать числа практикой из §1.
4. **Подтверждение нажатия кнопки** (`callback.answer` и подобные): не ретраить вообще — дедлайн истёк в
   момент отказа. В §1 это прямо соотнесено с `retry: false` у Sidekiq.
5. **Отказ отправки ответа больше не уходит только в лог.** Сегодня `processAcceptedIncomingEvent` пишет
   `logger.warn` и всё: единственный путь, где человек ждёт прямо сейчас, — единственный, где отказ невидим.
   Заменить на классификацию + `recordOperatorFailureIncident` (машинка уже есть и работает на соседних
   путях: `relayOutboundRoute.ts`, `sendSmsRoute.ts`, `sendEmailRoute.ts`) + постановку в
   `outgoing_delivery_queue` через существующий `enqueueOutgoingDeliveryIfAbsent` (идемпотентен по `eventId`).

**Строить новое не нужно** — обе машинки существуют. Работа в том, чтобы подключить их к пути, где их нет,
и развести лестницы.

## Гейт приёмки

По каждому пункту 1–5 — тест, краснеющий при внесённой поломке:
- заблокированный бот не порождает инцидент и не ретраится;
- временный отказ, исчерпавший попытки, порождает инцидент;
- служебный ответ уходит по короткой лестнице, а не по общей;
- подтверждение нажатия не ставится в очередь вовсе;
- отказ отправки ответа человеку виден не только в логе.
Полный прогон интегратора (сейчас 161), числа до и после. По каждому тесту — поломка и красный вывод.

## Границы

- Не менять поведение доставки напоминаний и рассылок — у них своя лестница, она верна.
- Не строить второй механизм инцидентов и вторую очередь: используем существующие.
- Числа лестницы обосновать практикой, а не вкусом; если практика не даёт числа — сказать прямо и выбрать
  минимально разумное, объяснив.
- Не изобретать требований: чего нет в §1 исследования и в этом брифе — строка в «развилки».
