## 1. Упавшая отправка ответа человеку сегодня только пишется в лог

### Что в коде

```bash
sed -n '41,83p' apps/integrator/src/kernel/domain/usecases/processAcceptedIncomingEvent.ts
# цикл по intents: try { dispatchIntent } catch { dispatchFailureCount++; logger.warn(...) }
# — и всё; ни очереди, ни инцидента

grep -n "throw providerError" apps/integrator/src/infra/adapters/dispatchPort.ts
#   350:        throw providerError;     ← порт бросает, ретрая внутри нет
```

Путь заканчивается строкой в логе. Наружу — ничего.

### Как делают

| Система | Как сделано | Источник |
|---|---|---|
| Amazon SQS | Необработанные сообщения уходят в dead-letter queue после `maxReceiveCount` попыток. Назначение DLQ прямо названо диагностическим: «DLQs are useful for debugging your application because you can isolate unconsumed messages to determine why processing did not succeed». Рекомендуется вешать CloudWatch-алярм на попадание в DLQ **[док]** | [AWS SQS: Using dead-letter queues](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html) |
| Amazon SQS | Явное предупреждение, что DLQ уместен **не всегда**: «Don't use a dead-letter queue with a FIFO queue if you don't want to break the exact order of messages or operations» **[док]** | там же |
| Sidekiq | 25 ретраев с экспоненциальным откатом, ≈20 дней; затем задача попадает в Dead set: «The Dead set is a holding pen for jobs which have failed all their retries. Sidekiq will not retry those jobs, you must manually retry them via the UI». Есть хук `sidekiq_retries_exhausted` и режим `retry: false` для задач, которые выполняются ровно один раз **[док]** | [Sidekiq wiki: Error Handling](https://github.com/sidekiq/sidekiq/wiki/Error-Handling) |
| Stripe (доставка вебхуков) | Ретраи с экспоненциальным откатом до **трёх суток**; событие можно переотправить вручную до 15 суток из Dashboard **[док]** | [Stripe: Webhooks](https://docs.stripe.com/webhooks) |
| Google SRE | «Always use randomized exponential backoff when scheduling retries»; «Limit retries per request. Don't retry a given request indefinitely»; «separate retriable and nonretriable error conditions. Don't retry permanent errors or malformed requests»; бюджет ретраев на процесс — «only allow 60 retries per minute in a process, and if the retry budget is exceeded, don't retry; just fail the request» **[док]** | [Google SRE Book, гл. 22 «Addressing Cascading Failures»](https://sre.google/sre-book/addressing-cascading-failures/) |

**Чем отличается «ответ на действие человека» от «рассылки» — главный вопрос брифа.** Прямой цитаты
«интерактивный ответ ретраить нельзя» я в документации не нашёл; вывод складывается из двух документированных
фактов **[набл]**:

- У ответа есть **дедлайн**, у рассылки его нет. Sidekiq ретраит 20 дней, Stripe — 3 суток, потому что получатель
  этих доставок — сервер, которому всё равно, пришло событие сейчас или через час. Человек, написавший в бот,
  ждёт секунды. Ответ, доставленный через 20 минут, — это уже не ответ.
- Оттого зрелые системы для интерактивного пути дают **не ретрай, а признание отказа**: SQS предлагает
  изолировать и разобрать (DLQ + алярм), Sidekiq — `retry: false` + Dead set, SRE — «Don't retry permanent
  errors» и ограниченный бюджет. Общее во всех трёх: **отказ становится наблюдаемым артефактом**, а не
  бесконечной попыткой.

То есть развилка не «ретраить или нет», а «видно отказ снаружи или нет». Ретрай — второстепенное.

### Как надо нам

**Строить ничего не нужно — обе машинки уже есть и уже работают на соседних путях.** Это главный вывод раздела:

```bash
grep -rn "reportOperatorFailure\|recordOperatorFailureIncident" apps/integrator/src --include=*.ts | grep -v test
# relayOutboundRoute.ts, sendSmsRoute.ts, sendEmailRoute.ts, operatorHealthProbeRunner.ts, writePort.ts …
grep -rn "enqueueOutgoingDeliveryIfAbsent" apps/integrator/src --include=*.ts | grep -v test
# handlers/reminders.ts:189, reportOperatorFailure.ts:131 и :169
```

Расклад получается парадоксальный:

| Путь | Кто получатель | Отказ сегодня |
|---|---|---|
| Напоминания (`handlers/reminders.ts`) | человек, но **не ждёт прямо сейчас** | durable-очередь `outgoing_delivery_queue` |
| Операторские алерты | оператор | инцидент + durable-очередь |
| Relay из вебаппа (`relayOutboundRoute.ts`) | человек | инцидент оператора |
| **Ответ на входящее сообщение** | **человек, ждёт прямо сейчас** | **`logger.warn` и всё** |

Единственный путь, где человек сидит и ждёт, — единственный, где отказ невидим. Это ровно наоборот
относительно шкалы «цена ошибки», которую сама карта объявила в разделе про порядок тестов.

**Рекомендация: в `processAcceptedIncomingEvent` заменить `logger.warn` на классификацию отказа —
и обязательный инцидент, а ретрай только короткий и ограниченный.**

Классификация — по уже существующему различению постоянный/временный отказ (оно в контракте
`DeliverySendResult`, карта отмечает его в `contracts/ports.ts`), и по классу intent:

- **ack-класс** (`callback.answer` и подобные): не ретраить вообще. Дедлайн прошёл в момент отказа,
  Telegram уже показал человеку крутилку. Это ровно случай Sidekiq `retry: false` **[док]**.
- **ответ человеку** (`message.send` в ответ на входящее): инцидент оператора — **всегда**; ретрай — только
  в пределах короткого окна, через уже существующий `enqueueOutgoingDeliveryIfAbsent` (он идемпотентен по
  `eventId`, повторная постановка дубля не создаст).
- **постоянный отказ** (бот заблокирован): ни ретрая, ни инцидента-тревоги — это нормальное состояние,
  канал помечается. Адаптер Telegram такие ошибки уже разбирает (`telegram/deliveryAdapter.ts`, карта, гр. 3.2).

### Что поменять

| Файл | Поведение |
|---|---|
| `kernel/domain/usecases/processAcceptedIncomingEvent.ts` | В `catch` вместо только `logger.warn` — классифицировать отказ и вызвать `recordOperatorFailureIncident` с отдельным `direction` (напр. `inbound_reply`), чтобы отказы ответа не смешались с отказами рассылки в дедупе инцидентов |
| там же | Для intent-класса «ответ человеку» — постановка в `outgoing_delivery_queue` с малым `maxAttempts`; для ack-класса — без ретрая |

**Цена бездействия:** сообщение человеку теряется полностью бесшумно. Ни оператор, ни разработчик не узнают об
этом, пока человек не пожалуется — а в медицинском сервисе человек, не получивший ответа, скорее уйдёт, чем
пожалуется. Из всех развилок эта — единственная с нулевой внешней наблюдаемостью.

**Осталось продуктовым (одна строка):** доставлять ли ответ, опоздавший больше чем на несколько минут, или
лучше промолчать — это вопрос к владельцу, а не инженерный.

## 2. Дедупликация событий записи на приём

### Что в коде (поправка к карте)

Карта утверждает, что дедуп живёт в памяти. **В проде это не так.**

```bash
sed -n '119,152p' apps/integrator/src/integrations/bersoncare/bookingLifecycleRoute.ts
# acquireBookingLifecycleKey: if (idempotencyPort) → tryAcquire(...), persistent: true
#                             иначе → Map-фолбэк, persistent: false
sed -n '34,60p' apps/integrator/src/infra/db/repos/idempotencyKeys.ts
# createPostgresIdempotencyPort: INSERT INTO integrator.idempotency_keys …
#   ON CONFLICT (key) DO UPDATE … WHERE target.expires_at < now() RETURNING key
```

То есть боевой путь — **атомарный захват ключа в Postgres**, TTL 24 часа, с корректным освобождением при
падении обработки. `Map` достижим только если `idempotencyPort` не передан, а `routes.ts:222-228` передаёт его
всегда, и `di.ts:254` всегда его конструирует.

### Как делают

| Система | Как сделано | Источник |
|---|---|---|
| Stripe (вебхуки) | Прямо признаёт дубли: endpoint «can sometimes receive the same event multiple times»; в отдельных случаях генерируются два разных объекта Event. Рекомендация — записывать обработанные ID событий и игнорировать уже записанные; для различения дублей использовать «the ID of the object in `data.object` along with the event type (`event.type`)» **[док]** (страница отдалась в локализованном виде; английские формулировки процитированы дословно, остальное — пересказ) | [Stripe: Webhooks](https://docs.stripe.com/webhooks) |
| Stripe | Горизонт ретраев — до **трёх суток** экспоненциально. Это и есть требуемое окно хранения ключа **[док]** | там же |
| Telegram Bot API | Дедуп встроен в протокол: «Update identifiers start from a certain positive number and increase sequentially. This identifier becomes especially handy if you're using webhooks, since it allows you to ignore repeated updates». Апдейты хранятся на сервере «not longer than 24 hours» **[док]** | [Telegram Bot API](https://core.telegram.org/bots/api) |

Общий знаменатель: **ключ в durable-хранилище, атомарная вставка (не «прочитал → проверил → записал»), окно
не короче горизонта ретраев отправителя** **[набл, обобщение трёх источников выше]**.

### Как надо нам

Наш Postgres-порт уже реализует ровно канонический паттерн: `INSERT … ON CONFLICT … WHERE expires_at < now()`
— это атомарный захват, гонки двух реплик он переживает. Архитектурно менять нечего.

**Рекомендация: архитектуру не трогать; убрать in-memory фолбэк, сделав `idempotencyPort` обязательным.**

Обоснование: `idempotencyPort?: IdempotencyPort` — опциональное поле (`bookingLifecycleRoute.ts:44`). Пока
`routes.ts` его передаёт, всё верно. Но тип разрешает не передать — и тогда дедуп **молча** деградирует с
durable до per-process, без ошибки и без записи в лог. Это ровно тот класс отказа, который карта по всему
интегратору называет самым злым: тихая потеря гарантии. Опасность не в сегодняшнем поведении, а в том, что
одна строчка рефакторинга возвращает ту проблему, которую карта уже считает существующей.

Про окно: 24 часа против трёхсуточного горизонта Stripe. Для нас отправитель — не Stripe, а наш собственный
вебапп, и его горизонт ретраев я в этом прогоне не проверял (см. «чего не выяснил»). Если вебапп ретраит
дольше 24 часов, окно надо равнять по нему; если меньше — 24 часа с запасом.

### Что поменять

| Файл | Поведение |
|---|---|
| `integrations/bersoncare/bookingLifecycleRoute.ts` | `idempotencyPort` сделать обязательным полем `BookingLifecycleRouteDeps`; удалить `bookingEventDedup`/`isBookingEventDuplicate`/`rememberBookingEventKey` и ветку `persistent: false` |
| (тестам) | Тесты, которые сегодня опираются на фолбэк, переводятся на `createInMemoryIdempotencyPort` — он уже есть в `infra/db/repos/idempotencyKeys.ts` |

**Цена бездействия:** сегодня — нулевая (боевой путь корректен). Завтра — двойное напоминание человеку,
если кто-то соберёт роут без порта, и это не поймает ни один тест и ни один тип.

**Цена в наших числах я назвать не могу** — бриф просил «сколько событий в сутки, как часто рестарт», но
прогон read-only, БД и логов прода я не читал. См. «чего я не смог выяснить».

## 3. Ограничение частоты входящих не реализовано

### Что в коде

```bash
cat apps/integrator/src/kernel/eventGateway/rateLimit.ts
# export async function checkGatewayRateLimit(_event: IncomingEvent): Promise<RateLimitResult> {
#   return { allowed: true };
# }
```

Ветка есть, срабатывать не может никогда. Карта описывает это верно.

### Как делают

| Система | Как сделано | Источник |
|---|---|---|
| nginx | `ngx_http_limit_req_module` ограничивает «request processing rate **per a defined key**» по алгоритму leaky bucket. Ключ — переменная, обычно `$binary_remote_addr` (IP). Превышение сверх `burst` → отказ, по умолчанию **503** (`limit_req_status`) **[док]** | [nginx: ngx_http_limit_req_module](https://nginx.org/en/docs/http/ngx_http_limit_req_module.html) |
| Cloudflare | Ограничение можно вешать не только на IP: доступные характеристики — «IP, IP with NAT support, Query, Host, Headers, Cookie, ASN, Country, Path, JA3/JA4 Fingerprint, JSON field value, Body, Form input value, Custom» (полный набор — на Enterprise) **[док]** | [Cloudflare: Rate limiting rules](https://developers.cloudflare.com/waf/rate-limiting-rules/) |
| Telegram Bot API | Документированные лимиты — на **исходящие** от бота: не более ~1 сообщения в секунду в один чат, не более 20 в минуту в группу, не более ~30 в секунду суммарно; превышение → ошибки 429 **[док]** | [Telegram Bots FAQ, «Broadcasting to users»](https://core.telegram.org/bots/faq) |
| Telegram (вебхуки) | Вебхуки приходят с подсетей **`149.154.160.0/20` и `91.108.4.0/22`**, и Telegram предупреждает, что диапазон может меняться **[док]** | [Telegram: Marvin's Marvellous Guide to All Things Webhook](https://core.telegram.org/bots/webhooks) |

**Что даёт каждый уровень и чего не может** — это главный вопрос брифа, и ответ у нас определяется
последними двумя строками таблицы:

- **Периметр (nginx) ключует по IP.** Но все входящие вебхуки Telegram приходят с двух подсетей Telegram
  **[док]**. Значит per-IP лимит на периметре считает не пользователя, а **самого Telegram**: один
  разбушевавшийся человек и вся остальная клиника попадают в один счётчик. Сработавший лимит — это не защита
  от абьюза, а рубильник, отключающий бота для всех **[набл, вывод из документированного диапазона IP]**.
- **Периметр может то, чего не может приложение:** отбить флуд **до** того, как процесс потратит на него
  сокет, парсинг и запрос к БД. Против мусора, который не является настоящим вебхуком, это единственный
  дешёвый уровень.
- **Приложение может то, чего не может периметр:** ключевать по **личности** — `channelUserId` из разобранного
  события. Ни nginx, ни Cloudflare этого не знают до разбора тела (Cloudflare на Enterprise умеет JSON field
  value **[док]**, но это платный тариф и дублирование знания о схеме события).

**Отдельный вопрос брифа: мессенджеры уже ограничивают частоту — что это меняет?** Меняет **меньше, чем
кажется**: документированные лимиты Telegram — это лимиты на то, как быстро **бот шлёт людям**, а не на то,
как быстро **человек шлёт боту** **[док на первое; отсутствие второго — набл: в цитируемом разделе FAQ
лимитов на входящие нет]**. То есть от нашего собственного перегруза мессенджер нас страхует, а от человека
или скрипта, долбящего в бота, — нет.

### Как надо нам

Дополнительная деталь по нашему деплою:

```bash
grep -rn "proxy_pass\|server_name" deploy/nginx/bersoncarebot-webapp.vhost.template.conf
grep -rn "limit_req\|limit_conn" deploy   # ничего не найдено
```

Единственный nginx-vhost в репозитории — **для вебаппа** (`__UPSTREAM__` = порт вебаппа), и `limit_req` в нём
не настроен нигде. То есть «отдать это периметру» сегодня означает «отдать никому».

**Рекомендация: реализовать лимит в приложении, в шлюзе, с ключом по личности отправителя — и держать
счётчик в памяти процесса.**

Два обоснования, оба важны:

1. **Место — приложение**, потому что единственный уровень, который знает, *кто* прислал событие, — это шлюз
   после разбора конверта. Сигнатура `checkGatewayRateLimit(event)` уже это позволяет: событие на входе есть.
2. **Хранилище — память, и это не та же ошибка, что в §2.** Разница принципиальная и её стоит записать явно:
   дедуп — это **гарантия корректности**, потеря состояния при рестарте даёт человеку второе напоминание;
   ограничение частоты — **приблизительная защита от перегруза**, потеря счётчика при рестарте даёт всего лишь
   пропущенное окно. Платить за rate-limit запросом в Postgres на каждое входящее событие — значит добавить
   нагрузку ровно на том пути, который лимит должен разгружать.

Про «удалять или оставлять» (карта формулирует развилку именно так): **заглушку, которая всегда возвращает
`allowed`, оставлять нельзя ни в каком случае**. Ветка, читающаяся как защита и не являющаяся ею, хуже
отсутствия ветки: она вводит в заблуждение и читателя кода, и аудитора.

### Что поменять

| Файл | Поведение |
|---|---|
| `kernel/eventGateway/rateLimit.ts` | Заменить заглушку на счётчик (token bucket / скользящее окно) с ключом по `source` + идентификатору отправителя из события; при превышении — `{ allowed: false, reason: 'RATE_LIMITED' }` |
| `kernel/eventGateway/index.ts` | Поведение уже описано картой: `rejected/RATE_LIMITED` и pipeline не запускается. Проверить, что при отказе dedup-ключ **не** захватывается |

**Цена бездействия:** один человек (или сломавшийся клиент) в цикле «нажал кнопку» способен занять воркер,

## 4. Токен входа в вебапп многоразовый в пределах пяти минут

### Что в коде

```bash
sed -n '86,116p' apps/integrator/src/integrations/webappEntryToken.ts
#   const exp = now + 300;              ← только срок, ничего одноразового
#   HMAC-SHA256 по base64url(payload), payload = { sub, role, bindings, purpose, exp }
```

Токен — **stateless**: подпись плюс срок. Ни `jti`, ни серверной отметки о применении. Карта описывает верно.

### Как делают

| Система | Как сделано | Источник |
|---|---|---|
| NIST SP 800-63B | Норматив, а не практика: «verifiers **SHALL** accept a given authentication secret **only once** during the validity period» (§5.1.3.2) и «In all cases, the authentication **SHALL** be considered invalid **if not completed within 10 minutes**» (§5.1.3.2). Назначение секрета — «securely bind the authentication operation on the primary and secondary channel» (§5.1.3) **[док]** | [NIST SP 800-63B](https://pages.nist.gov/800-63-3/sp800-63b.html) |
| Supabase | Magic links — «one-time use only»; срок жизни по умолчанию 1 час; запрос не чаще раза в 60 секунд **[док]** | [Supabase: Passwordless email logins](https://supabase.com/docs/guides/auth/auth-email-passwordless) |
| Microsoft Defender for Office 365 (Safe Links) | Причина, по которой прямолинейная одноразовость ломается в почте: «URLs that don't have a valid reputation are **detonated asynchronously in the background**»; «As long as Safe Links protection is turned on, URLs are **scanned prior to message delivery**»; есть режим «**Wait for URL scanning to complete before delivering the message**» — то есть ссылку открывает сканер, до человека и вместо человека **[док]** | [Microsoft: Complete Safe Links overview](https://learn.microsoft.com/en-us/defender-office-365/safe-links-about) |

Итого практика расходится с нормативом **из-за канала доставки**: NIST и Supabase требуют одноразовости,
а почтовые сканеры её ломают, «съедая» ссылку раньше адресата **[док на обе стороны]**. Отсюда все известные
обходы (allow-list домена, S/MIME, API-only режим — все перечислены Microsoft **[док]**).

### Как надо нам

**Ключевой факт: у нас канал не почта, и главная опасность одноразовости к нам почти не относится.**

```bash
grep -rn "webappCabinetUrl" apps/integrator/src/content/telegram/user/scripts.json | head
sed -n '960,970p' apps/integrator/src/content/telegram/user/scripts.json
#   "inlineKeyboard": [[ { "textTemplateKey": …, "webAppUrlFact": "links.webappCabinetUrl" } ]]
```

Ссылка уходит **кнопкой inline-клавиатуры** (`webAppUrlFact`), а не текстом в теле сообщения. Предпросмотр
ссылки Telegram строит для URL **в тексте** сообщения; для URL внутри кнопки предпросмотр не генерируется
**[набл — прямого утверждения в Bot API я не нашёл, см. «чего не выяснил»]**. Плюс в мессенджере нет
корпоративного сканера почты, который открывает ссылки за адресата. То есть сценарий «предпросмотр открыл
ссылку раньше человека» для нашей доставки в первую очередь **не воспроизводится**.

Зато цена многоразовости у нас максимальная: токен даёт вход в кабинет пациента, то есть **доступ к
медицинской истории**. Карта сама ставит «вход не в тот аккаунт» на верх шкалы необратимости. Пересланный
скриншот или сообщение в пределах пяти минут пускает второго человека.

**Рекомендация: сделать токен одноразовым — но одноразовым на обмен, а не на открытие ссылки.**

Оговорка обязательна, потому что прямолинейная одноразовость нас сломает — и вот почему:

```bash
sed -n '82,90p' apps/integrator/src/integrations/telegram/webhook.ts
#   links.webappHomeUrl      = `${baseWebappUrl}&next=…/app/patient`
#   links.webappRemindersUrl = `${baseWebappUrl}&next=…/app/patient/reminders`
#   links.webappCabinetUrl   = `${baseWebappUrl}&next=…/app/patient/cabinet`
#   links.webappAddressUrl   = `${baseWebappUrl}&next=…/app/patient/address`
```

**Один токен обслуживает четыре кнопки одного меню.** Наивная одноразовость означает: человек нажал одну
кнопку — остальные три перестали работать. Это не гипотеза, это прямое следствие того, что все четыре URL
собраны из одного `baseWebappUrl`.

Развязка в том, что обмен токена и последующая навигация — разные вещи. Вебапп меняет токен на сессионную
куку:

```bash
sed -n '70,80p' apps/webapp/src/app/api/auth/exchange/route.ts
#   const result = await deps.auth.exchangeIntegratorToken(token);   → далее ставится PLATFORM_COOKIE_NAME
```

Значит правильная форма одноразовости: **токен предъявляется один раз, дальше человек живёт на сессии**, и
вторая-третья кнопка не должны обменивать токен заново, если валидная сессия уже есть. Это ровно то, что NIST
и называет привязкой к сессии («securely bind the authentication operation») **[док]**.

### Что поменять

| Файл | Поведение |
|---|---|
| `integrations/webappEntryToken.ts` | Добавить в payload уникальный `jti`; срок оставить 300 с (укладывается в требование NIST ≤10 мин **[док]**) |
| `apps/webapp` — `exchangeIntegratorToken` / `api/auth/exchange` | Атомарно «погасить» `jti` при обмене — по тому же паттерну, что `integrator.idempotency_keys` (`INSERT … ON CONFLICT`); повторный обмен того же `jti` → отказ |
| страница входа `/app/tg`, `/app/max` | Если валидная сессионная кука уже есть — **не обменивать** токен повторно, а сразу уходить на `next`. Без этого шага одноразовость ломает меню из четырёх кнопок |

Важно: изменение **пересекает границу двух приложений**. Интегратор только подписывает; гасить токен может
только вебапп. По D25 это и есть правильное разделение (интегратору — доставка входа, вебаппу — идентичность),
но в план работ это должно войти как одна связанная задача, а не две независимые.

**Цена бездействия:** в течение пяти минут любой, кому переслали сообщение или кто увидел экран, входит в
кабинет пациента и читает медицинскую историю. Пять минут — это не «мало»: скриншот пересылается за секунды.

## 5. В логи ничто не запрещает попасть телефону, токену, тексту сообщения

### Что в коде (поправка к карте)

Редактирование есть:

```bash
sed -n '84,104p' apps/integrator/src/infra/observability/logger.ts
#   redact.paths: headers.authorization, headers.cookie, headers.x-*-secret-token,
#     *.authorization, *.token, *.secret, *.apikey, *.apiKey, *.password, *.phone, *.phone_number
#   serializers: { err: serializeError, error: serializeError }
```

Более того, `serializeError` (строки 35-59) сделан **safe-by-construction**: наружу отдаются только `type` и
провалидированный SQLSTATE, а `cause` намеренно не сериализуется вовсе. Это заметно лучше среднего уровня и
это надо зафиксировать как сделанное правильно.

**Но насколько широко накрывает `redact.paths`?** Документация pino глубину подстановки `*` не определяет,
поэтому замерил на нашем же конфиге:

```bash
# скопировал ровно paths из logger.ts во временный скрипт внутри apps/integrator и выполнил node
```
```json
{"phone":"+79990000001","user":{"phone":"[REDACTED]"},"ctx":{"user":{"phone":"+79990000003"}},
 "token":"TOKEN-TOP","auth":{"token":"[REDACTED]"},
 "message":{"text":"болит спина, диагноз"},"text":"болит спина, диагноз","msg":"probe"}
```

Результат однозначен — **`*.phone` накрывает ровно одну глубину**:

| Форма в логе | Результат |
|---|---|
| `{ phone: … }` (верхний уровень) | **НЕ скрыт** |
| `{ user: { phone: … } }` (глубина 2) | скрыт |
| `{ ctx: { user: { phone: … } } }` (глубина 3) | **НЕ скрыт** |
| `{ token: … }` (верхний уровень) | **НЕ скрыт** |
| текст сообщения (`text`, `message.text`) | **НЕ скрыт — ни одного пути под него нет** |

То есть точная формулировка развилки не «защиты нет», а «защита — кольцо шириной ровно в один уровень
вложенности, и текста сообщения оно не касается вовсе». Практический вывод карты при этом остаётся верным.

Насколько это реализовалось сегодня:

```bash
grep -rnE "logger\.(info|warn|error|debug)\(\s*\{[^}]*\b(phone|token|text|message)\s*[,:}]" \
  apps/integrator/src --include=*.ts | grep -v test     # пусто
grep -rcE "logger\.(info|warn|error|debug)\(" apps/integrator/src --include=*.ts | ... # 260 call sites
```

**Ни одного нарушения сейчас не нашёл** на 260 точках логирования. То есть утечки сегодня нет — есть
незащищённость от неё.

### Как делают

| Система | Как сделано | Источник |
|---|---|---|
| OWASP | Явный список того, что логировать нельзя: «Access tokens», «**Sensitive personal data and PII (health**, government identifiers)», «Authentication passwords», «Encryption keys and primary secrets», «Data classified higher than the logging system is authorized to store». Общий принцип: «**Never log data unless it is legally sanctioned**». Где нужен идентификатор, но не личность — «de-identification techniques such as deletion, scrambling or **pseudonymization**» **[док]** | [OWASP Logging Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html) |
| pino | Редактирование — конфигурация времени инициализации: «The `redact` option is intended as an initialization time configuration option. Path strings **must not** originate from user input». Подстановка стоит дорого: «Wildcard redaction does carry a non-trivial cost relative to explicitly declaring the keys (50% …)». Синтаксиса произвольной глубины (`**`) в документации **нет** **[док]** | [pino: Redaction](https://github.com/pinojs/pino/blob/main/docs/redaction.md) |
| 152-ФЗ (РФ) | Данные о состоянии здоровья отнесены к **специальным категориям** персональных данных (ст. 10); их обработка по общему правилу не допускается, кроме перечисленных случаев — в т.ч. медико-профилактических целей и оказания медицинских услуг **[док]** | [ст. 10 152-ФЗ, КонсультантПлюс](https://www.consultant.ru/document/cons_doc_LAW_61801/26edb2934b899bf9c74c3a8f7e574651c6565e6d/) |

**Где такой список живёт физически и кто его обновляет** — это вопрос брифа, и здесь честный ответ такой:
универсального ответа документация не даёт **[набл]**. Из процитированного следует лишь, что у pino список —
статическая конструкция, задаваемая при инициализации **[док]**, а у OWASP список — организационный документ
уровня политики логирования **[док]**.

### Как надо нам

Наш случай особый по двум причинам сразу: **текст сообщения пациента — это медицинские данные**
(человек пишет боту, на что жалуется), а медицинские данные в РФ — специальная категория по ст. 10 152-ФЗ
**[док]**. OWASP помещает health-данные в список «не логировать» напрямую **[док]**.

**Рекомендация: перенести гарантию с перечня путей на конструкцию типа — тем же приёмом, которым в этом же
файле уже решён `serializeError`.**

Обоснование, почему не «дописать ещё путей»: замер выше показывает, что перечень путей защищает от той формы
объекта, которую автор перечня предугадал. `*.phone` не спас бы ни `{ phone }`, ни `{ ctx: { user: { phone } } }`
— а обе формы естественны и обе пишутся не задумываясь. Расширять перечень до всех глубин нельзя: синтаксиса
произвольной глубины у pino нет **[док]**, а подстановка ещё и дорога **[док]**. Значит перечень путей —
последний рубеж, а не первый. Первым должен быть тип: логирующий код физически не должен иметь на руках
объект, в котором лежит сырой телефон или текст. `serializeError` в этом же файле — уже работающий образец
такого подхода, и его комментарий прямо называет принцип «safe-by-construction».

Для случаев, когда идентификатор в логе всё-таки нужен, канон уже есть в репозитории: `reportOperatorFailure.ts`
считает `buildRecipientDigest` — HMAC от идентификатора получателя вместо самого идентификатора. Это ровно
рекомендованная OWASP псевдонимизация **[док]**, и её стоит объявить общим приёмом, а не частным.

Про физическое место списка: у нас он должен жить **одним модулем рядом с логгером**, а не быть россыпью
внутри вызова `pino(...)`, и обновляться тем, кто добавляет поле. Одной дисциплины мало — владелец 28.07 уже
сформулировал общее правило репозитория, что обещание «впредь буду помнить» не работает и правило должно
стоять в двери. Здесь дверь — это CI: проверка, запрещающая имена запрещённых полей в аргументах `logger.*`.

### Что поменять

| Файл | Поведение |
|---|---|
| `infra/observability/logger.ts` | Перечень запрещённых полей вынести в отдельный экспортируемый модуль (напр. `redactPaths.ts`) — один список, одно место, видимый владелец |
| там же | Добавить в перечень то, чего в нём нет вовсе: поля текста сообщения; и верхнеуровневые формы (`phone`, `token`, …), которые сейчас не накрыты — замер выше |
| тип аргумента логирования | Ввести форму лог-payload, в которую сырые телефон/текст/токен положить нельзя (по образцу `serializeError`); для идентификаторов — псевдоним через digest, как уже сделано в `reportOperatorFailure.ts` |
| CI (`.github/workflows/`) | Проверка на запрещённые поля в аргументах `logger.*`. Сегодня такой проверки нет — искал |

**Цена бездействия:** утечки сегодня нет, но нет и того, что её удержит. Одна естественно написанная строка
`logger.info({ phone, text }, …)` кладёт в лог медицинские данные, попадающие под ст. 10 152-ФЗ **[док]** —
и, в отличие от четырёх остальных развилок, этот отказ **необратим**: лог уже уехал в хранилище, ротацию и
резервные копии, и «откатить» его нельзя.
