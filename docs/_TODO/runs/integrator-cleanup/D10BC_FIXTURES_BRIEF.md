## Что дал живой прогон (сделал лид, у тебя нет доступа к тестовому окружению)

Прогон против настоящей `bersoncarebot_test`: **2 теста из 6 прошли** — это прогресс, прежний отказ по правам
роли устранён. Оставшиеся 4 падают по ДРУГОЙ, новой причине:

```
error: new row violates row-level security policy for table "notification_delivery_attempts"
```

Разобрано мной по схеме тестовой базы:

1. **Политика строк** на `public.notification_delivery_attempts` (`saas_org_dormant_p0_8_4`) требует
   `app.is_staff() AND organization_id = app.current_org_id()`. Фикстура `insertAttemptJournalMarker`
   вставляет строку БЕЗ `organization_id` → `NULL ≠ current_org_id` → отказ.
2. **Внешний ключ**: `notification_delivery_attempts_organization_id_fkey → be_organizations(id)
   ON DELETE CASCADE`. Просто подставить `TEST_FIXTURE_ORGANIZATION_ID` нельзя: **такой организации в базе
   нет** (`be_organizations` содержит 2 строки, фикстурного идентификатора среди них нет).

## Что сделать

Сделать фикстуры самодостаточными: организация, на которую ссылается журнал, должна существовать на время
теста и исчезать после. Требования:

- тест не зависит от того, какие организации уже лежат в базе, и не портит их;
- после прогона база в исходном состоянии — проверить, что убралось всё созданное (каскад по ключу учесть);
- обязательные колонки журнала: `channel`, `status` (плюс `id`/`created_at` с умолчаниями);
- если создать организацию под `app_staff` не выходит по правам или политике — **назови точную причину с
  выводом ошибки и предложи, что нужно**, не подгоняй тест под обход и не ослабляй проверки.
