без пропусков. Колонки ровно те, что требует бриф:

1. **Сегодня** — что модуль делает по коду.
2. **Целевое** — один из трёх исходов: **ОСТАЁТСЯ** (канал/доставка) · **УЕЗЖАЕТ** (продуктовое решение → вебапп) ·
   **УДАЛЯЕТСЯ** (мёртвое или заменяемое). Гибриды называются явно: «остаётся часть X, уезжает часть Y».
3. **Поведение под тесты** — «дано … когда … тогда …», в терминах наблюдаемого результата.
4. **Чем доказывается сегодня** — есть ли тест/живое доказательство.

Сокращение в колонке 4: **нет теста** = ни одного `*.test.ts`, который исполняет этот модуль.

проходит в мастер незамеченной. Сам тест в шапке честно объясняет, почему mock-тест здесь бесполезен:
«the mock DbPort never applies a real PostgreSQL role/RLS check, so a wrong-principal write silently succeeds».

**Что обязаны ловить тесты по этой дыре** (это и есть очередь D20 по D3/D4):

1. дано: вебапп недоступен (транспорт кинул) → когда операция поддержки → тогда **фиксируется инцидент
   оператора и это наблюдаемо**, а не тихий legacy-путь.
2. дано: вебапп вернул `{ok:true}` без `canonicalWrite` → когда операция → тогда поведение **явно названо**:
   либо отказ, либо legacy с сигналом. Молчаливый legacy — красный тест.
3. дано: вебапп вернул `canonicalWrite` с чужим natural key → когда операция → тогда **отказ и инцидент**, а не
   фолбэк.
4. дано: реальный узкий принципал интегратора (`runWithIntegratorPrincipal`, org set, patient NULL,

   запускается в обычном CI**, а не по флагу.
5. дано: интегратору отозвано `public` DML (целевое состояние D17) → когда пациент пишет в поддержку → тогда
   сообщение **не теряется**: это сценарий, который `AUDIT_TRACKD_OPUS_RESULT.md` описал как «INSERT отклонён →
   обращение уходит в durable-outbox либо теряется». Сегодня ни один тест этого не проверяет.
6. дано: локальная техническая запись интегратора под реальным заблокированным принципалом → когда запись →
   тогда она проходит. Отдельная находка D5 (`task_53b67199`): роль `app_patient` не имеет INSERT/UPDATE на
   `integrator.*` вообще — то есть локальные записи многих хендлеров под реальным принципалом падают
   end-to-end. Не проверено ничем.

## Порядок написания тестов

Шкала одна: **цена молчаливой ошибки для человека**. Не «что легче замокать» и не «что крупнее по строкам».
Внутри одного уровня — сначала то, что уже сегодня работает в проде и может сломаться при переписывании.

### Уровень 0 — сообщение уходит не тому человеку (необратимо, это медицинские данные)

1. `shared/devDeliveryRedirect.ts` — **первым**. Ошибка «редирект активен в проде» отправляет переписку всех
   пациентов одному разработчику. Обратного хода нет. Модуль на 357 строк без единого теста.
2. `repos/platformUserByChannel.ts`, `repos/platformUserDeliveryPhone.ts`, `repos/userLookup.ts`,
   `max/maxRecipient.ts` — резолв получателя. Один телефон у двух пользователей, `chatId`, прочитанный как
   `userId`, — прямая отправка чужому.
3. `principal/organizationPrincipal.ts` + `db/withClient.ts` — принципал арендатора и очистка клиента при
   возврате в пул. Протёкший `SET ROLE` = данные одной клиники в руках другой.
4. `runtime/worker/outgoingDeliveryWorker.ts`, ветка `scope` → карантин: строка без разрешимого арендатора не
   должна отправляться «под текущим».

### Уровень 1 — вход не в тот аккаунт

5. `integrations/webappEntryToken.ts` — срок жизни 5 минут, подпись, привязка источника (`tg:`/`max:`),
   отсутствие секрета. Это единственная identity-функция, которую владелец интегратору оставил, — значит
   именно она должна быть непробиваемой.
6. `contracts/ports.ts` → `SetUserPhoneOutcome`: `noop_conflict` вместо `applied`, когда телефон занят.
   Плюс `directPublic/writeIdentityAndPreferencesDirect.ts` — отказ при чужом якоре канала.

   каналах. Расхождение форматов = один человек становится двумя аккаунтами, и половина его истории теряется.

человек не пожалуется; двойная отправка видна, но подрывает доверие; всё остальное чинится повторным
прогоном. Это ровно шкала «цена ошибки», а не «удобство написания».
