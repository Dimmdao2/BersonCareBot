# Слепой список поломок — BAH-01..04 (аудит горизонта записи)

Составлен ДО чтения существующих тестов, только по `docs/_TODO/BOOKING_AVAILABILITY_HORIZON_2026-09-04.md`
и по реализации. Формат каждой строки: «подали X — система ошибочно возвращает Y».

## BAH-01 — горизонт задаёт клиника, 14-дневного хардкода нет

- `K1` Клиника без собственной строки настройки: выдача доступности ограничена 14 днями (старый хардкод),
  а не эффективным клиническим значением.
- `K2` `horizonDays = 7`, запрос без `date`: вернулись дни за пределами `today..today+6`.
- `K3` `horizonDays = 7`, прямой запрос `date = today+30`: вернулись слоты — клиент обошёл список дней,
  подставив дату. (**Главный класс: обход первого списка датой.**)
- `K4` Прямой запрос `date = today-1`: вернулись слоты на прошедший день.
- `K12` Граница: `horizonDays = 1` обязан дать ровно `today..today`; `horizonDays = 30` — `today..today+29`.
  Ошибка на единицу (`+horizonDays` вместо `+horizonDays-1`) молча расширяет окно на сутки.
- `K13` Где-то остался второй путь вычисления диапазона, который 14 дней не потерял (второй колл-сайт).
- `K14` `today` вычислен в TZ процесса, а не в TZ филиала → горизонт съезжает на сутки.

## BAH-02 — настройка клиническая, не глобальная и не пациентская

- `K5` У org A горизонт 7, у org B — 60; запрос org B вернул выдачу, ограниченную 7 днями (или наоборот) —
  утечка значения между арендаторами (в т.ч. через общий процессный кэш слотов).
- `K6` Сохранение из кабинета клиники пишет строку с `organization_id IS NULL` → меняет всем клиникам.
- `K7` Значение живёт как свойство пациента/специалиста, а не клиники.
- `K10` Апдейт принял значение вне границ (`0`, `93`, `-1`, `3.5`, `"abc"`, `"30 "`), и планирование
  получило горизонт 0 дней/огромный/NaN.
- `K11` UI сохранил (200 OK), но планирование продолжает читать старое значение — пишется другой ключ,
  другой scope или другая организация.

- `K9` Провижининг создаёт строку со значением ≠ 30 (например 14) — «дефолт молча вернул 14 вместо 30».
