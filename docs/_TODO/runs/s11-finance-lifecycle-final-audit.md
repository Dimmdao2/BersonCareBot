### MUST FIX F1 — terminal booking replay может стать `dead` без operator incident

**Достижимый сценарий.** Durable `booking_lifecycle`/`paymentCaptured` row доходит до последней попытки;
signed webapp processing снова отвечает ошибкой; в этот момент persistence operator incident временно падает.
`recordBookingLifecycleReplayDeadIncident` ловит и только логирует эту ошибку
(`outgoingDeliveryWorker.ts:252-265`), после чего `finalizeClaimedRowFailure` всё равно выполняет
`queueMarkDead` (`:199-202`). Для reconciliation rows соседняя ветка корректно не глотает ту же ошибку.

**Impact.** Уже зафиксированные деньги могут оставить недоигранную проекцию/календарь/напоминание/feed в
terminal `dead`, но оператор не получит обязательного durable incident; повтор больше не произойдёт. Нарушены
S11 `PAY-REL-02` («terminal dead + operator incident») и owner-rule
`OWNER_PRODUCT_RULES.md` §24.1 (исчерпание попыток обязано оставить operator incident).

**Acceptance evidence.** Тест `keeps terminal replay reclaimable when its operator incident cannot be persisted`
на exact candidate получает `dead=[QUEUE_ID]`, хотя oracle требует `dead=[]` и reclaimable row.

### MUST FIX F2 — одна multi-slot оплата создаёт несколько постоянных feed-фактов

**Достижимый сценарий.** Один provider payment подтверждает два слота. Atomic outbox правильно создаёт один
payment-level job, но handler затем испускает по `booking.payment_captured` на слот
(`appointmentPaymentConfirmedHandler.ts:137-171`). Для второго события ставится только
`suppressPatientNotification`; consumer всё равно безусловно добавляет `patientPushStep`
(`bookingLifecycleRoute.ts:980-1009`). Этот шаг сначала пишет persistent inbox
(`patientWebPushNotify.ts:229-251`) и лишь после этого применяет external-push suppression (`:284-286`). Ключи
feed различаются по `bookingId`, поэтому store принимает обе строки.

**Impact.** Пациент видит две записи «оплата подтверждена» для одного денежного факта; webhook/worker dedupe не
может их схлопнуть. Нарушены S11 `PAT-NOTIF-03` («один доменный факт → одна запись в ленте», stable idempotency)
и owner-решение S8/S11 «одна оплата — одно сообщение», при сохранении отдельных calendar/reminder effects.

**Acceptance evidence.** Расширенный existing multi-slot test сохраняет два технических события, но требует
ровно один feed-bearing payload; exact candidate возвращает два (`expected length 1, received 2`).

### Patient-visible inventory

- `be_appointments` insert → `created` / `awaiting_payment`.
- `be_appointment_history_events` → `rescheduled`, `cancelled`, `no_show` (consumer maps to existing
  `booking.cancelled` variant), and completed/visit-confirmed status transition → `visit_completed`.
- reminder generation → one internal `reminder_due` occurrence even when external channel selection is empty.
- provider settlement → one payment-level durable job → per-slot technical lifecycle events; **F2** is the only
  inventory path producing more than one feed fact for the same owner-defined domain fact.
- `patient_payment` cash ledger → `cash_payment` / `cash_refund`; consumer maps the latter to existing refund fact.
- payment history → successful `refund_succeeded` and `prepayment_retained`.
- All consumer variants reach `runPatientWebPushNotify` → `appendPatientInboundAdminMessage`, which is the existing
  `patientNotifications`/patient inbox store; channel selection happens after append.
