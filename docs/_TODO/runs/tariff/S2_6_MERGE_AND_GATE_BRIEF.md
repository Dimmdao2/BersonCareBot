## Задача 1 — свести две работы, которые столкнулись

В ветке `feat/doctor-ui-rebuild` приземлён пункт **2.1a**: доступ в кабинет стал отдельным предметом
лестницы, у него своя ступень «терпение» и своё предупреждение
(`app-layer/guards/cabinetAccessGate.ts` → `cabinetGraceWarningMessage`).

В этом клоне лежит **2.6** (коммит `6b64ba7d8`): тексты предупреждений перестали быть агентскими — их
пишет владелец строками уведомлений (срок · условие · шаблон с переменными), а поле `count` из
предупреждения исчезло.

`git merge` этих двух даёт конфликт в `apps/webapp/src/app/app/doctor/layout.tsx` (два места) и оставляет
`cabinetGraceWarningMessage` написанным против СТАРОЙ формы предупреждения — он собирает агентскую фразу и
читает `warning.count`, которого больше нет.

**Целевое состояние, оно же решение владельца 31.07:** тексты пишет владелец, агентских фраз не остаётся
нигде — **включая кабинет**. Значит:

- предупреждение кабинета рендерится теми же строками уведомлений владельца, что и остальные механики
  (`entitlementGraceWarningMessages(warning, variables)`), с тем же набором переменных;
- агентская фраза `«Доступ в кабинет: полный доступ до … Предупреждений: N»` и таблица `CABINET_NEXT_STATE_LABELS`
  удаляются вместе с `cabinetGraceWarningMessage`, если после переноса у неё не остаётся вызывающих;
- сама механика 2.1a при этом НЕ теряется: ступень «терпение» у кабинета обязана остаться отличимой от
  полного доступа — предупреждение показывается, просто текст теперь владельца. Доказательство лестницы
  кабинета (`check-access-ladder-transitions.mjs`) обязано остаться зелёным и продолжать краснеть на своих
  самотестах;
- в `doctor/layout.tsx` живут ОБА результата: снимок прав (нужен 2.6 для имени тарифа в переменных) и
  разрешение доступа в кабинет (нужно 2.1a). Не выкидывай ни одно из них ради разрешения конфликта.

Порядок: `git fetch` и слияние свежей `feat/doctor-ui-rebuild` в этот клон, разрешение конфликта по
описанному выше, затем задача 2. Свою работу не откатывай.

## Задача 2 — дыра в механической проверке констант (2.6)

Гейт `src/modules/org-entitlements/ladderConstants.ts` ловит только литерал, стоящий ПРЯМО в свойстве, и
`??`/`||` с литералом справа. Достаточно дать константе ИМЯ — и гейт молчит. Дословная проверка лида: в
`service.ts` добавлено

```ts
const GRACE_DAYS = 14;
const TERMINAL = 'disabled';
export const agentPolicy = { graceDays: GRACE_DAYS, terminalState: TERMINAL };
```

`npx vitest run src/modules/org-entitlements/ladderConstants.test.ts` → **7 passed, 0 failed**. Агентская
длительность и агентское конечное состояние прошли гейт целиком — ровно то, ради чего пункт 2.6 существует.
Гейт сам по себе хороший (дерево разбора, а не регулярка), его надо дотянуть, а не переписывать:

1. **Резолвить идентификатор до его значения внутри файла.** `graceDays: GRACE_DAYS`, где `GRACE_DAYS`
   объявлена в этом же файле как `const` с литералом, — нарушение вида `literal`, со строкой самого
   свойства и именем константы в тексте нарушения. То же для `?? GRACE_DAYS` (вид `fallback`). Цепочку
   `const A = 14; const B = A;` разворачивать.
2. **Объявление, не доехавшее до поля владельца, нарушением НЕ считать** — иначе гейт станет шумным, его
   отключат, и он перестанет ловить что-либо.
3. **Самотесты дополнить именно этой поломкой**: именованная длительность, именованное конечное состояние,
   именованная подстановка, двухзвенная цепочка. Каждый самотест краснеет при снятии своей ветки резолва.
4. Константы, импортированные из других модулей: если резолв через границу файла не делаешь — написать это
   одной строкой в комментарии гейта как известную границу, не выдавая за полное покрытие.
