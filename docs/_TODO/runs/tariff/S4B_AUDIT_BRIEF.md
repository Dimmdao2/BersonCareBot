## Зачем сверка, а не новая работа

Прогон `worker-tariff-knobs` (`a60a39122`) закрыл этап 4b по своему отчёту: ручка понижения тарифа с обобщённой
функцией `evaluateTariffDowngrade`, удаление третьего конечного состояния `full_access`, тесты на управление
значениями. Лид проверил поломкой главное доказательство (значения ручки перестают учитываться → падают 4 теста).

**Но галочки в плане не проставлены, а пять подпунктов сформулированы конкретнее, чем один отчёт.** Задача —
пройти каждый подпункт против КОДА и сказать: закрыт, закрыт частично (чего не хватает), не закрыт.

## Что сверять — дословно по пунктам

- **4b.1** Квота НЕ ручка: достигли предела → новое не создаётся, существующее работает. Ни чтения, ни скрытия.
  **Убраны ли любые следы прежнего варианта** с выбором поведения на пределе — проверить поиском, а не памятью.
- **4b.2** Ручка «неоплата»: лестница на кабинет И на каждую механику; конечных состояния ровно ДВА
  (`только чтение`, `выключено`); значения `скрыто` быть не должно нигде.
- **4b.3** Ручка «переход на тариф меньше»: числовые — `не давать переход` / `дать переход, заморозить рост`;
  возможности — `не давать переход` / `выключить сразу` / `оставить только чтение`. Для объёма файлов значение
  владельца уже названо: `заморозить рост` — проверить, что именно оно и стоит.
- **4b.4** Вычищены ли из КОДА И ПЛАНОВ правила по конкретным сущностям («пациентов только при создании»,
  «филиалы блокируем», «файлы особые») — они должны быть значениями, а не ветками. Проверка та же, что в плане:
  тест ставит одной механике разные значения и получает разное поведение без правки кода.
- **4b.5** Неотключаемые свойства при ЛЮБЫХ значениях: данные не удаляются, отказ всегда видимый, включение
  возвращает всё в прежнем виде. Тест на каждое — есть ли, и краснеет ли.
