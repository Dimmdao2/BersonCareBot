## Что есть и чего нет

Есть: единый резолвер доступа и состояния `выключено` / `только чтение` / `доступно`. Нет самой ЛЕСТНИЦЫ —
переписи 31.07: «единой лестницы состояний с настраиваемыми владельцем сроками в коде ещё нет, сегодня у механик
только простое включено/выключено, без ступеней и без предупреждений».

## Что должно появиться

Ручка «что делать при неоплате», на ДВУХ уровнях — кабинет целиком и каждая механика отдельно. Четыре поля:

| Поле | Смысл |
| --- | --- |
| дней полного доступа | «терпение» — всё работает как обычно |
| число предупреждений | сколько раз предупредить за это время |
| дней только чтения | клиника видит и выгружает, менять не может |
| конечное состояние | `только чтение` · `выключено` |

Жёсткие требования:

1. **Политика — данные, не код.** Значения живут в настройках тарифа и меняются без выкатки и без миграции.
   Ноль дней означает «этой ступени нет». Агент не подставляет числа по умолчанию.
2. **Уровень механики сильнее уровня кабинета.** Не задан — действует уровень кабинета.
3. **Ступень «только чтение» касается ТОЛЬКО клиники** (владелец 31.07: «всё то же самое, пациента она не
   блокирует»): специалист не может создавать и менять, пациентская сторона работает полностью.
4. **Критичные механики в лестницу не входят вообще** — список в каноне §4a; их состояние всегда «доступно».
5. **Данные не удаляются никогда**, включение возвращает всё как было, отказ всегда видимый.

## Приёмка

- тесты на переходы: полный доступ → терпение → только чтение → конечное состояние, по датам, а не по «сейчас»;
- тест: изменение значений в настройках меняет поведение БЕЗ правки кода — это главное доказательство механизма;
- тест: у механики свои значения перебивают значения кабинета;
- тест: критичная механика остаётся доступной при любых значениях;
- каждый тест краснеет при снятии соответствующей проверки — приложить дословный вывод до и после;
- `pnpm --filter webapp lint` и `typecheck` зелёные;
- галочки плана не ставить, push и merge не делать.
