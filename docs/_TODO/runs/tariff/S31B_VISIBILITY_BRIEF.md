## Что требуется

Требование владельца 30.07 дословно: при выключенной механике «ни он не видит в кабинете этого раздела, ни его
клиенты не увидят». Сегодня адаптер видимости — пустая заглушка, то есть требование не исполняет ничто: отказ
приходит только при попытке войти в ручку, а разделы продолжают отображаться.

Сделать ОДИН адаптер видимости, через который спрашивают все три поверхности:

1. навигация специалиста в кабинете;
2. пациентская навигация;
3. прямой переход по адресу (человек сохранил ссылку) — страница обязана вести себя так же, как скрытый раздел.

Состояние берётся тем же путём, что и в 3.1a: через `resolveMechanicAccess` / общий guard
(`apps/webapp/src/app-layer/guards/requireEntitlement.ts`). Второй ветки вычисления не заводить,
собственных списков «какие разделы прятать» рядом с реестром механик не создавать.

## Граница

- «Только чтение» раздел НЕ прячет — прячет состояние «выключено». В режиме только чтения раздел виден,
  недоступна запись (это уже сделано).
- Числовые механики (места, объём файлов) не трогать: у них нет состояния «выключено».
- Тарифные числа, витрину и биллинг не трогать.

## Приёмка

- тест на каждую из трёх поверхностей: при выключенной механике раздела нет в навигации специалиста, нет в
  пациентской навигации, прямой адрес не отдаёт содержимое;
- каждый тест обязан покраснеть, если убрать проверку видимости — приложить дословный вывод обоих прогонов;
- `pnpm --filter webapp lint` и `typecheck` зелёные;
- галочки плана не ставить, push и merge не делать.
