## Что аудитор успел установить

**Статические гейты кандидата зелёные:** `shared-contracts build`, webapp typecheck и полный webapp
lint — exit 0, включая `check-no-new-raw-sql` и infra-boundary self-test.

**Новых дверей в базу кандидат не открывает** (прямая проверка требования плана): детали берутся
через существующий `app.read_current_patient_appointment_history()` и мапятся только из строк
текущего пациентского принципала; новой функции, маршрута или принципала нет.

**Блокер P2.3 подтверждён настоящим:** у видеовстречи есть только вход пациента по `meetingId`;
чтения `appointmentId → meetingId` в портах, репозиториях и API видеовстреч нет. Дословно: «объявленный
blocker P2.3 реален, а подстановка appointment ID была бы неверной».

**Вход:** пароль у DEV-пациента не работает (403 «Вход по паролю не доступен»), аудитор вошёл штатным
email-OTP по §1a. У пациента не было предстоящих записей (10 исторических, 0 upcoming), поэтому он
временно перевёл существующую запись `3287f296…` в `awaiting_payment` с дедлайном `now()+5 мин` и
одним audit-only намерением с безопасным `example.test`-адресом. **Уборку проверил ведущий:** запись
снова `confirmed`, намерений по ней ноль.

## Главная находка — и она НЕ про кандидата

`/api/booking/payment-status` отвечает **500 на любой записи**. Дословно из протокола аудитора:

> Канонический env подтвердил, что это не stale-config: на исходном кандидате
> `/api/booking/payment-status?...` стабильно 500. Достижимый сценарий — любой `awaiting_payment`;
> карточка вместо суммы/срока/CTA показывает «Не удалось проверить статус оплаты». Причина в вызове
> route под `withExplicitOrganizationPrincipal`: repo переводит его в `tenant_service`, но такого
> webapp-port capability нет.

Аудитор сначала заподозрил своё окружение (SHA двух DEV env различались на 10 байт), перезапустил
кандидата с каноническим runtime основного дерева — и получил тот же 500. Это добросовестно: он не
записал в находки то, что могло быть его собственной конфигурацией.

**Ведущий подтвердил независимо**, дважды и другим способом: внутрипроцессный вызов того же пути дал
`CAUSE: Missing declared webapp port capability: tenant_service`, а запрос по живому маршруту с
настоящей пациентской сессией — `HTTP=500`. Дефект принадлежит приземлённому коду S4, а не кандидату
карточки: маршрут оборачивает пациентское чтение в принципал организации, которому произвольные
реляционные чтения не разрешены. Заведено этапом **S9** в
`docs/_TODO/APPOINTMENT_PREPAYMENT_VISIBILITY_2026-09-11.md`.

Чтобы не остановить аудит на первой ошибке, аудитор временно подменил принципал маршрута на
существующий пациентский, прошёл остальной UI и правку откатил (дерево клона чисто — проверено
ведущим). Он же прямо записал: «Исходный кандидат от этого PASS не получит».
