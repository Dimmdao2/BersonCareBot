## 2. Проверка делом — ответ на три вопроса

### Вопрос 1. Блокер доступа к БД — **ЛОЖНЫЙ**. Это главная находка.

Воркер прав в двух частных фактах и неправ в выводе.

**Что подтвердилось** (его наблюдения верны):

```
$ sudo -n -u postgres psql -tAc "select current_user"
sudo: The "no new privileges" flag is set, which prevents sudo from running as root.

$ stat -c '%F' apps/webapp/.env.example deploy/env/empty.local-migration.env
character special file          ← оба замаскированы в /dev/null, это и есть 10 «M» в git status
```

`sudo` действительно мёртв, env-файлы действительно замаскированы. Но из этого **не следует**
«нет способа создать одноразовую базу»: и `sudo`, и общий кластер бокса нужны только если
одноразовую базу делать НА кластере бокса. Это лишнее условие, которое воркер не поставил под сомнение.

**Путь A — свой кластер из-под `dev`, без sudo вообще (проверено делом):**

```
$ ls /usr/lib/postgresql/16/bin/ | tr '\n' ' '
... initdb pg_ctl postgres psql pg_dump pg_restore ...     ← сервер целиком на месте

$ initdb -D /tmp/auditb_pg/data -U dev --auth=trust        → rc=0
$ pg_ctl -D /tmp/auditb_pg/data -o "-p 55432 ..." start    → rc=0
$ psql ... -tAc "select current_user, rolcreatedb, rolsuper from pg_roles where rolname=current_user"
dev|t|t                                                     ← СУПЕРЮЗЕР и CREATEDB
$ psql ... -c "CREATE DATABASE disposable_probe_1;"
CREATE DATABASE
```

**Путь B — docker, образы уже скачаны (проверено делом):**

```
$ id
uid=1001(dev) ... groups=...,990(docker)                    ← юзер в группе docker
$ docker images | grep postgres
postgres:15          ...   postgres:16-alpine  ...          ← оба УЖЕ локально
$ docker run -d --rm --name auditb_pg_probe -e POSTGRES_PASSWORD=probe postgres:16-alpine  → rc=0
$ docker exec auditb_pg_probe psql -U postgres -c "CREATE DATABASE disposable_probe_2;"
CREATE DATABASE
```

**Путь C — и это тяжелее всего: РЕПОЗИТОРИЙ УЖЕ УМЕЕТ ЭТО САМ.** В репозитории лежат три скрипта,
которые поднимают одноразовый кластер ровно механикой пути A, без sudo и без общего кластера:

| Скрипт | Что делает |
|---|---|
| `scripts/verify-a0-greenfield-baseline.mjs:137-220` | `resolveTrustedPostgresBinaries(['initdb','pg_ctl','psql'])` → `initdb` во временный каталог → `pg_ctl start` → `CREATE DATABASE … OWNER …` |
| `scripts/verify-a1-rls-conformance.mjs:140-249` | то же самое, для проверки RLS |
| `scripts/verify-b3-booking-concurrency.mjs:15,183` | то же самое, для гонок брони |

И резолвер бинарей отрабатывает в этой самой песочнице:

```
$ node -e "import('./scripts/a0-greenfield-baseline-lib.mjs').then(m=>console.log(
    m.resolveTrustedPostgresBinaries(['initdb','pg_ctl','psql'])))"
{ initdb: '/usr/lib/postgresql/16/bin/initdb',
  pg_ctl: '/usr/lib/postgresql/16/bin/pg_ctl',
  psql:   '/usr/lib/postgresql/16/bin/psql' }
```

Отчёт воркера не упоминает эти три скрипта ни разу. Он спроектировал харнесс так, что тот **требует
внешнего суперюзера** (`POSTGRES_INTEGRATION_SUPERUSER_URL` или `…_SUDO_POSTGRES=1`,
`harness-lib.ts:58-78`), тогда как рядом в репозитории лежит готовый образец, которому не нужно
ничего. Это же делает харнесс непригодным для CI: раннеру GitHub Actions неоткуда взять
`sudo -u postgres`, а `initdb` — есть.

> **Вывод по вопросу 1: владелец для разблокировки НЕ нужен.** Ни `sudo`, ни пароль, ни доступ к
> общей `bcb_webapp_dev` не требуются. Требуется переписать транспорт харнесса на уже имеющийся в
> репозитории `resolveTrustedPostgresBinaries` + `initdb`/`pg_ctl`.

### Вопрос 2. Харнесс — что он обещает и что делает

Доступ нашёлся, поэтому проверял прогоном, а не чтением. Все прогоны — на **своём** кластере
(порт 55432, сокет `/tmp/auditb_pg`), общая `bcb_webapp_dev` не тронута ни на чтение, ни на запись.

#### Хорошая новость: молчаливой деградации схемы НЕТ

Мои гипотезы B1/B2/B4/B5 (фолбэк на дамп, фолбэк на `bcb_webapp_dev`, проглоченная ошибка миграции,
`db push` вместо миграций) — **не подтвердились**. Харнесс честен: `runMigrationsAgainst`
(`harness-lib.ts:167-184`) проверяет `result.status !== 0` и бросает; фолбэков нет; `sanitizedChildEnv`
(`:110-116`) вычищает `DATABASE_URL`/`PG*` у дочерних процессов. Это сделано аккуратно.

#### Находка Б-1 (критическая): цепочка миграций НЕ СТРОИТСЯ С НУЛЯ ВООБЩЕ

Первый же реальный прогон `build-template`:

```
$ POSTGRES_INTEGRATION_SUPERUSER_URL="postgres://dev@127.0.0.1:55432/postgres" \
    pnpm exec tsx scripts/postgres-integration/cli.ts build-template
[migrate] failure migration=0001_charming_champions idx=1 reason=schema_mismatch sqlstate=42P01
[postgres-integration-harness] FAILED: migration chain failed while building the
  disposable-PostgreSQL template (status 1)
```

Воспроизвёл вручную по шагам:

```
$ psql .../pbt_chainprobe -v ON_ERROR_STOP=1 -f 0000_wandering_famine.sql     → rc=0
$ psql .../pbt_chainprobe -v ON_ERROR_STOP=1 -f 0001_charming_champions.sql
ERROR: relation "public.platform_users" does not exist
```

`0001_charming_champions.sql:44` вешает FK на `public.platform_users`. Кто её создаёт:

```
$ grep -rniE "create[[:space:]]+(table|view|materialized)[^;]*platform_users" *.sql | wc -l
0                    ← НИ ОДНА из 287 миграций не создаёт platform_users
$ grep -c platform_users docs/ARCHITECTURE/DB_DUMPS/a0-greenfield/schema.sql
190                  ← она есть только в ДАМПЕ
```

**Требование Б1 «база строится прогоном цепочки миграций с нуля, дампами не наливается никогда»
сегодня невыполнимо в принципе.** Цепочка не самодостаточна: она — дельта поверх greenfield-дампа.
Это ровно то, о чём предупреждает канон `host-psql-database-url.mdc`: «Не собирать схему миграциями
«с нуля» (кросс-скоуп порядок ломается) — базу+леджер даёт дамп, `pnpm migrate` накатывает дельту».

Следствие, которое важнее самого факта: **доказательство №1 из плана вырождается**. «Заведомо битая
миграция роняет прогон» нельзя отличить от «цепочка и так всегда красная». Пока чинить нечего —
харнесс не может выдать template ни разу, значит ни один `*.postgres.integration.test.ts` не может
быть выполнен. Это развилка для владельца, а не работа воркера (см. §4).

#### Находка Б-2 (критическая): «тесты никогда не видят `bcb_webapp_dev`» — НЕВЕРНО

`vitest.postgres.setup.ts:7` утверждает: «Test files never see the template or `bcb_webapp_dev` —
only their own throwaway clone». Механика: `DATABASE_URL` подставляется в `beforeAll` (`:34-44`).
Но пилотный тест строит пул в теле `describe` (`pgDisposableHarness.postgres.integration.test.ts:21`),
то есть **на этапе сбора, ДО того как `beforeAll` отработал**. Проверил отдельным зондом (вне репо):

```
AT COLLECTION (что видит new pg.Pool()): <undefined>
AT RUN TIME   (после beforeAll)        : CLONE_URL_SET_BY_BEFOREALL
```

А теперь то же самое на машине разработчика, где `DATABASE_URL` экспортирован — а канон
`host-psql-database-url.mdc` предписывает работать именно так (`set -a && source … && set +a`):

```
AT COLLECTION (что видит new pg.Pool()): postgres://bcb_webapp_dev_user@127.0.0.1:5432/bcb_webapp_dev
AT RUN TIME   (после beforeAll)        : CLONE_URL_SET_BY_BEFOREALL
```

**Пул подключается к общей `bcb_webapp_dev`.** Пилотный тест это заметит (у него есть
`expect(current_database()).toMatch(/^pbt_/)`), а вот будущая матрица стен арендатора В1 — нет:
она про принципалов и организации, имя базы ей проверять незачем. Она молча пойдёт по живой DEV-базе
и будет в ней **писать**. Это и есть то место, где харнесс молча деградирует, — не фолбэк на дамп,
а приоритет переменной окружения. Защита имени (`pbt_`-guard) здесь не срабатывает вообще: она
охраняет то, что харнесс создаёт и удаляет, а не то, к чему подключается тест.

#### Находка Б-3 (критическая): роль клона не имеет прав на схему клона

Воспроизвёл точную последовательность SQL харнесса (`harness-lib.ts:187-256`) — миграции
выполняются под ролью `<template>`, а тесту отдаётся URL под ролью `<clone>`:

```
$ psql "postgres://pbt_clone_c3d4@127.0.0.1:55432/pbt_clone_c3d4" -tAc "SELECT count(*) FROM platform_users;"
ERROR:  permission denied for table platform_users
```

`CREATE DATABASE … OWNER <clone>` меняет владельца **базы**, но таблицы внутри копии остаются за
ролью `<template>` (владение копируется по OID). Роль клона — `NOSUPERUSER … NOBYPASSRLS` и не член
роли шаблона, поэтому не может прочитать ни одной таблицы. Даже если починить цепочку миграций,
каждый тест упадёт на `permission denied`.

#### Находка Б-4: одноразовые базы текут именно в сценарии-витрине Б1

`buildTemplateDatabase` создаёт роль и базу (`:192-202`), затем гоняет миграции (`:215`). `try/finally`
нет. Когда миграции падают — а по находке Б-1 они падают всегда — созданное остаётся навсегда:

```
$ psql -tAc "select 'DB '||datname from pg_database where datname like 'pbt%'
             union all select 'ROLE '||rolname from pg_roles where rolname like 'pbt%'"
DB   pbt_tpl_1785535477048_11c550        ← мусор от ОДНОГО упавшего build-template
ROLE pbt_tpl_1785535477048_11c550
```

Хуже: уборка каскадно ломается сама. Если тест-файл падает и клон утёк, teardown шаблона
(`dropDisposableDatabase`, `:258-270`) делает `DROP DATABASE` шаблона, а потом `DROP ROLE`:

```
ERROR:  role "pbt_tpl_a1b2" cannot be dropped because some objects depend on it
DETAIL:  1 object in database pbt_clone_c3d4
```

База шаблона уже удалена, роль — нет, teardown бросает исключение, и каждый следующий прогон
добавляет мусор. Требование Б1 «после прогона одноразовые базы удалены» не выполняется.
