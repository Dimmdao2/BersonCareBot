## Скоуп — два пункта

### Б1 — харнесс одноразовой базы

Требования, каждое из плана, не из вкуса:

1. **Схема только из миграций, с нуля.** Никаких дампов, никакого копирования TEST или DEV. Прямое следствие,
   которое надо сохранить и показать: **битая цепочка миграций роняет тестовый прогон** — сегодня это ловит
   только деплой.
2. **Скорость — шаблонной базой.** Собрали схему один раз за прогон, дальше на тест — клон
   (`CREATE DATABASE … TEMPLATE …`), а не повторный прогон миграций.
3. **⛔ Общую `bcb_webapp_dev` не трогать ничем** — ни читать как источник, ни писать. Канон это прямо
   запрещает, и именно это делают нынешние legacy-тесты.
4. **Тесты на харнессе видны раннеру.** Суффикс `*.postgres.integration.test.ts` и свой vitest-project, иначе
   файл повторит судьбу тех 22 (их разбираешь ниже) и параллельный гейт М4 покраснеет на твоей же работе.
5. **Прогон должен быть запускаем одной названной командой** и не входить в быстрый PR-шард по умолчанию —
   решение по месту в CI прими сам и обоснуй временем прогона (замерь и назови число).

**Доказательство работоспособности харнесса — не «поднялось», а поведение:**
- намеренно битая миграция → прогон красный (показать дословно, вернуть как было);
- две последовательные сборки дают одинаковую схему (детерминизм);
- база после прогона удаляется, соседние базы бокса не задеты (перечислить `\l` до и после).

Пилотный тест на харнессе — **ровно один**, минимальный, только чтобы доказать, что связка живая. Матрицу
стен арендатора (блок В1) **не писать**: это следующая работа и отдельный скоуп.

### Б3 — разбор 22 файлов `*.devDb.integration.test.ts`

Они лежат в дереве и не запускаются ничем (`vitest run <файл>` → `No test files found`). Владелец 31.07:
«надо их проверить, что они вообще тестируют и нужны ли они».

По КАЖДОМУ файлу — строка таблицы: что он реально проверяет (не по названию, а по телу), какую поломку ловит,
и решение — **перенести на харнесс Б1** или **удалить с названной причиной**. Критерий переноса — канон
«назови поломку»: если поломка не называется или неправдоподобна, файл удаляется. Известно заранее (из
инвентаря `TESTSUITE_CRITICAL_TARGETS_SOL_RESEARCH_2026-07-30.md`, раздел C), что часть из них — read-only
smoke, не выполняющий проверяемого действия вовсе: например `platformUserFullPurge` только читает строку и
самого удаления не делает. Такое честно называй пустышкой.

**Переносить сразу — не больше трёх файлов**, самых ценных по цене ошибки (там есть настоящие двухсоединённые
гонки: атомарное гашение кода, эскалация блокировки). Остальные — решение в таблице, перенос отдельной работой.
Удаление выполняй только по строкам таблицы, и в том же коммите, что и таблица.

## Приёмка

- харнесс поднимает базу из миграций с нуля, шаблон+клон работает, время прогона названо числом;
- три доказательства из Б1 (битая миграция → красный; детерминизм; чистота бокса) — дословным выводом;

- отчёт содержит раздел «НЕ СДЕЛАНО» — даже если пустой.
