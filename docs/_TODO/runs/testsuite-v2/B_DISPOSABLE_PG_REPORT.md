## Блокер: в этом клоне нет PostgreSQL-доступа с правом создавать базы

Обнаружено до первой строки кода, при попытке следовать `.cursor/rules/host-psql-database-url.mdc`
(«сначала загрузить env-файл, потом psql»).

**Хост подтверждён настоящий** (`hostname -I` → `151.241.228.122`, тот самый DEV/RELAY/TEST хост из
`SERVER CONVENTIONS.md`), локальный PostgreSQL 16 живой (`pg_lsclusters` → `16 main 5432 online`,
`ss -tlnp` → `127.0.0.1:5432` слушает). Но:

1. **`.env.dev` / `.env.example` в этом рабочем дереве — не файлы, а `/dev/null`.**
   `ls -la apps/webapp/.env.dev` → `crw-rw-rw- 1 root root 1, 3 … .env.dev` (major/minor `1,3` =
   character device `/dev/null`). То же для корневого `.env.example`,
   `deploy/env/empty.local-migration.env` и ещё 6 env-файлов — это именно те файлы, что стоят
   modified в `git status` этого клона с самого начала сессии (не моя правка, артефакт
   изоляции этого worktree). Для сравнения: в каноническом клоне
   `/home/dev/dev-projects/BersonCareBot/apps/webapp/.env.dev` — обычный файл `-rw-------`. Это
   специфика именно `bcb-wt-portsmoke`, не факт о хосте.
2. **`sudo` недоступен вообще**, даже с `dangerouslyDisableSandbox`: `sudo -n -u postgres psql …` →
   `sudo: The "no new privileges" flag is set, which prevents sudo from running as root.` — это
   `PR_SET_NO_NEW_PRIVS` на уровне контейнера этого клона, не файл-пермишен, который можно обойти.
   Deploy-скрипты репозитория (`deploy/host/migrate-dev.sh`,
   `docs/_TODO/SAAS_FOUNDATION/scripts/run-saas-disposable-dormant-rehearsal.mjs`) сами полагаются
   именно на `sudo -n -u postgres psql` как единственный DEV-safe транспорт — в этом клоне он не
   работает.
3. **`pg_hba.conf` не читается** (`Permission denied`), пиринг-аутентификация для `postgres`/`dev`
   отклонена, TCP на `127.0.0.1:5432` требует пароль, которого негде взять легитимно (ни в env, ни
   в `~/.pgpass`, ни в `/opt/env`).

Я не подбирал пароли и не пытался обойти это иначе, чем чтением документированных путей — по
`AGENTS.md` §STOP-GATE и общему принципу «не выдумывать источники». Дальше: всё, что не требует
живого соединения с PostgreSQL, сделано; всё, что требует — написано, но помечено unverified и
описано построчно в «НЕ СДЕЛАНО».

### Что НЕ проверено (требует PostgreSQL с `CREATEDB`/суперюзером)

Ни одно из трёх обязательных поведенческих доказательств Б1 не получено:

   дважды подряд, сравнить `information_schema.columns`/`pg_indexes` двух получившихся баз (`diff`

3. **Чистота бокса — `\l` до/после.** Не воспроизведено. Команда:

Плюс: время прогона (брифом требуется назвать числом) — не измерено, т.к. прогон не состоялся.

**Транспорт учётных данных.** Харнесс требует `POSTGRES_INTEGRATION_SUPERUSER_URL=postgres://…`

## Б3 — разбор 22 файлов `*.devDb.integration.test.ts`

Прочитаны все 22 файла целиком (не по названию, по телу). Ниже — построчная таблица; решения:
**T-now** (перенесено физически сейчас — 0, см. блокер выше), **T-later** (реальная поломка
названа правдоподобно, перенос — отдельная работа, файл **сохранён**), **DELETE** (поломка не
называется/неправдоподобна — «пустышка», файл **удалён этим коммитом**).

Критерий по канону `tests-check-behaviour-not-circumstances.mdc`: «одна строка — какая поломка,
подали X получили неправильное Y» + правдоподобность. Тест, зависящий от того, есть ли сейчас в
`bcb_webapp_dev` живые строки (без фикстур, тихо `return` на пустой выборке), не проходит критерий
дважды: и как «зависимость от обстоятельств запуска», и как «поломку не назвать» (утверждение
срабатывает только когда кому-то повезло с данными).
