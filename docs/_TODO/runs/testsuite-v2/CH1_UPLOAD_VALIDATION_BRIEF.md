# Ч1 — единая проверка загружаемого файла, мимо которой принять файл нельзя

(run: `worker-ch1-upload-validation`, клон `bcb-wt-testsuite2`, ветка `wt/ch1-upload`)

**План (authority):** [`docs/_TODO/SINGLE_ENTRY_CLEANUP_2026-08-01.md`](../../SINGLE_ENTRY_CLEANUP_2026-08-01.md),
чек-лист, пункт **Ч1**. Карточка `#1082`.

**Строка плана, дающая оракул:** Ч1 — «Шесть маршрутов, три разные реализации проверки, один маршрут без
проверки вовсе. Готово = единый валидатор, вызываемый конструкцией приёма файла, плюс запрет принять файл
мимо него». И общее требование плана: «Выполненным пункт считается только когда есть единая точка И
механическая проверка, роняющая сборку на попытке пройти мимо».

**Базовая линия — не перемерять:** числа взяты из переписи
[`CHOKEPOINT_SWEEP_REPORT.md`](CHOKEPOINT_SWEEP_REPORT.md), строка 7 таблицы — там же команды, которыми они
получены. Заново пересчитывать поверхность не надо; надо проверить, что список маршрутов не изменился с
момента переписи, и работать по нему.

## Что сделать

1. **Найти маршрут без проверки и назвать его первым.** Это прямая дыра, а не стилистика: он принимает файл,
   не проверив ни тип, ни размер. Что именно он принимает и чем это грозит — первой строкой отчёта.
2. **Свести три реализации в одну.** Сравнить их построчно и выписать расхождения: у кого какой предел
   размера, какой список типов, как ведёт себя на пустом файле и на несоответствии заявленного типа
   фактическому. Расхождения — это и есть сегодняшнее поведение системы; **выбор целевого поведения по
   каждому расхождению обосновать**, а не усреднить молча. Если расхождение выглядит как продуктовое решение
   (например, для одного вида вложений умышленно больший предел) — это **вопрос владельцу в отчёт**, не твой
   выбор.
3. **Сделать проход единственным.** Приём файла должен идти через одну точку так, чтобы мимо неё файл принять
   было нельзя по конструкции — предпочтительно, чтобы обход не компилировался, а не «ловился гейтом».
   Если конструктивно это невозможно в нынешней форме маршрутов — сделать гейт и **сказать в отчёте, почему
   конструкция не вышла**, а не выдавать гейт за целевое.
4. **Гейт с самотестом.** Механическая проверка обязана краснеть на намеренно заведённом маршруте, который
   принимает файл мимо единой точки. Дословный вывод «до/после» — в отчёт.
5. **Существующие обходы, которые не успеваешь перевести, — в список исключений** (список, который имеет право только
   сокращаться), а не в исключение «навсегда».

## Границы

- Продуктовое поведение не менять сверх сведения проверок: если после унификации какой-то маршрут начнёт
  отвергать то, что раньше принимал, — это **изменение поведения**, его надо назвать в отчёте явно, а не
  «заодно починить».
- Тесты писать по канону: `*.route.test.ts` через настоящий публичный handler; тест обязан краснеть при
  снятии проверки. Ты не сертифицируешь свои тесты — слепой список поломок составит аудитор.
- Полный CI не гонять — точечно; полный прогон делает лид.
- Ветка `wt/ch1-upload`, коммиты только в неё. **Push и merge не делать, галочки плана не ставить.**
