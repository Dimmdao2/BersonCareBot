# Вынести TEST-фикстуры из общего оверлея телеметрии изоляции

раздел «ПОРЯДОК РАБОТ v2», блок Б (пункт Б2 — эталон схемы). Работа заказана владельцем 01.08: «вынеси

**Строка плана, дающая оракул:** правило `AGENTS.md` §5 — «появился второй способ сделать то же самое —
значит первый перестал быть проходом и стал одним из вариантов; с этого момента правило нарушено, даже если
оба варианта сегодня работают верно». Здесь то же в другой форме: **тестовая фикстура и боевой API живут в
одном файле, поэтому подключить один без другого нельзя.**

**Базовая линия — не перемерять, установлено лидом:**
`deploy/postgres/saas-isolation-telemetry.sql`, 440 строк, содержит две разные вещи:
строки **113–297** — боевой API телеметрии (запись события изоляции, покрытие, чтения), нужен ВЕЗДЕ, включая
прод; строки **299–397** — фикстуры сценариев TEST (`app.set_saas_isolation_test_scenario`,
`app.read_saas_isolation_test_scenario_fixture_counts`), нужны ТОЛЬКО на TEST, что написано в самом файле:
«Operator-only TEST fixture state». Оверлей применяется только `deploy/host/deploy-test-saas.sh`
(строки 72, 706, 2267, 2438); в `deploy/host/deploy-prod.sh` упоминаний **ноль**.

**Риск, ради которого режем:** боевая половина проду нужна. Как только оверлей подключат к прод-деплою,
фикстуры приедут вместе с ней — они в том же файле. Предохранитель по имени базы внутри функции останется
вторым рубежом, но первым рубежом должно быть «этого объекта там просто нет».

## Что сделать

1. **Разрезать файл на два.** В `saas-isolation-telemetry.sql` остаётся боевой API и всё, что нужно везде.
   Фикстуры уезжают в новый файл (имя выбрать по конвенции соседних файлов в `deploy/postgres/`), в шапке —
   одна строка, почему он отдельный и где применяется.
2. **Подключить новый файл только к TEST** — в `deploy-test-saas.sh`, рядом с существующим оверлеем, тем же
   способом, каким подключён он (переменная + `-f` + проверки наличия в обоих местах, где они есть сейчас:
   строки 2267 и 2438 — не пропустить).
3. **Предохранитель `current_database() <> 'bersoncarebot_test'` в теле функций НЕ трогать** — он остаётся
   вторым рубежом.
4. **Проверить, что боевая половина ничего не потеряла:** сравнить список создаваемых объектов до и после
   разреза (имена функций, гранты, владельцы) — он обязан совпасть по объединению двух файлов.
5. **Находка, которую надо назвать, но не чинить:** обе функции сегодня существуют в `bcb_webapp_dev`, хотя
   `deploy/host/migrate-dev.sh` этого оверлея не применяет. Как они там оказались — выяснить по факту
   (история команд/скрипты/`pg_stat`-следы, что найдётся) и написать в отчёт. Удалять их из DEV **не надо**:
   это отдельное решение владельца.
