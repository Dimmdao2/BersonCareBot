## М3 — Stryker как diff-scoped гейт

### Разведка перед стройкой (что снимает «существенную машинерию»)

Ключевая находка, снимающая главный риск раздутия: **Stryker JS уже умеет мутировать конкретный
диапазон строк файла** — синтаксис `mutate: ["path:startLine-endLine"]` (проверено, задокументировано
в `@stryker-mutator/core` schema). Это значит, стоимость прогона растёт с размером ДИФФА, а не с
размером файла — не нужно мутировать файл целиком и потом фильтровать результат постфактум.

Замер на существующем пилоте (`stryker.entitlements.json`, 2 файла, 808 строк, весь файл):
`724 мутанта, 2m10s`. Тот же файл, диапазон в одну изменённую строку: `0-1 мутант, ~35 секунд` (почти
весь бюджет — фиксированный dry-run прогон 142 тестов, ~28с, не зависящий от числа мутантов). Вывод:
diff-scoped режим **дешевле** файл-scoped на порядок для типичного диффа (несколько строк в
нескольких файлах), потому что платим за диапазон, не за файл.

**Среда:** локально Stryker падал на `EACCES` при копии `apps/webapp/.env.example` в песочницу — тот
же артефакт маскировки секретов, что и в М2 (файл превращён в `/dev/null`-character-device этим
боксом). Решено штатной опцией `ignorePatterns: [".env.example"]` (Stryker и так не должен копировать
файл, не нужный для прогона тестов) — не обход, а корректная настройка, полезная и в обычном CI.

### Сделано

- `scripts/check-stryker-diff-scoped.mjs`: по паре `--base <ref>`/`HEAD`
  1. берёт список изменённых `apps/webapp/src/**/*.ts(x)` (не тестовых) файлов
     (`git diff --name-only --diff-filter=ACMR`);
  2. для каждого — точные диапазоны НОВЫХ/изменённых строк из `git diff --unified=0` (заголовки
     `@@ -a,b +c,d @@`, `d` строк начиная с `c` — ровно то, что реально изменилось, без строк контекста);
  3. вырезает из этих диапазонов тривиальные («arid») строки — пустые, комментарии, импорт/реэкспорт,
     чистый `console.*` — механический прокси из плана («логи, тривиал»), не полная классификация;
  4. собирает Stryker `mutate: ["path:start-end", ...]` только по оставшимся диапазонам и прогоняет
     Stryker с этим конфигом (временный, не коммитится);
  5. читает JSON-отчёт; любой мутант со статусом, отличным от `Killed`/`Timeout` (то есть `Survived`
     или `NoCoverage`) на этих строках — **гейт красный**, печатает файл:строку и мутатор.
  6. если в диффе нет файлов `apps/webapp/src` или все изменённые строки — arid, гейт зелёный тривиально
     (нет решений — нечего судить).
- CI: новый job `stryker-diff-scoped` в `.github/workflows/ci.yml` — `fetch-depth: 0` (нужна база для
  диффа), базу берёт из `github.event.pull_request.base.sha` (PR) или `github.event.before` (push),
  фолбэк `HEAD~1`. Стиль — тот же, что у соседних job (`setup-pnpm`, `cancel-on-failure`).
- Порог процента нет по решению М5 — критерий бинарный (убит/не убит).

**Служебные проверки**: без `--base`/`STRYKER_DIFF_BASE` гейт отказывает (`exit=2`, не 0/1 — это
ошибка вызова, не вердикт); диф без изменений (`--base HEAD`) — тривиальный `OK` без запуска Stryker.

### ⚠️ Находка про сам Stryker (не мой код, но важно для доверия к гейту)

При отладке зелёного самотеста воспроизвелось: если на ОДНОЙ строке несколько мутационных точек
(например, тернарник с двумя строковыми литералами, или if-условие вместе со своим return на соседней
строке) и единственный покрывающий тест — тот же самый для всех них, `@stryker-mutator/vitest-runner`
9.6.1 в этом проекте иногда репортует **`Survived` с `testsCompleted: 0`**, хотя тот же самый мутант,
протестированный ИЗОЛИРОВАННО (диапазон в одну строку с ОДНОЙ мутационной точкой), убивается тем же
тестом корректно. Проверено дважды с `coverageAnalysis: "perTest"` и один раз с `"all"` — тот же
результат независимо от режима анализа покрытия. Это похоже на баг конкретно в связке
`@stryker-mutator/vitest-runner` + composite-выражения этого проекта (Next.js/Vite alias-резолюция),
не в диапазонной мутации как таковой — изолированный один мутант на диапазон убивается стабильно
(проверено трижды).

**Практическое следствие, а не блокер:** направление ошибки безопасное — гейт может **ложно
покраснеть** на составном выражении (потребует ручной проверки автором PR: реально ли мутант выжил),
но никогда не позеленеет на реально непойманной поломке (что и требовалось — false positive, не false
negative). Рекомендация в план: если гейт красный на строке с составным выражением (тернарник,
`&&`/`||` в одной строке) и тест визуально покрывает её — перепроверить вручную/локально перед тем как
считать находку реальной дырой в тестах, а не завести отдельную задачу на разбор самого Stryker.

### Побочный вывод

Прогонять этот job для диффов ВНЕ `apps/webapp/src/**/*.ts(x)` не пришлось конфигурировать отдельно —
скрипт сам обнаруживает пустой список файлов и выходит `OK` без запуска Stryker (проверено).

## НЕ СДЕЛАНО

- CI-обвязка job `stryker-diff-scoped` (резолв базы из `github.event.pull_request.base.sha` /
  `github.event.before`) написана по конвенции соседних job, но **не проверена живым прогоном
  GitHub Actions** — из этого бокса нет доступа поднять реальный PR/push event. Сам механизм гейта
  (`scripts/check-stryker-diff-scoped.mjs`) проверен полностью и многократно с явным `--base`;
  непроверена только тонкая обвязка вокруг выбора ref. Рекомендация: первый реальный прогон в CI
  посмотреть глазами при следующем PR, тронувшем `apps/webapp/src`.
- Стабильность на БОЛЬШИХ диффах (десятки файлов/сотен строк за один PR) не замерена — только на
  диапазоне 1-2 строк (секунды) и на whole-file пилоте 808 строк/724 мутанта (2m10s) как верхняя
  оценка стоимости одного файла. Если такой PR обнаружит время за пределами 20-минутного таймаута
  job — следующий шаг таков, каким его и предлагает план: смотреть на числа, не строить кэш заранее
  вслепую.
- Найденный баг Stryker/vitest-runner на составных выражениях (см. выше) не исправлен и не заведён
  отдельным issue — не мой код и не моя роль здесь; записан как известная особенность гейта.
