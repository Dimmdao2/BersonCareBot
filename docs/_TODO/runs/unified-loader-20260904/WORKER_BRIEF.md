# Worker brief: единый лоадер кабинетов

Прочитай `AGENTS.md`, особенно §15, §16, §17, §21, §24, и соответствующие UI style guide. Authority этого bounded-прохода — явное указание владельца в этом brief.

## Указание владельца

Во всех кабинетах — доктор, администратор и пациент — состояния загрузки должны использовать один визуальный элемент: серый текст `Загрузка…` нормального читаемого размера и рядом один вращающийся индикатор-«лучик». Элемент центрируется горизонтально и вертикально в доступной области. Не добавлять пульсацию текста: движение даёт только spinner. Не оставлять уточнения вида «Загрузка календаря/графика/сообщений» в контентных loading-state. Не заменять этим компонентом action labels (`Загрузить файл`, `Сохранение…`, прогресс загрузки файла) — это не состояния ожидания контентной области.

## Scope и порядок

1. Сначала через code-search и затем точный `rg` найди существующие shared loading primitives, route `loading.tsx`, Suspense fallbacks и вручную нарисованные content-loading states в `apps/webapp`.
2. Не создавай второй общий компонент рядом с уже пригодным: выбери/расширь существующую нейтральную точку, если она есть. Если единого нейтрального примитива действительно нет, создай ровно один в общем shared UI без импорта doctor/patient зональных компонентов. Зональные публичные имена допустимы только как re-export/alias того же implementation, если нужны для совместимости.
3. Переведи на него достижимые content/page/panel/modal loading states во всех кабинетах. Не делай механическую замену всех слов `Загрузка`: различай ожидание контента и пользовательское действие/прогресс.
4. Соблюди физическую изоляцию patient/doctor UI из §17 и strict TypeScript; не добавляй зависимостей и `any`.
5. Не пиши тесты на наличие компонента, конкретный текст, число элементов или форму DOM — владелец прямо назвал такие тесты вредными. Проверка: `git diff --check`, релевантный typecheck/lint по изменённым файлам; тесты только если найдётся реальное повторяемое поведение, не разметка.
6. Не запускай и не перезапускай общий DEV 5200, не трогай БД, миграции, TEST/PROD, не пушь и не деплой.
7. В конце самостоятельно перечитай полный diff, перечисли оставшиеся `Загрузка`/spinner-вхождения и объясни, почему каждое не является content-loading state либо почему не может использовать общий примитив. Закоммить только файлы этого scope явным списком (не `git add -A`) в ветку `wt/unified-loader-20260904`, сообщи SHA и проверки. Не заканчивай ход с незакоммиченным результатом.

## Критерий готовности

Один implementation отвечает за внешний вид контентного loader во всех кабинетах; все найденные достижимые контентные loader-состояния либо используют его, либо имеют доказанное техническое исключение. Текст/размер/цвет/расположение не размножены локальными копиями. Живую визуальную приёмку после интеграции делает ведущий.
