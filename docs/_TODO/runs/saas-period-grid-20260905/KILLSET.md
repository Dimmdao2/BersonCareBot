## A. Одна глобальная сетка периодов (решение 1)

| ID | Поломка (подали X → получили неверное Y) | Класс |
|----|------------------------------------------|-------|
| A1 | Период с произвольным числом месяцев (напр. 4) заведён в данных, но продуктовая логика знает закрытый список кодов/меток/месяцев → период не покупается, цена не считается, владелец не может настроить сетку. Отказ дорогой (деньги/невозможность продать) и молчаливый (никто не падает, период просто «не работает»). | **ТЕСТ** |
| A2 | Набор выбираемых периодов зависит от тарифа: тариф A отдаёт `{1,12}`, тариф B — `{1}` → клиника видит разные лестницы, владелец потерял единую сетку. | **ТЕСТ** |
| A3 | Снятый (`retired`/не-selectable) период продолжает предлагаться к новой покупке/продлению → продаём то, что владелец снял. | **ТЕСТ** |
| A4 | Порядок периодов (`sort_order`) — данные, а не хардкод перечисления в UI/сервисе. | **ВЗГЛЯД** |

## B. Полная матрица цена×период у каждого активного тарифа (решение 2)

| ID | Поломка | Класс |
|----|---------|-------|
| B1 | Активный тариф сохраняется/активируется с ДЫРОЙ в матрице (нет цены на выбираемый период) → клиника выбирает период без цены, счёт на 0 либо падение на оплате. Дорого и молчаливо. | **ТЕСТ** |
| B2 | Дублирующая пара `(tariff_id, billing_period_code)` принимается → две цены на один период, побеждает случайная. | **ТЕСТ** (+ **ВЗГЛЯД**: UNIQUE в схеме) |
| B3 | Отрицательная цена принимается → отрицательный счёт. | **ТЕСТ** |
| B4 | Неизвестный код периода принимается в матрице → цена, привязанная к несуществующему периоду. | **ТЕСТ** |
| B5 | Новый период становится выбираемым, когда ещё НЕ у всех активных тарифов есть цена на него → см. B1 для всех остальных тарифов сразу. | **ТЕСТ** |
| B6 | Снятие периода разрушает историю: удаляет строки цен, на которые ссылаются подписки/инвойсы, либо снимается не глобально. | **ТЕСТ** + **ВЗГЛЯД** (FK/DELETE-права) |
| B7 | Валюта задаётся на уровне строки матрицы, а не тарифа → один тариф в двух валютах. | **ВЗГЛЯД** (схема) |

## C. Изменения — только на границе оплаченного периода (решение 3)

| ID | Поломка | Класс |
|----|---------|-------|
| C1 | Смена тарифа перезаписывает ТЕКУЩИЙ тариф/снимок или двигает `current_period_ends_at` → клиника теряет уже оплаченный доступ. Дорого (деньги+доступ) и молчаливо. | **ТЕСТ** |
| C2 | Смена ТОЛЬКО периода при том же тарифе не планируется (отвергается как «нет изменений» или молча теряется) → владелец не может продать годовой период текущему месячному клиенту. | **ТЕСТ** |
| C3 | Отмена подписки обрезает доступ немедленно вместо конца оплаченного периода, либо не гасит продление/автосписание → либо украли оплаченное, либо списали после отмены. | **ТЕСТ** |
| C4 | Немедленный/пропорциональный upgrade остался достижим (доплата разницы, немедленное включение нового снимка). | **ВЗГЛЯД** (удаление пути) + покрывается C1 |

## E. Деньги: пара (тариф, период) — единственный источник суммы

| ID | Поломка | Класс |
|----|---------|-------|
| E1 | Сумма/тариф/период/снимок инвойса перезаписываются после выставления → счёт задним числом меняет цену. | **ТЕСТ** |
| E2 | Первичная покупка берёт легаси `saas_tariffs.price_minor`/`billing_period` вместо выбранной пары → клиника платит не ту цену. Дорого и молчаливо. | **ТЕСТ** |
| E3 | Продление берёт легаси цену/период, а не пару подписки → каждое продление списывает не ту сумму. | **ТЕСТ** |
| E4 | Оплата/settlement не переносит отложенную пару в текущую (pending→current) и/или считает конец периода не от месяцев выбранного периода. | **ТЕСТ** |
| E5 | API принимает сумму/месяцы/цену от клиента, а не выводит их на сервере из `tariffId`+кода периода → клиника платит 1 ₽ за год. Дорого и молчаливо. | **ТЕСТ** (route) |
| E6 | Конец оплаченного периода считается хардкодом (месяц/год), а не числом месяцев периода → 4-месячный период даёт месяц доступа. | **ТЕСТ** |

## G. Права БД — одна исполняемая декларация (решение 6)

Все пункты — **ВЗГЛЯД**: разовое состояние ролей/грантов, доказывается rollback-only интроспекцией и
исполнением под ролью, НИКОГДА текстом SQL (§10a «Как НЕ надо» п.5).

| ID | Поломка |
|----|---------|
| G1 | Новые колонки подписки (`billing_period_code`, `pending_*`) отсутствуют в колоночных INSERT/UPDATE-грантах clinic/platform и в UPDATE воркера → `42501` на первом живом вызове, для пользователя это «функция работает неверно». |
| G2 | Корень refresh/промоушена не видит колонок текущего/отложенного периода. |
| G3 | У `app_worker` нет SELECT на `saas_tariff_period_prices` → продление падает. |
| G4 | Сервис продления зовёт clinic-корень каталога периодов, недоступный воркеру; лечится точной существующей способностью (due-root с доверенными месяцами), а не широким грантом. |
| G5 | `DELETE` платформы на периодах/ценах — овергрант и противоречит «снятие не разрушает историю» (B6). |
| G6 | Full-replace чекпоинта DELETE-ит строки цен и конфликтует с FK из подписок/инвойсов. |
| G7 | `PLATFORM_ROLE_SCOPE.mayTouch` — доказать видимость правки генератором через runtime-импорт и фактический вывод, а не чтением файла. |
| G8 | Новая авторитетность расползлась по рукописным дополнениям (`function-census.ts`, `relation-access.ts`) вместо единой декларации. |
| G9 | Именованные корни-владельцы получили доступ шире фактически трогаемых колонок (мед./кросс-арендные данные). |
| G10 | Рантайм-логин глобального админа достаёт платформенную роль мимо существующего отдельного пула/членства. |

**Минимальная матрица к проверке (из brief):** platform — periods/prices SELECT+INSERT+колоночный UPDATE,
БЕЗ DELETE; clinic billing — чтение активных тарифов/периодов/применимой цены, запись выбранной пары
только через существующий clinic-chokepoint; worker — чтение цены/периода для продления и UPDATE пары для
settlement/promotion; корни-владельцы — ровно те колонки, что трогают тела; глобальный админ — только через
существующий отдельный пул/членство.
