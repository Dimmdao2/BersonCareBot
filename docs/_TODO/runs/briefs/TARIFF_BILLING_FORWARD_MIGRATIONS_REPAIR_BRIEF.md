# Системное восстановление пропущенных DEV-миграций

## Разрыв в пути человека

Высокий номер в журнале DEV скрывает шесть более ранних миграций: четыре изменения тарифов/биллинга, очистку
старого бронирования и перевод планировщика напоминаний на канонические правила. Поэтому эти пути нельзя считать
реально применёнными на DEV, а обычный `max(created_at)` больше не является достаточным доказательством.

## Authority и границы

- `AGENTS.md` §1, §4a, §9–10, §24.
- `docs/_TODO/NIGHT_WAVE_AUDIT_QUEUE_2026-07-28.md`: номера `0323`–`0327` уже забронированы.
- Исходные принятые миграции: `0291`, `0298`, `0304`, `0305`, `0312`, `0318`.
- PROD и TEST не трогать. Старые файлы и существующие строки Drizzle ledger не менять.
- Не проектировать новое поведение: только forward-only повтор уже принятого SQL.

Источник оракула: этот bounded brief, раздел «Authority и границы» — «только forward-only повтор уже принятого SQL».

## Реализация

1. `0323` повторяет итоговое действие `0312`: scheduler читает `public.reminder_rules`, FK/history cutover
   сохраняется; старую migration и историю не переписывать.
2. `0324` повторяет итоговое действие `0291` и остаётся идемпотентной.
3. `0325` объединяет идемпотентный cleanup `0298` и `0304`: старые product-каталоги и пять legacy booking
   projections отсутствуют; канонические `be_*` таблицы не затрагиваются.
4. `0326` повторяет итоговый SQL `0305` без смысловых изменений функций тарифного доступа.
5. `0327` повторяет `0318`: fixed-key capability `app.read_saas_billing_payment_provider()`, без общего
   `SELECT` на `system_settings`.
6. Каждая forward migration содержит машинно читаемую ссылку на исходные теги, которые она фактически
   восстанавливает.
7. Канонический webapp migration runner после применения сверяет весь `_journal.json` с
   `drizzle.__drizzle_migrations`: текущий hash обязан присутствовать либо быть покрыт уже применённой более
   поздней forward migration. Высокий `created_at` не скрывает непокрытый ранний hash; лишняя историческая строка
   ledger сама по себе не является ошибкой.
8. В feature-клоне journal `idx/when` временные. Окончательную следующую последовательность назначает лид при
   land после синхронизации с фактическим `feat`.

## Проверка этапа

- Сравнить каждый forward SQL с исходным по исполняемым statements, игнорируя только комментарии, номер и
  допустимое объединение двух cleanup-файлов.
- Self-test общего hash-reconciliation gate обязан доказать: ранний непокрытый hash красный; ещё не дошедшая
  новая migration допустима до migrate; применённый forward marker закрывает только названный исходный тег;
  неизвестный/обратный/неприменённый marker не закрывает разрыв.
- Запустить journal/freeze/diff gates и существующие точечные тарифные/биллинговые проверки, которые покрывают
  `0291`, `0305`, `0318`; для cleanup доказать отсутствие старых таблиц и сохранность канонических таблиц.
- Не применять DEV до независимой приёмки. После PASS лид синхронизирует journal, land и выполняет один
  `bash deploy/host/migrate-dev.sh --preflight && bash deploy/host/migrate-dev.sh --execute`.
- Документация получает фактическое состояние и доказательство в том же land-коммите; прежние ложные утверждения
  «применено на DEV» исправляются, а не дублируются новой строкой.
