# Тест или взгляд: read-only классификация DEV-данных перед S03 reconcile

Это разовая инженерная инспекция данных и связей, не повторяемое product-поведение. Постоянный тест,
новый DB harness и проверка текста SQL не нужны. Authority: `AGENTS.md` §1/§3a/§5/§6/§24,
`docs/ARCHITECTURE/SERVER CONVENTIONS.md`, `docs/ARCHITECTURE/LOCAL_DEV_AND_AGENT_TESTING.md`,
`docs/_TODO/runs/testsuite-v2/V9B_IMPLEMENTATION_SLICES.md`,
`docs/_TODO/runs/briefs/V9B_S03_BOOKING_OWNERSHIP_BRIEF.md` и текущая ветка
`wt/v9b-s03-booking-ownership` после commit `ab213178d`.

## Последствие и вопрос аудита

Миграция 0309 обязана присвоить `organization_id` только по доказуемому владельцу и abort-иться при любой
неразрешённой строке. Read-only census на DEV дал 673 `zero_match` (263 `patient_bookings`, 410
`appointment_records`), поэтому текущую миграцию нельзя применять или приземлять. Нужно по фактическим данным и
writer/read paths определить, какие классы строк:

1. имеют другой детерминированный канонический путь к организации;
2. являются legacy-проекциями, уже выведенными из пользовательского пути отдельным принятым этапом;
3. представляют достижимые пользовательские данные, для которых владельца доказать нельзя.

Это инженерное решение аудитора. Не задавай владельцу вопрос «какую организацию поставить» и не называй его
гейтом.

## Порядок

1. Сначала `code-search` по `patient_bookings`, `appointment_records`, их writers/readers, external/native IDs,
   удалённым booking-проекциям и canonical appointment relations; затем точечные `rg`/git history по найденным
   символам.
2. DEV читать только через канонический `apps/webapp/.env.dev`. До `psql` загрузить env; строку подключения,
   секреты, телефоны, ФИО и email не печатать. Все запросы выполнить в явно read-only транзакции либо с
   `PGOPTIONS='-c default_transaction_read_only=on'`; никаких DDL/DML, migration apply, seed или restart.
3. Воспроизвести пять reason-counts 0309 и разложить каждый ненулевой класс дальше по доказуемым связям. Для
   каждого числа привести точный обезличенный SQL/команду. При проверке RLS-пустоты учитывать AGENTS.md §3a:
   показать роль/принципал или использовать безопасную статистику, а не считать скрытый ноль пустой таблицей.
4. Для каждой группы назвать минимальное действие reconcile и доказательство, что оно не смешивает арендаторов.
   Если связь нельзя доказать, назвать точный потерянный ключ и достижимое пользовательское последствие.
5. Проверить, что предлагаемое действие не возвращает удалённую legacy-сущность и не создаёт вторую модель
   владения рядом с canonical appointment/organization.

## Запрещено

- менять DEV/TEST/PROD, применять 0309, запускать `migrate-dev.sh`, писать backfill/reconcile-код;
- default organization, догадки по единственной клинике пользователя, delete/quarantine или ослабление abort;
- новый harness, таблица, колонка, миграция, постоянный source-text тест;
- менять product/plan/queue файлы; допустим только один audit report под
  `docs/_TODO/runs/testsuite-v2/` и его явный commit без push.

## Результат

Отчёт содержит:

- точные команды и counts с суммой, равной исходным 673 либо честным объяснением изменения DEV;
- таблицу `класс → доказуемая связь → действие → защита от cross-org`;
- бинарный вердикт `READY_FOR_RECONCILE` (каждая строка имеет детерминированное действие) либо
  `BLOCKED_BY_UNPROVABLE_DATA` (с точным классом и отсутствующим ключом);
- минимальный bounded brief следующего worker-а без реализации и без вопроса владельцу.
