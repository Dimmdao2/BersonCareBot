## Инцидент и проверяемый результат

После выкладки `28319b24af10cc39f5bd9f70c945193e9d7e362a` TEST реально поднялся, но `deploy-test.sh` вернул
ложный FAIL: `http://127.0.0.1:6300/api/health` получил 404, потому что новый единый surface resolver
fail-closed отклоняет неизвестный Host `127.0.0.1`. Тот же сокет с `Host: test.bersoncare.ru` ответил
`200 {"ok":true,"db":"up"}`; публичный `https://test.bersoncare.ru/api/health` тоже ответил 200.

Коммит `33e93b2a8` изменил ровно:

- `deploy/host/deploy-test.sh` — берёт Host из `APP_BASE_URL` canonical TEST env, валидирует его и передаёт в
  локальный webapp health probe;
- `deploy/host/deploy-webapp-prod.sh` — делает то же для обычного PROD systemd deploy;
- `deploy/docker/docker-compose.yml` — blue/green container healthcheck извлекает Host из `APP_BASE_URL` внутри
  контейнера и проверяет `/api/health`.

## Kill-set до чтения проверок

Проверь независимо следующие реальные классы отказа:

1. bare loopback Host больше не может дать ложный красный deploy после Host-aware resolver;
2. probe по-прежнему проверяет сам локальный процесс и его DB health, а не только публичный nginx или статическую
   страницу;
3. Host происходит из canonical `APP_BASE_URL`, а не захардкожен в старый либо будущий домен;
4. неверный/пустой `APP_BASE_URL` fail-closed и не превращается в shell/header injection;
5. Compose escaping оставляет `$` для shell внутри контейнера, а не съедается Compose;
6. TEST, обычный PROD и blue/green PROD используют одну и ту же семантику; будущая раздельная доменная схема не
   требует возвращать loopback bypass;
7. изменения не переключают домены, не меняют nginx/env и не выполняют PROD-операций.

## Разрешённые действия и результат

Только read-only inspection и безопасные локальные проверки синтаксиса/подстановки. Можно проверить живой TEST
loopback без изменения состояния. Нельзя запускать deploy, рестартовать службы, менять env/nginx/БД, обращаться к
PROD или делать продуктовый fix. Не добавляй тест на строки исходника. Временную fault injection выполняй только
если она действительно нужна и полностью откати до завершения.

Итог дай бинарно `PASS` или `FAIL`. Для каждого finding назови достижимый сценарий, impact, точный нарушенный
пункт kill-set и доказательство. Если findings нет, перечисли фактически выполненные команды и какие пункты
kill-set они закрывают. Файлы не менять и коммит не создавать.
