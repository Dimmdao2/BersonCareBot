## Вопрос аудита

Пройти путь человека по каждой реально существующей механике: что он пытается сделать, какую тарифную границу
ожидает владелец, где сегодня фактическая запись/выдача проходит без контроля, и какое достижимое последствие это
даёт. Сначала измерить, сколько уже построено; не считать пункт плана работой сам по себе.

Для каждого кандидата назвать точные команды и текущие file:line:

1. Есть ли реальная write/read surface и кто её вызывает.
2. Есть ли usage source, атомарный enforcement и UI-показ; не подменять одно другим.
3. Есть ли уже общий порт/таблица/паттерн, который надо соединить, а не дублировать.
4. Пересекается ли кандидат с `0308`, billing/fiscalization или Track D/#987 directPublic cleanup.
5. Какой один следующий batch даёт наибольшее реальное устранённое последствие при умеренном scope.

Не создавать owner-gates для инженерных решений. Настоящий вопрос владельцу допустим только про цену/продуктовую
политику после доказанного поиска в repo и мировой практике; такой вопрос сформулировать плейн-языком, но никуда не
отправлять.

## Выход

- Краткая таблица `механика → surface → usage → enforcement → человеческий разрыв`.
- Один рекомендуемый следующий batch, exact files, миграция нужна/нет, acceptance и 3–5 fault injections.
- Что уже сделано и какие открытые строки плана устарели.
- Никаких изменений, коммитов, push, DEV/TEST/PROD или новых тестовых harness.
