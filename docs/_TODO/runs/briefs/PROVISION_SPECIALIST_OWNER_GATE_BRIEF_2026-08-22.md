## Задача

Регистрация клиники доходит до `specialist-signup/confirm` и умирает на выдаче специалиста. Замер
предыдущего воркера (`docs/_TODO/runs/integrator-cleanup/` рядом с Б2 в WORK_ORDER): корень
`app.provision_specialist_owner(uuid)` объявлен старым гейтом
`require_attested_context_for_roles(..., ARRAY['app_patient'])`, а EXECUTE на него явно отозван у
`app_pre_session` — при этом маршрут доходит под bootstrap-принципалом. Это ровно тот же перевод, который
уже сделан для десяти корней миграцией
`apps/webapp/db/drizzle-migrations/20260822T100000_pre_session_email_and_signup_roots_accept_their_named_context.sql`;
`provision_specialist_owner` в те десять не попал.

Сделай тот же перевод для этого корня (и для тех корней, которые он зовёт, если они упираются в ту же
стену — но только для них, ширить объём нельзя):

1. Тело берётся **побайтно из `pg_proc` на именованной DEV `bcb_webapp_dev`**, а не из старой миграции —
   иначе затрёшь более поздние правки других веток. Гейт `require_accepted_context` должен стать **первым
   исполняемым оператором**; если у тела форма SQL, где это невозможно, переписывай в PL/pgSQL, как сделано
   в `20260822T100000`.
2. Владелец, сигнатура, аргументы, возвращаемое значение — прежние. `CREATE OR REPLACE`, чтобы OID и
   владелец сохранились. Секционные заголовки `BCB-MIGRATION-OWNER` и проверка `BCB-MIGRATION-VERIFY`
   (что ни одно тело больше не содержит старый гейт) — как в `20260822T100000`.
3. Декларация: если нужен EXECUTE для `app_pre_session` — объявляй его в
   `deploy/postgres/privileges/declaration.ts` и перегенерируй артефакты. **Миграция прав не выдаёт**
   (§1: ни GRANT/REVOKE, ни CREATE/ALTER ROLE, ни ALTER DEFAULT PRIVILEGES, ни CREATE POLICY).
4. **Разбор прав по §1 обязателен** и пишется в отчёт: какие отношения трогает тело, под какой ролью
   исполняется, хватает ли ОБЪЯВЛЕННЫХ прав, чтобы тело ВЫПОЛНИЛОСЬ. Известное соседнее место:
   `permission denied for table organization_slug_claims` — в декларации INSERT есть, в кластере DEV нет,
   то есть DEV просто не сведён; это НЕ повод править декларацию. Сначала проверь, действительно ли
   объявленного набора хватает, и только если чего-то нет в декларации — добавляй.
5. Таймштамп миграции строго больше последней применённой: мигратор применяет по watermark `created_at`,
   НЕ по хешу, и миграция с более ранним временем не накатится никогда.
