# Brief — `C3`, находка `F-1`: SQL-корень очереди срезает маркер `clinic_if_configured`

Repo canon: `AGENTS.md` (`grep -n "^## \|^### " AGENTS.md`, затем свои разделы).

Источник оракула: `docs/_TODO/THERAPYSTO_PATIENT_BRANDING_INITIATIVE/IMPLEMENTATION_PLAN.md`, пункт `C3`,
дословно: «удалить любой достижимый platform fallback для них.»

Находка `F-1` независимого аудита круга 3 (`THERAPYSTO_PATIENT_BRANDING_INITIATIVE/AUDIT3_C3_2026-08-24.md`,
раздел «F-1») — прочитай его целиком первым делом. Факты аудитора:

`app.enqueue_outbound_message` собирает payload как `(v_content - 'senderScope')` и возвращает маркер обратно
только при значении `'clinic_required'` (`deploy/postgres/generated/prod-to-target/schema-pre.sql:5681,5693,5709-5710`).
Значит `clinic_if_configured` до потребителя не доходит.

Последствия, ровно два:

- путь по умолчанию НЕ ломается: без маркера `clinicSenderScope` отдаёт `clinic_preferred`, без кредентиала это
  наш бот, и пациент сообщение получает;
- но у клиники СО своим включённым ботом на продюсере, ходящем через SQL-очередь, откат на платформенного
  отправителя ОСТАЁТСЯ (`dispatchPort.ts:409-413`), тогда как маркер довёл бы до `clinic_required`. Это прямое
  нарушение оракула: достижимый platform fallback не удалён.

## Задача (ровно это)

1. Провести `clinic_if_configured` через `app.enqueue_outbound_message` наравне с `clinic_required` — маркер
   должен доходить до потребителя без потерь. Изменение делается миграцией по канону репозитория.
2. Доказать сквозным тестом на обоих концах: (а) клиника без своего бота получает прежний путь; (б) клиника со
   своим включённым ботом отката на платформенный не получает и на этом продюсере тоже.
3. Инъекция обязательна: верни срезание маркера — тест должен покраснеть.
4. Аудитор проверял по дампу схемы, живую БД не смотрел. Скажи в отчёте прямо, сверял ли ты определение функции
   с живой DEV-базой или тоже только по файлам.
