## Первый шаг — ЖИВОЙ ПРОГОН, не чтение кода

Прошлый прогон утонул именно в том, что объяснял по чтению. Начни с измерения на **DEV** (PROD не трогать):

воспроизведи путь капчера под тем же принципалом, что и вебхук, и напечатай в одной транзакции:
`current_user`, `app.current_org_id()`, результат `UPDATE saas_billing_invoices SET status='paid' …` с числом
затронутых строк, затем `app.apply_paid_saas_billing_tariff(...)`. Это разом отсекает почти все гипотезы:
видно, есть ли контекст, кто ты по роли, и на каком именно стейтменте теряются строки.

Если UPDATE даёт 0 строк — сузь до причины: RLS (`USING` / `WITH CHECK` политики
`saas_billing_invoices_staff_capture_update`), гранты (`0344`), или предикат самого UPDATE.
Если UPDATE проходит, а аксессор всё равно `false` — причина в аксессоре (`0348`, строки 54-62) или в том,
что транзакция откатывается раньше.

Непроверенные гипотезы, в порядке стоимости проверки (не принимать ни одну на веру):
1. ветка `principalSnapshot?.kind === 'infra'` в `drizzle.ts:113` **пропускает** установку принципала — какой
   `kind` реально у принципала из `runWithDbOrganizationPrincipal` на этом пути;
2. `WITH CHECK` у политики capture-update (при `USING` истинном `WITH CHECK` может резать запись);
3. полнота грантов `0344` на `UPDATE` для `app_staff`;
4. FORCE RLS внутри SECURITY DEFINER, чей владелец без `BYPASSRLS` (см. память force-rls-backstops-definer-seam).

## Потом — починка

Чинить **причину**, а не симптом. Границы:

- **не ослаблять** RLS-политику, FORCE RLS и guard-триггер `app.reject_staff_commercial_organization_update`
  ради прохождения платежа — если для капчера нужен доступ, это узкий SECURITY DEFINER аксессор, как уже
  сделано четырежды (`0343`, `0348`, `0351`), а не широкий грант;
- миграция, если нужна, — **временный номер `NNNN_..._local`**, следующий свободный по журналу (последний
  занятый — `0352`); финальный номер назначается при сведении. Уже применённые миграции **не переименовывать**;
- вебхук не подделывать: доводить до конца настоящим повторным платежом либо повторной доставкой события
  провайдером;
- PROD не трогать.
