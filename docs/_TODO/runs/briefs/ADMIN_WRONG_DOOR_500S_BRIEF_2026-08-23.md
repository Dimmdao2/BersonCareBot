## Что измерено на живом TEST 23.08 (обход владельца, кабинет `dimmdao@gmail.com`)

| Кнопка, страница | Ответ | Причина из журнала вебаппа |
|---|---|---|
| «Сохранить», «Сохранить оформление» — `/app/admin/notification-templates` | `500 /api/admin/notification-templates` | `MechanicWriteClearanceRequiredError: mechanic write clearance required: branding` |
| «Включить», «Восстановить» — `/app/admin/notifications` | `500 /api/doctor/web-push/status` | `Patient port context requires an organization-scoped patient principal` |

Класс один: **запрос уходит в дверь, рассчитанную на другого принципала.**

- Платформенные шаблоны уведомлений админа перекрыты **арендной** механикой `branding` — то есть
  тарифом клиники. Глобальный админ не арендатор: тарифа у него нет и быть не должно, значит эта
  проверка на платформенном пути стоит не на своём месте.
- Админский экран уведомлений зовёт `/api/doctor/web-push/status` — дверь, которая требует
  организационно-скоупленного ПАЦИЕНТСКОГО принципала. Админ таким быть не может.

## Что сделать

1. **Сначала назови настоящую границу, потом чини.** По каждому из двух путей ответь: что здесь
   платформенное, а что арендное. Правка «ослабить проверку, чтобы прошло» не принимается — если
   механика `branding` защищает арендные шаблоны, значит у платформенных должен быть свой путь,
   а не общий с клиникой.
2. Для web-push статуса в админском кабинете: либо экран не должен звать пациентскую дверь вовсе,
   либо ему нужна своя дверь под принципала админа. Выбор обоснуй; расширять права админа на
   пациентские отношения **нельзя** (см. `Р-АДМИН`).
3. **`500` — неверный ответ в обоих случаях.** Отказ по правам или по механике — это осознанный
   отказ, а не сбой: человек должен увидеть, что именно недоступно и почему. Проверь, нет ли рядом
   других мест, где `MechanicWriteClearanceRequiredError` вылетает наружу необработанным.
4. Права — только через `declaration.ts` + генерация, если они вообще понадобятся. В миграции нет
   `GRANT`/`REVOKE`/`CREATE POLICY`.
