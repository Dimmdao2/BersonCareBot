## Задача — РОВНО Ш1 и Ш2, ничего сверх

**Ш1 — вид в карте, поведение не меняется.** Миграция timestamp-forward:
`ALTER TABLE app_ext.variant_a_identity_refs ADD COLUMN ref_kind text NOT NULL DEFAULT 'actor'` плюс CHECK на
допустимые значения. Первичный ключ пока прежний. В той же ветке `ref_kind` добавляется в список колонок
таблицы и в `relationSurfaces` обоих резолверов в `deploy/postgres/privileges/declaration.ts`
(схема называет строки 2466, 6173, 6194 — проверь их на текущей голове, номера могли сдвинуться).

**Ш2 — ключ по паре.** Миграция: PK → `(physical_user_id, ref_kind)`, UNIQUE на `opaque_ref` сохраняется.
Все существующие строки имеют вид `'actor'`, поэтому уникальность не нарушается ни одной из них.

**Ш3 и дальше в этот объём НЕ входят.** Резолверы сигнатуру не меняют, приложение не трогается,
`portContextRuntime.ts` не правится. Если по ходу выяснится, что Ш1/Ш2 без Ш3 не встают — это СТОП и отчёт
ведущему, а не расширение объёма (§24.6).

## Требования

- Миграции: `BCB-MIGRATION-OWNER`, `BCB-MIGRATION-VERIFY` (утверждает факт — наличие колонки с NOT NULL и
  DEFAULT, затем состав PK), без `GRANT`/`REVOKE`/`CREATE POLICY`. Применённые миграции не редактируются.
- **Разбор прав по §1 обязателен:** новая колонка попадает в поверхности резолверов, значит её надо
  объявить; проверь отдельно, не появляется ли где-то `SELECT … FOR UPDATE`/`FOR SHARE` без привилегии
  класса UPDATE (гейт `deploy/postgres/privileges/row-lock-privileges.test.mjs` должен остаться зелёным).
- **Откат назвать явно** в отчёте по каждому шагу: Ш1 — `DROP COLUMN ref_kind` и возврат декларации,
  Ш2 — возврат PK на `physical_user_id` (обратим, пока строк вида `'subject'` нет).
- **Тест поведения (§10a):** вход человека (staff/patient/admin) продолжает работать, разрешение ссылки в
  физический id не изменилось. Тест на текст исходника, на количество строк или на наличие файла — запрещён.
