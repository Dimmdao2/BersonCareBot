# Brief — находка `S-1` (`TPB-15`): имя отправителя в письмах и кодах входа приходит параметром

Repo canon: `AGENTS.md` (`grep -n "^## \|^### " AGENTS.md`, затем свои разделы).

Источник оракула: `docs/_TODO/THERAPYSTO_PATIENT_BRANDING_INITIATIVE/IMPLEMENTATION_PLAN.md`, пункт `TPB-15`,
дословно: «Нужен параметр от вызывающего, а не дефолт у получателя, то есть механизм этапа `C`.»

Развилка, которая держала эту работу, ЗАКРЫТА владельцем — §1.2f от 23.08.2026, дословно: «Имя в тексте письма
и в поле «от кого» … Два: Therapysto персоналу, Therapygo пациентам». То есть имён три по месту вызова:
**Therapysto** — персоналу, **Therapygo** — пациенту общего входа, **бренд клиники** — пациенту клиники.
Подстановка одного имени по умолчанию запрещена: она нарушит `TPB-06` и `TPB-08`.

## Что сломано (находка `S-1`, факты из плана)

Текст кода входа по e-mail и SMS до сих пор говорит «BersonCare», и его видит **ПЕРСОНАЛ**:

- регистрация специалиста `api/auth/specialist-signup/start` и приём приглашения персонала
  `api/clinic/invites/accept/start` идут через `startEmailChallenge`;
- живой источник текста — definer-функция `app.email_auth_start_challenge`
  (`deploy/postgres/organization-member-invites-rls.sql:929,931`);
- те же строки хардкодом в `apps/integrator/src/integrations/bersoncare/{sendEmailRoute,sendSmsRoute,sendOtpRoute}.ts`.

Четыре круга аудита это пропустили, потому что мерили идентичность СТРАНИЦЫ, а текст письма — не страница
и живёт не в webapp.

## Задача

1. Имя отправителя приходит ПАРАМЕТРОМ от вызывающего на всём пути: вызов → `startEmailChallenge` →
   definer-функция → интегратор. Дефолта-подстановки у получателя не остаётся; отсутствие параметра — это
   ошибка вызова, а не повод подставить «BersonCare».
2. По месту вызова подставляется правильное из трёх имён. Переиспользуй УЖЕ существующий механизм этапа `C`
   (`MailProfileRequest.kind = 'branded'` несёт `clinicName` и `platformName`, резолвер поверхности знает,
   staff это или пациент) — второго источника имён не заводить.
3. Хардкод «BersonCare» из трёх маршрутов интегратора убрать; в исторических данных и технических
   идентификаторах ничего не переименовывать (`TPB-15` это прямо запрещает).
4. Тесты, краснеющие на подмене: персонал получает Therapysto, пациент общего входа — Therapygo, пациент
   клиники с купленным брендом — имя клиники. Инъекция «вернуть дефолт у получателя» обязана покраснеть.
5. Изменение определения definer-функции делается миграцией по канону.

## Границы (решения владельца, не инженерные развилки)

- Миграции никогда не содержат `GRANT`/`REVOKE`/`CREATE ROLE`/`ALTER DEFAULT PRIVILEGES`/`CREATE POLICY`.
- Не трогать `app.read_integrator_clinic_delivery_credential` и миграции `20260823T030000…` / `20260823T043206…`;
  обе роли в одном списке не разрешать.
- Не трогать `app.enqueue_outbound_message` и гейт готовности каналов (`C5`) — по ним идут соседние ветки.
- SMS выключен в базовой поставке (§1.2e) — новых SMS-имён не заводить, только убрать неверный текст.
- Прод не трогать, `--execute` на DEV не запускать, в `feat/doctor-ui-rebuild` не вливать, реальным адресатам
  ничего не слать. Своя находка вне плана — вопрос владельцу, а не новая работа.
