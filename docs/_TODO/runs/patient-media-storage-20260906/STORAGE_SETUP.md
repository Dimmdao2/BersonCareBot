# Хранилище данных пациентов — что настроено и чем это доказано

Дата: 06.09.2026. Решение владельца, дословно: «на яндексе хранить только зашифрованные
клиентские видео пациентов, все что связано с библиотеками упражнений или фидео в контенте cms -
на селектел - это основной траффик и объем и он на селектел дешевле».

## Что где лежит

| Что | Где | Шифрование |
|---|---|---|
| Библиотека упражнений, медиа CMS, публичные карточки клиник | Selectel, основной бакет (`S3_*`) | нет (Selectel не умеет серверного шифрования) |
| Файлы пациентов, видео пациентов по программе | Yandex, `bcb-patient-media` (`PATIENT_S3_*`) | SSE-KMS, ключ `abj14atq11q9r4vkdsa5` |

Разделение выключено, пока не задан `PATIENT_S3_BUCKET`: обе цели ведут в основной бакет, и
приложение ведёт себя ровно как до изменения.

## Yandex: каталоги и доступ

Облако `b1g5m46deciu3ij4r992` (`cloud-dimmdao`).

| Каталог | Содержимое | Кто имеет доступ |
|---|---|---|
| `b1g6vvb10o9hvissjtg1` (`bcb-patient-data`) | бакет `bcb-patient-media`, KMS-ключ `abj14atq11q9r4vkdsa5` | приложение `aje94a4g8br74o5venv5` — `storage.editor` |
| `b1gq15hnqb7975r022ms` (`default`) | `bcb-backup-prod` | только ключ бэкапов |

Каталоги разные именно поэтому: роль в Object Storage выдаётся на КАТАЛОГ, а не на бакет —
это проверено замером (политика бакета умеет только сужать доступ, выдать его она не может).
Пока оба бакета лежали в одном каталоге, аккаунт приложения читал бэкапы.

`storage.editor`, а не `uploader`+`viewer`: приложению нужно УДАЛЯТЬ объекты (уборка брошенных
загрузок, удаление файла пациента врачом, удаление исходного MP4 после пересборки в HLS).
Роли «только удаление» в Яндексе нет, `storage.editor` — минимальная, которая его включает.
Остаточный риск: этой ролью аккаунт приложения может удалить и сам бакет. Сузить политикой
бакета нельзя — любая политика в Яндексе становится единственной властью над бакетом и отбирает
доступ у всех, кому он был выдан ролями каталога (проверено, чинил 403 у ключа бэкапов).

Служебный аккаунт настройки `ajeq100ivnb6266dkgdq` (`bcb-storage-admin`, ключ
`/home/dev/.ssh/yc-bcb-storage-admin.json`) держит `storage.admin`, `kms.admin` и
`resource-manager.admin`. **Он временный — удалить вместе с ролями и файлом ключа, когда работа
по хранилищу закрыта.**

## Что доказано живьём (06.09.2026)

Проверки шли ключами ПРИЛОЖЕНИЯ (`/home/dev/.ssh/yc-app-storage.env`), не админскими.

1. **Объект шифруется, даже когда клиент об этом не просит.** Загрузка идёт presigned PUT из
   браузера, а браузер SSE-заголовков не шлёт. На бакете включено шифрование по умолчанию:
   обычный `PUT` без единого `x-amz-server-side-encryption` → `HEAD` возвращает
   `x-amz-server-side-encryption: aws:kms` и наш `key-id`. Без этого свойства весь замысел
   не работал бы: код не может заставить браузер шифровать.
2. **Шифрование прозрачно для видео.** `Range: bytes=1000-1999` по зашифрованному объекту →
   `206`, 1000 байт, побайтово совпадают с исходником. Значит перемотка видео работает, и
   проксировать поток через приложение не нужно.
3. **Полный жизненный цикл объекта.** PUT → 200, GET → 200, Range → 206, LIST → 200,
   DELETE → 204. До выдачи `storage.editor` DELETE отдавал 403 — это и был бы отказ уборки.
4. **Изоляция от бэкапов.** Тот же ключ приложения в `bcb-backup-prod` → 403.

## Что осталось

- CORS на `bcb-patient-media` — отложен до того, как станут известны итоговые домены
  (Therapysto/TherapyGo). Без него браузер не сможет делать presigned PUT с нашего origin.
- Версионирование НЕ включено намеренно: без правила удаления неактуальных версий «удалённый»
  файл пациента продолжал бы лежать в хранилище, а это спецкатегория персональных данных.
- Удалить служебный аккаунт настройки и его ключ.
