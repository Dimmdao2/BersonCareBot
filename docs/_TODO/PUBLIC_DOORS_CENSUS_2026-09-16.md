# Открытые наружу адреса: перепись и вырезание

Владелец 16.09.2026, дословно: «что у нас за куча открытых наружу адресов, мы блять наоткрывали
дверей для инъекций зачем то. Надо их вообще все найти и исследовать - скорее всего повырезать все
нахер»; и следом: «это все потенциальные уязвимости - резать нещадно. Все такое должно браться
только из системы без внешних дверей».

Повод — `/api/references/<категория>`: открытый без входа адрес, отдающий платформенный справочник,
у которого в коде не осталось ни одного вызывающего. Он оказался не единственным своего рода.

## Перепись (замер, не оценка)

Инструмент переписи лежит в репозитории: `tools/census-open-routes.mjs`. Он берёт КАЖДЫЙ
`route.ts` под `apps/webapp/src/app/api`, ищет в файле вызов любой двери (`require*`, `with*Access`,
`assert*`, `verifyInternalJobBearer`, `verifyIntegratorSignature`, `getCurrentSession`) и отдельно —
метку `stampBootstrapPrincipal`, которой помечают заявленно-публичный вход. Для каждого адреса без
двери он считает вызывающих по всему дереву `apps` и `packages`, отделяя боевой код от тестов.

Замер 16.09.2026 на `8d5bb8c08`:

- всего маршрутов: **482**;
- **49** не зовут в своём файле ни одной двери;
- из них **44** помечены `stampBootstrapPrincipal` (то есть публичность объявлена осознанно),
  **5** не помечены ничем.

Важно: первые две редакции переписи давали 110 и 62 «открытых» — обе врали, потому что шаблон не
знал части имён дверей (`requireAuthenticatedApiSession`, `assertIntegratorGetRequest`). Числа
проверены точечным чтением файлов: пятнадцать интеграторских GET оказались закрыты подписью HMAC.
**Цифру без прогона этого скрипта не называть.**

## Разбор по природе адреса

### Группа A — вход, которого снаружи не миновать (25 адресов)

`auth/check-phone`, `auth/email-otp/confirm`, `auth/email-password/{login,login/challenge,`
`login/factor,forgot,reset,setup-code/complete}`, `auth/exchange`, `auth/max-init`,
`auth/oauth/{start,callback,callback/apple,callback/google,callback/vk,callback/yandex}`,
`auth/passkey/login/{options,verify}`, `auth/phone/{confirm,messenger-bind/status}`,
`auth/specialist-signup/{start,slug}`, `auth/telegram-init`, `auth/telegram-login`,
`auth/telegram-login/config`.

Их нельзя «взять из системы»: человек ещё не вошёл, и до входа он по определению снаружи. Вырезать
их — значит отключить вход. Работа по этой группе другая: **сузить каждую до минимума** — что она
принимает, что отдаёт в ответе, и нет ли в ответе того, что снаружи знать не нужно. Это та же
линия, по которой уже идут этапы Д и С (`docs/_TODO/AUTH_DOORS_FIX_2026-09-16.md`,
`docs/_TODO/STAFF_DOORS_HARDCODED_2026-09-16.md`), и отдельного дублирующего этапа тут не заводим.

### Группа B — приглашения, присоединение, поддержка (9 адресов)

`clinic/invites/accept/{lookup,start,confirm}`, `join/{exchange,email/start,email/confirm}`,
`leads/public/captcha`, `public/account-protection`, `public/support`,
`public/notifications/unsubscribe`.

Тоже по природе снаружи: человек приходит по ссылке из письма и ещё не вошёл. Проверять здесь надо
не факт публичности, а **что отдаётся до подтверждения личности** (например, что показывает
`invites/accept/lookup` тому, кто подставил чужой токен).

### Группа C — платёжные вебхуки (3 адреса)

`payments/webhook/[provider]`, `payments/saas-webhook/[provider]`,
`payments/patient-acquiring-webhook/[provider]`.

Вызывающих в репозитории нет и быть не может — их зовёт банк. Резать нельзя; проверяется подпись
провайдера и идемпотентность.

### Группа D — кандидаты на вырезание (проверять и резать)

- [ ] **D1. `references/[categoryCode]`** — вызывающих: **0**. Остаток раннего устройства, когда
      селекты наполнялись через HTTP; экраны давно читают справочник из базы напрямую. Отдаёт
      платформенный baseline любому, кто знает имя категории. **Резать вместе с чёрным списком
      `visit_manipulation` внутри него**; заодно снимается вопрос, зачем этот список нужен в теле
      SQL-функции `app.get_public_reference_baseline`.
- [ ] **D2. `booking/public/catalog/cities`** — вызывающих: **0**.
- [ ] **D3. `booking/public/catalog/services`** — вызывающих: **0**. Обе — публичный каталог записи;
      живой публичный виджет их не зовёт (проверить, что не зовёт и внешний встраиваемый код, прежде
      чем резать: у публичного виджета вызывающий может лежать вне этого репозитория).
- [ ] **D4. Пять адресов без двери И без метки** — `version`, `health`, `media/s3-status`,
      `public/domains/probe`, `brand/app-icon/[mediaId]/[variant]`. У каждого есть внутренний
      вызывающий, поэтому просто снести нельзя; по каждому решается отдельно: увести внутрь
      (серверное чтение вместо HTTP), закрыть дверью или оставить с явной меткой. `health` зовёт
      интегратор по сети — эту оставить, но проверить, что она не отдаёт состав системы.
- [ ] **D5. `internal/domains/ask`** — зовётся ОДНИМ местом: соседним маршрутом
      `public/domains/ask/route.ts`, то есть наш же сервер ходит сам к себе по HTTP. Это ровно то,
      что владелец назвал «должно браться только из системы»: свести в прямой вызов, адрес убрать.
- [ ] **D6. `patient-app/client-boot-report`** — принимает отчёт о загрузке от неаутентифицированного
      клиента. Проверить, что именно записывается и нельзя ли этим засорять хранилище снаружи.

## Как это резать (порядок, обязательный)

1. Перед удалением адреса — доказать, что вызывающих нет, ДВУМЯ способами: скриптом переписи и
   отдельным поиском по строке пути во всём дереве, включая `apps/integrator` и `packages`. Пустой
   результат доказывается перечислением того, где искали.
2. Проверить внешних потребителей вне репозитория: публичный виджет записи и боты живут своей
   жизнью. Адрес, который может звать чужой встроенный код, не режется без слова владельца.
3. Удаление — вместе с его тестами и со всеми упоминаниями в документах; мёртвая ссылка в активном
   плане — это работа, поставленная над несуществующим кодом.
4. После каждого удаления — затронутые тесты и `tsc --noEmit`; полный CI, когда в `feat` приедет
   исполняемый код.
