# Аналитика специалиста — tenant-scoped rebuild

Дата owner-решения: 2026-09-06. Taskdb: `#811` (возобновлён более новым решением владельца после отмены 2026-07-29).

## Цель

Специалист видит только аналитику по доступным ему пациентам и получает два понятных разреза: записи и фактическую активность назначенных программ. Платформенная cross-clinic аналитика и технические ошибки плеера остаются только у global admin.

## Фактическая база перед реализацией

- Старый doctor analytics из `main` не восстанавливается: он читал глобальные агрегаты без `organizationId` и visibility actor.
- Текущий врачебный пункт ведёт на `/app/doctor/material-ratings`; retained `DoctorAnalyticsShell` содержит устаревшие глобальные вкладки.
- Tenant-scoped KPI записей уже доступны через `DoctorAppointmentsPort.getScheduleKpis`.
- Фактические отметки упражнений, сессии и параметры подходов/повторов/веса уже доступны через scoped doctor APIs.
- Точное «назначено по расписанию / выполнено» недоступно: частота назначения хранится свободным текстом.
- Реальные минуты просмотра и точный split promo/assigned не собираются; существующая оценка по длительности файла не выдаётся за время просмотра.

## A. Граница маршрутов и доступа — первый этап

- [ ] `AN-ROUTE-01` — `/app/doctor/analytics` принадлежит кабинету специалиста и требует `requireDoctorWorkspaceContext`; ordinary specialist получает экран без global-admin роли.
- [ ] `AN-ROUTE-02` — платформа получает отдельный `/app/admin/analytics`; platform navigation и legacy redirects ведут туда, не сталкиваясь с doctor route.
- [ ] `AN-ROUTE-03` — врачебная навигация «Аналитика» ведёт на `/app/doctor/analytics`, а не на `material-ratings`.
- [ ] `AN-SCOPE-01` — каждый doctor aggregate ограничен `organizationId` и visibility actor/заранее разрешёнными patient IDs; `getDefaultOrganizationId` и global loader запрещены.
- [ ] `AN-SCOPE-02` — чужая организация и невидимый пациент не влияют ни на KPI, ни на график, ни на drill-down; ordinary specialist и clinic admin проверяются отдельно.
- [ ] `AN-SCOPE-03` — фраза «Платформа за выбранный период (не фильтр по вашим пациентам)» и пустой platform content block удалены из doctor UI; корректная tenant-scoped таблица оценок сохраняется.

## B. Общий интерфейс — первый этап

- [ ] `AN-UI-01` — экран переиспользует `DoctorAppShell`, `DoctorPageHeader`, `doctorSectionTabClass`, `DoctorSection`, `DoctorStatCard` и существующие chart/period primitives; параллельный shell и локальная дизайн-система не создаются.
- [ ] `AN-UI-02` — нижний/section tab row устроен как в расписании и карточке пациента; вкладки ровно `Записи` и `Активность`, поддерживают mobile/desktop и URL `?tab=`.
- [ ] `AN-PERIOD-01` — доступны пресеты `24 часа`, `7 дней`, `30 дней` и произвольный диапазон дат.
- [ ] `AN-PERIOD-02` — границы периода вычисляются в бизнес-таймзоне специалиста/организации последовательно для KPI, рядов и drill-down; start inclusive, end exclusive.
- [ ] `AN-STATE-01` — loading/error/empty состояния относятся к конкретной вкладке, не показывают сырые ошибки и не рисуют выдуманные нули вместо недоступной метрики.

## C. Вкладка «Записи» — первый этап

- [ ] `AN-REC-01` — показать существующие scoped KPI: всего записей, будущие/состоявшиеся, отмены, переносы, первичные/повторные и уникальные пациенты за выбранный период; подписи не обещают финансовую или клиническую семантику, которой нет.
- [ ] `AN-REC-02` — реализовать непустой scoped временной ряд записей по дням для выбранного периода через существующий `DoctorAppointmentsPort`; SQL/фильтры записи не дублируются в UI/API.
- [ ] `AN-REC-03` — график и KPI используют один scope и дают согласованный drill-down на соответствующие записи.
- [ ] `AN-REC-04` — отмены видны отдельной серией/значением; технические player/app ошибки на вкладке отсутствуют.

## D. Вкладка «Активность» — первый этап

- [ ] `AN-ACT-01` — считать только доступных специалисту пациентов с активной назначенной программой.
- [ ] `AN-ACT-02` — показать фактические метрики: пациентов с программой, пациентов с отметками за период, число отметок/выполнений, дни с активностью и долю активных пациентов.
- [ ] `AN-ACT-03` — временной ряд показывает фактическую активность по дням и не называется точным процентом соблюдения назначения, пока нет структурированного expected schedule.
- [ ] `AN-ACT-04` — drill-down пациента ведёт в существующую карточку/календарь упражнений; невидимый пациент недоступен.
- [ ] `AN-ACT-05` — корректная tenant-scoped статистика оценок материалов остаётся доступна из «Активности» ссылкой или существующей секцией; global `ContentEngagementStatsResponse` не переиспользуется.
- [ ] `AN-ACT-06` — для сопровождения/избранных и остальных пациентов предусмотрен честный scoped разрез, если текущая доменная метка уже доступна без нового предположения; если нет — пункт остаётся открыт с фактическим blocker, а не симулируется.

## E. Следующие этапы — не имитировать в первом ship

- [ ] `AN-MONEY-01` — стоимость/предоплата: определить с владельцем, что агрегируется — созданные записи, состоявшиеся визиты, начисления, фактические платежи или net после возвратов; затем добавить стоимость, требуемую и полученную предоплату.
- [ ] `AN-ADHERENCE-01` — точный процент «ожидалось / выполнено» требует структурированного расписания назначения; до появления модели не выводить фиктивный процент.
- [ ] `AN-VIDEO-01` — собирать реальные playback progress seconds и контекст открытия (назначенное упражнение / разминка / promo); затем показывать открытия и реальные минуты отдельно.
- [ ] `AN-APP-01` — specialist-scoped частота входов, page views и active minutes через отдельный read model поверх существующего org/user rollup.
- [ ] `AN-REMINDER-01` — patient-facing reminder sent/open/seen/done без внутренних error codes; включение в doctor product требует отдельного решения владельца.

## F. Явно только global admin

- [ ] `AN-ADMIN-01` — cross-clinic totals, платформенные регистрации/каналы/top pages и вся operational analytics не доступны doctor route/API.
- [ ] `AN-ADMIN-02` — player/HLS/proxy/transcode/storage errors, user-agent и внутренние reminder delivery error codes показываются только global admin.

## G. Приёмка первого этапа

- [ ] `AN-TEST-01` — behavioral tests доказывают tenant isolation, visibility actor, ordinary specialist vs clinic admin, период/таймзону и согласованность KPI↔drill-down.
- [ ] `AN-TEST-02` — новый DB-root/read model, если появится, проходит named DEV RLS/privilege proof; миграционные права объявлены в центральной declaration, не в migration.
- [ ] `AN-AUDIT-01` — независимый аудитор даёт бинарный verdict по `A–D`, `F`, `G`; визуальную приёмку выполняет владелец на TEST.
- [ ] `AN-INTEGRATION-01` — после принятия ветка по одному приземлена в `feat/doctor-ui-rebuild`, worktree/branch удалены, общий интеграционный CI и TEST deploy выполняет оркестратор.
