## 0. Находки хуже, чем «просто нетипизировано» (сначала это)

### 0.1 Гейт не видит `packages/*` — текстовый SQL сбегает из-под проверки целиком

`scanRoots` в `scripts/check-no-new-raw-sql.mjs` — это ровно три пути:

```js
const scanRoots = ['apps/integrator/src', 'apps/media-worker/src', 'apps/webapp/src'];
```

`packages/platform-merge/src/**` в этот список не входит. А это не мёртвый код: восемь файлов там —
`mergeContactFallback.ts`, `messengerBindAuditEnrichment.ts`, `phoneHistorySync.ts`,
`messengerPhonePublicBind.ts`, `identityProjectionWrite.ts`, `userIdentityFioWrite.ts`, `pgPlatformUserMerge.ts`,
`userContactsMirrorWrite.ts` — содержат тексты `SELECT`/`INSERT INTO`/`UPDATE`/`DELETE FROM`, а
`packages/platform-merge/src/mergeSql.ts:54` выполняет их через `db.query(text, params)` — тот самый сырой вызов,
который правило `AGENTS.md` §5 запрещает для нового кода. Мост в это выполнение из вебаппа —
`apps/webapp/src/infra/repos/pgMessengerPhoneHttpBind.ts` (`asMessengerPhoneBindDb`): он оборачивает
`runWebappPgText` под интерфейс пакета именно потому, что пакет общий с интегратором и не может зависеть от
drizzle-порта вебаппа впрямую (`identityPhoneSql.ts` — тот же паттерн для другого моста).

**Смысл находки:** «`check-no-new-raw-sql: production debt: 0`» — верно только про три просканированных дерева;
пакет, к которому текущий гейт даже не притрагивается, уже несёт нетипизированный SQL с реальной записью
(`INSERT`/`UPDATE`, не только чтение). Это не «60-й файл в переписи», это дыра в периметре самой проверки —
любое усиление гейта (раздел 4) обязано включить `packages/*/src` в `scanRoots`, иначе оно защищает только часть
дерева и создаёт ложное чувство «production debt: 0», не проверив пакеты.

Команда: `grep -rlc "SELECT \|INSERT INTO\|UPDATE \|DELETE FROM" packages/platform-merge/src/*.ts | grep -v ':0'`
→ восемь файлов; `grep -rn "\.query(" packages/platform-merge/src/mergeSql.ts` → строка 54.

### 0.2 `SELECT *` от реальной таблицы в раннер, типизированный вручную

`apps/webapp/src/infra/repos/pgPatientBookings.ts:399,410,422` — три вызова `SELECT * FROM patient_bookings …`
против **реальной, изменяемой таблицы** (не функции), результат которой льётся в `runWebappPgText<Row>`, где
`Row` — вручную объявленный тип (строки 20–40 того же файла). Компилятор не видит связи между `Row` и схемой
`patient_bookings`: переименование или удаление колонки в миграции не сломает сборку — сломает `undefined` в
рантайме на первом обращении. Это ровно класс дефекта, который владелец назвал причиной существующего
подхода к плану («построитель проверяет имена колонок на этапе компиляции, строка — нет»).

Отличать от безопасного случая: `apps/webapp/src/infra/repos/pgStaffSecurity.ts:49` тоже делает
`SELECT * FROM app.get_staff_security_profile()`, но результат сразу проходит `profileRowSchema.parse(row)`
(zod, строка 30) — рантайм-валидация есть, хоть и не компайл-тайм. Восемь других `SELECT *` в переписи (раздел 2)
идут против `app.<function>()` — форма определяется сигнатурой SECURITY DEFINER функции в БД, а не таблицей;
риск тот же (сигнатура может измениться без сборки), но не «таблица под ногами двигается от каждой миграции».

### 0.3 Ручная сборка литерала вместо `$n`-параметра

`apps/webapp/src/infra/repos/pgDoctorClients.ts:120-121`:

```ts
function sqlLiteralUuid(value: string): string {
  return `'${value.replaceAll("'", "''")}'::uuid`;
}
```

Используется на строках 259 и 1495 — `organizationId` (не пользовательский текст, приходит из серверного
контекста принципала) вклеивается в текст запроса вручную экранированной строкой вместо параметра. Сегодня это
не эксплуатируется: экранирование кавычек корректно, и `::uuid`-каст отбрасывает всё, что не является UUID,
до выполнения. Но это ручная защита силами разработчика в файле с наибольшим числом вызовов моста в переписи
(36, раздел 2) — один неосторожный copy-paste этой функции туда, где значения нет каста в конкретный тип,
и защита пропадает молча. `$n`-параметр даёт то же самое без ручной работы.

Рядом, вне периметра переписи (файл не использует `runWebappPgText`, поэтому не входит в 57 из раздела 1), тот
же паттерн — `apps/webapp/src/infra/repos/pgProgramActionLog.ts:469,495,522,551` — `sql.raw(\`'${iana...}'\`)`
для IANA-таймзоны. Там перед вклейкой стоит `if (!/^[-+/_0-9a-zA-Z]+$/.test(iana)) throw`, так что это
безопаснее `sqlLiteralUuid`, но структурно тот же обходной путь: ручная сборка литерала вместо параметра.

## 2. Три бакета

Критерий: **convert** — обычный `SELECT`/`INSERT`/`UPDATE`/`DELETE` по одной таблице или простому join,
который построитель выражает так же коротко и не менее читаемо, без `WITH RECURSIVE`, оконных функций,
множественных `LATERAL`, тяжёлой ручной сборки `WHERE` из фрагментов. **Оставить осознанно** — построитель либо
не выражает конструкцию нативно (рекурсия, `LATERAL`, `ON CONFLICT`-гимнастика, `array_agg`/`jsonb_agg`
корреляты), либо это вызов SECURITY DEFINER функции (`SELECT app.fn(...)`), где построитель не даёт вообще
ничего — весь «запрос» это один вызов функции, разницы между `sql\`select app.fn($1)\`` и текущим текстовым
мостом с точки зрения типобезопасности нет. **Решить позже** — неоднозначно, вопрос указан явно.

### 2.2 Оставить осознанно (26 файлов)

Причина у каждой группы — конкретная, не «сложно вообще».

**Чистые RPC-обёртки — `SELECT app.<security-definer-функция>(...)`.** Запрос — это сам вызов функции;
построитель не выражает вызов хранимой функции нативно, а `db.execute(sql\`select app.fn(${x})\`)` — тот же
уровень типобезопасности, что и сейчас, только без моста `$n`↔`sql.param`. Перевод не даёт защиты от дрейфа
сигнатуры функции — ту же проблему решает контрактный тест на сигнатуру, не построитель.

`pgEmailAuth.ts` (388L/21, 23 RPC), `pgOAuthBindings.ts` (41L/1, чистый RPC), `pgOrgEntitlements.ts` (407L/6,
6 RPC), `pgOrganizationProvisioning.ts` (265L/6, 6 RPC), `pgPasskeyStore.ts` (228L/5, 13 RPC-сигнатур),
`pgPatientBookingCatalog.ts` (47L/1, RPC + `SELECT *`, см. 0.2), `pgPatientMaintenanceHistory.ts` (46L/1, то же),
`pgUserPasswordCredentials.ts` (308L/6, 8 RPC), `pgStaffSecurity.ts` (119L/10, 10 однострочных RPC-вызовов),
`app-layer/media/playbackStatsHourly.ts` (31L/1, один RPC), `pgSystemSettings.ts` (775L/29, 26 RPC + 4
ON CONFLICT).

**`LATERAL`/оконные функции/рекурсивная агрегация — построитель длиннее и менее читаем, чем SQL.**

`pgLfkDiary.ts` (503L/14, 1 window + 2 LATERAL — обложка комплекса через `LEFT JOIN LATERAL`),
`pgLfkExercises.ts` (893L/12, 1 LATERAL + 10 array_agg — список упражнений с превью медиа коррелированным
подзапросом), `pgLfkTemplates.ts` (761L/7, `ROW_NUMBER() OVER (PARTITION BY …)` для рэнкинга упражнений
внутри шаблона + 2 LATERAL + 5 array_agg), `pgCourses.ts` (402L/1, но тот единственный вызов — сводка курса с
пятью коррелированными подзапросами COUNT + агрегированные `id`-массивы по каждому), `pgDoctorAnalyticsMetricAccounts.ts`
(809L/25, 14 LATERAL — построение аналитической ленты событий по пациенту, каждое событие — свой
LATERAL-подзапрос).

**Динамическая сборка `WHERE`/`SELECT` из общих фрагментов (видимость пациента, исключение
пользователей) — общий межфайловый паттерн, требует решения ДО перевода, не файл за файлом.**

`pgDoctorClients.ts` (1538L/36 — больше всего строк и второе место по числу вызовов; помощники

архитектурный вопрос (как построитель выражает составной, переиспользуемый предикат видимости) дважды.

## 3. Порядок бакета convert — не по размеру файла

Критерий упорядочивания: (а) путь пациента/пользователя — прямой пользовательский трафик впереди
редко-используемых админ-инструментов; (б) частота обращения — то, что дергается на каждый запрос страницы,
впереди фонового/разового; (в) тихий отказ — запрос, чья поломка не бросит исключение (просто вернёт не те
строки/0 строк), впереди запроса, который упадёт с ошибкой и будет замечен сразу. Размер файла в строках — не
критерий: `pgTreatmentProgram.ts` (1916 строк) стоит ниже `catalogMediaLadderLookup.ts` (60 строк), потому что
у первого один вызов моста на весь файл, у второго — единственная точка входа на горячем пути (превью медиа
на каждой странице каталога).

## 4. Как остановить появление новых — предложение, не реализация

Действующий `check-no-new-raw-sql.mjs` разрешает текстовый SQL, если он идёт через один из перечисленных
port-файлов (`portFiles`/`migrationExecutors`) — список закрытый и структурный (комментарий в самом файле:
«This is intentionally structural, not a debt allowlist: adding a repository or runtime file here is not an
option»). Проблема не в этом списке — он и так закрыт для новых port-файлов. Проблема в том, что 57 файлов
раздела 1 сами НЕ являются port-файлами: они снаружи гейта, потому что зовут `runWebappPgText` — разрешённую
функцию — а не `pool.query` напрямую. Гейт запрещает **обходить** мост; он не запрещает **пользоваться** им
для нового кода. Значит «не делать нового текстового SQL» сегодня держится дисциплиной автора PR, не структурой.

**Рассмотренные варианты:**

- **Заморозить список из 57 файлов как allowlist, падать на любом новом файле/новом вызове вне списка.**
  Механически реализуемо (тот же принцип, что уже применён к `portFiles`, просто на уровень выше — список
  вызывающих, а не портов). Плюс: реально останавливает новые файлы с первого коммита. Минус, и он серьёзный:
  это ровно debt-allowlist, тот класс, который сам `check-no-new-raw-sql.mjs` в собственном комментарии
  называет неприемлемым для port-файлов («not an option»). Список из 57 файлов будет расти по факту
  конвертации (файл вычёркивается по мере перевода), но пока список живой, он несёт тот же риск, что и любой
  allowlist: конвертированный файл, к которому кто-то по привычке дописал новый текстовый вызов, гейт не
  поймает, пока файл физически не вычеркнут из списка — задача превращается в «не забыть вычеркнуть», ровно то,
  от чего allowlist чек и уводит.
- **Считать НОВЫЕ вызовы `runWebappPgText`/`webappSqlFromPgText`/`runPgPoolPgText` в файле, которого нет в
  git-истории до этой правки (новый файл), и падать только на них — старые файлы не трогать, даже если в них
  добавили ещё один вызов.** Не требует allowlist-списка файлов, но требует гейту знать git-дифф (что уже
  делает часть инфраструктуры репо для других проверок «нового кода» — прецедент есть). Минус: не ловит
  добавление 53-го вызова в уже существующий `pgSupportCommunication.ts` — а именно там (раздел 2.2, самый
  вызываемый файл) риск роста самый высокий.
- **Считать количество вызовов на файл на момент этой переписи (424 — раздел 1) и падать, если общее число
  вызовов моста в дереве выросло** — не привязываясь к тому, какой файл. Не требует поимённого списка (значит
  не allowlist в смысле «список путей»), ловит рост и в новых, и в старых файлах. Минус: не ловит замену
  старого простого запроса новым сложным при том же числе вызовов; не различает «добавили тривиальный
  lookup» от «добавили 50-строчный ON CONFLICT».

**Рекомендация: третий вариант (порог по числу вызовов), с CI-скриптом, который печатает точный дифф-список
файлов при падении.** Он не заводит поимённый allowlist (не противоречит комментарию `check-no-new-raw-sql.mjs`
про «not a debt allowlist» — это счётчик, не список разрешённых путей), не требует гейту сложной git-археологии
(диффа по файлам, ренеймов, кто первым тронул файл), и его нельзя обойти правкой существующего файла без
осознанного шага «поднять порог» — то есть он превращает «не добавлять новый текстовый SQL по возможности» из
слов в раздел 2.1 в измеримое число, которое либо не растёт, либо растёт по явному решению того, кто поднимает
порог в этом же PR. Стоимость: при каждой конвертации файла из раздела 2.1 порог нужно СНИЖАТЬ тем же PR
(иначе счётчик перестаёт быть гейтом и превращается в потолок, который никогда не достигается) — это
единственная дисциплина, которую придётся не забывать, и она заметно дешевле поддержки поимённого списка.

Обязательное условие для любого из трёх вариантов, независимо от выбора: **`scanRoots` должен включить
`packages/*/src`** (раздел 0.1) — иначе усиленный гейт защищает три дерева из четырёх, а мост в
`packages/platform-merge` продолжит расти незамеченным.
