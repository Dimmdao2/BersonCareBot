> **⛔ ПЕРЕД СТАРТОМ ЭТАПА — перечитать, не по памяти:** `AGENTS.md` (§24 оркестрация, §7-9 коммит/CI/пуш feat),
> `docs/ORCHESTRATION_BINDINGS.md`, `docs/ORCHESTRATOR_CHECKLIST.md`, релевантные `.cursor/rules/*.mdc`.
> Агентов запускать только через `tools/orch-launch.sh`. **НЕ ИЗОБРЕТАТЬ:** сначала искать готовое.

## Решение владельца, дословно

- «тесты ради тестов - явно нет»;
- «мой вывод - удалять все эти тесты прямо сейчас» (о тестах, пиннящих текст исходников);
- «пройти фильтром «назови ошибку»» → **«отлично. запускай»**;
- о карте: «нужна карта - разбить файлы с тестами на группы либо по смыслу либо по модулям, потом по каждому
  составить файл с тестами, потом решить какие там вообще полезны. Работы много, но надо делать».

Владелец также сформулировал, каким тест должен быть: «дали на вход это — получили это; что внутри функции
тесту должно быть насрать», плюс отдельные классы — поведение (нажали → получили), безопасность (неверный
пароль → отказ, повтор → задержка) и доступ к данным в БД.

Классификация 1797 тестовых файлов по типу проверки: поведение — 1041, только заглушки — 381, отрисовка UI —
235, **текст исходника — 112**, живая база — **28**.

⚠️ **Про «381» и «34» — это ДВА РАЗНЫХ признака, не опечатка** (расхождение поймано аудитом плана 29.07):
- **381** — широкий признак карты: в файле три и более заглушки, нет живой базы, нет отрисовки UI, нет чтения
  файлов. Это просто «тест на заглушках» — само по себе НЕ дефект, так пишут нормальные тесты портов.
- **34** — узкий признак: более 80% утверждений в файле — про то, что **наша собственная заглушка была
  вызвана** (`toHaveBeenCalled*`). Вот это подозрительно: тест может проверять сам факт вызова, ничего не
  зная о результате. Список: `docs/_TODO/testsuite-mock-echo.txt`.
- Выборочная проверка узкого списка показала, что часть из 34 — **законные проверки контракта на границе**
  (например: при ошибке интегратора отправка в учёт ошибок вызвана с нужными аргументами, при успехе — не
  вызвана). Поэтому этап 4 — разбор глазами, а не удаление по признаку.

Ключевой перекос: про права, изоляцию и запросы мы почти всё «знаем» **не проверив** — живую базу трогают 28
файлов из 1797, а текст исходника — 112. Сегодняшний дефект прав (функция пересчёта квоты без права на чтение
таблицы) был зелёным во всех тестах именно поэтому.

## Фильтр «назови ошибку» — процедура

Для КАЖДОГО теста ответить одной строкой: **какую конкретную поломку он поймает**, в форме
«подали такое — получили неправильное такое». Абстракции («проверяет корректность») не принимаются.

- ответ вида «поймает переименование / смену форматирования / что мы не вызвали свою же заглушку» → **удалить**;
- ответ называет правдоподобную поломку (лимит не сработал, чужой пациент виден, счётчик попыток не вырос) →
  **оставить**;
- спор → **объективный арбитр**: внести названную поломку в код руками и посмотреть, покраснел ли тест. Не
  покраснел — тест не ловит то, ради чего написан.

**Фильтр применяет НЕ автор теста.** Автор всегда найдёт оправдание — 28.07 исполнитель закрепил тестом
собственную ошибку.

## Куда писать результат и кто применяет фильтр

- **Результат этапа 3** пишется в `docs/_TODO/testsuite-verdicts-batch1.md` и `...-batch2.md`, по одной строке
  на тестовый случай: `файл:строка | название теста | какую поломку поймает | оставить/удалить/переписать`.
  Строка без графы «поломка» считается неразобранной и не засчитывается.
- **Применяет фильтр отдельный агент-ревизор**, не тот, кто писал тест, и не тот, кто чинил этот модуль в
  ночной волне 28.07. Лид назначает его через `tools/orch-launch.sh` и НЕ принимает вердикты по отчёту:
  выборочно перепроверяет спорные строки арбитром (внести поломку руками → тест обязан покраснеть).
- **Удаление после этапа 3 — отдельный шаг** и отдельный коммит: сначала таблица вердиктов, потом правки.

## Критерий «готово» по этапам

| этап | готово, когда |
|---|---|
| 1 | 45 файлов удалены (или обоснованно оставлены поимённо), `pnpm --dir apps/webapp test` и `--dir apps/integrator test` зелёные, числа до/после в отчёте |
| 2 | в 21 файле не осталось утверждений по тексту прочитанного файла, все прочие проверки сохранены, опустевшие файлы удалены и названы |
| 3 | обе таблицы вердиктов заполнены целиком: строк ровно столько, сколько тестовых случаев в 200 файлах; спорные перепроверены арбитром |
| 4 | по каждому из 34 файлов записан вердикт в тех же таблицах |

Общий гейт на всё: **зелёный полный `pnpm run ci` и живая проверка на TEST** — «тесты стали чище» само по себе
не «готово» (канон: `docs/ORCHESTRATOR_CHECKLIST.md`, пункт 10).

## Что НЕ делаем

- Не гонимся за числом тестов: медиана в 10 проверок на файл здорова, перекос сидит в десятках гигантов.
- Не переписываем 40 SQL-пиннингов в интеграционные тесты: **деплой уже проверяет то же самое против живой
  базы** и строже (права ролей, число защищённых функций, опись политик, владелец таблиц). Дублировать незачем.
- Не трогаем 28 файлов с живой базой — это самое ценное, что есть.
