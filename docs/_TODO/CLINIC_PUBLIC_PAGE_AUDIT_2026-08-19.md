## НАХОДКИ

### F1 (критично, блокирует приземление) — новый канонический адрес записи мёртв для посетителя

`/{clinic}/booking` отдаёт «Каталог временно недоступен» ЛЮБОМУ анониму, для любой клиники.
Причина названа в самом репозитории — `apps/webapp/src/app-layer/principal/publicBookingPrincipal.ts:14-16`:
новая публичная точка входа обязана добавить свою строку в `PUBLIC_BOOKING_PRINCIPAL_SOURCES`,
иначе попадёт на реляционный путь, которого у класса `tenant_service` нет. Ветка этого не сделала:
`loadBookingEntry.ts:79` ставит `source: 'app/[clinicSlug]/booking:entry'`, которого в списке нет.
Вторая половина той же причины: `loadBookingEntry.ts` читает каталог **кабинетным** листером
`listInPersonServicesForBranch` (`db.select()` напрямую) и `catalog.listSpecialists()`, тогда как
публичный путь обязан идти через объявленную дверь `listPublicBookableServicesForBranch`
(так делает старый `publicOrganizationBooking.ts:127`).

Доказательство причинности (временные правки внесены и откачены):
добавление строки в список → падение уезжает с `listBranches` на `listServices`;
плюс подмена листера на `listPublicBookableServicesForBranch` → первый экран рисуется полностью.
С параметром `?specialist=` экран остаётся мёртвым и после обеих правок, потому что
`listSpecialists` — тоже реляционное чтение без публичной двери.

Последствие для живого человека: `publicBookPaths.forSlug` переведён на новый адрес, поэтому
**старая ссылка из письма подтверждения записи** (`/book/{slug}`) теперь честным 308 уводит человека
на страницу, где вместо услуг написано «Каталог временно недоступен». Публичная запись перестаёт
работать целиком. Конструктор ссылки (Ш7) при этом штампует ссылки с `?specialist=`, которые мертвы
даже после починки первых двух шагов.

Команда:
```
curl -s http://127.0.0.1:5310/dmitryberson/booking          # → «Каталог временно недоступен»
curl -s -L -w '%{url_effective}\n' http://127.0.0.1:5310/book/dmitryberson   # 308 → тот же мёртвый экран
```
В логе: `Missing declared webapp port capability: tenant_service`.

Почему это не поймали: `bookingEntryScreen.unit.test.ts` (6/6 зелёные) подменяет `deps` целиком и
принципала не ставит; ни одного route/live-теста на новый адрес нет. Прогнанные мной 7 файлов /
33 теста этой поверхности зелёные при мёртвом продукте.

### F2 (высоко) — в ветку закоммичены неразрешённые маркеры merge-конфликта в двух deploy-артефактах

`deploy/postgres/generated/port-context-capabilities.bcb_webapp_dev.sql:179-184` и
`…bersoncarebot_test.sql:179-184` содержат `<<<<<<< HEAD` / `=======` / `>>>>>>> a8c2d3d59…`.
Файл — не текст, а SQL: применение даёт синтаксическую ошибку. Внутри конфликта сторона «theirs»
несёт две capability соседней ветки (`booking.public-catalog.read`, `booking.public-slot-snapshot.read`),
то есть любое «разрешить в свою пользу» их потеряет.

Вторая половина находки — гейт этого не ловит: `node deploy/postgres/privileges/generate-cli.mjs --check`
(на который план Ш2 ссылается словами «побайтно») проверяет только `privileges` и `allowlist`
и выходит **0**. Артефакт port-context сверяется лишь под отдельным флагом:
```
node deploy/postgres/privileges/generate-cli.mjs --check --port-context-only   # exit 1, «расхождений 2»
```
Ни один скрипт деплоя и ни один CI-шаг этот флаг не зовёт (`grep -rn "port-context-only"` — только
сам generate-cli). Последствие: заявленное «побайтно» неверно для этого артефакта, и корректность
объявленного каталога capability сегодня ничем не удерживается.
