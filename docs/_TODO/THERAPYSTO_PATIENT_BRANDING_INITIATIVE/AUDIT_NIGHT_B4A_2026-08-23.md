## 1. Что сделано в коммите

`apps/webapp/src/modules/org-branding/service.ts:177` — снято одно условие:

```diff
-  if (effective.resolution !== 'applied' || !effective.core.isActive) return null;
+  if (!effective.core.isActive) return null;
```

То есть анонимная проекция бренда больше не требует `resolution === 'applied'`: активная
организация всегда проецирует своё имя ядра, а платные поля либо перекрывают его, либо падают на
платформенные значения. `null` остался за неактивной организацией. Плюс переписаны три существующих
unit-ожидания, добавлен один route-тест и перевёрнута галочка `B4a`.

## 3. `F-1` (блокер). Активная клиника с длинным названием получает `404` на весь хост

**Класс нарушения:** owner requirement `B4a` — «`404` остаётся только для неизвестной метки,
неактивной и удалённой организации». Клиника с длинным названием — ни одно из трёх.

**Механика, по шагам, без предположений:**

1. `apps/webapp/src/app/api/auth/specialist-signup/start/route.ts:46` —
   `organizationTitle: z.string().trim().min(1).max(200)`. Форма регистрации принимает **до 200
   знаков**.
2. `apps/webapp/src/modules/organization-provisioning/service.ts:12-14` — `normalizeTitle` только
   схлопывает пробелы, длину не режет.
3. `deploy/postgres/specialist-owner-provisioning-rls.sql:229-239` — значение уходит в
   `be_organizations.title` как есть; `apps/webapp/db/schema/bookingEngine.ts:76` объявляет колонку
   `text NOT NULL` **без ограничения длины**, DB-CHECK на длину названия в репозитории нет.
4. `apps/webapp/src/modules/org-branding/ports.ts:17` — именно `be_organizations.title` и есть
   `core.displayName`.
5. **Новый путь этого коммита** отдаёт `core.displayName` в анонимную проекцию без нормализации.
   Платный путь так не может: `normalizeDisplayNameOverride` (`service.ts:134-140`) режет платные
   имена по `MAX_DISPLAY_NAME_LENGTH = 120`.
6. `apps/webapp/src/shared/lib/surface/requestSurface.ts:90-99` — санитайзер поверхности отбрасывает
   бренд при `effectiveDisplayName.length > 120` (и `patientAppName.length > 120`, в фолбэке это то
   же значение) → `sanitizeEffectivePatientBrand` возвращает `null`.
7. `requestSurface.ts:161-162` → `resolveRequestSurface` возвращает `null`; `proxy.ts:58-66` на
   `null` отдаёт `404` **на любой путь этого хоста**.

Итог: клиника, назвавшаяся при регистрации, например, «Автономная некоммерческая организация
реабилитации и восстановительного лечения…» (121–200 знаков), и не купившая брендинг, получает
мёртвый адрес — ровно то последствие, которое §1.2b-1 описывает словами «пациент видит поломку
вместо записи, поисковики выкидывают адрес из индекса».

**Это не регрессия коммита:** до него такая клиника получала `404` вместе со всеми остальными
неоплатившими. Это **незакрытая часть требования**, из-за которой галочка `[x]` на `B4a` сегодня
неверна.

**Падающий acceptance-тест (handoff воркеру, §24.5):**
`apps/webapp/src/proxy.route.test.ts` → «оставляет живой адрес клинике с длинным названием
(регистрация принимает до 200 знаков)» → `AssertionError: expected 404 to be 200`.

**Чего в находке НЕТ.** Я не назначаю способ починки: обрезать имя ядра теми же 120 знаками в
анонимной проекции, поднять предел санитайзера или ограничить название на записи — это выбор
исполнителя пункта. Пункта «ограничить длину названия организации» в плане владельца нет, и заводить
его я не могу; чинится существующее требование `B4a`, а не новое.

## 7. Неблокирующее

### `R-1`. Галочку `B4a` перевернул сам исполнитель

Коммит правит `IMPLEMENTATION_PLAN.md:680` с `[ ]` на `[x]`. По §24.7 галочки ставит ведущий после
собственной проверки полноты; `worker done` — входной сигнал, не отметка. Здесь это не формальность:
галочка стоит на пункте, требование которого не выполнено (`F-1`).

### `R-2` (вопрос владельцу, не работа). `B4a` сам по себе не делает адрес клиники живым

Боевой шов арендатора в `proxy` до сих пор заглушка: `proxy.ts:34`,
`const NO_TENANT_SURFACE: TenantSurfaceLookup = async () => ({ status: 'unknown' })`, и другого
`TenantSurfaceLookup` в продуктовом коде нет. То есть сегодня `<slug>.therapygo.ru` отдаёт `404` для
**любой** клиники — и с брендом, и без, — потому что метка вообще не резолвится. Это известно и
названо ещё аудитом `B4` («шов не написан, живьём ничего не сломано»), объёму `B4a` не противоречит
(оракул прямо ставит проверку «на резолве поверхности»), но означает: закрытие `B4a` **не** даёт
владельцу живую страницу до подключения шва в `B5`. Мой тест из §4.1 показывает, что этот шов
собирается из уже готовых кусков без нового резолвера.

### `R-3`. Санитайзер поверхности рассчитан на платные имена, а теперь получает имя ядра

Предел `120` в `sanitizeEffectivePatientBrand` совпадает с `MAX_DISPLAY_NAME_LENGTH` платного пути —
и это совпадение перестало быть верным ровно в этом коммите: имя ядра приходит из колонки без
ограничения. `F-1` — первое следствие; второе того же класса — пустое/пробельное название
организации (`patient-organization/service.ts:46` подставляет «Организация» именно потому, что такие
строки в данных встречаются), которое санитайзер тоже отвергнет в `404`. Регистрация пустое имя не
пропускает, поэтому отдельной находкой не пишу; чинить осмысленно одним решением вместе с `F-1`.
