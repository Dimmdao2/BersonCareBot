### Тест, написанный по классификации `A`/`B` брифа

`B` (cookie host-only) — **написан и зелёный**: `apps/webapp/src/modules/auth/sessionCookieHostOnly.unit.test.ts`,
три проверки, два уровня. Поведенческий — реальный заголовок `Set-Cookie` наших builder-ов не несёт `Domain`.
Структурный — ни один writer в `src/` не передаёт `domain` в опции; builder-ов два, а мест записи cookie
десять, поэтому одного поведенческого уровня мало. Прогон: `3 passed`.
**Fault injection (обязательна, иначе зелёный тест ничего не значит):** добавил `domain: '.therapygo.ru'`
в `sessionCookie.ts:190` и в `middleware/platformContext.ts:41` → `2 failed | 1 passed`, причём
структурный уровень поимённо назвал `middleware/platformContext.ts`. Инъекции откачены, дерево чистое.

`A` (hard 404 на неизвестном Host) — **тест не написан, и это сама находка.** Проверяемого поведения в коде
не существует ни в каком виде (инвариант 3 выше), поэтому любой такой тест был бы красным с первой минуты.
Красный тест на ненаписанную функцию — это не гейт, а заявка на работу, которой нет в плане владельца.
Оракул для `A` появится вместе с резолвером этапа `B`; классификация брифа («тест») верна, но исполнима
только после `B`.

## `V5` Passkey: независимый перемер

Замер `sol` — на DEV `0` ключей. Перемерил своим способом, двумя независимыми сигналами, потому что «ноль
строк» сам по себе может быть артефактом RLS, а не пустой таблицей:

```bash
# 1) счёт строк
sudo -n -u postgres psql -X -h /var/run/postgresql -p 5432 -d bcb_webapp_dev -At \
  -c "SELECT 'credentials_rows='||count(*) FROM public.user_passkey_credentials;"
# → credentials_rows=0

# 2) каталожный факт, RLS его не фильтрует
sudo -n -u postgres psql -X -h /var/run/postgresql -p 5432 -d bcb_webapp_dev -At -c "
SELECT c.relname||' reltuples='||c.reltuples||' pages='||c.relpages
FROM pg_class c JOIN pg_namespace n ON n.oid=c.relnamespace
WHERE n.nspname='public' AND c.relname IN ('user_passkey_credentials','user_passkey_challenges');"
# → user_passkey_challenges  reltuples=-1 pages=0
# → user_passkey_credentials reltuples=-1 pages=0

# 3) ни одной церемонии за всю историю DEV
sudo -n -u postgres psql -X -At -d bcb_webapp_dev \
  -c "SELECT rp_id, count(*) FROM public.user_passkey_challenges GROUP BY 1;"
# → пусто
```

**`relpages=0` — это heap без единой страницы**, факт из системного каталога, который читается мимо RLS;
плюс я читал как `postgres` (BYPASSRLS). То есть ноль здесь означает именно пустую таблицу, а не
«принципал не назначен».

**Замер `sol` подтверждён: на DEV `0` credentials, и ни одна церемония passkey на DEV никогда не
начиналась.** Момент фиксации RP ID действительно бесплатный — на DEV.

## Неблокирующие находки

### `N1` §7 «Доказательство пустых результатов» приводит неверный результат собственной команды

§7 утверждает: «`rg -n '/setup' apps/webapp/src` и `rg -n 'therapysto\.ru|therapygo\.ru' deploy` вернули
ноль строк». Фактически:

```bash
rg -n '/setup' apps/webapp/src | wc -l          # → 15
rg -n 'therapysto\.ru|therapygo\.ru' deploy | wc -l  # → 0
```

Пятнадцать строк — это `/api/auth/email-password/setup-access` и `/setup-code/complete`, к странице `/setup`
отношения не имеющие, поэтому **вывод `C14` («публичного host-specific `/setup` нет») верен**. Неверен сам
протокол доказательства — а §7 существует ровно для того, чтобы «нет» доказывалось перечислением попыток
(глобальный канон: «“Нет” без списка мест, где искал, — не “нет”»). Правильная формулировка: точный поиск
даёт 15 совпадений, все — auth-API; страничного маршрута `/setup` в `app/` нет
(`find apps/webapp/src/app -iname '*setup*'` → пусто).

### `N2` `C11` объявляет отсутствующим существующий composed brand resolver

Подробно в `V1`. Риск конкретный: `TPB-16` запрещает параллельные резолверы, а строка «Нет» ведёт
исполнителя строить второй рядом с `modules/org-branding/service.ts:205`.

### `N3` `proxy.ts` не вызывается на публичных путях — а §4 назначает его choke point'ом

§4 схемы: «`proxy.ts` остаётся обязательным choke point для нормализации Host … и передачи одного
проверенного `ResolvedSurface`».

`apps/webapp/src/proxy.ts:126-128`:

```ts
export const config = {
  matcher: ['/app', '/app/:path*', '/api/:path*'],
};
```

То есть proxy **не выполняется** на `/`, `/<clinicSlug>`, `/legal/**`, `/book/**`, `/join/**` — и не будет
выполняться на будущем `/setup`. А это ровно те адреса, которые схема кладёт в основу брендированной
поверхности: §2 говорит, что корень брендированного адреса — визитка клиники (`/<clinicSlug>`), §1.2a — что
установка идёт с `/setup`. Резолвер, размещённый в `proxy.ts` как есть, не увидит ни один из них.

Схема этого не упоминает; ни одна строка `C01…C36` не покрывает. Это первый вопрос, на который упрётся
этап `B`: либо matcher расширяется, либо `ResolvedSurface` берётся не из proxy — и это архитектурная
развилка, а не деталь.

### `N4` OAuth на брендированных host не сходится с инвариантом 4 схемы

§3 матрица объявляет `OAuth / Yandex` = `ON⇄` для `patient` и на `*.therapygo.ru`, и на custom domain.
Инвариант 4 той же схемы: cookie host-only, cross-domain SSO нет.

Вместе они сегодня не работают:

- `redirect_uri` — **одна глобальная настройка** (`getYandexOauthRedirectUri()`,
  `modules/auth/yandexOAuthCallbackHandler.ts:86`; та же одна на `app/api/auth/oauth/start/route.ts:152-170`);
- финальный редирект после входа строится от `env.APP_BASE_URL`
  (`modules/auth/oauthWebSession.ts:26`, `yandexOAuthCallbackHandler.ts:64`).

Значит вход по Яндексу, начатый на `klinika.therapygo.ru`, завершится на host из `APP_BASE_URL`, и по
инварианту 4 сессия останется **там**, а не на брендированном адресе. Человек вернётся на брендированный
host неавторизованным.

`C23` («одна global Yandex config, gated по surface — Частично») ловит только половину: что
`authChannelPolicy.ts:55-106` не принимает surface. Более тяжёлая половина — единственный фиксированный
callback origin — не названа ни в одной строке. Владелец `OG-4` закрыл как «Яндекс не трогаем», то есть
работы тут может и не быть; но тогда `ON⇄` в матрице для брендированных host — обещание, которого схема не
может сдержать, и это надо либо снять из матрицы, либо признать отдельным пунктом.

### `N5` Строки про PWA/metadata платформенного админа в таблице нет, а состояние уже не нейтральное

§2 схемы про `admin.therapysto.ru`: «staff PWA молча не подменяет admin app». Сегодня — подменяет:

```
apps/webapp/src/app/app/admin/layout.tsx:24
export const metadata: Metadata = staffPwaLayoutMetadata;   // → title 'Therapysto', appleWebApp.title 'Therapysto'
```

Админская поверхность уже наследует staff-идентичность вкладки и PWA-метаданные. С учётом `Q4` («PWA
платформенному админу не нужно», §1.2g) это конкретное место, которое этап `B` обязан развести. Ни одна
строка `C01…C36` его не покрывает.

### `N6` Правка `F1` не доведена: две строки плана сохранили отменённую редакцию

§8 схемы, пункт 4: «`F1` больше не запрещает OAuth типом». `F1` действительно переписан. Но в том же файле
остались:

- `IMPLEMENTATION_PLAN.md:373` (§1.6): «настройка staff-поверхности **физически не может включить** на ней
  OAuth» — ровно та редакция, которую `OG-5` объявил отменённой на строках 439-442;
- `IMPLEMENTATION_PLAN.md:431` (`TPB-17`): «route-тест, что OAuth start/callback на staff origin отвечают
  отказом, а не редиректом» — формально совместимо с «выключено по умолчанию → недоступно», но читается как
  требование архитектурного запрета.

Плану владельца это не противоречит (`OG-5` — его же решение и оно позднее), но противоречие внутри
документа осталось, а §8 схемы сообщает, что оно снято. Строку 373 стоит пометить как перекрытую `OG-5`
там же, где она стоит.

### `N7` `C35` занижает размер: параллельных источников origin уже два, а не «нет единого»

`C35` — «Частично», доказательство только про `passkeyAuth.ts:21-35`. Фактически в дереве уже два
независимых источника абсолютного адреса:

- `config/env.ts:31` `APP_BASE_URL` — более двадцати мест: возвраты платежей
  (`modules/memberships/service.ts:332`, `modules/saas-billing/service.ts:57-58`), письма
  (`modules/patient-booking/canonicalCreate.ts:481-482`), deep links
  (`modules/messaging/notifyDoctorPatientMessage.ts:59`), OAuth (`modules/auth/oauthWebSession.ts:26`),
  web-push (`modules/patient-notifications/patientWebPushNotify.ts:238`), passkey;
- `shared/lib/http/getRequestOrigin.ts:5` — per-request origin с учётом `x-forwarded-host`, используется в
  двух auth-роутах (`app/api/auth/logout/route.ts:10`, `app/api/auth/dev-public/route.ts:19`).

Плюс третий кандидат в несведённой ветке (`wt/therapysto-stage-a-20260822:apps/webapp/src/config/productSurfaces.ts`).
`ResolvedSurface.publicOrigin` станет **четвёртым**, если `TPB-16` не скажет явно, что он поглощает первые два.
§4 схемы разбирает только судьбу таблицы маршрутов и про источники origin молчит — а именно они и есть
«параллельные getters», о которых `TPB-16`.

## Ответы на «взгляд» `D` и `E` брифа

**`D` — существует ли матрица «поверхность × механика входа»?** **Нет, ни в каком виде.**
`modules/auth/authChannelPolicy.ts:21-32,55-106` и `modules/auth/publicAuthSnapshot.ts:12-33` не принимают
аргумента поверхности вообще: `buildPrefetchedPublicAuthConfig()` вызывается без параметров и отдаёт один
глобальный набор всем поверхностям сразу. `C18` («Нет») — верно.

**`E` — единственность резолвера, нет ли параллельных getters/resolvers/stores?** Резолвера поверхности нет,
значит дублировать пока нечего. Но два параллельных источника origin уже есть (`N7`), а composed brand
resolver — ровно один и его нельзя дублировать (`N2`). Для `dependency/architecture audit по diff`, которого
требует `TPB-16`, это и есть две конкретные точки контроля.
