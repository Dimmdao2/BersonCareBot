## 1. Итоговое решение

Делаем **не два webapp и не форк**, а один webapp с четырьмя request-surface:

1. `staff` — Therapysto для специалистов и администраторов;
2. `platform_admin` — Therapysto для платформенного администратора на отдельном host;
3. `patient_default` — стандартное patient-приложение на отдельном полном домене и под отдельным именем;
4. `patient_branded` — то же patient-приложение на домене клиники с effective brand этой клиники.

Один запрос проходит через один `RequestSurfaceResolver`. Его результат содержит `surface`, `publicOrigin`,
`organizationId` (только для branded surface) и `EffectivePatientBrand`. Этот результат переиспользуют routing,
metadata/manifest, auth/OAuth, абсолютные ссылки и transactional delivery. Отдельные функции «получить имя для
header», «получить имя для письма», «получить домен для OAuth» не создаются.

### 1.1 Единственные источники данных

| Смысл | Единственный источник | Что не создаём |
| --- | --- | --- |
| Therapysto staff identity/origin | точное имя `Therapysto` + существующий typed deploy config (`APP_BASE_URL`) | DB-настройку названия платформы |
| Стандартное patient-приложение | один typed deploy config: обязательные `name` и `origin` | tenant-строку в БД, hardcoded placeholder |
| Домен клиники | существующий per-org `system_settings.org_custom_domain_hostname` | `hostname_binding`/`custom_domains` table |
| Опубликованный бренд | существующий `org_brand_revisions` и его service/port | второй branding module/store |
| Карточка, запись, контакты | существующая `clinic_public_directory_entries` и clinic-public-card port | копию публичного профиля внутри brand |
| SMTP/боты | существующие per-org settings и `dispatchPort`/`clinicDeliveryCredentials` | второй delivery dispatcher |
| OAuth credentials | DB-backed `system_settings`; один OAuth-config resolver выбирает запись по surface | env-секреты и отдельные OAuth flow |

`EffectivePatientBrand` — один composed read model. Для `patient_default` он строится из deploy identity. Для
`patient_branded` он берёт published org brand, а данные карточки/записи/контактов — из существующей public-card
проекции. Дублировать имя/контакты между этими хранилищами нельзя. Если patient app name должен отличаться от
названия клиники, в **существующую** brand revision добавляется одно optional поле `patientAppName` с fallback на
`displayName`; для цвета — один optional accent token с безопасным default. Полноценный theme/CMS не строится.

### 1.2 Адрес клиники: по умолчанию НАШ поддомен (решение владельца 22.08.2026)

**`W3` ЗАКРЫТ вариантом (а).** Пациент клиники приходит на **наш** поддомен вида
`<slug клиники>.therapygo.ru` (домен закрыт владельцем 22.08.2026, см. §5; например
`bersoncare.therapygo.ru`). Собственный домен клиники — **опция поверх этого дефолта** (расконсервирована
22.08.2026 в ручном виде, см. ниже), а не замена ему: клиника без своего сайта получает адрес за минуту и
ничего не настраивает.

Основание — проверка аналогов 22.08.2026: Medbridge отдаёт white-label портал на СВОЁМ домене
(`upmc.medbridgego.com`) даже клиенту размера UPMC; Physitrack вместо домена даёт клинике нативное приложение в
магазинах под её именем. Ни один из двух не ставит пациента на домен клиники.

Что это даёт: от клиники не требуется ничего (ни DNS, ни похода к регистратору, ни ожидания), один
wildcard-сертификат покрывает все клиники, подключение — минута в админке. Для клиник, которые этой опцией не пользуются, снимаются целиком: apex-домен,
привязка к вечному IP, мониторинг чужих доменов, риск HSTS на чужом домене, захват освободившегося домена,
подтверждение владения (`W2`). Это и есть смысл дефолта — не «своего домена не бывает», а «чтобы начать
работать, домен не нужен».

- **Базовый путь:** резолвер сопоставляет метку поддомена с организацией; источник метки — существующий slug
  организации, новой сущности не заводится. Неизвестная метка — hard 404, не platform fallback.
- **Собственный домен клиники — РАСКОНСЕРВИРОВАН 22.08.2026 в РУЧНОМ виде** (был отложен утром того же дня).
  Причина: первый арендатор — сам владелец, у него уже есть `bersoncare.ru`, и опция нужна ему сразу.
  Механизм — существующий `org_custom_domain_hostname`; всё, что описано ниже про custom domain, относится к
  нему. Отдельного подтверждения владения (`W2`) не вводим: подключение ручное, оператор проверяет DNS до
  включения HTTPS.
  **Отложенным остаётся только САМООБСЛУЖИВАНИЕ** — автоматический выпуск и продление сертификатов на сотни
  чужих доменов, мастер подключения в интерфейсе, мониторинг чужих доменов как продукт. Именно оно трудное,
  а не подключение одного домена руками.

  **Поправка к прежней формулировке (владелец 22.08: «ты сказал что сложно и поэтому так никто не делает —
  твои слова»).** Формулировка выше действительно перечисляла трудности так, будто они относятся к любому
  своему домену. Это неточно, и вот разделение по факту:

  | Что | Трудно ли | Почему |
  |---|---|---|
  | Один домен, привязка руками оператором | **нет** | две DNS-записи от клиники + сертификат; ровно то же делает Тильда, и подтверждения владения она не просит |
  | Поддомен вида `app.клиника.ru` | **нет** | `CNAME` на нас, apex-проблемы не возникает вообще |
  | Корень вида `клиника.ru` без `www` | чуть сложнее | на корне `CNAME` запрещён стандартом, нужна `A`-запись на наш постоянный IP; у нас он есть |
  | Сотни доменов автоматически, самообслуживанием | **да** | лимиты выпуска сертификатов, продление, мониторинг истечения, захват освободившегося домена, необратимость HSTS на чужом домене |

  Аналоги (Medbridge на своём `upmc.medbridgego.com`) избегают именно ПОСЛЕДНЕЙ строки, а не первой.

- **Направление редиректа (владелец 22.08.2026):** не `bersoncare.ru` → наш поддомен, а наоборот —
  `bersoncare.therapygo.ru` → `app.bersoncare.ru`. Наш поддомен остаётся техническим адресом, который всегда
  работает, а человек видит домен клиники. Обратное направление задачу не решает: после редиректа в адресной
  строке остаётся ЦЕЛЬ, то есть имя клиники было бы не видно.
- `org_custom_domain_hostname` остаётся каноническим нормализованным hostname.
- В существующий write path добавляется защита от дубля hostname. На актуальной DEV schema создаётся узкий
  partial unique expression index для непустого `value_json->>'value'` только у этого key; новой таблицы нет.
- Настройку домена оставляем `owner`-only, как сегодня. Расширение прав не нужно для результата и не является
  owner-вопросом этого плана.
- DNS, TLS и proxy binding выполняет оператор. Домен начинает принимать трафик только после этой ручной
  операции; отдельный lifecycle/marketplace/self-service не строится.
- Resolver признаёт branded surface только при точном совпадении нормализованного Host, действующей
  `custom_domain` capability и published brand. Неизвестный/дублирующийся Host — hard 404, не platform fallback.
- Host выбирает surface, но никогда не выдаёт доступ к tenant data. Авторизация остаётся по session/membership/
  enrollment через существующие guards.

### 1.2a Раскладка адресов у клиники со своим доменом (владелец, 22.08.2026)

Дословно: «bersoncare.ru — лендинг приложения; app.bersoncare.ru — логин; app.bersoncare.ru/setup —
инструкция установки приложения, с которой ставится оно».

| Адрес | Что там | Чьё |
|---|---|---|
| `bersoncare.ru` | лендинг: описание приложения, ссылка «войти» | сайт клиники, вне нашей системы |
| `app.bersoncare.ru` | вход пациентов и кабинет | наш webapp, branded surface |
| `app.bersoncare.ru/setup` | инструкция установки, **отсюда ставится приложение** | наш webapp |

Следствия:

- Лендинг остаётся у клиники и нами не строится. Это же снимает вопрос владельца «у кого есть свой сайт —
  доп. лендинг не нужен»: мы отдаём только продукт, начиная с экрана входа.
- **Установка приложения получает свою страницу, а не кнопку где попало.** Отдельная страница-инструкция
  нужна потому, что установка PWA на iOS и Android делается по-разному и требует объяснения человеку;
  сегодняшний `PwaInstallSection` — заготовка под неё.
- Та же раскладка действует и для наших собственных адресов: `therapygo.ru` — вход пациентов,
  `therapygo.ru/setup` — установка; `therapysto.ru` — вход персонала и своя установка.
- **Инженерная деталь для этапа `B` (не owner-вопрос):** установленное приложение описывается манифестом с
  полями `scope` и `start_url`; сегодня это `/app` и `/app/patient`. Страница установки обязана попадать в
  этот `scope`, иначе браузер не предложит установку с неё. Поэтому `/setup` реализуется внутри области
  пациентского приложения, а не рядом с ней; конкретный путь выбирает исполнитель этапа `B`, `id`/`scope`
  уже установленных приложений при этом не меняются.

### 1.2b Что показывает корень адреса клиники (решение владельца 22.08.2026)

**Правило:** корень адреса клиники показывает её визитку, а визитка показывает **то, что заполнено**.
Отдельного «конструктора страниц» и выбора типа страницы не делается.

- заполнены описание, услуги, контакты → выглядит как визитка, внизу запись и вход в приложение;
- не заполнено ничего → остаётся имя клиники, кнопка записи и вход. Страница вырождается в экран входа
  сама, без настройки.
- **Один переключатель — «сразу вход, визитку не показывать»** — для клиник, у которых уже есть свой сайт и
  вторая визитка не нужна. Первый такой случай — сам владелец: `bersoncare.ru` его лендинг,
  `dmitryberson.ru` его личная визитка, значит `app.bersoncare.ru` показывает сразу вход.

**Это не новая работа.** Публичную страницу клиники с настройкой содержимого владелец заказал 19.08.2026
(«надо сделать публичную страницу для клиник уже — не записи а просто их визитку с описанием, и в кабинете
админа клиники настройку что на ней писать»); дизайн зафиксирован и часть исполнена — см.
`docs/_TODO/CLINIC_PUBLIC_PAGE_AND_URL_FLIP_2026-08-19.md`, маршрут `app/[clinicSlug]`, модуль
`modules/clinic-public-card`, встраиваемая запись `app/book/embed.js`. Настройка содержимого уже строится
там. Здесь добавляется ровно одно: **куда смотрит корень брендированного адреса**, плюс упомянутый флаг.

**Мировая практика, на которую опираемся:** платформа отдаёт ОДНУ страницу, а домен решает только адрес, но
не содержимое; различается не тип страницы, а то, сколько клиника заполнила. Jane App —
`clinicname.janeapp.com` одновременно визитка, запись и вход, у кого есть свой сайт — ставят ссылку или
встраивают форму. SimplePractice развёл то же самое в два продукта: «портал клиента» (вход и запись) и
отдельный опциональный «сайт практики», и практики со своим сайтом берут только портал. Booksy, Fresha,
Calendly — профиль и есть визитка с записью. Переключателя «визитка или вход» как настройки почти ни у кого
нет, поэтому и у нас это флаг для частного случая, а не режим страницы.

#### 1.2b-1 Клиника без купленного брендинга (решение владельца 23.08.2026)

**Правило: адрес клиники на нашем поддомене живёт ВСЕГДА, покупка влияет только на то, чьё имя на
странице.** `<slug>.therapygo.ru` у клиники, которая брендинг не покупала, отдаёт живую страницу с именем
клиники (`core.displayName`), кнопкой записи и входом — то есть ровно вырожденную визитку из §1.2b, с нашим
брендом платформы. `404` на хост означает только «такой клиники нет»: неизвестная метка, неактивная или
удалённая организация.

**Плашки «на Therapygo» с платным снятием НЕ делаем.** Владелец выбрал вариант 1 из трёх, названных
23.08.2026: (1) страница живёт, показывает имя арендатора и бренд платформы; (2) страница живёт, но с
плашкой платформы, снятие плашки — платное (модель Calendly); (3) дефолтное оформление платформы, брендинг
поверх. Плашка остаётся возможной надстройкой поверх варианта 1 на будущее — обратный порядок невозможен.

**Почему так:** ни один продукт этого класса не гасит валидный адрес арендатора из-за неоплаченного
оформления — это ломает запись к специалисту, то есть деньги самой клиники. SimplePractice держит
`<имя>.clientsecure.me` у всех тарифов, «своё» вынесено в отдельный продукт с отдельным доменом; Calendly
на бесплатном тарифе оставляет страницу полностью рабочей и монетизирует лишь СНЯТИЕ своего логотипа;
Jane, Cliniko, Fresha считают цвета и логотип косметикой поверх работающей страницы. Смешивать «не заплатил
за оформление» с «не существует» вредно втройне: пациент видит поломку вместо записи, поисковики выкидывают
адрес из индекса, а мы сами перестаём отличать опечатку от неоплаченного тарифа.

**Граница:** правило про НАШ поддомен. На своём домене клиники (§1.2, `B8`) `404` при ненастроенном бренде
остаётся верным — чужой домен без настройки на нас указывать и не должен.

**Расхождение с текущим кодом, требующее правки:** сегодня `<slug>.therapygo.ru` без опубликованного бренда
отдаёт `404` на весь хост (`{"status":404,"surface":null}`, измерено аудитом `B4` 23.08.2026 прогоном
настоящего `proxy`). Это против настоящего пункта.

### 1.2c Решения владельца 22.08.2026 (вечер): админ-поддомен, текст входа, passkey

**`admin/` — удалить.** Владелец: «это какая-то древняя древняя хуйня, нам это не надо». Каталог не входит в
`pnpm-workspace.yaml`, не собирается штатной сборкой, не деплоится, содержит заглушку и упоминает
несуществующий четвёртый домен `admin.bersonservices.ru`.

**Платформенный админ входит через свой поддомен `admin.therapysto.ru`.** Новое требование владельца, в
прежних редакциях плана его не было. Следствия, которые обязан учесть этап `B`: это ЧЕТВЁРТЫЙ хост (плюс
`therapysto.ru`, `therapygo.ru`, `<клиника>.therapygo.ru` и домены клиник), он входит в wildcard-сертификат
`*.therapysto.ru` или получает свой, и он же — ещё одна поверхность в резолвере и в матрице механик входа.
⚠️ Это НЕ то же самое, что `staff.therapysto.ru`/`patient.therapysto.ru`, запрещённые требованием `TPB-04`:
там запрещено дробить ОДНУ поверхность персонала на поддомены, а здесь отдельная поверхность —
платформенный админ, у которого другой круг людей и другие механики входа.

**Текст письма и SMS с кодом входа — чинится ОДИН раз на этапе `C`, а не сейчас** (закрывает `Q1`).
Владелец дословно: «когда мне надо чинить два раза наполовину, надо чинить один раз. Один раз и правильно.
Текст входа для персонала, для персонала клиник и для клиентов, вероятно, будет разный. И ещё он будет
зависеть от того, есть ли у клиники домен свой или нет».
То есть текст — функция от (поверхность × роль × наличие своего домена у клиники), и это ровно тот
механизм, который строит `C`. Подэтап `A5` НЕ заводится. До этапа `C` персонал продолжает получать письма
от «BersonCare» — осознанная временная плата, а не забытый дефект.

**Passkey — вопрос ПЕРЕОТКРЫТ владельцем и переходит из «исключено» в «спроектировать».** Дословно:
«мы решили, что мы не делаем passkey, потому что там какая-то херня с доменами… я просто сказал, наверное,
не трогать его. Я не знаю, как надо, я не знаю, как это даже работает, если честно. Но если у нас passkey
будет для Therapysto и персонал клиники захочет подключить passkey как второй фактор авторизации, то почему
нет? Я просто не знаю, как сделать, чтобы passkey было там и там, чтобы пациенты могли заходить».

### 1.2d Юридические документы: один комплект, принадлежит компании (владелец, 22.08.2026)

- **Владелец документов — юридическое лицо компании,** а не бренд поверхности и не клиника. Это совпадает с

### 1.2i Длина названия клиники — 100 знаков (владелец, 23.08.2026)

Владелец: «конечно же, сто знаков, конечно. Зачем больше?» — после разбора, откуда в коде взялись 200 и 120.

**Ни 200, ни 120 никто не решал**: `200` стоит в схеме регистрации
(`app/api/auth/specialist-signup/start/route.ts:46`), `120` — в проекции бренда
(`org-branding/service.ts:96`, `surface/requestSurface.ts:92,94`). Числа поставлены разными исполнителями на
глаз и в разное время; их расхождение и породило мёртвый адрес у клиники с длинным названием (аудит `B4a`).

**Решение: одно число — 100 знаков, и стоит оно НА ВВОДЕ**, в форме, где название печатают. Тогда обрезания
и расхождений дальше по дороге не возникает: что ввели, то и показываем. Ориентир — Google Business Profile
(100 знаков на имя организации); в CRM держат 255, но это ограничение поля хранения, а не продукта.

Границы решения:

- **это НЕ адрес.** Адрес (`<метка>.therapygo.ru`) — 3…30 знаков, §`B1a`, не путать;
- полное юридическое наименование («Общество с ограниченной ответственностью…») в это поле не кладём:
  ему место в реквизитах рядом с ИНН, там длину не режем;
- обрезание в проекции бренда после этого становится ненужным и должно быть снято, а не перенастроено:
  два числа вместо одного — та же ошибка в новой обёртке.

### 1.2h Что клиника обязана настроить сама (владелец, 23.08.2026)

Владелец разбирал сценарий подключения клиники и пришёл к выводу, что настраивать ей практически нечего;
запись фиксирует итог, чтобы `C5` не блокировал пустоту.

**На пути по умолчанию клиника не настраивает НИЧЕГО:**

- **адрес** — `<метка>.therapygo.ru` обслуживается нашей wildcard-записью; клиника не трогает DNS вообще,
  ждать нечего. Метку выбирает сама при регистрации (3–30 знаков, вне списка зарезервированных),
  переименование поддерживается историей переименований адреса;
- **почта** — отправлять от адреса клиники нельзя без её DNS-подписей, поэтому инфраструктура отправки наша,
  а имя отправителя совмещённое: имя клиники и имя платформы (`MailProfileRequest.kind = 'branded'` уже несёт
  `clinicName` и `platformName`);
- **бот** — по умолчанию наш, в тексте сообщения названа клиника-отправитель;
- **OAuth** — Яндекс не трогаем, per-org регистраций нет; Gmail не подключаем.

**Опции для тех, кто дорос** (обязанностью не являются): своя почта (свой SMTP плюс DNS-подписи на её стороне)
и свой бот. Включаются только после успешной живой отправки — гейт (б) пункта `C5`.

**Свой домен клиники** (`B8`, отложен): CNAME на нас, а не A-запись с IP — IP меняется при переезде сервера
и разом ломает всех; A-запись только для примитивных DNS без CNAME. Сертификат выпускаем мы.

**Второй фактор к домену не привязан.** К домену привязан только passkey. Код на почту и приложение-аутентификатор
доменов не знают, а персонал всегда живёт на `therapysto.ru` и никогда на домене клиники — менять RP-домен
второму фактору не от чего. У пациентов второго фактора нет.

**Поломка канала после включения адрес не гасит.** Сменили пароль, отключили бота — сигналим клинике и себе,
но адрес оставляем живым: погасить его больнее для пациентов, чем сама поломка.

### 1.2f Два имени — это два текста, а не две инфраструктуры (владелец, 23.08.2026)

Вопрос владельца: «зачем нам надо делать два имени, если Physitrack и Medbridge рассылают письма со своим
основным именем?»

Разведка показывает обратное на самом близком аналоге: **Physitrack как раз держит два имени.** Специалист
входит в Physitrack; в пациентском письме видимый отправитель — имя специалиста или practice name, а в теле
обязательно стоит `app_name` = **PhysiApp** либо имя Branded App. У Medbridge точный отправитель в открытых
источниках не проверен, так что он ничего не доказывает ни в одну сторону.

Существенное различие, которое снимает опасение про стоимость:

| Что | Сколько стоит | Решение |
| --- | --- | --- |
| Имя в тексте письма и в поле «от кого» | 0 ₽, это строка-параметр | Два: Therapysto персоналу, Therapygo пациентам |
| Почтовый домен с SPF/DKIM/DMARC | Настройка один раз | **Один** платформенный на всё |
| Буквенное имя SMS | 1 700–3 000 ₽/мес за имя у оператора | **Ноль**, SMS выключен (§1.2e) |

То есть «два имени» не означает второй почтовый домен, вторую репутацию или второй счёт. Therapysto остаётся
основным брендом компании; Therapygo — имя пациентского приложения, которое пациент видит в письме, потому что
именно его он ставит на телефон.

### 1.3 Поверхности и маршруты

- `therapysto.ru` обслуживает специалистов, администраторов клиник и свою marketing/login поверхность;
  `admin.therapysto.ru` обслуживает только платформенного администратора. Patient-only путь на обоих host
  переводится на канонический путь стандартного patient origin без переноса cookie.
- Стандартный patient origin обслуживает общий patient login/recovery/cabinet и существующие clinic card/booking
  по slug. Therapysto marketing home там не рендерится.
- Branded origin обслуживает то же patient tree. Корень показывает effective clinic/app brand, login/recovery,
  clinic card и ссылку/форму booking; slug клиники в URL не обязателен, потому что организация уже определена Host.
- Существующие clinic card/booking services переиспользуются; второго route tree с копиями UI и логики нет.
- Session cookie остаётся host-only. Cross-domain SSO не вводится. CSRF продолжает использовать request origin.
- Passkey НЕ удаляется. Он становится одной из переключаемых механик входа и по умолчанию выключен у докторов
  (§1.6). Уже написанный код сохраняется.
  Прежняя строка «Yandex OAuth на patient surfaces обязателен и не отключается» ОТМЕНЕНА решением владельца
  21.08.2026 (§1.6): на staff surface OAuth выключен по умолчанию, но переключаем; на patient surface действует
  одна global Yandex registration.
- Metadata, OpenGraph и manifest вычисляются через тот же resolved surface; отдельные manifest-файлы под бренды
  не создаются.
- **Какое приложение ставится «на экран телефона» — определяет ХОСТ (владелец, 22.08.2026, дословно):**
  «с therapysto.ru ставится приложение для персонала, с therapygo.ru — для пациентов». То есть манифест,
  имя, иконки и `start_url` устанавливаемого приложения выбирает та же резолюция поверхности по Host, что и
  всё остальное — отдельного правила и отдельного переключателя под установку не заводится.
  До переезда на два домена (`B`) один хост обслуживает обе поверхности, и выбор идёт по пути запроса.
  Промежуточное следствие, которое НЕ является дефектом: лендинг `/` — это staff-маркетинг («Therapysto —
  кабинет специалиста»), поэтому установка с него даёт приложение персонала. После переезда это же
  поведение будет получено уже хостом, и правило пути на корне станет ненужным.

### 1.4 OAuth: включён у пациентов, выключен у специалистов

**Действует под §1.6.** `OG-4` ЗАКРЫТ владельцем 22.08.2026: **Яндекс не трогаем**, он остаётся у пациентов как
есть — одна глобальная регистрация, отдельных регистраций на клинику не делаем. На staff/admin surface OAuth
выключен по умолчанию (`OG-5` (б)): механика и provider config остаются доступны для включения настройкой.

Несколько redirect URI у одного Yandex-приложения решают callback, но **не меняют имя/иконку consent**. Владелец
принял эту цену: обе patient-поверхности используют одну существующую global registration (`OG-4`, `W4`).

- На `staff` и `platform_admin` OAuth выключен значением матрицы по умолчанию, но остаётся переключаемой
  механикой согласно `OG-5`; тип поверхности не запрещает включить его без правки кода.
- Отдельных per-org регистраций и consent identity для клиник не создаём.
- Один OAuth-config resolver допускает global config только на поверхности, где Yandex включён; start и callback
  не имеют параллельных реализаций. Signed state связывает surface, normalized origin и organization id, а
  callback сверяет exact allowlist и снова резолвит surface.

### 1.5 Боты и transactional mail

- Все patient-facing intents, начатые на branded surface — login/contact confirmation, recovery/security codes и
  notifications — несут `organizationId` и `senderScope='clinic_required'` для Telegram/MAX. Platform bot fallback
  запрещён и уже обеспечивается существующим `dispatchPort`; задача — провести через него все эти intents.
- Branded activation требует настроенные Telegram/MAX credentials для каналов, которые UI предлагает пациенту.
  Неготовый канал не показывается; готовый не откатывается на platform sender.
- SMS остаётся отдельной tariff capability и в branding не включается.
- Existing `clinic_smtp_outbound` остаётся transport source. Один transactional-mail profile resolver соединяет
  его с `EffectivePatientBrand` и per-org template overrides.
- Template overrides хранятся в одном новом per-org `system_settings` key и допускаются только для реально
  существующих patient transactional template IDs и allowlisted variables. Используется один renderer;
  произвольный mass-mail editor/рассылки не строятся.

### 1.6 Политика входа по поверхностям (решение владельца 21.08.2026)

Владелец сверился с мировыми аналогами (Physitrack, Medbridge) и зафиксировал:

> «У них нет OAuth вообще для специалистов. Значит и у нас не будет — делаем как они. Для пациентов — оставим вход
> по имейл и по номеру телефона (с подтверждением через бота). Возможно оставлю Яндекс OAuth, но может и нет.»

- **Staff/admin (Therapysto): OAuth выключен** (`OG-5`, вариант (б), владелец 22.08.2026). Механика остаётся в
  списке админки и в коде, но у докторов её значение по умолчанию — «выключено»: ни OAuth-кнопки на входе, ни
  работающего provider config на этой поверхности, пока настройку не включат.
**Модель (владелец, 22.08.2026, дословно): «все механики включаются в админке — отдельно для докторов и отдельно
для пациентов».** То есть способ входа — это НЕ развилка в коде и не удаление кода, а значение настройки для
конкретной поверхности. Матрица «поверхность × механика» живёт в админке, у каждой ячейки есть значение
по умолчанию.

- **🔴 СКВОЗНОЕ ПРАВИЛО: механики не вырезаем, их выключают.** Владелец, 22.08.2026: «я же тебе сказал уже,
  механики не вырезаем, просто я выключу что не надо»; ранее — «я просто не хочу удалять то что уже сделано».
  Правило действует на ЛЮБУЮ механику входа и доставки, а не только на passkey: выключенная механика остаётся в
  коде и включается настройкой. Формулировки вида «удалить путь», «вырезать», «доказательство отсутствия» в этом
  плане запрещены — вместо них «выключено по умолчанию» и доказательство «выключено → недоступно, включено →
  работает».
- **Значения по умолчанию для докторов (владелец, 22.08.2026):** email + пароль включены; вторым фактором —
  код на email ИЛИ код 2FA из приложения (TOTP); владелец: «я думаю этого достаточно».
- **Passkey у докторов — выключён по умолчанию, но сохранён как опция.** Владелец: «мы этот passkey может и
  включим потом как 2FA или сам доктор так захочет, а мы дадим как опцию». То есть у него два возможных будущих
  режима — платформенный (включает админ) и личный (включает сам доктор себе). Реализация не обязана открывать
  оба сразу, но НЕ должна закрывать второй архитектурно.
- **PIN не нужен нигде** (владелец, 22.08.2026). Он вырезан целиком 04.08.2026 (`39ececd53`) — работы нет,
  только запрет заводить заново.
- **Patient (стандартное приложение и branded clinic): email и номер телефона** с подтверждением через бота.
- **Яндекс OAuth для пациентов — ОСТАЁТСЯ** (`OG-4` закрыт 22.08.2026: «не трогать яндекс, просто не паримся с
  именем которое они увидят»). Работает как сейчас, одной глобальной регистрацией; на consent-экране пациент
  увидит имя платформы, а не своей клиники — принято осознанно. Google OAuth остаётся выключенным (решение
  по #1035) — выключенным, не вырезанным.
- **Следствие, которое и есть работа:** поверхностей теперь две с РАЗНОЙ политикой входа, а в global admin сегодня
  один переключатель входа на всю платформу. Нужна политика входа per-surface: staff и patient настраиваются
  раздельно, OAuth у staff выключен значением по умолчанию и включается настройкой без правки типа или кода
  (`OG-5`, 22.08.2026).

Это правит §1.3 и §1.4 выше и добавляет `TPB-17…19` в §2.

### Решение владельца 22.08.2026: общий вход `/app` на одном хосте не решаем; работа не приземляется

  переезда: они гарантируют, что зона персонала не наследует пациентскую идентичность независимо от хоста.
  Это не временная подпорка под одно-хостовый случай.
- **Ведущий не сводит этапы в `feat`** — см. шапку файла. Этап `A` живёт на `wt/therapysto-stage-a-20260822`.
