## 5. Блокирующая находка

### `B-1` (блокер). Бренд, за который клиника заплатила, пропал из кабинета пациента — молча, без теста

**Что сделано.** `9a07bed69` вырезал из `apps/webapp/src/app/app/patient/layout.tsx` вызов
`withPatientOrganizationPrincipal(… resolveEffectiveOrgBranding(patientOrganizationId))` и заменил
его чтением уже разрешённой поверхности:

```ts
// apps/webapp/src/app/app/patient/layout.tsx:129-141
const resolvedPatientBrand =
  resolvedSurface.surface === 'patient_branded' &&
  resolvedSurface.organizationId === patientOrganizationId
    ? resolvedSurface.effectivePatientBrand
    : null;
… title: resolvedPatientBrand?.effectiveDisplayName ?? patientContext.organization.title,
```

**Почему это ломает живого человека.** `patient_branded` в проде недостижим: `proxy` подставляет
шов арендатора только когда второй аргумент — функция, а Next всегда передаёт туда `NextFetchEvent`,
то есть объект:

```ts
// apps/webapp/src/proxy.ts:33,42-45
const NO_TENANT_SURFACE: TenantSurfaceLookup = async () => ({ status: 'unknown' });
const resolveTenantSurface =
  typeof nextContextOrTenantLookup === 'function' ? (…) : NO_TENANT_SURFACE;
```

Шов арендатора — работа этапов `B1`/`B3`, и он ещё не написан (`B3` в плане не отмечен). Значит
`resolvedPatientBrand` теперь ВСЕГДА `null`, и заголовок контекста клиники у пациента всегда
показывает `patientContext.organization.title` — каноническое имя ядра, а не купленное имя бренда.

**Конкретные значения, а не рассуждение.** На живой `bcb_webapp_dev` такая строка существует ровно
одна:

```
org_brand_revisions: status=published, organization_id=a0000000-…-0001, display_name='Дмитрий Берсон'
be_organizations:    id=a0000000-…-0001, title='Точка Здоровья', is_active=t
```

До `9a07bed69` пациент, записанный в эту организацию, видел в шапке контекста «Дмитрий Берсон»
(`PatientOrganizationContext.tsx:182,190,192,202`). После — «Точка Здоровья». Это не гипотеза о
будущем, это сегодняшнее состояние DEV.

**Подтверждение со стороны прав.** Политика `rev10_org_brand_revision_select_129` и грант
`GRANT SELECT … TO app_patient` существуют ровно затем, чтобы пациент под своим принципалом читал
опубликованную ревизию своей клиники. После этого коммита в коде **не осталось ни одного
вызывающего**, который читает branding под пациентским принципалом:
`grep resolveEffectiveOrgBranding` даёт только `loadDoctorWorkspaceShell.ts:66` (персонал) и тесты.
Пациентская дверь стала мёртвой поверхностью прав.

**Чего в находке НЕТ.** Я не утверждаю, что консолидация неверна: `TPB-16` действительно требует не
плодить резолверы, и целевая модель §1.2 ставит пациента клиники на `<slug>.therapygo.ru`, то есть
на `patient_branded`. Утверждение узкое: **между этим коммитом и работающим швом арендатора платная
фича не работает, теста на это нет, и в отчёте авторов об этом ни слова.** Пункта «убрать
пациентский резолв бренда» в плане владельца нет — поэтому решение, чинить это в `B4` или явно
записать в план как принятую временную плату (как это сделано для писем «от BersonCare» в §1.2c),
принимает владелец/ведущий, а не я.

### `N-1` (вопрос владельцу). Брендированный адрес клиники без купленного бренда отдаёт 404, а не визитку

### `N-5`. Формат акцента на границе не защищён тестом — а это вектор CSS-инъекции

Инъекция `I-6`. Значение из санитайзера уходит в инлайновое кастомное свойство
`style={{ '--patient-brand-accent': … }}` (`app/layout.tsx:56`), которое затем подставляется в
`--patient-color-primary`. Кастомные свойства принимают почти произвольную последовательность
токенов, поэтому строка вида `#123456; background:url(https://…)` в этом месте — не косметика.
Сегодня её отбивают ещё два рубежа (CHECK базы и `normalizeAccentToken` сервиса), проверенные выше
живьём, так что находка про глубину обороны, а не про дыру. Отказ третьего рубежа тестом не
ловится.

### `N-6`. `normalizeAccentToken` на пути ЧТЕНИЯ бросает исключение

`service.ts:157` кидает `org_brand_accent_token_invalid`, и этот же нормализатор вызывается на
опубликованной ревизии при каждом резолве (`service.ts:242`). Одна строка с неправильным акцентом
кладёт весь резолв бренда в 500 вместо деградации к дефолту — при том что соседний
`normalizeDisplayNameOverride` в той же ситуации молча обрезает. Сегодня недостижимо: CHECK базы не
даёт такой строке появиться (проверено, п. 2.2). Оставляю как расхождение стиля отказа на пути
чтения.

### `N-7`. База принимает `patient_app_name` из одной табуляции

Живой замер: `btrim()` без второго аргумента снимает только пробелы, поэтому `E'\t'` проходит
`btrim(patient_app_name) <> ''`. Ровно то же верно для существующей
`org_brand_revisions_display_name_check` — это унаследованный шаблон, а не новая ошибка `B4`.
Видимых последствий нет: и сервис, и санитайзер зовут JS `.trim()`, который табуляцию снимает, и
значение схлопывается в `null` с обычным фолбэком.

### `N-8`. У анонимного читателя нет двери в базу, а у двух новых полей — ни одной записи

Два наблюдения о том, что `B4` заявленно и не должен был делать, но без них слайс не даёт
