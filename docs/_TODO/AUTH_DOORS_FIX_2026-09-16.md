## Порядок и состояние

- [ ] **Д1. Сотрудничьи двери задаются кодом.** Закрывает находки F1 (глобальный админ входит кодом
      на почту мимо 2FA) и F2 (пациентская телефонная дверь выдаёт сессию сотруднику без пароля).
      Ведётся отдельным планом — `docs/_TODO/STAFF_DOORS_HARDCODED_2026-09-16.md`, этапы С1…С6.
      Основание: решение владельца 16.09 + таблица дверей канона.
- [ ] **Д2. Мёртвая пара `messenger/start` + `messenger/poll` удаляется.** Находки U1 и D1:
      вызовов в исходниках нет (ведущий проверил сам — поиск по пути даёт только артефакты сборки
      `.next`), при этом `poll` умеет выдать сессию, а `start` раскрывает `user_not_found`. Живую
      привязку телефона к мессенджеру обслуживает `phone/messenger-bind`. Основание: слово владельца
      «лишнее» + принцип канона «вход стоит ровно столько, сколько самый слабый способ попасть
      внутрь».
- [ ] **Д3. Двери пароля перестают различать состояние учётки до проверки кода.** Находка F4:
      `email-password/forgot`, `setup-access` и `setup-code/complete` отвечают по-разному на
      неизвестный адрес, contact-only и учётку с паролем. Основание — прямая строка канона:
      существующий и несуществующий адрес не различаются ни текстом, ни кодом ответа.
- [ ] **Д4. Дубли-двойники сводятся к одной двери каждый.** Находки D2 (три проекции одного
      публичного конфига входа), D3 (`logout` отдельно GET и POST, GET меняет состояние), D5 (две
      двери запускают один и тот же password-setup challenge), D6 (два URL одного яндексовского
      callback). Основание: слово владельца «дубли». Для каждой пары в отчёте указать, какая дверь
      остаётся и кто переучен на неё.
- [ ] **Д5. `oauth/start` проверяет явно названную дверь, а не только Host.** Находка F5. Сюда же
      F6 — экран админки подсказывает несуществующий VK callback URL.
- [ ] **Д6. Contact-only пациенту не предлагается setup пароля, который завершение обязано
      отклонить.** Находка F7.
- [ ] **Д7. Две пациентские регистрации по почте, одна из которых всегда запрещена.** Находка D4:
      решить, какая остаётся, вторую снять.
- [ ] **⛔ Д8. Канонически снятые входы: deep-link обмен токена и Mini App.** Находка F3. Канон
      требует убрать обмен токена как класс и временно отключить мини-приложения целиком, но эта
      правка **режет живой вход той самой когорте, у которой нет почты** (замер 15.09: 91 человек
      приходит через мессенджер). Поэтому этап стоит ПОСЛЕ требования почты при входе (Э5) и
      начинается только по отдельному слову владельца. Сам по себе список «чинить всё» его не
      открывает: слишком дорогая цена ошибки в порядке действий.
- [ ] **Д9. Четыре вопроса аудита без строки канона** (Q1–Q4: удаление двух незваных config-адаптеров;
      привязка OAuth `state` к начавшему браузеру и одноразовость; нужен ли state-changing
      `GET /api/auth/logout`; двойное создание сессии при первом specialist signup). Инженерные
      решаю сам по мировой практике, продуктовые выношу владельцу одним листом, а не по одному.

## Границы для всех этапов

Пациентский вход не ломается: каждый этап обязан назвать, что именно продолжает работать как сейчас.
Прод и TEST не трогаются. Миграции из клона на DEV не накатываются — только откатываемый preflight.
Полный CI гоняется, только когда в `feat` приедет исполняемый код, а не markdown. Галочка этапа не
ставится, пока не пройден независимый адверсарный аудит другой моделью, чем автор.
