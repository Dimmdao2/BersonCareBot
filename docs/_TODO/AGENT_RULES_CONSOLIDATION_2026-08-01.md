# Консолидация правил агентов — единый компактный канон

## Проблема

Агенту одновременно предъявлены несколько текстов, каждый из которых называет себя каноном. Они расходятся по
запуску агентов, тестовому lock, audit/fix-циклу, push воркера, dev-серверу, лимитам и фактическим возможностям
`tools/orch-launch.sh`. Из-за этого агент тратит время на разрешение противоречий, может выбрать устаревшее правило и
не получает обязательные правила механически в своём brief.

## Действующие решения

- Владелец, 2026-08-01: «я хочу чтобы правила были логичными, реально полезными, компактными и удобными».
- Владелец, 2026-08-01: порт предпочтителен для репозиторной работы, потому что даёт гейты; прямой spawn допустим
  для простых advisory/read-only действий, которые не создают и не принимают репозиторный результат.
- Владелец, 2026-08-01: аудит сначала классифицирует пункт как проверку качества разового действия или проверку
  повторяемого поведения. Разовое действие проверяется взглядом, поиском или фактическим состоянием; тесты на
  отсутствие строк, кода и hardcode не создаются.
- Для повторяемого поведения действует слепое тестирование: отдельный `auditor-live` составляет kill-set по плану
  до чтения тестов, лично вносит поломки и проверяет существующую защиту. Повтор готового kill-set после исправления
  механический и не требует нового дорогого слепого аудита.
- Единственный нормативный текст для агента — `AGENTS.md`. Delivery-shims только маршрутизируют; runbook описывает
  команды; `runs/` и git хранят историю. Устаревшие и superseded редакции не остаются активными правилами.

## Scope

Разрешены изменения только в:

- `AGENTS.md`;
- `CLAUDE.md`;
- `.cursor/rules/**`;
- `docs/AGENT_AUTORUN_SCHEME.md`;
- `docs/ORCHESTRATION_BINDINGS.md`;
- `docs/ORCHESTRATOR_CHECKLIST.md`;
- `tools/orch-launch.sh` и узких проверках/скриптах, необходимых для синхронизации правил;
- `package.json`, только если нужен вызов механического rule-checker;
- этот план и краткий audit/run artifact в предусмотренном существующими правилами месте.

Вне scope: продуктовый код, схемы и миграции БД, deploy/runtime-конфигурация, taskdb schema, планы продуктовых
инициатив, архивные документы и переписывание истории решений.

## Чек-лист

- [ ] **AR-01 — Инвентаризация.** Составить карту всех активных нормативных утверждений и разрешить каждое
  расхождение явным действующим правилом; ни одно уникальное правило `AGENTS.md` §1–§24 не потеряно.
- [ ] **AR-02 — Единый канон.** `AGENTS.md` содержит действующие правила с устойчивыми секциями/ID и коротким
  routing по роли, действию и file-scope; в нём нет конкурирующих active-редакций одного требования.
- [ ] **AR-03 — Разделение слоёв.** `CLAUDE.md` и `.cursor/rules/*` являются delivery-shims без собственного
  нормативного поведения; orchestration docs являются ссылочным runbook/объяснением, а не вторым каноном.
- [ ] **AR-04 — Режимы агентов.** Прямой spawn разрешён только для advisory/read-only результата без acceptance;
  worker/fixer/acceptance-auditor и любое изменение репозитория запускаются через `tools/orch-launch.sh`.
- [ ] **AR-05 — Канон аудита.** Первый шаг — «тест или взгляд»; разовое действие проверяется фактическим осмотром,
  поведение — слепым kill-set до чтения тестов; audit не создаёт scope и не принимает собственный fix.
- [ ] **AR-06 — Тесты и CI.** Targeted-проверки запускаются напрямую; полный прогон приложения и полный CI идут
  через host-lock; stage/milestone/plan completion разведены, повтор успешного gate без изменения SHA запрещён.
- [ ] **AR-07 — Оркестрация и Git.** Устранены расхождения по веткам, push воркера, `land`, dev-серверу, лимитам,
  audit/fix-повтору и cleanup; machine-enforced значения не расходятся с нормативным текстом.
- [ ] **AR-08 — Механический drift-gate.** Узкая проверка ловит возврат второго нормативного источника, битые
  маршруты/ID и рассинхрон ключевых launcher-policy; она имеет собственный отрицательный self-check либо иное
  прямое доказательство, что реально падает на нарушении.
- [ ] **AR-09 — Независимый аудит.** Отдельный аудитор проверил сохранность уникальных правил, отсутствие новых
  противоречий, компактность routing и соответствие `orch-launch` активному канону.
- [ ] **AR-10 — Интеграция.** Targeted checks зелёные; изменения закоммичены с taskdb ID, слиты в
  `feat/doctor-ui-rebuild`, запушены; taskdb/план синхронизированы.

## Definition of Done

- Агенту достаточно открыть `AGENTS.md`, выбрать обязательные секции из routing и не разрешать конфликты между
  документами.
- Stateful-агент получает обязательные правила через launcher; advisory/read-only spawn имеет узкий явно
  ограниченный режим и не может считаться acceptance.
- Аудитор выбирает «тест или взгляд» до проверки; слепой протокол и его дешёвый replay сформулированы без
  противоречий.
- Устаревшие orchestration/test формулировки не подаются агенту как активный канон.
- Механический checker и независимый audit подтверждают результат.
