## Группы: одна причина — такие-то пункты — такая-то починка

### G-A. Уже починено 17.08, работы нет — L-2, L-3, L-5, L-6

Одно предложение: эти четыре отказа устранены коммитами `89f39b07c`, `105b42ea3`, `5f91faaa7`
от 17.08, а список владельца составлен до них.

Доказательство принадлежности: по каждому пункту я прошёл живой сценарий под ролью владельца
клиники и получил 200 + ожидаемое поведение экрана (см. таблицу); для L-3 дополнительно
`git log -S "Нет политики для выбранного уровня"` показывает, что строку удалил именно `89f39b07c`.

**Починка: не требуется.** Требуется только живая приёмка владельцем — эти четыре пункта закрываются
его кликом, не нашим отчётом.

### G-B. Кириллический `fieldKey` не проходит серверную схему — L-4 (один)

Одно предложение: клиент делает технический ключ поля из русского названия вопроса, оставляя в нём
кириллицу, а серверная zod-схема принимает только `^[a-z][a-z0-9_]*$` — значит любое поле, названное
по-русски, отбивается с 400, а названное латиницей создаётся.

Доказательство: `POST` с `fieldKey: "probe_diag_field"` (латиница) → **200**, поле создано; тот же
маршрут из UI с названием «Диагностическая проба L4» → `fieldKey: "диагностическая_проба_l4"` → **400
`invalid_body`**. Это единственный пункт с таким механизмом.

**Наименьшая честная починка — одно изменение в одном файле:** привести `slugFieldKey` к серверному
контракту (транслитерация кириллицы в латиницу + запасной ключ `field_N`, если после очистки пусто).
Править серверную регулярку не советую: `fieldKey` — технический идентификатор, латиница здесь
намеренная, и её ослабление потянет за собой публичную форму и экспорт.
Побочно: сегодня пользователь видит на экране голое `invalid_body` — это тоже стоит перевести в
человеческий текст, но это уже второй, отдельный вопрос.

### G-C. Отложенный триггер исполняется после `RESET ROLE` — L-7 (один)

Одно предложение: гарантия целостности slug-переименования оформлена отложенным constraint-триггером,
который срабатывает на `COMMIT`, а порт БД снимает роль **до** `COMMIT`, поэтому тело триггера
выполняется под login-ролью, у которой нет доступа к схеме `public`.

Доказательство: `where: PL/pgSQL function app.assert_organization_slug_rename_complete() line 15 at IF`
+ `permission denied for schema public` + `routine: aclcheck_error`; функция `prosecdef = false`
(SECURITY INVOKER), `proconfig = {search_path=pg_catalog}`, тело обращается к `public.*`;
`has_schema_privilege('bcb_dev_webapp_staff','public','USAGE') = false`, при
`has_schema_privilege('app_staff','public','USAGE') = true`; порядок `RESET ROLE` → `COMMIT` виден в
`packages/db-principal/dist/portContext.js:334-336`. Пункт в группе один.

**Наименьшая честная починка — одна миграция:** сделать оба guard-а
(`app.assert_organization_slug_rename_complete()`, `app.assert_organization_slug_alias_complete()`)
`SECURITY DEFINER` с владельцем, имеющим доступ к `public`, и с явным `search_path`. Это узкая правка
двух функций.
Два соблазна, которые я НЕ предлагаю: переносить `RESET ROLE` за `COMMIT` (трогает каждый порт
приложения разом) и выдавать login-ролям `USAGE` на `public` (снимает стену, ради которой её
поставили). Выбор между «одна миграция на две функции» и «переделать порядок в порту» — решение
владельца, потому что второе меняет общий контракт порта.
Оценка: одно изменение, но после него путь надо прогнать до конца — дальше по маршруту
`claimReservedSlug`/`renameSlug` есть ещё записи, которые ни разу не исполнялись.

### G-D. Роль `app_clinic_billing` без прав на запись — L-8 (один)

Одно предложение: биллинговый принципал владельца клиники умеет читать свои таблицы, но не имеет прав
записать ни строку аудита, ни счёт, поэтому обе кнопки тарифа падают на `42501`.

Доказательство: `permission denied for table admin_audit_log` при `INSERT` из
`pgSaasBilling.ts:762` и `permission denied for table saas_billing_invoices` при `INSERT` из
`pgSaasBilling.ts:58`, оба под `runWithDbClinicBillingPrincipal`;
`information_schema.column_privileges` для `app_clinic_billing`: `admin_audit_log` — **0** строк,
`saas_billing_invoices` — `INSERT` на 18 колонок из 24. Пункт в группе один; с G-C его роднит только
класс («запись владельца клиники отбита Postgres по 42501»), но механизм и починка разные.

**Наименьшая честная починка — одна миграция с грантами:** `app_clinic_billing` → `INSERT` на
нужные колонки `admin_audit_log` и на недостающие шесть колонок `saas_billing_invoices`.
Оценка: **скорее несколько итераций, чем одна.** Путь смены тарифа не исполнялся до конца ни разу —
за первым отказом почти наверняка стоят следующие записи (подписка, аккаунт, событие провайдера),
которые тоже упрутся в гранты. Честная оценка: одна миграция + прогон, и по итогам прогона, вероятно,
вторая.
Отдельно замечу инженерную деталь, а не вкусовщину: drizzle перечисляет в `INSERT` **все** колонки,
включая те, что отдаются `default`, а Postgres проверяет привилегию на **каждую названную** колонку.
Поэтому «колоночные гранты по факту записываемых полей» здесь структурно не работают — гранты надо
давать на весь набор колонок таблицы либо перестать перечислять `default`-колонки.

### G-E. Валидация календаря называет не те поля — L-9 (один)

Одно предложение: шесть разных незаполненных полей дают одно и то же сообщение, которое перечисляет
только три из них, — поэтому пользователь ищет отсутствующие «филиал, услугу и специалиста», хотя
не заполнено «Начало».

Доказательство: скриншот `L9-submit.png` — «Специалист», локация, услуга и длительность заполнены,
«Начало» пусто, под кнопкой «Заполните филиал, услугу и специалиста.». Пункт в группе один.

**Не баг ли это, а незавершённая фича?** Нет. Селекторы услуги и специалиста на форме **есть**
(их вернул `89f39b07c`), продуктовое решение не требуется. Осталась ровно ошибка сообщения.

**Наименьшая честная починка — одно изменение в одном файле:** расщепить условие на конкретные
сообщения («Выберите дату и время», «Выберите услугу», …) в
`DoctorCalendarEventPanel.tsx:444-452`.
