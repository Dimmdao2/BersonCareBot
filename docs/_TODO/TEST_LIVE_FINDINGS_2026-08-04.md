## 1. «Что-то пошло не так» / `Failed to load chunk … 404` — ПОДТВЕРЖДЕНО (а), почищено

**Причина, доказанная проверкой:** `journalctl -u bersoncarebot-webapp-test.service` показывает рестарт
TEST-деплоя **01:24:36–01:24:57 MSK** — через 2-3 минуты после того, как владелец открыл страницу
(01:22). Каталог текущей сборки на диске — `.next/static/_L-zPn0hn7jhJB_fmZ-kT`; чанка
`05s6q8mdxeter.js` из ошибки в нём нет вообще — это чанк ПРЕДЫДУЩЕЙ сборки. Вкладка была открыта до
деплоя, после рестарта её JS-бандл стал ссылаться на уже не существующие файлы. `/api/health` в это
время отвечал `{"ok":true}` — сам сервис был жив, ловушка чисто клиентская (стейл-вкладка через деплой).
Это случай **(а)** из брифа, не потеря чанков при выкладке.

**Реальный баг, который это вскрыло:** обработчик ошибок сегмента (`SegmentRouteError`, общий для
patient/doctor, это то, что видит пользователь на `/app/account` — она не под `doctor/`, значит грузится
через `app/app/error.tsx` → patient-вариант) уже умел молча перезагружать страницу при протухшем server
action (`isStaleServerActionError`), но **не** делал этого при ошибке загрузки чанка — просто показывал
«Что-то пошло не так» с кнопкой «Попробовать снова» (`reset()`), которая чанк не чинит. У корневого
`global-error.tsx` детектор `isChunkLoadFailure` уже был, но тоже не вызывал автоперезагрузку сам — только
переименовывал кнопку.

**Починено:** вынес детектор в `shared/lib/isChunkLoadFailure.ts` (было продублировано только в
`global-error.tsx`), завёл причину `'chunk-load-error'` в уже существующем гвардированном
`safeReload()` (cooldown/max-count/deny-list/busy-input уже есть — защита от цикла бесплатная) и подключил
его в обоих местах:

- `apps/webapp/src/app/global-error.tsx` — авто-`safeReload('chunk-load-error')` при монтировании;
- `apps/webapp/src/shared/ui/patient/SegmentRouteError.tsx` и
  `apps/webapp/src/shared/ui/doctor/SegmentRouteError.tsx` — то же самое плюс кнопка теперь тоже
  зовёт `safeReload`, а не бесполезный `reset()`.

Итог: при повторе того же сценария (стейл-вкладка пережила деплой) пользователь один раз тихо
перезагрузится на новую сборку вместо экрана «Что-то пошло не так». Если билд действительно сломан
(случай б) — `safeReload` откажется после `RELOAD_MAX_COUNT=3` попыток за 10 минут, и экран ошибки
всё равно покажется, ничего не зацикливается.

## 3. Пункты меню без иконок — БАГ, починено

Меню строится в `DoctorMenuAccordion.tsx`, функция `getIconForMenuId(id)` — свитч id → иконка
`lucide-react`. Для трёх id платформенного меню (`platformNavLinks.ts`) свитч-кейса не было вообще:
`account-security` (Безопасность аккаунта), `clinics` (Клиники), `payments` (Платежи) — отсюда пустое
место вместо иконки, все остальные пункты меню (Аналитика, Тарифы и триал, Настройки приложения,
Авторизация, …) свою иконку имеют.

**Починено:** добавил три `case` в тот же свитч, тем же источником (`lucide-react`, уже используется в
файле, новых зависимостей нет):

- `account-security` → `Shield`;
- `clinics` → `Building2`;
- `payments` → `Wallet` (не `CreditCard` — та уже занята пунктом «Тарифы и триал», чтобы не было двух
  одинаковых иконок в одном меню).

## 4. Экран «Клиники» без данных — ВОПРОС, ответ ниже; починки не делал

**Что должно показывать.** `/app/admin/clinics` (`ClinicsConsoleClient.tsx`) — готовый, не заглушка:
список клиник платформы (название, тариф, статус жизненного цикла, пробный период), клик → карточка
клиники (аккаунты, переопределения тарифа, расход по лимитам, биллинг). Источник —
`GET /api/admin/organizations` → `platformEntitlements.listOrganizations()` → таблица `be_organizations`.

**Есть ли данные на TEST.** Проверено напрямую в БД (`sudo -u postgres psql -d bersoncarebot_test -c
"SELECT count(*) FROM public.be_organizations"`) → **2 строки**: «Точка Здоровья» (создана 2026-05-30) и
«Тест Клиника» (создана 2026-07-25). Данные есть, не ноль.

**Реализован ли запрос.** Да, полностью: RLS-политика `be_organizations_platform_operations_select`

ограничения по клинике — то есть по замыслу список должен быть не пуст. Путь простановки этой роли
(`requirePlatformOperationsPage` / `requirePlatformOperationsApiContext` →

`requireRole.ts` и `isPlatformUserUuid.ts`) после похожего класса бага именно на TEST.

выключен намеренно, `ALLOW_DEV_AUTH_BYPASS=false` — см. `SERVER CONVENTIONS.md`), поэтому кликнуть по
экрану под настоящей сессией владельца я не могу. Код и данные проверены и выглядят корректно; живого
воспроизведения «пусто» у меня нет.
