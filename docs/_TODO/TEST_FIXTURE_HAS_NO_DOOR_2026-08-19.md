# Фикстуру на две клиники нечем запустить на TEST

Найдено 19.08.2026. Работа ОСТАНОВЛЕНА по правилу владельца: «пошел на 4 круг одной проблемы — то
все. Стоп и снимай тик».

## Что нужно было

Сделать TEST по-настоящему многоарендным: тест изоляции арендатора отказывается доказывать что-либо
на одной клинике («ДОКАЗЫВАТЬ НЕЧЕГО»), а на `bersoncarebot_test` организация ровно одна —
«Точка Здоровья», один сотрудник, 259 зачислений.

## Что нашлось

Сочинять данные не требуется: `apps/webapp/scripts/seed-saas-test-walkthrough-fixtures.ts` уже
описывает ДВЕ синтетические клиники — A (3 сотрудника, 5 пациентов) и B (1 сотрудник, 3 пациента),
с записями, абонементами, программами и прогрессом. Идемпотентная, с собственным доказательством
сходимости при двойном прогоне.

На TEST она **никогда не запускалась**, и в `deploy/host/deploy-test.sh` её вызова нет вовсе.

## Почему её нельзя запустить — точная причина, доказано

Инструмент состоит из двух половин, и они предполагают РАЗНЫХ запускающих.

**Половина «база».** Скрипту нужен `DATABASE_URL`. Все роли, достижимые по URL
(`bcb_test_webapp_staff`, `..._patient`, `..._global_admin`, `bcb_test_integrator`), сидят за mTLS
и за FORCE RLS — сырые записи drizzle им запрещены. Роли, которые писать МОГУТ
(`bcb_test_migrator`, `app_object_owner`), объявлены `NOLOGIN`; штатная выкатка ходит под ними
через `sudo -n -u postgres psql` + `SET ROLE`, то есть **по сокету из-под OS-пользователя
`postgres`**. Это я прошёл: сеятель успешно стартует от `postgres`.

**Половина «пакет».** `saas-test-fixture-packet.mjs` требует, чтобы файл настроек был
`root:deploy`, режим `0640` — и проверяет это, отказываясь читать что-либо иное. То есть
запускающий обязан состоять в группе `deploy`. Замерено: `getent group deploy` → `deploy,storylama`.
Пользователя `postgres` там нет и по смыслу быть не должно.

Итог — дословная ошибка на живом прогоне из-под `postgres`:

    EACCES: permission denied, open '/etc/bersoncarebot/saas-test-fixture.env'
      at readSaasTestFixturePacket (deploy/host/saas-test-fixture-packet.mjs:86)

Согласованного запускающего не существует: кто читает пакет — не может писать в базу; кто пишет в
базу — не может читать пакет. Свести их можно только добавив `postgres` в группу `deploy`, то есть
раздав пользователю базы доступ ко всем секретам выкатки. Это правка прав ради удобства
инструмента, поэтому я её не делаю.

Дополнительно: скрипт по цепочке импортов тянет `src/config/env.ts` приложения и требует
`SESSION_COOKIE_SECRET` и секрет интегратора, которыми сам НЕ пользуется — то есть инструмент
провижининга привязан к рантайм-конфигу приложения. Это обходится подстановкой значений из
`webapp.test`, но само по себе неправильно.

**В `AGENTS.md` про фикстуры и сеятель нет ни слова** — штатной двери не описано.

## Что уже подготовлено и лежит на месте

`/opt/env/bersoncarebot/saas-test-fixture.env` — пакет по контракту `saas-test-fixture-packet.mjs`
(root:deploy, 0640, `SAAS_TEST_FIXTURE_ENABLED=1`). Значения credentials намеренно не записываются в git;
packet валиден и ждёт запуска.

## Развилка для владельца — три варианта, выбирать ему

1. **Отвязать сеятель от рантайм-конфига** (убрать импорт `env.ts` из цепочки) и вызывать его из
   `deploy-test.sh` тем же способом, каким выкатка ходит в базу — `sudo -u postgres` + `SET ROLE`
   на роль, у которой права уже есть. Ничего нового не заводится. Похоже на правильный ответ, но
   это правка инструмента, а не данных.
2. Оставить сеятель как есть и дать ему логин-роль с нужными правами — но БЕЗ `BYPASSRLS` и с
   явным сроком. Это заведение новой учётной записи, поэтому решение владельца.
3. Ничего не запускать; тогда тест изоляции на TEST остаётся вечно красным «доказывать нечего»,
   и его вызов в `deploy-test.sh` придётся снять.

## НЕ СДЕЛАНО

- Вторая клиника на TEST не заведена. Тест изоляции на TEST по-прежнему доказать ничего не может.

# Продолжение 19.08, после разрешения владельца на временного суперюзера

Владелец: «Дай ты сеятелю права postgres на момент выкатки, создай суперюзера — потом сразу удали».
Сделано ровно так: роль `bcb_test_seed_tmp` создаётся, используется, удаляется в том же прогоне;
после каждого запуска проверено `SELECT count(*) FROM pg_roles` → 0. Права перестали быть преградой.

За ними открылось ЧЕТЫРЕ разных дефекта. Первые три починены, четвёртый — развилка.

## 1. На TEST нельзя было создать ни одной клиники — ПОЧИНЕНО

`public.reference_catalog_baselines` пуста, а триггер `be_organizations_reference_catalog_snapshot`
берёт последнюю строку через `SELECT ... INTO STRICT`. Нет строки — вставка организации падает
с `P0002 query returned no rows`. Это ломало не фикстуру, а **живую регистрацию новой клиники**.

На dev строки есть (версии 1 и 2, 8 и 9 разделов), но ни одна миграция их не создаёт — внесли
руками. Содержимое зафиксировано в миграции `0034`; на TEST применено, теперь строк 2.

**УСТАРЕЛО/ЗАМЕНЕНО 2026-08-21:** это было верно до B0-перехода. Историческая `0034` действительно
исправляла тогдашний TEST, но owner decision 20.08 вывел весь `0000`–`0049` chain из активного
контура; после reset её DML больше не доезжает. На 21.08 прямой count на именованном TEST снова дал
`0` строк в `public.reference_catalog_baselines` (DEV: `2`), а точная fixture упала с `P0002 query
returned no rows` в `app.seed_reference_catalog_snapshot(uuid)`. Новый B0-forward repair —
`20260821T025935_restore_reference_catalog_baselines.sql`: он идемпотентно возвращает глобальные
версии 1 и 2. До его первого sanctioned deploy reviewed TEST fixture door под временной ролью
reconciles тот же canonical asset, не применяя и не записывая migration ledger.

## 2. Миграция без отметки класса — ПОЧИНЕНО

`0034` не несла `BCB-MIGRATION-OWNER`/`BCB-MIGRATION-BACKFILL`, и парсер миграций отказывал.
Добавлена `BCB-MIGRATION-BACKFILL`; `migrate-local-parse.test.mjs` снова зелёный.

## 3. Фикстура отстала от схемы — ПОЧИНЕНО

Публичный каталог клиник защищён триггером `app.guard_clinic_directory_current_slug`: адрес
клиники обязан быть её действующей заявкой в `organization_slug_claims`. Фикстура заявку не
писала вовсе — её написали позже триггера. Добавлено; цель конфликта повторяет частичный
уникальный индекс (`targetWhere`, а не `setWhere`).

## 4. РАЗВИЛКА ЗАКРЫТА ВЛАДЕЛЬЦЕМ 19.08: таблицу удалить целиком

нельзя записать НИ ОДНОЙ строки, кроме как от системы, которой больше нет. Фикстура пишет
`saas_test_fixture` и получает `23514`.

**Решение владельца 19.08, дословно:** «так эту таблицу надо просто удалить, у нас не будт записей

# Что осталось после удаления таблицы (19.08, ветка `wt/drop-external-mappings-20260819`)

Блокер §4 снят: `23514` больше физически невозможен, таблицы нет. Но **сеятель на DEV прогнать
нельзя по его собственному предохранителю**, а не по правам:

    seed-saas-test-walkthrough-fixtures.ts:623  assertRequiredDatabaseName()
    → refusing_database_target:expected_bersoncarebot_test

Предохранитель точный и намеренный: синтетические клиники пишутся ТОЛЬКО в `bersoncarebot_test`.
Ослаблять его ради проверки я не стал — это ровно тот класс правки «поменять предохранитель под
удобство инструмента», из-за которого этот документ и появился. Поэтому сходимость сеятеля на TEST
остаётся за ведущим, а на DEV проверено то, что проверить можно без обхода предохранителя:
перевыраженный запрос-доказательство исполнен на живой `bcb_webapp_dev` в READ ONLY-транзакции и
считает те же две величины на реальных доступностях.
