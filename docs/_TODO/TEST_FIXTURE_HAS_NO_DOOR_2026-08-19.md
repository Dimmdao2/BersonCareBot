# Фикстуру на две клиники нечем запустить на TEST

Найдено 19.08.2026. Работа ОСТАНОВЛЕНА по правилу владельца: «пошел на 4 круг одной проблемы — то
все. Стоп и снимай тик».

## Что нужно было

Сделать TEST по-настоящему многоарендным: тест изоляции арендатора отказывается доказывать что-либо
на одной клинике («ДОКАЗЫВАТЬ НЕЧЕГО»), а на `bersoncarebot_test` организация ровно одна —
«Точка Здоровья», один сотрудник, 259 зачислений.

## Что нашлось

Сочинять данные не требуется: `apps/webapp/scripts/seed-saas-test-walkthrough-fixtures.ts` уже
описывает ДВЕ синтетические клиники — A (3 сотрудника, 5 пациентов) и B (1 сотрудник, 3 пациента),
с записями, абонементами, программами и прогрессом. Идемпотентная, с собственным доказательством
сходимости при двойном прогоне.

На TEST она **никогда не запускалась**, и в `deploy/host/deploy-test.sh` её вызова нет вовсе.

## Почему её нельзя запустить — точная причина, доказано

Инструмент состоит из двух половин, и они предполагают РАЗНЫХ запускающих.

**Половина «база».** Скрипту нужен `DATABASE_URL`. Все роли, достижимые по URL
(`bcb_test_webapp_staff`, `..._patient`, `..._global_admin`, `bcb_test_integrator`), сидят за mTLS
и за FORCE RLS — сырые записи drizzle им запрещены. Роли, которые писать МОГУТ
(`bcb_test_migrator`, `app_object_owner`), объявлены `NOLOGIN`; штатная выкатка ходит под ними
через `sudo -n -u postgres psql` + `SET ROLE`, то есть **по сокету из-под OS-пользователя
`postgres`**. Это я прошёл: сеятель успешно стартует от `postgres`.

**Половина «пакет».** `saas-test-fixture-packet.mjs` требует, чтобы файл настроек был
`root:deploy`, режим `0640` — и проверяет это, отказываясь читать что-либо иное. То есть
запускающий обязан состоять в группе `deploy`. Замерено: `getent group deploy` → `deploy,storylama`.
Пользователя `postgres` там нет и по смыслу быть не должно.

Итог — дословная ошибка на живом прогоне из-под `postgres`:

    EACCES: permission denied, open '/etc/bersoncarebot/saas-test-fixture.env'
      at readSaasTestFixturePacket (deploy/host/saas-test-fixture-packet.mjs:86)

Согласованного запускающего не существует: кто читает пакет — не может писать в базу; кто пишет в
базу — не может читать пакет. Свести их можно только добавив `postgres` в группу `deploy`, то есть
раздав пользователю базы доступ ко всем секретам выкатки. Это правка прав ради удобства
инструмента, поэтому я её не делаю.

Дополнительно: скрипт по цепочке импортов тянет `src/config/env.ts` приложения и требует
`SESSION_COOKIE_SECRET` и секрет интегратора, которыми сам НЕ пользуется — то есть инструмент
провижининга привязан к рантайм-конфигу приложения. Это обходится подстановкой значений из
`webapp.test`, но само по себе неправильно.

**В `AGENTS.md` про фикстуры и сеятель нет ни слова** — штатной двери не описано.

## Что уже подготовлено и лежит на месте

`/etc/bersoncarebot/saas-test-fixture.env` — пакет по контракту `saas-test-fixture-packet.mjs`
(root:deploy, 0640, `SAAS_TEST_FIXTURE_ENABLED=1`, синтетические почты
`clinic-a@saas-test.bersoncare.ru` / `clinic-b@…`, пароль `123456testTEST`). Валиден, ждёт запуска.

## Развилка для владельца — три варианта, выбирать ему

1. **Отвязать сеятель от рантайм-конфига** (убрать импорт `env.ts` из цепочки) и вызывать его из
   `deploy-test.sh` тем же способом, каким выкатка ходит в базу — `sudo -u postgres` + `SET ROLE`
   на роль, у которой права уже есть. Ничего нового не заводится. Похоже на правильный ответ, но
   это правка инструмента, а не данных.
2. Оставить сеятель как есть и дать ему логин-роль с нужными правами — но БЕЗ `BYPASSRLS` и с
   явным сроком. Это заведение новой учётной записи, поэтому решение владельца.
3. Ничего не запускать; тогда тест изоляции на TEST остаётся вечно красным «доказывать нечего»,
   и его вызов в `deploy-test.sh` придётся снять.

## НЕ СДЕЛАНО

- Вторая клиника на TEST не заведена. Тест изоляции на TEST по-прежнему доказать ничего не может.
