# Post-production: мягкое удаление файлов и отложенная физическая очистка

**Статус:** TODO после запуска production. Не является gate текущей работы по инфраструктуре, DEV или TEST.

**Owner decision 17.08.2026, дословно по смыслу:** «удаление сделаем мягким, сначала помечается строка и чистятся
ссылки, потом через сутки воркер чистит файл если он нигде больше не используется. Но это ПОТОМ… это будем делать
когда прод уже заработает».

## 1. Как сделано сегодня

Удаление жёсткое и немедленное: сначала удаляется объект в S3, затем каноническая строка, и строка сохраняется,
если объект удалить не удалось (`502`, объект уходит в общую очередь повторной очистки) —
[`route.ts:72-77`](../../apps/webapp/src/app/api/doctor/patients/[userId]/files/[fileId]/route.ts).
Единственная защита от случайности — проверка использования: если файл участвует в программе, приходит `409
media_in_use`, и удаление требует явного `confirmUsed=true`.

Окна восстановления нет. Версионирование на рабочем бакете выключено решением владельца 17.08
([`INFRASTRUCTURE_SECURITY_PLAN.md`](INFRASTRUCTURE_SECURITY_PLAN.md), `IS-I2-08`), поэтому иного пути отката,
кроме независимой копии, сегодня не существует.

## 2. Зачем это меняется

- «Врач удалил намеренно» и «мы потеряли из-за бага, миграции или промаха в правах» снаружи неразличимы. Первое —
  ответственность врача, второе — наша, и сейчас у нас нет способа показать разницу.
- Срок хранения медицинской документации не находится в распоряжении врача: его удаление не снимает обязанность
  с оператора.
- Мягкое удаление даёт обратимость нашей собственной ошибки, не меняя ничего для врача: из интерфейса файл
  исчезает мгновенно.

## 3. Целевое поведение

1. Удаление помечает строку и снимает ссылки на файл во всех местах, где он используется. Для врача файл исчез.
2. Через **24 часа** фоновый воркер физически удаляет объект — но только если файл не используется больше нигде.
3. Проверка «нигде не используется» выполняется на момент физического удаления, а не на момент пометки: за сутки
   связи могли измениться.

## 4. Что предстоит решить при исполнении

- **Квота клиники.** Байты освобождаются в момент физической очистки, а не пометки — иначе появляется способ
  бесконечно перезаписывать файлы, не выходя за лимит. Механика квоты — `files`, единица «байты»,
  [`org-entitlements/types.ts:62`](../../apps/webapp/src/modules/org-entitlements/types.ts).
- **Окно восстановления равно суткам.** Это строже обещания «удалённое исчезает отовсюду максимум за 30 дней»,
  конфликта нет. Но следствие: восстановление после нашей собственной ошибки возможно только в течение суток,
  дальше остаётся независимая копия.
- **Отказ физического удаления** не должен молча оставлять помеченную строку навсегда: нужен предел попыток и
  видимый сигнал, иначе появятся вечные полуудалённые записи.
- **Существующая очередь повторной очистки** (`storage_delete_failed` path) и новый воркер — это один механизм,
  а не два параллельных.
- Взаимодействие с 409 `media_in_use`: подтверждение врача остаётся, но теперь оно не приводит к необратимому
  действию, и текст предупреждения стоит пересмотреть.
