В таблице «включён» означает фактическую возможность получить сессию на штатной двери роли. «Существует, но нет» означает, что код/route физически есть, однако policy либо последующий role/surface gate не дают штатного входа. ### 2.3. Где решается роль, где поверхность

- Роль сессии — поле canonical `platform_users` в загруженном `SessionUser` со значениями `client | doctor | admin`. Login-time env resolver теперь всегда возвращает `client`, поэтому staff-role приходит из БД, кроме отдельного pinned-owner email exception. `apps/webapp/src/shared/types/session.ts:1-1`, `apps/webapp/src/modules/auth/envRole.ts:5-25`, `apps/webapp/src/modules/auth/envRole.ts:64-79`
- Администратор клиники не отдельная auth-role: после сессии `doctor` membership `owner/admin` даёт `organization.management`; global `admin` получает только `platform.operations` и `account.self`. `apps/webapp/src/app-layer/guards/workspaceCapabilities.ts:31-77`
- Поверхность решает единственный Host resolver: `staff`, `platform_admin`, `patient_default`, `patient_branded`; неизвестный/двусмысленный Host и неполный tenant result дают `null`. `apps/webapp/src/shared/lib/surface/requestSurface.ts:27-27`, `apps/webapp/src/shared/lib/surface/requestSurface.ts:294-390`

## 3. Простота и чистота фактической схемы

### 3.1. Что устроено чисто

- Host → surface имеет одну функцию, один сериализованный proxy-header и fail-closed parsing; downstream не резолвит Host заново. `apps/webapp/src/shared/lib/surface/requestSurface.ts:294-310`, `apps/webapp/src/shared/lib/surface/requestSurface.ts:426-496`, `apps/webapp/src/proxy.ts:381-398`

### 3.2. Дублирование дверей и правил

1. **Главный расходящийся дубль — общий и прямой session-mint paths.** Обычные password/email/passkey/OAuth/invite flows зовут `setSessionFromUser`, где есть единый role-vs-surface gate; exchange, Telegram initData, MAX initData и Telegram Widget зовут `persistNewAuthSession` напрямую. ### 3.5. Fail-open

1. **Clinic-required 2FA fail-open:** отсутствие membership port или любой `membership.ok === false` возвращает `false`, то есть password login продолжается без обязательного email-factor. Ошибка/отказ resolver неотличимы от «клиника не требует фактор». `apps/webapp/src/app/api/auth/email-password/login/route.ts:65-85`, `apps/webapp/src/app/api/auth/email-password/login/route.ts:270-317`
2. **Null channel в signed token fail-open относительно auth-toggle:** route проверяет toggle только при `verifiedChannel !== null`; валидный bare UUID token классифицируется как `null`, затем загружает canonical DB user и создаёт сессию. `apps/webapp/src/app/api/auth/exchange/route.ts:54-60`, `apps/webapp/src/modules/auth/service.ts:430-438`, `apps/webapp/src/modules/auth/service.ts:641-693`
3. **Principal stamping fail-open на уровне authentication:** `finalizeCurrentSession` глотает исключение resolver и возвращает сессию; комментарий обещает, что закрытые DB ports затем fail-closed, но сам факт аутентификации сохраняется. `apps/webapp/src/modules/auth/service.ts:129-146`
4. **Не fail-open:** неизвестный/двусмысленный Host, повреждённый surface-header, неизвестный tenant, disabled/unconfigured OAuth и неразрешённый auth channel заканчиваются `null`/404/false. `apps/webapp/src/shared/lib/surface/requestSurface.ts:308-366`, `apps/webapp/src/shared/lib/surface/requestSurface.ts:426-496`, `apps/webapp/src/proxy.ts:228-257`, `apps/webapp/src/modules/auth/authChannelPolicy.ts:23-45`, `apps/webapp/src/modules/auth/authChannelPolicy.ts:139-149`
