**Дата:** 2026-08-07 / 08. **База замеров:** живая TEST `bersoncarebot_test`.
**Правило этого документа:** сюда попадает только то, что доказано командой или живой пробой.
Каждый пункт несёт способ перепроверки. Неподтверждённое вынесено в отдельный раздел в конце и

## Часть 1. Что случилось

За 07.08 в логах TEST найдено 10 дефектов одного класса. Механизм у всех один: запрос обращается к
объекту, на который у его роли нет прав → Postgres отвечает `42501`/`42P01` → вызывающий код ловит
ошибку и подставляет значение по умолчанию → ничего не логируется, ничего не падает.

Ущерб, каждый пункт проверен отдельно:

| Что не работало | Проверка |
|---|---|
| врач, пишущий боту в Telegram/MAX, **не распознавался как сотрудник** | `doctor_telegram_ids` = `["364943522"]` в БД, чтение падало 42501 |
| у двух клиник **молча отключён Google Calendar** | `google_refresh_token` есть у 2 организаций, конфиг читался как пустой |
| клиники с оплаченным брендированием **слали от имени платформы** | чтение `clinic_*` кредов падало, resolver возвращал null |
| **критические алерты оператору не уходили** | `reportOperatorFailure` выходил до отправки |
| вход пациента по телефону — **500** | `permission denied for table user_channel_preferences` |
| тик планировщика падал **17 246 раз в сутки** | `journalctl -u bersoncarebot-scheduler-test \| grep -c "Runtime scheduler tick failed"` |
| админская настройка политики телефона игнорировалась | в БД `public_only`, рантайм жил на `public_then_contacts` |

Второй, более опасный класс, найденный проходом 04.08: **тихий ноль** — RLS возвращает 0 строк для
существующих данных, ошибки нет вообще.

## Часть 4. Опровергнутые гипотезы

Только то, что опровергнуто исполнением. Каждая — с воспроизводимой пробой.

### 4.1. «`EXPLAIN` под ролью доказывает, что запрос разрешён» — ОПРОВЕРГНУТО

Планировщик не доходит до исполнения. Опровергнуто **семью** способами:

| № | Проба | `EXPLAIN` | Реальность |
|---|---|---|---|
| 1 | `INSERT INTO be_organizations(id,title)` под `app_staff` | зелёный план | `ERROR: new row violates row-level security policy` |
| 2 | таблица с `INSERT`, но без `USAGE` на sequence | зелёный | `permission denied for sequence` |
| 3 | таблица с триггером, пишущим в закрытую таблицу | зелёный | `permission denied for table trigger_sink` |
| 4 | `SELECT app.fn()`, где владелец не имеет прав внутри тела | зелёный | `permission denied for table` внутри функции |
| 5 | `SELECT` из `system_settings` под `app_staff` без принципала | зелёный | **0 строк** вместо данных |
| 6 | представление, исполняемое от владельца | — | видно **больше**, чем роли положено |
| 7 | `CALL` процедуры и `SET ROLE` | `42601 syntax error` | не проверяемы вовсе |

Дополнительно: `ALTER TABLE ADD COLUMN secret` → существующий **неизменённый** `SELECT *`
начинает возвращать новую колонку. Диффа кода нет, значит ни один гейт по коду это не увидит.

**Что `EXPLAIN` всё-таки ловит** (проверено, сильнее ожидаемого): отсутствие права на таблицу,
колоночные права, отсутствие `EXECUTE` на функции, неквалифицированные имена мимо `search_path`,
и права на таблицы внутри подзапросов политик. `EXPLAIN (GENERIC_PLAN)` принимает `$1` без
значений, и его вывод одинаков с установленным принципалом и без него.

### 4.2. «`PREPARE` проверит права дешевле» — ОПРОВЕРГНУТО

`PREPARE` на запрещённой таблице под `app_operational_scheduler` **прошёл успешно**. Права при
подготовке не проверяются.

### 4.3. «Отказ прав всегда бросать исключением» — ОПРОВЕРГНУТО

| Довод | Проверка |
|---|---|
| Вебхук вернёт ошибку и мессенджер повторит | **неверно**: вебхук возвращает `200` во всех ветках, включая внутренние исключения. Повтора не будет — сообщение пропадёт |
| Так безопаснее | **неверно**: в `integrator-login-public-identity-grants.sql` записано, что попытка закрыть это грантом **уже роняла TEST** — «breaking ALL inbound Telegram/Max»; в коде стоит комментарий, что грант — «the WRONG fix» |
| Технически возможно | **неверно**: контракт `healthCheckDb(): Promise<boolean>` существует, чтобы вернуть `false`; бросок превратит проверку здоровья в падение |
| Ошибку некуда будет проглотить | **неверно**: `try { await port() } catch {}` не запрещён ничем. Принуждает только порт, возвращающий результат вместо броска — то есть обратное |

Дополнительно: функция инцидентов `app.open_or_touch_operator_incident` **не исполняема ролями
webapp** — отказ прав вёл бы к отказу прав.

### 4.4. «Статический детектор найдёт места гашения» — ОПРОВЕРГНУТО

Написан AST-анализатор, проверен на фикстуре из 21 случая: **0 верных срабатываний, 6 ложных**.

| Дыра | Доказательство |
|---|---|
| форма `.catch(() => null)` не видна вовсе | **577** таких мест в серверном коде против 68, которые находил скрипт |
| `catch (e) { if (e.code==='42501') return DEFAULT; throw e }` | считается чистым — проверено инъекцией |
| флагует сам порт | `runIntegratorSql.ts` и `withClient.ts` в списке находок |

Скрипт удалён, а не исправлен: «отказ не дошёл до человека» — не синтаксическое свойство.

### 4.5. «Поверхность запросов соберём из тестов» — ОПРОВЕРГНУТО

| Факт | Проверка |
|---|---|
| тесты webapp физически не ходят в БД | `env.ts` обнуляет `DATABASE_URL`, если нет `USE_REAL_DATABASE=1`; переменная не выставлена нигде в CI |
| тесты integrator не трогают БД | полный набор проходит за 17 секунд, DB-файлы скипаются |

### 4.6. «Ровно один из 61 оверлея сверяет желаемое с фактическим» — ОПРОВЕРГНУТО

```
$ grep -lP 'EXCEPT(?!ION)' deploy/postgres/*.sql
c4-operational-runtime.sql
c5a-platform-operations-runtime.sql
$ grep -lP 'RAISE EXCEPTION' deploy/postgres/*.sql | wc -l
28
```

`c5a` сверяет **больше**, чем `c4`: table ACL, function ACL и инвентарь политик двусторонним
`EXCEPT`.

### 4.7. «Atlas не покрывает SECURITY DEFINER» — ОПРОВЕРГНУТО

Покрывает: `security = "DEFINER"` и `config_params.search_path`. Обоснование «строить своё» на этом
доводе несостоятельно.

### 4.8. Мои собственные ошибки в цифрах — ОПРОВЕРГНУТЫ

| Утверждал | На самом деле |
|---|---|
| 12 075 падений тика в сутки | **17 246** |
| откат транзакции на каждой отправке | **10** за сутки |
| 51 файл ходит через порт integrator | **48** |
| «три порта» | 9 файлов-провайдеров, физических пулов больше |
| «нет третьей таблицы с той же проблемой» | не доказано; проверка велась по неверному критерию |
| причина 42P01 — нет `USAGE` на схему `integrator` | `USAGE` **есть**; причина — неквалифицированное имя и `search_path` |

### 4.9. Дефект, внесённый мной при починке — ОПРОВЕРГНУТ проверкой

В allow-list каналов записал `'sms'`. Контракт кодовой базы: канал называется `'smsc'`, в живой БД
**457 строк** `smsc` и **ноль** `sms`. Каждая SMSC-доставка падала бы. Плюс порядок в оверлее:
`ALTER FUNCTION` стоял на 60 строк **раньше** `CREATE`, деплой падал на первой строке —
проверено исполнением файла целиком.

## Часть 6. Выводы

1. **Проблема не в состоянии БД, а в управлении.** Гигиена чистая; сломано то, как права
   назначаются и как отказы становятся видимыми.
2. **Статика не может доказать авторизацию.** Ни планировщик, ни разбор синтаксиса, ни сбор
   поверхности из тестов. Доказано семью пробами и одним удалённым инструментом.
3. **Класс дефекта двусторонний.** «Код не видит своих данных» и «код видит чужие». Второе
   опаснее и до 08.08 не рассматривалось вовсе.
4. **Доказательства уже существуют.** Журнал PostgreSQL содержит 141 248 строк отказов с ролью и
   запросом, включая классы, недоступные статике. Он пишется сервером до отправки ошибки клиенту,
   поэтому ни один `catch` в приложении на него не влияет.
