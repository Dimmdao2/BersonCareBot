## 0. Как читать: у каждого утверждения есть метка источника

День путаницы вырос из того, что проверенный факт, отчёт агента и догадка выглядели в тексте

| Метка | Что значит | Чему можно доверять |
|---|---|---|
| `[ФАКТ]` | выполнена команда/запрос на живой системе, вывод виден | утверждению целиком; команда приведена, воспроизводима |

| `[ОТЧЁТ]` | сказал агент, я лично не перепроверял | направлению, не числу. Требует перепроверки перед решением |

| `[ГИПОТЕЗА]` | не проверено ничем, записано, чтобы не забыть | ничему; это очередь работ, а не знание |
| `[ОПРОВЕРГНУТО]` | было утверждением, снято — указано **чем именно** | как предупреждению: сюда уже ходили |

## 4. Postgres как инструмент — проверено на одноразовых кластерах

Это факты о СУБД, а не о нашей системе; они определяют, какой гейт вообще может работать.

`[ФАКТ]` **`EXPLAIN` не заменяет исполнение.** Проверяет права на таблицы/колонки/функции и
разрешение имён — и **не видит**: `WITH CHECK`, `USAGE` на последовательности, триггеры, тела
`SECURITY DEFINER`, видимость строк, представления, исполняемые от владельца.
`CALL` процедуры и `SET ROLE` не поддаются `EXPLAIN` вовсе (`42601`). `PREPARE` прав не проверяет.
`EXPLAIN (GENERIC_PLAN)` в PG16 принимает `$1` без значений.

`[ФАКТ]` (мерил Sol, максимальный тир) Два способа вранья планировщика, не найденные другими:
**триггер** — `EXPLAIN` зелёный, исполнение `permission denied for table trigger_sink`;
**представление от владельца** — видно **больше** положенного. То есть дефект **двусторонний**:
не только «код не видит своего», но и «код видит чужое».

`[ФАКТ]` **Ограничительные политики складываются через И, разрешающие — через ИЛИ.** Разрешающая
`USING(true)` + ограничительная `USING(false)` → `One-Time Filter: false`, ноль строк. Модель
«достаточно одной выполнимой политики» семантически неверна. **В нашей живой базе такая политика уже
есть — на `operator_job_status`.**

`[ФАКТ]` **`SET row_security = off`** — встроенный переключатель: вместо тихой фильтрации Postgres
поднимает ошибку. Это меняет дизайн: тихий ноль не нужно ловить сравнением с эталоном.
(Но переключатель НЕ ловит **избыточную** видимость — сравнение остаётся нужным для утечки.)

`[ФАКТ]` `SET ROLE` из суперпользовательской сессии применяет ACL и RLS —
`SET ROLE app_patient; SELECT count(*) FROM public.system_settings` → `permission denied`.
**Оговорка `[ФАКТ]`:** `SET ROLE` **не применяет** `rolconfig` роли (у трёх ролей там
`search_path=public, integrator`) — проба обязана выставлять `search_path` явно. И `SET ROLE` ≠ вход
по логину: не проверяются `pg_hba`, `rolconfig`, `options` строки подключения.

`[ФАКТ]` `SELECT *` после `ADD COLUMN` начинает возвращать новую колонку без единой правки кода —
ни один гейт по диффу кода этого не увидит.

`[ФАКТ]` `DO` с `EXCEPTION WHEN OTHERS THEN NULL` над несуществующей таблицей даёт **0** строк
журнала — гашение внутри сервера возможно.

`[ФАКТ]` Строку журнала пишет серверный процесс **до** пересечения сокета — `try/catch` в Node
физически не может её стереть. Поэтому все места гашения, все пулы и все места вызова ниже по течению.

### 4.1 Механизмы целевой архитектуры — доказаны исполнением (Ф0/В0.2, 08.08)

`[ФАКТ]` (мерил Sol на одноразовом PG16, полные транскрипты — `evidence/12`). Все 10 пунктов
подтверждены; несущие для дизайна:

- **Deny by default достижим и долговечен**: на свежей таблице единственный неявный обладатель
  прав — её владелец; после разовой настройки (REVOKE PUBLIC на базе/схемах + чистка глобальных
  default privileges создающих ролей) новая таблица рождается закрытой, рантайм-роль получает
  42501 без каких-либо дальнейших действий. **Оговорка:** defaults живут ПО-СОЗДАЮЩЕЙ-РОЛИ —
  множество создателей должно быть закрытым и перечисленным.
- **Event trigger как стена в точке рождения — работает**: рабочий прототип `ddl_command_end`
  ставит RLS+FORCE до возврата `CREATE TABLE`; режим reject (не в allowlist → 42501, DDL
  откатывается) — работает; ловит и `CREATE TABLE AS`, и `ALTER TABLE ADD COLUMN organization_id`
  (поздняя org-таблица), и DDL суперпользователя. **Оговорки:** обработчик обязан включать тег
  `ALTER TABLE` + защиту от рекурсии (его собственные ALTER снова зовут триггер); владеть
  event trigger может только суперпользователь — снять его может только суперпользователь
  (компрометация суперпользователя вне этой стены).
- **Колоночный GRANT** даёт громкий 42501 на `SELECT *` после добавления невыданной колонки, при
  этом поимённые выданные колонки продолжают работать — ровно нужное поведение против «новая
  колонка молча втекает в запросы».
- **Полное переприменение генератора идемпотентно и атомарно**: два прогона — побайтно одинаковый
  `relacl`; сбой в середине транзакции — откат, ACL нетронуты. **Оговорка про живой трафик:**
  REVOKE+GRANT в ОДНОЙ транзакции не блокирует и не ломает открытых читателей; раздельными
  autocommit-операторами — открытая транзакция читателя ловит 42501 в окне. Деплойное
  переприменение — только одной транзакцией.
- Разрешающая+ограничительная политика: ноль строк без ошибки — подтверждено и на этом кластере.

## 5. Мировая практика — исследование, не факт о нас

`[ИССЛЕД]` Полный разбор: `evidence/07-industry-practice-research.md`.

`[ОТЧЁТ]` **Проверка по живым первоисточникам (Ф0, 08.08, адверсарный веб-проверщик): 14 из 15
несущих утверждений ПОДТВЕРЖДЕНЫ**, большинство дословным совпадением цитат (Liquibase-предписание;
dbt #6238 wontfix; pg_permissions двусторонний + CIS-бенчмарк PG11, не «12»; шесть линтов Splinter;
AWS REL_3; `row_security` дословно; слепота pgaudit подтверждена по исходникам pgaudit.c И
execMain.c PG16 — хук зовётся только после успешной проверки прав; Atlas HCL+Pro $9; четыре
оговорки `ALTER DEFAULT PRIVILEGES` дословно; PostgREST; DISA STIG SV-233530; все три CVE; Sqitch;
dbt v1.2). Единственное расхождение: **OTel — `SHOULD NOT`, а не `MUST NOT`** (рекомендация, не
запрет; практический вывод «правильно настроенный OTel отбросит этот сигнал» устоял). Плюс два
мелких непроверенных штриха у Atlas (длина триала; линт-предикат `security=INVOKER` на цитируемой
странице не найден). Не проверялась второстепенная фактура (Terraform #197, цифры pgbedrock,
Medplum/Nile/PlanetScale) — несущей она не является.

- **Двусторонняя сверка каталога** (`expected EXCEPT actual` И `actual EXCEPT expected`) — шаблон
  `pg_permissions`, упомянут в бенчмарке CIS PostgreSQL. Односторонняя сверка пропускает лишние права.
- **`SET row_security = off`** — штатный способ отличить «нет строк» от «строки скрыты».
- **pgTAP** (`table_privs_are`, `policies_are`) — декларативные утверждения о правах в тестах.
- **Supabase Splinter** — каталог линтов для ровно этого класса (RLS выключен, политика без FORCE).
- **AWS Well-Architected SaaS Lens, REL_3 «Validating tenant isolation»** — изоляция проверяется
  автоматическим набором, гоняемым в конвейере, а не ревью.

`[ГИПОТЕЗА]` Пригодность Atlas (декларативные схемы+права) к нашему случаю **не оценена**. Стояла в
плане v4 как решение — основания под этим не проверены.

## 7. Процесс — почему шесть кругов аудита ничего не дали

Полный текст: `evidence/09-audits-existing-only-in-conversation.md` §A.

`[ФАКТ]` Замер по десяти коммитам этой работы: **1091 строка markdown против 54 строк исполняемого
кода**. Шесть кругов аудита прошли против текста, который ни одна машина не исполняла.

`[ФАКТ]` Правило «повторять, пока два аудита подряд не чистые» на единице «система прав»
(235 таблиц × 11 ролей) не сходится: компетентный адверсарный аудитор всегда найдёт дыру. На единице
«одна таблица добавлена в стенд» — сходится, потому что утверждение бинарно.

**Условие приёмки инкремента — три транскрипта в сообщении коммита:** красный на непочиненной
реальности → зелёный после починки → снова красный при повторном внесении дефекта в откатываемой
транзакции. Транскрипт невозможно написать, не выполнив.

**Растяжка владельцу, еженедельно:**
```bash
git log --since="7 days ago" --grep="db-privileges" --numstat --format="" \
 | awk '{a=$1+0; if($3 ~ /\.md$/) d+=a; else c+=a} END {print ".md:", d+0, " executable:", c+0}'
```
Строк `.md` не должно превышать строк кода ни в одну неделю.
