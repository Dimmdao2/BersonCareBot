# Система доступа к БД — v3

**От:** владелец, 2026-08-07 («не заплатка, а правильная система, на которой всё чётко и
безопасно, и агенты не смогут напортачить»)
**Ведёт:** Claude. **Статус:** план; деплой Шага 0 владелец остановил («подожди катать») —
работы v3 от него не зависят.

## Инвариант (одна фраза)

Каждое обращение к БД идёт через порт под объявленным контуром; роль контура **может
спланировать** этот запрос (права + имена), на каждой затронутой таблице **есть политика,
выполнимая при форме этого контура** (видимость), и любой отказ в рантайме **громкий**.

## Почему это система, а не набор проверок

Проверки формы (что написано в коде) обходятся — доказано на моём же lint. Здесь ни одна
проверка не смотрит на форму:

- **вердикт о правах выносит Postgres** — `EXPLAIN` планирует запрос под реальной ролью, не
  выполняя его; обмануть нельзя, потому что проверяется не текст, а настоящий план;
- **вход в БД один** — порт; всё, что порт видит, попадает в проверяемую поверхность
  автоматически; чтобы спрятать запрос от проверки, надо пройти мимо порта, а мимо порта
  не пропускают импорт-стены (AST-уровень, не regex) + уже существующий
  `scripts/check-db-chokepoint.mjs`;
- **решение «что делать при отказе» забрано у вызывающих** — его принимает порт; проглотить
  ошибку в `catch` и подставить дефолт физически негде.

Агенту, чтобы напортачить, нужно не «обойти проверку», а **изменить сам механизм** — а это
видимый diff в одном из трёх маленьких файлов, который не пройдёт ревью.

## Пять механизмов

### M1 — порт решает судьбу отказа (громкость)
Сегодня ~10+ мест ловят `42501/42P01` и молча подставляют дефолт — каждое решило само, и
каждое неправильно. Решение переезжает в порт: отказ прав = проброшенное исключение +
операторский инцидент, ВСЕГДА. Fail-safe дефолты не запрещаются — они переезжают в **один
объявленный реестр** (ключ → дефолт → причина, один файл), и применяет их порт, а не
разбросанные `catch`.
- [ ] Инвентарь всех гасящих `catch` вокруг вызовов порта (минимум 10 известны)
- [ ] Порт: отказ прав → throw + `app.open_or_touch_operator_incident`-класс сигнала
- [ ] Реестр объявленных дефолтов; вызывающие теряют право ловить ошибки порта
- [ ] Проверка поломкой: снять грант на выброшенной роли → инцидент виден, дефолт не подставился

### M2 — поверхность запросов, доказанная Постгресом (права)
Порт в тест-режиме записывает каждую пару **(контур → роль, канонический SQL)** во время
существующих тестов и смоука → коммитится `db-surface.tsv`. CI прогоняет каждую пару через
`EXPLAIN (GENERIC_PLAN)` под **реальной login-ролью** на schema-true базе. Любой отказ —
красная сборка. Новый запрос = видимый diff в поверхности на ревью.
- [ ] Хук записи в порт (env-флаг), генерация `db-surface.tsv` из тестов+смоука
- [ ] CI-скрипт: EXPLAIN всех пар под ролями; параметры не нужны (GENERIC_PLAN берёт `$1`)
- [ ] Проверка поломкой: вернуть запрос T-1 → сборка красная
- [ ] После этого regex-lint `93ca870d8` понизить/удалить — его заменяет непроходимое

### M3 — выполнимость политик по форме контура (тихий ноль)
Тихий ноль не даёт ошибки — его ловит только статика: для каждой пары (форма контура ×
таблица из поверхности M2) должна существовать политика, выполнимая при этой форме.
Считается из **уже существующей** дескрипторной модели (`rls-descriptor-model.mjs`,
`tiers-218.tsv`) — не строить заново.
- [ ] Скрипт выполнимости: форма контура ⊨ хотя бы одна политика на таблице (USING и, для
      записи, WITH CHECK)
- [ ] Проверка на известном случае: `integrator`-принцип (app_patient, org задан,
      patient NULL) × `platform_users` → механизм обязан флагнуть (это CRITICAL от 04.08)

### M4 — точная декларация прав в БД (дрейф)

### M5 — авторинг: права рождаются из реестра, не из рук (чистота при дальнейшей разработке)

M1–M4 проверяют; M5 отвечает на «а как добавлять новое». Правило одно: **SQL слоя прав руками

## Жизненный цикл при дальнейшей разработке

| Действие разработчика/агента | Что происходит |
|---|---|
| Новая таблица | миграция создаёт; CI красный, пока нет строки в реестре; политики и гранты рендерит генератор; M4 сверяет |
| Новый запрос | diff в `db-surface.tsv` на ревью; EXPLAIN под ролью в CI; прав нет → красный; чинится строкой в реестре, не GRANT'ом |
| Новая роль/контур | строка в реестре (форма + поверхность); генератор создаёт; M3 проверяет выполнимость политик под этой формой |
| Новая capability | тело функции — код в одном файле (ревью как логика); ACL/owner/search_path — из реестра |
| Попытка нового оверлея | некуда положить: ручной SQL прав не принимается гейтом |
| Попытка заплатки «поймаю и подставлю дефолт» | некуда положить: ошибки порта вызывающим не выдаются; дефолт — только строкой в реестре дефолтов (M1) |

Заплатке негде жить не потому, что «запрещено правилом», а потому, что у неё нет места в
конструкции: каждый обходной путь упирается либо в красную сборку (M2/M5), либо в отсутствие
API, куда её вписать (M1).

## Как в итоге назначаются гранты

Руками — никак. Два пути, оба через реестр:

- **Базовые** выводятся из тира и контура: строка «таблица X, тир SCOPED» уже означает
  сгенерированные политики и гранты по правилам тира (так p0-8-генераторы работают сегодня).
- **Точечные** — спросом: код написал новый запрос → M2 красный «роль не может SELECT X» →
  разработчик добавляет строку в реестр → генератор рендерит грант → зелёный. Diff строки
  реестра — и есть предмет ревью. Вопрос ревью меняется с неотвечаемого «этот GRANT
  корректен?» на отвечаемый «должен ли этот контур это уметь?».

Лишние права снимает обратная сверка: **выдано ∖ используется** (из поверхности M2) = список
кандидатов на REVOKE, каждый — конкретный вопрос «у app_staff есть DELETE на X, ни один путь
кода не удаляет из X — почему?».

## Проверка текущей схемы и полнота («как не забыть таблицу»)

Полнота — не из списков, а из **каталога Postgres**: перечисляется `pg_class`, а не
человеческий файл. Каждая таблица обязана быть заявлена ровно одной строкой реестра (тир
INFRA/TELEMETRY/LEGACY — тоже тиры, «нет тира» нелегитимно всегда); незаявленная = красный CI.
То же для ролей (`pg_roles`), функций (`pg_proc`), политик (`pg_policies`). Забыть нельзя то,
что перечисляешь из каталога.

**Живой baseline (замерено 2026-08-07):** в базе 235 таблиц, в реестре тиров 227 строк;
**10 таблиц базы не заявлены** (все `saas_billing_*`, `org_brand_revisions`, slug-таблицы,
`manual_patient_commands`, `booking_calendar_map`) и **2 строки реестра мертвы** (таблица
переехала из `integrator` в `public` — реестр не заметил). Из 10 забытых 9 защищены RLS+FORCE
— команда держала дисциплину руками; реестр отстал молча, потому что census-гейт существует и
не подключён. Ровно тот отказ, который M5 закрывает.
- [ ] Начальная выверка: 10 таблиц классифицировать, 2 мёртвые строки снять
- [ ] Census-гейт (по каталогу, обе стороны) — в CI

Корректность «кому что выдавать» (не только полнота): начальный реестр — снимок живого
состояния, но снимок ≠ правильность. Правильность добивается двумя сверками: недодача ловится
M2 (EXPLAIN красный), передача — ревью списка «выдано ∖ используется» (конечный список
конкретных вопросов, а не 291 политика глазами). Прод: тот же census + M4 гоняются против
прод-базы при деплое — прод-специфичный дрейф становится виден, а не предполагается.

## Проверенные факты (2026-08-07, живая TEST-база; НЕ предположения)

- `PREPARE` **не** проверяет права (прошёл на запрещённой таблице) — идея отвергнута.
- `EXPLAIN` проверяет права **без выполнения**: таблицы (42501), имена/search_path (42P01),
  **и EXECUTE на функциях** — всё проверено живьём под реальными ролями.
- `EXPLAIN (GENERIC_PLAN)` принимает `$1` без значений (PG16) — параметры не нужны.
- `pg_stat_statements` не в preload — и не нужен: точка захвата — порт (все 51 файл ходят
  через него).
- Гигиена самой БД чистая: 0 definer-функций без закреплённого search_path, 0 с EXECUTE у
  PUBLIC, 0 RLS-таблиц без политик — фундамент держит, менять модель доступа не нужно.

## Минимальность

**Ноль новых зависимостей.** Nest — отвергнут (DI-фреймворк ничего не знает о правах БД,
месяцы переезда, нулевой эффект на инвариант). Atlas — не нужен (M4 уже построен в репо
лучше). ORM-миграции, переписывание истории — не входят. Вся система = вычитание разбросанных
`catch` + один хук в порт + два скрипта против каталогов Postgres + расширение готового
c5a-паттерна.
