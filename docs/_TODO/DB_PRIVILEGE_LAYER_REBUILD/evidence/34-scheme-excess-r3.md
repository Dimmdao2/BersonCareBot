## КРИТИЧЕСКОЕ

### К1. Переход логин → рантайм-роль остался без механизма: PostgreSQL так не умеет

Три строки схемы, которые вместе неисполнимы:

- стр. 100–104: «До accepted context нет standing membership с `SET TRUE` к роли, у которой есть table ACL.
  Verifier атомарно устанавливает context и **разрешает только exact target** текущего backend/transaction…
  Любое прямое или транзитивное ребро login → table-granted role без этой привязки — FAIL свипа»;
- стр. 61: «до `ACCEPTED` переход к exact runtime-role невозможен»;
- стр. 86–87 (жизненный цикл): «verify/install context → **переход в exact role** → queries».

В rev3 на этом месте стояло `SET LOCAL ROLE` и постоянное членство, а громкость держал statement-hook
расширения. Rev4 сняла и расширение, и членство — и **не назвала, чем именно выполняется переход**. Замена
конкретного `SET LOCAL ROLE` на неопределённое «переход в exact role» (diff `31d2f893e→4a56d9b2f`, §2.3) —
единственное место ревизии, где механизм заменён словом.

Механики PostgreSQL 16, которые здесь работают:

1. `SET ROLE` проверяет членство **session user**, а не текущего `current_user`. Проверено живьём на
   `bcb_webapp_dev` (PG 16.14):

   ```
   psql "$DATABASE_URL" -c "SET ROLE app_staff;"
   ERROR:  permission denied to set role "app_staff"
   ```

   Логин `bcb_webapp_dev_user` не член `app_staff` — переход отклонён. Без записи в каталоге
   (`GRANT app_staff TO <login> WITH SET TRUE`) перехода не существует вовсе.
2. `SECURITY DEFINER` меняет `current_user`, но не `session_user`, поэтому `SET ROLE` внутри verifier
   проверяется против того же логина и падает так же. Сверх того PostgreSQL восстанавливает userid и
   sec-context на выходе из definer-функции, поэтому смена роли внутри неё не переживает возврат.
3. Единственный оставшийся вариант — verifier выдаёт членство сам (`GRANT … WITH SET TRUE`). Это каталожная
   запись: она **переживает `COMMIT`**, видна всему кластеру, а не «текущему backend/transaction», и со
   второй транзакции превращается ровно в то standing membership, которое стр. 100 запрещает. Плюс запись в
   `pg_auth_members` на каждый запрос порта — сериализация на строке роли.

Последствия, каждое против плана владельца:

- **Приёмка недостижима по построению.** §8 п.3 (стр. 295–296) требует «отдельный свип доказывает ноль
  login/role paths, где table grant достижим без accepted context». Свип видит только каталог. Ноль путей в
  каталоге = порт не работает; путь есть = FAIL. Это тот же класс, что мой круг 2 N2: пункт приёмки,
  который нельзя пройти ни при каком исходе работы.
- **Положительный контроль не собирается.** §8 п.7 (стр. 301–302) требует, чтобы через оба порта staff,
  patient, platform, service и integrator получили объявленный результат. Пути к рантайм-роли нет — контроль
  не проходит. `PLAN.md:36–37`: «Стена, которая не пускает никого, включая приложение, доказывает не
  безопасность, а поломку».
- **Это не «деталь реализации».** П3 владельца («заранее продумываются ДВА места») означает, что механика
  самих портов и есть предмет проектирования; всё остальное чинит отладка. Именно этот механизм — то, что
  схема обязана назвать.

**Компонент предлагать не буду** — его в этом workstream уже отклонили. Наименьшее закрытие без нового
компонента: вернуть постоянное `GRANT <runtime_role> TO <login> WITH INHERIT FALSE, SET TRUE, ADMIN FALSE`
(форма rev2/rev3) и записать честно, **какой механизм несёт громкость в каком случае**:

- логин, который не делал `SET ROLE`, — гранты: ноль table ACL, `42501` от permission check на любом плане,
  включая `WHERE false` и `LIMIT 0` (эта часть rev4 верна: проверка прав идёт на старте executor'а, до scan);
- сессия, сделавшая `SET ROLE` без контекста, — бросающий accessor в restrictive policy: громко на любом
  плане, который посещает строки, **тихо на плане, который не посещает ни одной**;
- системный каталог — вне стены (см. С1).

Третий пункт этого перечня — именно то, что HIGH-1 круга 2 (`evidence/31`) назвал нарушением критерия
владельца. Значит без компонента буквальный критерий на этом одном классе планов не выполняется, и выбор
здесь не инженерный, а владельческий — см. «Вопросы владельцу».

## СУЩЕСТВЕННОЕ

### С1. «Любой table statement без контекста → `42501`» неверно для системного каталога

Схема, стр. 14–16: «до принятия контекста соединение остаётся в login-роли без table/column/sequence ACL…
поэтому **любой table statement**, включая `WHERE false` и `LIMIT 0`, получает statement-level `42501` от
permission check». §8 п.2 (стр. 292–294) переносит это в приёмку: «первый table statement отклонён permission
check, строк нет, log event есть».

Проверено на `bcb_webapp_dev` обычным прикладным логином, без ключа и без контекста:

```
psql "$DATABASE_URL" -At -c "SELECT count(*) FROM pg_class;"          -- 1896
psql "$DATABASE_URL" -At -c "SELECT count(*) FROM pg_policy;"         -- 285
psql "$DATABASE_URL" -At -c "SELECT count(*) FROM pg_proc WHERE prosrc IS NOT NULL;"  -- 3766
psql "$DATABASE_URL" -At -c "SELECT has_table_privilege('public','pg_catalog.pg_proc','SELECT');"  -- t
```

Строки отданы, ошибки нет. `SELECT` на `pg_catalog` принадлежит `PUBLIC` по установке кластера, и генератор
её не снимает: §6.2 стр. 254 отзывает «всё **управляемое**», а §6.1 стр. 244 относит системные объекты к
bootstrap-владельцу, то есть к неуправляемым. §8 п.4 проверяет у `PUBLIC` только `CONNECT`, schema `USAGE`,
`TEMPORARY` и defaults — каталог там не назван.

Что при этом видно без контекста: имена всех ролей и таблиц, тексты всех policy, **тела всех функций**
(`pg_proc.prosrc`), структура `app_ext.port_key_hashes`. Ключа и арендных данных — нет.

Это прямое последствие удаления расширения: hook rev3 проверял каждый `SELECT`, то есть закрывал и каталог.
Rev4 заменила его грантами, которые на каталоге не действуют, и границу не назвала. Форма без дефекта —
одна фраза в §1 и один пункт в §8: стена гарантирована на **управляемых прикладных relations**, чтение
системного каталога логином остаётся возможным и является именованным остаточным риском. Дальше — вопрос
владельцу, потому что его критерий написан как «любой запрос к базе данных».

**1. Насколько буквально читать «любой запрос к базе данных без контекста»?** От вашего ответа зависит,
можно ли построить схему вообще без нового компонента (один такой в этой работе уже отклонён).

- Если критерий покрывает **запросы, которые не читают ни одной строки** (`WHERE false`, `LIMIT 0`) и

  `pg_catalog`, а политика на плане без scan не вычисляется. Тогда нужен либо перехватчик statement'ов
  (компонент), либо смягчение критерия.
- *Рекомендация: сузить критерий до **управляемых прикладных таблиц и запросов, которые действительно
  обращаются к данным**.* Запрос `WHERE false` данных не выносит, а чтение каталога отдаёт имена и тела
  функций, но не данные клиник и пациентов. При таком чтении rev4 строится штатным PostgreSQL, а граница
  записывается в схему явно и проверяется приёмкой — вместо обещания, которое не выполняется.
