## СУЩЕСТВЕННОЕ (блокирует приёмку)

### С1. Отзыв `pg_stat_activity` не закрывает утечку, ради которой он сделан: тот же текст запроса соседней сессии виден через `pg_stat_get_backend_activity`

Развилка 30 (стр. 344) называет причину дословно: «view и `pg_stat_get_activity` закрыты от runtime/login,
потому что **same-login pool показывает patient literals соседней сессии**». Отзыв объявлен в трёх местах и
везде перечислены ровно два объекта:

- стр. 29–30: «view `pg_stat_activity` и `EXECUTE pg_stat_get_activity(integer)` отозваны у `PUBLIC` и
  login/runtime-ролей»;
- стр. 259 (инвариант генератора): «`pg_stat_activity` и `pg_stat_get_activity(integer)` не имеют
  `PUBLIC`/login/runtime ACL»;
- стр. 300 (приёмка §8 п.4): «same-login sentinel не виден через view или `pg_stat_get_activity`».

В PostgreSQL 16 текст чужого запроса отдаёт и второе, независимое семейство функций —
`pg_stat_get_backend_activity(integer)` поверх `pg_stat_get_backend_idset()`. Проверка на этом кластере
(read-only, `bcb_webapp_dev`, PG 16.14; фоновая сессия того же логина держит `SELECT pg_sleep(6)`):

```
psql "$DATABASE_URL" -At -c "BEGIN TRANSACTION READ ONLY;
  SELECT 'as_login', pg_stat_get_backend_activity(b.id)
    FROM pg_stat_get_backend_idset() b(id)
   WHERE pg_stat_get_backend_activity(b.id) ILIKE '%pg_sleep%';
  SELECT 'acl', proname, coalesce(proacl::text,'NULL(PUBLIC)') FROM pg_proc
   WHERE proname IN ('pg_stat_get_backend_activity','pg_stat_get_backend_idset');
ROLLBACK;"
# as_login|SELECT pg_sleep(6);            <-- полный текст запроса соседней сессии
# acl|pg_stat_get_backend_activity|NULL(PUBLIC)
# acl|pg_stat_get_backend_idset|NULL(PUBLIC)
```

Проверка границы — та же команда после переключения роли:

```
psql "$DATABASE_URL" -At -c "BEGIN TRANSACTION READ ONLY; SET LOCAL ROLE app_identity_bootstrap;
  SELECT 'after_set_role', current_user, pg_stat_get_backend_activity(b.id)
    FROM pg_stat_get_backend_idset() b(id); ROLLBACK;"
# after_set_role|app_identity_bootstrap|<insufficient privilege>
```

Дверь открыта **ровно в том состоянии, против которого построена вся схема**: атакующий с верным паролем
логина и без ключа порта. Проверка внутри `pg_stat_get_backend_activity` — `has_privs_of_role(current_user,
st_userid)`; пока сессия сидит в login-роли, `current_user` = логин = `st_userid` соседней сессии пула, и
текст виден целиком. После `SET LOCAL ROLE` (runtime-роль не член логина) — `<insufficient privilege>`, то
есть у легитимного пути этой видимости и так нет.

Почему это блокирует, а не «мелочь на потом»:

1. **Заявленная цель фикса не достигнута.** Развилка 30 закрывала конкретную утечку; она осталась открытой
   по эквивалентному пути. `proacl = NULL` = `PUBLIC EXECUTE` по умолчанию, то есть отзыв надо объявлять
   явно — сам он не наступит.
2. **Приёмка загорится зелёным над живой утечкой.** §8 п.4 проверяет sentinel «через view или
   `pg_stat_get_activity`» — обе названные двери закрыты, пункт пройден, а sentinel читается. Это худший
   класс: галочка поверх дефекта.
3. **Против дословного критерия владельца** (`OWNER_DECISIONS.md:208`): запрос без контекста возвращает
   строки, молча, без ошибки в журнале.

**Компонента не предлагаю, нового скоупа нет.** Минимальное закрытие — расширить перечень объектов в уже
существующих трёх строках: к `pg_stat_activity`/`pg_stat_get_activity(integer)` добавить семейство
`pg_stat_get_backend_*` (несущая — `pg_stat_get_backend_activity(integer)`, вместе с перечислителем
`pg_stat_get_backend_idset()`), и в §8 п.4 гонять sentinel-пробу именно этим путём, а не только через view.
Три правки списка, ноль новых сущностей.

## МЕЛКОЕ

**М1. Сверка `current_user` с target role не оговорена для definer-швов — фикс С1 круга 4 fail-closed
задевает все 42 шва.** Стр. 15/82/105: accessor сверяет `current_user` с ролью транскрипта. Внутри
`SECURITY DEFINER`-функции `current_user` — это владелец шва, а не target role. Стр. 162 требует
обязательную restrictive context-policy на каждой managed relation, стр. 222 говорит, что доступ владельца
шва к relation тоже идёт «exact columns/operations и policies»; владелец шва не владелец таблиц, значит RLS
к нему применяется. Буквальное чтение: любой шов, читающий прикладную таблицу внутри принятого контекста,
получит `42501`. Расширения доступа нет — отказ строго в сторону меньшего (П1: «ошибиться в сторону меньшего
доступа — рабочая ситуация»), и §8 п.8 (positive controls) это поймает живьём. Но ловить это на реализации
42 швов дороже, чем одна оговорка: назвать, с чем сверяется accessor внутри шва (target role принятого
состояния **либо** объявленный владелец шва при attested root-call), либо сказать, что обязательная
restrictive policy объявляется `TO` runtime-ролям, а швы держат свои. Одна строка; закрыть тем же ходом,
что С1.

**М2. Требование к публичному ключу `P` недоговорено.** Стр. 62–63 и 66–67: challenge шифрует
`app_ext.pgp_pub_encrypt_bytea`, `P` назван «public encryption key». pgcrypto принимает только OpenPGP-ключ
с ключом шифрования (RSA/ElGamal); ключ без encryption-capable (под)ключа отвергается прямо на вызове —
проверено: `ERROR: No encryption key found` на RSA-ключе `[SC]`, успех после добавления `[E]`-подключа.
Полстроки в §2.1 («OpenPGP RSA/ElGamal, encryption-capable»), иначе первая же ротация упрётся в это на
живом прогоне.

**М3 (перенесено из круга 4, не закрыто). `PLAN.md:143` по-прежнему без пометки.** Схема расхождение назвала
(§1.3) и держит его единственным вопросом §10; источник — строка Ф3б «эту дверь закрыть: неизвестный не
получает соединения» — стоит в прежней редакции без ссылки на §1.3 (grep `SCHEME.md` по `PLAN.md`: единственное
упоминание — стр. 93, не про Ф3б). Пока пометки нет, галочка Ф3б не ставится честно ни при каком исходе.

**М4. Косметика: между развилкой 31 и `## 10` нет пустой строки** (стр. 345–346) — в строгих markdown-парсерах

## НЕ РАСШИРИЛ ЛИ ДОСТУП КАЖДЫЙ ИЗ ЧЕТЫРЁХ ФИКСОВ

**1. Сверка роли в аксессоре — сужение.** Добавляет условие к уже существующей проверке, ничего не
разрешает. Важно, что gate закреплён не только в аксессорах, но и в форме самой policy (стр. 164–165):
`USING (true)` для service-ролей (стр. 174–177) теперь тоже проходит через role-bound accessor — дыра,
которую я называл в круге 4, закрыта в том числе на этом пути. Единственный побочный эффект — М1,
fail-closed.

**2. pgcrypto-обмен — сужение, зависимость названа честно и проверена.** `pgcrypto 1.3` установлен в схему
`app_ext`, `pgp_pub_encrypt_bytea(bytea,bytea)` существует — не план, а факт кластера:

```
psql "$DATABASE_URL" -At -c "BEGIN TRANSACTION READ ONLY;
  SELECT e.extname, n.nspname, e.extversion FROM pg_extension e JOIN pg_namespace n ON n.oid=e.extnamespace;
  SELECT p.proname, n.nspname, pg_get_function_identity_arguments(p.oid) FROM pg_proc p
    JOIN pg_namespace n ON n.oid=p.pronamespace WHERE p.proname LIKE 'pgp_pub_%'; ROLLBACK;"
# pgcrypto|app_ext|1.3 ; pgp_pub_encrypt_bytea|app_ext|bytea, bytea ; …
```

Функция реально работает на этом кластере и стоит дёшево: 100 шифрований (с `dearmor` на каждом вызове)
— **3.97 ms**, то есть ~0.04 ms на транзакцию (одноразовый RSA-2048 ключ, сгенерённый в scratchpad,
плюс `\timing`). Криптографически схема стала строже rev5: БД больше не хранит секрета, эквивалентного
ключу порта (в rev5 хранился `S = SHA-256(C)`, из которого проверялся HMAC), таблица §2.2 честно
перечисляет, что даёт dump, logged proof и их сочетание. Новая зависимость сверх БД одна и она внешняя —
порту нужен локальный OpenPGP-декриптор; в тексте она подразумевается («порт локально расшифровывает
ciphertext приватным `K`»), но как зависимость не выписана. Претензии не делаю: это библиотека внутри
порта, а не компонент схемы. Требование к формату ключа — М2.

**3. Отзыв activity views — легитимного потребителя не ломает.** Свип по репозиторию:

```
grep -rn "pg_stat_activity\|pg_stat_get_activity\|pg_read_all_stats" --include=*.ts --include=*.mjs \
  --include=*.sql --include=*.sh . | grep -v node_modules
# apps/webapp/scripts/postgres-integration/harness-lib.ts:737      pg_terminate_backend(...)
# docs/_TODO/SAAS_FOUNDATION/scripts/{smoke-phase3…,prove-u5a…,run-saas-disposable-dormant-rehearsal}.mjs
```

Все пять — ops/тестовые скрипты, которые уже требуют административного соединения (`pg_terminate_backend`,
`CREATE DATABASE`); ни одного runtime-пути вебаппа или интегратора. В самой БД тоже нет потребителя:
`SELECT … FROM pg_proc WHERE prosrc ~* 'pg_stat_activity|pg_stat_get_activity'` вне системных схем — пусто,
то есть шов 37 «curated system health» activity не читает. Health-проба §8/шов 31 от этого не зависит.
Названное следствие (не дефект): отзыв у `PUBLIC` снимает видимость и с владельцев швов, и с любой будущей
мониторинговой роли — такой роли понадобится поимённый grant или `pg_read_all_stats`, а предопределённая
роль вне allowlist по стр. 269–270 — FAIL, значит её придётся объявлять.

**4. `NOLOGIN` у мигратора — сужение с названной операционной ценой.** Схема говорит прямо: окно — «одно
локальное соединение `postgres`» (стр. 274), развилка 31 фиксирует выбор. Цена, которую стоит видеть

## ЧТО ПРОВЕРЕНО И ЧИСТО

- **One-time gate работает так, как обещает §1.2 — воспроизведено на планировщике этого кластера.**
  Некоррелированный scalar subquery в квале становится `InitPlan` + гейт-узел `One-Time Filter` НАД сканом,
  и вычисляется до него — а значит существующий и отсутствующий indexed value неразличимы:

```
psql "$DATABASE_URL" -At -c "BEGIN TRANSACTION READ ONLY; EXPLAIN
  SELECT count(*) FROM product_analytics_hourly
   WHERE organization_id='00000000-0000-0000-0000-000000000000'::uuid
     AND (SELECT 1/((random()*0)::int))=1; ROLLBACK;"
# Aggregate → InitPlan 1 → Result: One-Time Filter: ($0 = 1) → Index Only Scan (Index Cond: organization_id = …)
```

  Прогоны: значение существует → `ERROR: division by zero`; значения нет → **тот же** `ERROR`; seq-scan без
  совпадений → тот же `ERROR`; `WHERE false` → тихий `0`; `LIMIT 0` → тихо пусто. Это построчно совпадает с
  текстом стр. 36–38, включая границу «тихий ноль допустим лишь при no-scan». Existence oracle закрыт не
  декларацией, а механикой планировщика.
