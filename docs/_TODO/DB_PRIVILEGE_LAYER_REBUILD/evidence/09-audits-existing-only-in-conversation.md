## A. Диагноз процесса (исследователь процесса, Opus)

**Ошибка была не «пишу до проверки». Ошибка в том, что артефактом была ПРОЗА.**

Замер по десяти коммитам этой работы: **1091 строка markdown против 54 строк исполняемого кода.**
Шесть кругов аудита прошли против текста, который ни одна машина ни разу не исполнила.

**Правило владельца «повторять, пока два аудита подряд не будут чистыми» — верное, а единица работы
неверная.** На «системе прав» (235 таблиц × 11 ролей) вероятность чистого аудита ≈ 0: компетентный
адверсарный аудитор всегда найдёт дыру, поэтому круги не сходятся — единица неопровержима за один
проход. То же правило **достижимо** на «одна таблица добавлена в стенд», где утверждение бинарно и
проверяется машиной.

**Условие приёмки инкремента — три состояния, все три транскрипта в сообщении коммита:**

1. **КРАСНЫЙ** — гейт падает на сегодняшней непочиненной реальности (дефект настоящий, гейт его видит);
2. **ЗЕЛЁНЫЙ** — гейт проходит после починки;
3. **СНОВА КРАСНЫЙ** — гейт падает после повторного внесения дефекта в откатываемой транзакции.

Нет состояния 1 → гейт прошёл бы и так, ничего не доказано. Нет состояния 3 → гейт не подключён к
тому, что заявляет. **Транскрипт невозможно написать, не выполнив** — в этом весь смысл для автора,
склонного сочинять правдоподобную структуру. Утверждение перестаёт быть предложением, которое можно
составить, и становится выводом, который пришлось получить.

**Три роли, никогда один агент и никогда одна модель:**
- **Доказыватель** — правит только стенд и одну миграцию, прозу писать не имеет права, выдаёт три транскрипта;
- **Ломатель** — Opus, **не видит рассуждений доказывателя**, задача одна: сделать так, чтобы гейт
  прошёл при наличии дефекта. Успех ломателя = инкремент отклонён;
- **Владелец** — читает одно число (растяжка ниже).

**Растяжка для владельца, одна команда, еженедельно:**
```bash
git log --since="7 days ago" --grep="db-privileges" --numstat --format="" \
 | awk '{a=$1+0; if($3 ~ /\.md$/) d+=a; else c+=a} END {print ".md:", d+0, " executable:", c+0}'
```
**Правило: строк `.md` не должно превышать строк исполняемого кода ни в одну неделю.** На момент
замера — 1091 против 54, отношение 20:1. Сработало бы на первом круге, до заказа первого аудита.
Вторая, медленная растяжка: **ноль инкрементов за две недели подряд** → стоп и эскалация.

**Первое действие было названо:** починить стенд `verify-a1-rls-conformance.mjs`, пока он не даст
`PASS`, — «ничто иное в этой работе не приемлемо». Выполнено, коммиты `d6b5ce0df`, `b0bebf320`.

## B. Разбор мест гашения ошибок (агент, Opus)

Обследованы 20 названных мест плюс сплошной поиск по `23505`. Вывод: **правило «отказ прав всегда
бросать исключение» ложно и опасно.**

**Группа A — внутри самого порта.**

| Место | Что ловится | Вердикт |
|---|---|---|
| `client.ts:235` `healthCheckDb` | сам `SELECT 1` | **конфликт.** Контракт `Promise<boolean>` существует, чтобы вернуть `false`. Бросок превращает проверку здоровья в падение |
| `apps/webapp/.../client.ts:98` `checkDbHealth` | то же | **конфликт**, та же причина |
| `runIntegratorSql.ts:22-43` | быстрый путь drizzle | не настоящее гашение: проваливается во второй путь, который сам бросит 42501 |
| `withClient.ts:213` | `ROLLBACK` внутри обработчика ошибки | **обязательное гашение.** Исходная ошибка всегда перебрасывается; глушится только вторичный сбой отката, чтобы не затереть первичный |
| `writePort.ts:404-542` | вся транзакция привязки телефона | **настоящий конфликт.** Ошибка прав логируется, но превращается в мягкий бизнес-результат `db_transient_failure` |

**Группа C — входящие вебхуки. Здесь опровергается сама посылка.**

Вебхук **уже возвращает HTTP 200 во всех ветках**, включая внутренние исключения — три независимых
слоя превращают любой бросок в не-бросающий исход до формирования ответа. Значит «порт бросит →
мессенджер повторит» **фактически неверно**. Реально меняется другое: какие сбои роняют **всё
входящее сообщение** вместо деградации одного необязательного поля.

Дословно из кода (`max/webhook.ts:157-168`):
> «Fail open like every other pre-routing lookup in this file… a transient DB/privilege hiccup here
> (e.g. the bare bootstrap login role 42501-ing on public.system_settings / app.current_org_id())
> must degrade admin-detection to "not admin", not crash the whole inbound MAX pipeline. See
> deploy/postgres/integrator-login-public-identity-grants.sql for why granting this access is the
> WRONG fix (it took TEST down) and fail-open in code is the correct one.»

И (`handleIncomingEvent.ts:152-160`): 42501 на предмаршрутизации «must degrade to "no linked user /
no draft / no open conversation"… not propagate and drop the whole inbound message».

**Подтверждено в оверлее:** попытка закрыть это грантом **уже роняла TEST** — «breaking ALL inbound
Telegram/Max on TEST».

**Группа B — воркеры.** Сырой 42501 в очереди доставки **по умолчанию считается повторяемым**
(`isOutgoingDeliveryDispatchErrorRetryable` возвращает `true` для неизвестных сообщений) → постоянная
ошибка прав повторяется до исчерпания попыток, затем мертвится. Ограниченно, но впустую.
В медиа-воркере бросок **внутри** `withPoolTransaction` откатывает захват строки
(`FOR UPDATE SKIP LOCKED`) → батч умирает на первой отравленной строке **каждый тик**, блокируя
очередь за ней.

**Группа D.** `getOperatorHealthProbeConfig` при броске остановил бы планирование тех самых проб,
которые должны обнаруживать этот класс — самоподрыв.

**Единственное место, где правило улучшило бы дело:** `pgEmailSetupFlowPort` отображает любую
ошибку, включая 42501, в `reason:'user_not_found'` — то есть **лжёт о причине**.

**Предупреждение на будущее:** ~25–27 мест намеренно ловят `23505` (нарушение уникальности) как
законную идиому «вставить, если нет». Широкий запрет «не ловить ошибки порта» сметёт их все; правило
обязано смотреть на конкретный SQLSTATE, а не на форму `try/catch`.

## C. Разбор статического анализатора мест гашения (агент, Opus)

Написанный AST-анализатор проверен на фикстуре из 21 случая: **0 верных срабатываний, 6 ложных.**
Точность 0%, полнота 0%.

| Дыра | Доказательство |
|---|---|
| форма `.catch(() => default)` не видна вовсе | **577** таких мест в серверном коде против 68 находок анализатора |
| `catch (e) { if (e.code==='42501') return DEFAULT; throw e }` | считается чистым — любой `throw` где угодно в теле засчитывается как проброс |
| флагует **сам порт** | `runIntegratorSql.ts`, `withClient.ts` — единственные места, где правка уместна |
| режим гейта `--check` | **не реализован**, вышел бы зелёным всегда |
| список точек входа короче на ~21 | `getPool`, `runWebappTransaction`, `runPgPoolPgText` и другие |
| область сканирования пропускает 121 файл | включая сам `packages/db-principal` |

**Вывод о дизайне:** «отказ не дошёл до человека» — **не синтаксическое свойство**. Формы, которые
детектор не увидит никогда: любое поглощение вне `try/catch`; запрос на расстоянии вызова (нет графа
вызовов); условный проброс; намерение (различие 42501 и сетевого сбоя существует только в рантайме);
и обратный дефект — отказ, который **проброшен**, пойман границей ошибок фреймворка и отрисован как
общий 500, о котором никто не узнал.

**Правильное место — сам порт:** одна проверка кода ошибки ловит все формы независимо от того, что
делает вызывающий. Двадцать строк против двухсот тридцати, полнота против нуля.

Анализатор удалён, а не исправлен.

## D. Вердикт по корректности решений плана v3 (Sol, максимальный тир)

Проверял на одноразовом кластере PG16 (доступа к TEST у него не было). **Два способа вранья
планировщика, которых не нашёл никто другой:**

- **триггеры:** `EXPLAIN` зелёный; выполнение → `permission denied for table trigger_sink`. Триггер
  выполняется своей ролью, и его отказ планированию не виден;
- **представления, исполняемые от владельца:** видно **больше**, чем роли положено. То есть класс
  дефекта **двусторонний** — не только «код не видит своих данных», но и «код видит чужие».

Дополнительно им же:
- **последовательности:** право `INSERT` на таблицу есть, `USAGE` на sequence нет → `EXPLAIN`
  зелёный, выполнение падает. Ломает посылку **даже без RLS и без definer-функций**;
- **`SELECT *` после `ADD COLUMN`:** неизменённый запрос начинает возвращать новую колонку
  (`{"a":1,"secret":"newly_exposed"}`). Диффа кода нет — ни один гейт по коду этого не увидит;
- **`CALL` процедуры и `SET ROLE`** не поддаются `EXPLAIN` вовсе (`42601 syntax error`);
- **ограничительные политики:** одна разрешающая `USING(true)` плюс одна ограничительная
  `USING(false)` → `One-Time Filter: false`, ноль строк. Модель «достаточно одной выполнимой
  политики» семантически неверна: разрешающие складываются через ИЛИ, ограничительные — через И.
  В живой базе такая политика уже есть — на `operator_job_status`;
- **частичная видимость:** роль вернула **подмножество** строк — не ноль. Ноль хотя бы подозрителен,
  подмножество выглядит как нормальные данные.

**Ограничение инструментов, выясненное на нём же:** агенты, запущенные через мозговой порт, работают
в песочнице с `no_new_privileges` и **не достают до базы** — `sudo` блокируется до Postgres. Два
прогона потеряны на этом: они полчаса поднимали собственный кластер и умирали. Запуск Sol напрямую
через `codex exec --sandbox danger-full-access` доступ даёт — проверено (`postgres | tables=307`).
