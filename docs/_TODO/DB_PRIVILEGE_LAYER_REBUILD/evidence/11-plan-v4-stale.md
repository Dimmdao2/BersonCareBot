## 1. Идея одной фразой

Все факты об авторизации читаются из **собственных записей PostgreSQL**, а не из кода, плана или
теста. Записей две, и они дополняют друг друга:

- **Журнал** — какие полномочия запрашивались и были отклонены;
- **Каталог под живым исполнением** — какие полномочия реально есть.

Один гейт читает обе, сверяет с зафиксированным эталоном и падает при расхождении.

## 2. Почему это нельзя обойти обычным кодом

**Сторона журнала.** Postgres пишет строку об отказе внутри серверного процесса, **до** того как
ошибка ушла в сокет. `try { await port() } catch {}` в Node выполняется позже и не может стереть
уже записанное. Поэтому все ~177 мест гашения, 577 форм `.catch(() => …)`, 9 пулов, 51 сырой
`new Pool` и все места вызова находятся **ниже по течению** — они физически не влияют на запись.

**Сторона каталога.** Нельзя создать таблицу без строки в `pg_class`, выдать право без записи в
`relacl`, завести роль без `pg_roles`, добавить политику без `pg_policies`. Гейт перечисляет из
живого каталога и падает на всём, чего нет в эталоне.

**Честно и асимметрично:**
- внести полномочие незаметно — **нельзя**;
- скрыть отказ — **нельзя**;
- написать код, который просит не то, — **можно**, и это станет видно после первого же исполнения
  в любой среде. Задержка — одно исполнение, не один релиз.

**Чем можно сломать:** правкой `postgresql.conf` или удалением гейта из деплоя. Оба — root-уровень
и одиночный очевидный дифф. Проверено: `log_min_error_statement` и `log_min_messages` имеют
`context=superuser`, то есть сессия не может отключить логирование сама себе.

**Это снимает главное противоречие v3.** M1 требовал, чтобы отказ долетал до человека;
документированные fail-open пути требуют, чтобы он НЕ долетал, иначе падают входящие сообщения.
Конфликт был неразрешим, пока видимость требовала распространения. Она не требует.

## 3. Где доказывается авторизация

**Не на месте вызова, а на ячейке полномочий.**

Авторизация — свойство тройки `(роль, объект, принципал)`, а не строки кода. Мест вызова ~2353, и
покрыть их тестами нельзя: покрытие 0%, потолок 5–13%, а тики планировщика, ~40 типов задач
воркера и вебхуки не покрываются никогда. Ячеек — конечное перечислимое число из `pg_class` ×
`pg_roles`, и они покрываются **на 100% без единого теста**. Если роль R корректно работает с
объектом O под принципалом P — авторизованы все места вызова, работающие с O как R.

**Момент и место:** внутри `BEGIN … ROLLBACK` на живой базе, под `SET ROLE`, с установленным
принципалом, **исполнением, а не планированием**. Поэтому все семь способов вранья планировщика
исчезают разом: планировщика здесь нет.

**Нюанс для реализации:** `SET ROLE` **не применяет** `rolconfig` роли (у трёх ролей там
`search_path=public, integrator`), поэтому проба обязана выставлять `search_path` явно. Логин-факты
(`pg_hba`, `rolconfig`, `options` в строке подключения) остаются за существующим
`deploy/host/assert-c4-operational-runtime-ready.sh`.

## 4. Как ловится тихий ноль, частичная и избыточная видимость

Не эвристика «вернулось ли что-нибудь», а **равенство независимому эталону**. С установленным
принципалом организации A, для каждой таблицы с `organization_id`:

```sql
-- УТЕЧКА (избыточная видимость) — обязано быть 0
SELECT count(*) FROM t
 WHERE organization_id IS NOT NULL AND organization_id <> :orgA;   -- под ролью

-- СЛЕПОТА (тихий ноль и частичная — одним уравнением) — обязано быть равно
SELECT count(*) FROM t WHERE organization_id = :orgA;   -- под ролью
SELECT count(*) FROM t WHERE organization_id = :orgA;   -- под владельцем (эталон)
```

| Соотношение | Класс |
|---|---|
| `утечка > 0` | избыточная видимость |
| `роль = 0` и `эталон > 0` | тихий ноль |
| `0 < роль < эталон` | частичная видимость |
| `роль = эталон`, `утечка = 0` | чисто |

Одно сравнение, три класса, ошибка не нужна.

**Спутник, не зависящий от данных.** Проба выше видит утечку только там, где у второго арендатора
есть строки. Один каталожный запрос ловит ту же форму без данных вообще: таблица с
`organization_id`, читаемая арендной ролью, **обязана** иметь RLS+FORCE. Живьём — 5 нарушений
(FINDINGS §3.3).

**Новая колонка в `SELECT *`.** Тот же механизм со вторым столбцом эталона: каждая ячейка хранит
набор колонок, видимых роли (`has_column_privilege`). `ADD COLUMN` меняет набор → эталон краснеет
→ решает человек. Без дополнительной машинерии.

**Правило области объявляется.** Правило «своя организация» верно для staff-подобных ролей и
неверно для `app_patient`, у которого стена — только свои данные. Отсюда единственный
декларативный файл: **11 строк**, по одной на рантайм-роль, `роль → область ∈ {ORG, OWN, GLOBAL,
NONE}`. Ожидания для 235 таблиц выводятся из этих 11 строк плюс живой каталог.

## 5. Почему записи именно две, а не одна

| Группа ролей | Что видит матрица | Что видит журнал |
|---|---|---|
| 6 операционных | почти всё «запрещено» — они работают через definer-функции, матрица к ним слепа | их реальный дефект: 61 050 отказов в сутки |
| `app_staff`, `app_patient` | утечка / слепота / чисто | **ничего** — видимость не даёт ни строчки в журнал |

Каждая запись слепа ровно там, где видит другая. Это разбиение задачи, а не дублирование проверок.

## 9. Долгосрочный горизонт — не сейчас

Второй генератор предложил конечное состояние: **закрытый capability-API** — рантайм-роли лишаются
всех прав на таблицы, колонки и последовательности и могут только вызывать фиксированный список
функций; приложение теряет произвольный SQL и получает генерируемых клиентов своего контура.
Обойти нельзя, потому что прав просто нет.

Он сам оценивает миграцию как «большую»: это переписывание всего доступа к БД, отмена `Pool` и
Drizzle. Записано как направление, которому v4 не противоречит — способ доказательства остаётся
тем же. Решение о движении туда — владельца, и не раньше, чем закроются шаги 0–4.

## 10. Остаточный риск

Дизайн, заявляющий нулевой риск, — провальный. Здесь риск назван.

1. **Ячейки «недоказано».** Проба не может судить о таблице, где у арендатора-противника нет
   строк. Ш5 сводит 200 → ~0, но каждая новая таблица начинается отсюда. Гейт падает, если их
   число **растёт**. Нулём не станет никогда.
2. **Авторизация записи детектируется, а не предсказывается.** Отказ на пути, который нигде не
   исполнялся, невидим до первого исполнения. Принято сознательно — синтез валидных строк для 172
   таблиц с внешними ключами и есть та работа, на которой раздулся бы v3.
3. **Гашение внутри сервера.** `EXCEPTION`-обработчик в plpgsql перехватывает ошибку до журнала.
   Сегодня таких 4 из 253, ни один не `WHEN OTHERS`. Ш4(ii) замораживает список, но обработчик,
   добавленный **внутрь** одной из этих четырёх, — реальное слепое пятно, лечится только ревью.
4. **Семантическая правильность вне охвата.** Гейт доказывает, что БД исполняет объявленное в
   `roles.tsv`. Если объявлена неверная гранулярность — гейт зелёный, продукт неверный. Ловится
   только продуктовым суждением владельца.
5. **Ротация журнала.** Отказ, случившийся однажды, может выпасть из окна (65 МБ за ~6 дней).
   Лечится тем, что строки эталона не удаляются автоматически — только человеком.
6. **`SET ROLE` ≠ вход по логину.** Матрица не проверяет `pg_hba`, `rolconfig` и `search_path` из
   строки подключения (`platformUserFullPurge.ts` ставит обратный порядок схем, а имена
   `idempotency_keys` и `schema_migrations` существуют в обеих). Покрыто частично двумя разными
   средствами: существующим readiness-гейтом и 42P01 в журнале.
7. **Root может выключить.** Правка `postgresql.conf` или удаление гейта из деплоя.
8. **Инструменты.** Гейту нужен `sudo -u postgres`. Агенты через Codex-порт до базы не достают
   (`no_new_privileges`), Opus-агенты достают. Гейт живёт как шаг деплоя или крона, его вывод
   коммитится, иначе агенты в песочнице не смогут проверить собственную работу.

## 11. Что сознательно НЕ делаем

`EXPLAIN` в любом виде · статический анализ мест гашения · M1 (бросок из порта, инцидент из порта,
правка ~177 мест) · программу покрытия тестами и сбор `db-surface.tsv` · модель выполнимости
политик (M3) · декларативный генератор прав, переписывание миграций, новые измерения реестра (M5) ·
консолидацию пулов · синтез строк для проб записи · смену фреймворка · новые зависимости.

Каждый пункт отвергнут не по вкусу, а по доказательству — FINDINGS, часть 4.
