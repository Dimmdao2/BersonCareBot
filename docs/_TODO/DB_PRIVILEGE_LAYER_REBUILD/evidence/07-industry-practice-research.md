## 1. Декларативное управление правами

### Atlas — заявление «не покрывает SECURITY DEFINER» ЛОЖНО, проверено

Atlas HCL для PostgreSQL имеет атрибут `security` на блоках `function`/`procedure`
(`enum (DEFINER, INVOKER)`), блоки `role` с `bypass_rls`, блоки `permission`
(schema/table/view/function/sequence/**column**), блоки `policy` (PERMISSIVE/RESTRICTIVE),
`ALTER DEFAULT PRIVILEGES`.

- https://atlasgo.io/hcl/postgres · https://atlasgo.io/guides/postgres/security-declarative
- Более того: Atlas несёт **линт-предикаты** `row_security_enabled { eq = true }`,
  `row_security_enforced { eq = true }`, правило `no-unexpected-bypassrls`
  («BYPASSRLS только по аудируемому allowlist, никогда на login-роли»), предикат
  `security { eq = "INVOKER" }`. https://atlasgo.io/guides/rls-policy · https://atlasgo.io/hcl/rule
- **Цена:** роли, права, RLS, функции, sequences и тест-фреймворк — всё в **Atlas Pro**,
  $9/место/мес, 30 дней триала, требует облачной авторизации. https://atlasgo.io/pricing
- **Применимо здесь.** Единственный инструмент, покрывающий всю поверхность одной моделью И
  умеющий линтить ровно те инварианты, которые здесь нашли живьём. Блокер — лицензия и облачный
  вход, а не возможности. **Решение, принятое на ложной посылке, следует переоткрыть.**

### pgschema — бесплатная альтернатива с одной решающей дырой

Apache 2.0, только Postgres. Покрывает GRANT/REVOKE для таблиц **включая колоночные**, sequences,
функции, процедуры, типы, `WITH GRANT OPTION`; политики RLS с PERMISSIVE/RESTRICTIVE, покомандно,
USING/WITH CHECK; функции с SECURITY DEFINER; `ALTER DEFAULT PRIVILEGES`.

- https://github.com/pgplex/pgschema · https://www.pgschema.com/syntax/grant_revoke.md
- **НЕ поддерживает:** `CREATE ROLE`/`CREATE USER`, `CREATE SCHEMA`, `CREATE EXTENSION`,
  `CREATE EVENT TRIGGER`, publications, RENAME. https://www.pgschema.com/syntax/unsupported.md
- **Частично применимо:** покрыл бы 1369 строк грантов + 291 политику + 253 ACL функций бесплатно,
  но 45 ролей потребуют отдельного механизма. Молодой проект.

### pg_permissions (Cybertec) — паттерн, к которому здесь пришли независимо

Таблица `permission_target` хранит желаемое состояние; `permission_diffs()` возвращает строки, где
`missing = TRUE` (должно быть, нет) и `missing = FALSE` (есть, не объявлено). Обновляемые
представления выполняют GRANT/REVOKE. NULL-колонки работают как wildcard. Покрывает базу, схему,
таблицу, представление, **колонку**, sequence, **функцию**.

- https://github.com/cybertec-postgresql/pg_permissions
- Процитирован в **CIS PostgreSQL 12 benchmark**.
- **Не покрывает:** политики RLS, роли, default privileges.
- **Применимо напрямую, и это самая обнадёживающая находка отчёта.** Здешний
  `c5a-platform-operations-runtime.sql` с двусторонним `expected EXCEPT actual` по table ACL +
  function ACL + инвентарю политик — **это и есть** данный паттерн, полученный независимо, с
  прецедентом уровня отраслевого стандарта. Работа — **расширить его на все 45 ролей**, а не заменять.

## 2. Схема против прав в миграциях

**Единой нормы нет, но рассматриваемое разделение — нормально и поддержано вендорами.** Liquibase
предписывает явно. Flyway даёт механизм. dbt в версии 1.2 вынес гранты из хуков в декларативный
конфиг именно потому, что хуки вызывали **простой с «permission denied» между прогонами моделей**.
https://docs.getdbt.com/blog/configuring-grants

**Три находки, меняющие подход:**

**(а) ❌ `ALTER DEFAULT PRIVILEGES` не спасёт — четыре причины из документации.**
«Не влияет на привилегии уже существующих объектов»; «права на новые объекты определяются
default-привилегиями **текущей роли** и **не наследуются** от ролей, членом которых она является»;
привязаны к **создающей** роли; посхемные defaults только добавляют и не могут отозвать глобальный
грант. https://www.postgresql.org/docs/current/sql-alterdefaultprivileges.html
**Применимо:** при 377 миграциях смешанного происхождения и 244 definer-функциях следует
предполагать дыры, а не покрытие. Любой план на «настроить defaults один раз» несостоятелен.

**(б) ❌ Два движка, спорящих за один ACL, — задокументированный `wontfix`.** dbt-core #6238: на
инкрементальных моделях `apply_grants` отзывает гранты, не переприменяя выведенные из
default-привилегий, **затирая права, выставленные другой системой**. Закрыт как wontfix.
https://github.com/dbt-labs/dbt-core/issues/6238
**Применимо:** что бы ни выбрали, оно должно быть **единственной** властью над теми ACL, которых
касается. Не накладывать desired-state движок поверх default privileges.

**(в) Политики RLS должны остаться версионируемыми.** Никто из авторитетных не советует слепое
переприменение тел политик; движок диффа Supabase не видит `ALTER POLICY`; и принципал мигратора
взаимодействует с политиками.

**Путь консолидации для 107 смешанных + 57 «только права»:** устоявшаяся практика —
**сжать в baseline, сохранив историю**. Протокол Django нагляднее всех: сжать → сохранить старые
файлы → выпустить → дождаться обновления всех систем → **только потом** удалить. Flyway советует
архивировать, а не удалять; Atlas `baseline` помечает миграцию применённой без выполнения.
Приёмочный тест: прогнать старый и сжатый пути в контейнерах и **сравнить
`information_schema.role_table_grants` + `pg_policies`**.

**Пробел:** не найдено **ни одного** рассказа от первого лица о команде, вынесшей GRANT-ы из потока
миграций. Никто этого не публиковал.

## 3. Доказательство изоляции арендаторов

**Да, практика установлена — и есть ровно одно авторитетное предписание.**

**AWS Well-Architected SaaS Lens, REL_3** — «Как вы тестируете мультиарендные возможности вашего
SaaS?» Best practice *Validating tenant isolation*: «Создайте тесты, проверяющие, что приложение
применяет политики изоляции»; «Внедряйте токены арендатора, имитирующие SaaS-личность»; «Создайте
тесты, пытающиеся сменить контекст арендатора подстановкой другого идентификатора. Убедитесь, что
подстановка не пересекает границу арендатора»; и где изоляцию обеспечивает общий фреймворк —
«введите тесты, нагружающие эти фреймворки и проверяющие, что они корректно применяют политики».
https://wa.aws.amazon.com/saas.question.REL_3.en.html

✅ **Последняя фраза важна: предписано тестировать ФРЕЙМВОРК, а не каждую таблицу.** Стенд,
покрывающий одну таблицу, — не «1 из 235 сделано», а правильная форма; остальное покрытие берётся
другим механизмом.

**Как индустрия масштабируется на 235 таблиц: каталожный свип, а не 235 стендов.**

- **Supabase Splinter** — поддерживаемые вендором SQL-запросы над `pg_catalog`, их Security
  Advisor. Нужные правила: `0007_policy_exists_rls_disabled`, `0008_rls_enabled_no_policy`,
  `0013_rls_disabled_in_public`, `0010_security_definer_view`,
  `0006_multiple_permissive_policies`, `0003_auth_rls_initplan`. **Обычный SQL, Supabase не
  требуется.** https://supabase.github.io/splinter/
- **GitLab** доказывает паттерн на 1000+ таблиц без RLS: каждая org-таблица обязана объявить
  `sharding_key`, что проверяется одним спеком, перебирающим всю схему.

**pgTAP даёт точные двусторонние проверки прав — прямой ответ на 1369 строк грантов.**
`table_privs_are`, `function_privs_are`, `column_privs_are`, `policies_are`, `policy_roles_are`,
`policy_cmd_is` — все сообщают и *«Extra privileges:»*, и *«Missing privileges:»*.
https://pgtap.org/documentation.html

✅ **Паттерн pgsodium — тот, что стоит скопировать:** проверить ожидаемую матрицу, затем одним
set-returning вызовом свести все *остальные* роли к пустому множеству:
```sql
SELECT table_privs_are('pgsodium','key', rolname, '{}'::text[])
  FROM pg_catalog.pg_roles WHERE rolname NOT IN (...);
```
**Три пробела, которые pgTAP НЕ покрывает — писать самим:** `relrowsecurity` (RLS включена),
`relforcerowsecurity` (**FORCE**), атрибуты ролей (`rolbypassrls`).

**Прецедент в здравоохранении — честный ответ: его нет.** **Medplum**, ведущая открытая
FHIR-платформа, имеет **ноль** вхождений `ENABLE ROW LEVEL SECURITY` — доступ обеспечивается на
уровне приложения. Aidbox использует отдельные инстансы. **Nile прямо отвергает RLS** как «сложную
в поддержке, отладке и подверженную ошибкам». **PlanetScale не рекомендует RLS**, называя
*«ошибки конфигурации политик, молчаливые отказы и взаимодействие с пулингом соединений»* — ровно
наш класс дефектов. https://planetscale.com/blog/approaches-to-tenancy-in-postgres

**Регуляторика — в основном миф.** Ни HIPAA, ни HITRUST, ни SOC 2 не называют тестирование
изоляции арендаторов. HIPAA §164.308(a)(8) требует периодической оценки без указания метода.
Рычаг обратный: **записать контроль самим** — «каждый деплой прогоняет автоматический гейт изоляции»
становится аудируемым контролем SOC 2, а история CI — доказательством.

❌ **Поправка к набору проверок стенда:** «чужой доступ вернул 0 строк» недостаточно. Нужно
проверять, что **свой доступ вернул ровно ожидаемое N**. Иначе политика, молча возвращающая
*подмножество своих же данных*, проходит тест при сломанном приложении. Публичных источников с
такой проверкой нет — это наше преимущество, а не отставание.
*(Внедрено 2026-08-08, коммит b0bebf320.)*

**Зафиксировать минорную версию PG16.** Есть три CVE на корректность RLS: CVE-2024-10976 (RLS ниже
подзапросов игнорирует смену пользователя), CVE-2025-8713 (статистика оптимизатора раскрывает
данные строк, скрытых RLS), CVE-2023-2455. https://www.postgresql.org/support/security/

## 4. Молчаливый отказ и тихий ноль

### ⚠️ Крупнейшая находка: в Postgres есть переключатель, превращающий тихую фильтрацию RLS в ошибку

`row_security` (boolean), дословно из документации:

> «Эта переменная определяет, вызывать ли ошибку вместо применения политики защиты строк. При `on`
> политики применяются обычным образом. **При `off` запросы, к которым применилась бы хотя бы одна
> политика, завершаются ошибкой.** По умолчанию `on`. **Меняйте на `off` там, где ограниченная
> видимость строк может привести к неверным результатам**; например, pg_dump делает это по
> умолчанию. Переменная не действует на роли, обходящие все политики, — суперпользователей и роли
> с атрибутом `BYPASSRLS`.»

И из главы про RLS: «Установка `row_security` в off сама по себе не обходит защиту строк; она
**вызывает ошибку, если результаты запроса были бы отфильтрованы политикой. Причину ошибки затем
можно исследовать и устранить.**»

- https://www.postgresql.org/docs/16/runtime-config-client.html
- https://www.postgresql.org/docs/16/ddl-rowsecurity.html

**Это первоклассная возможность самой СУБД, чьё назначение по документации — ровно наш класс
«тихого нуля», и в плане она не фигурировала ни разу.** Прогонять смоук/интеграционный набор под
каждой реальной login-ролью с `row_security = off`: каждый путь, зависящий от фильтрации RLS,
поднимет ошибку вместо молчаливого урезания. `platform_users` под принципалом интегратора упал бы
громко при первом же прогоне. Диагностический инструмент, не продакшн-настройка.

*(Проверено на живой TEST 2026-08-08: `SET row_security = off` под `app_staff` →
`ERROR: query would be affected by row-level security policy for table "system_settings"`.
Тот же запрос при `on` молча вернул 111 строк.)*

### Проглоченный 42501

✅ **Журнал сервера — отраслевой ответ, он уже включён, и в нём уже лежат все десять дефектов.**
`log_min_messages` по умолчанию `WARNING`, что **включает** `ERROR`. `log_min_error_statement` по
умолчанию `ERROR` — «операторы, вызвавшие ошибки, будут залогированы»; чтобы это выключить, нужно
поставить `PANIC`. Добавить `log_error_verbosity = verbose` (или `jsonlog`/`csvlog`) для
машиночитаемого SQLSTATE. Кодифицировано как контроль: Datadog поставляет его с привязкой к
**CIS Controls v8 §8.5**. https://www.postgresql.org/docs/16/runtime-config-logging.html

**Применимо в высшей степени:** единственная точка наблюдения, покрывающая все ~2353 места вызова
и все 9+ пулов, без единой правки кода, ретроспективно. Тик планировщика, падавший 17 246 раз в
сутки, писал 17 246 строк в сутки неделями. Добавить `%a` в `log_line_prefix` и отдельный
`application_name` на пул, чтобы отнести залогированный 42501 к конкретному из девяти.

❌ **pgaudit доказанно слеп к отказам — не ставить ради этого.** `log_select_dml()` висит на
`ExecutorCheckPerms_hook`, который PostgreSQL вызывает **только после** успешной проверки прав.
Отклонённый оператор возвращается раньше. Проверено по исходникам обоих проектов. README самого
pgaudit признаёт, что путь ошибок принадлежит «стандартному механизму логирования».

❌ **Не рассчитывать на APM/OpenTelemetry — спецификация предписывает обратное.** Раздел Recording
Errors, дословно: «Ошибки, которые были повторены или обработаны (позволив операции завершиться
штатно), **НЕ ДОЛЖНЫ** записываться в спаны или метрики, описывающие эту операцию.» Все 177 мест
гашения — «обработанные» ошибки по этому определению. Корректная настройка OTel закономерно отбросит
ровно нужный сигнал. https://opentelemetry.io/docs/specs/semconv/general/recording-errors/

✅ **Удалённый AST-анализатор — не некомпетентность: задача статически неразрешима.** «Error hiding»
— каталогизированный антипаттерн с настолько скудной литературой, что статья в Wikipedia ссылается
на **один** источник. Два линтера, на которые обычно кивают, не покрывают: ESLint `no-empty` целит
только в *пустые* блоки (catch с возвратом дефолта проходит), а `@typescript-eslint/no-floating-promises`
**удовлетворяется наличием `.catch()`** — все 577 мест `.catch(() => default)` проходят его чисто.
Настраивать нечего. Результат 0/6 был верным.

⚠️ **Отдельно: «всегда бросать» отвергнуто, но Result-типы — другое, и отказ на них не переносится.**
Всегда-бросать отнимает у вызывающего выбор и ломает документированные fail-open пути. Возврат
`Result<T, DbError>` из порта не отнимает ничего: fail-open пути остаются законными и продолжают
работать, но становятся **явными ветками, которые компилятор заставил кого-то написать**. Режим
отказа, положивший TEST, при этом невозможен — компилятор ловит до деплоя. Effect (Cloudflare,
MasterClass, OpenRouter) и neverthrow (~500 тыс. загрузок в неделю) — мейнстримные реализации.
Честная оговорка: строгих кейсов миграции ради устранения молчаливых отказов не найдено, и 2353
места осилимы только постепенно, начиная с порта.

**Детект избыточной видимости и подмножеств в рантайме: устоявшейся практики нет.** «Canary row»
как термин означает **honeytoken** — обнаружение несанкционированных *чтений*, обратное нужному.
Мониторы количества строк в data-observability работают под привилегированными учётками, которые
RLS не фильтрует. `pgaudit.log_rows` — единственный готовый счётчик строк на оператор, дорогой.
**Строя пробы с засеянной видимостью, вы опережаете опубликованную практику, а не догоняете её.**

## 5. Capability-only API базы данных

❌ **Конечное состояние, к которому сошлись оба генератора, противопоказано всеми найденными
авторитетами по Postgres и ухудшило бы положение.**

**Паттерн реален, но это ответ SQL Server.** Microsoft документирует явно: «выдавайте только права
EXECUTE на хранимые процедуры; права на нижележащие таблицы можно отозвать или запретить» — и это
опирается на **цепочку владения (ownership chaining)**, которой в Postgres **нет**. Эквивалент в
Postgres — `SECURITY DEFINER`, более рискованная конструкция.
https://learn.microsoft.com/en-us/previous-versions/dotnet/framework/data/adonet/sql/managing-permissions-with-stored-procedures-in-sql-server

**Все нативные авторитеты Postgres предписывают явные GRANT на таблицы + RLS + FORCE RLS**, считая
definer-функции аудируемым исключением:

- **PostgREST** (каноническая система «база как API»): `GRANT SELECT, INSERT, UPDATE(message_body),
  DELETE ON chat TO webuser;` плюс RLS. https://docs.postgrest.org/en/v12/explanations/db_authz.html
- **Supabase**: «используйте оба контроля для каждого открытого объекта»; «RLS не применяется к
  функциям… **тщательно проверяйте каждую SECURITY DEFINER функцию**». Их изменение от октября 2026
  двигалось **к** явным грантам на таблицы, а не от них.
- **Nile, pgEdge, AWS** предписывают RLS на таблицах + сессионные переменные; definer-представления
  и функции упоминают только как опасность.
- **DISA PostgreSQL STIG** CD12-00-002200: предписанный текст исправления — буквально
  `GRANT SELECT ON TABLE test.test_table TO bob`. Стандарт хардининга Минобороны США не требует
  capability-only.
- **OWASP Database Security Cheat Sheet** ни разу не упоминает доступ только через процедуры.

❌ **Решающее техническое возражение из первичной документации:** «Владельцы таблиц **обычно
обходят защиту строк**… хотя владелец может выбрать подчинение ей через
`ALTER TABLE ... FORCE ROW LEVEL SECURITY`», и «`NO FORCE ROW LEVEL SECURITY` … **по умолчанию**».

Пропуск 100% рантайм-доступа через 244 definer-функции превращает **291 политику, которые применяет
сам движок**, в **244 императивных тела, корректность которых зависит от того, вспомнил ли автор про
фильтрацию** — и делает FORCE RLS на всех 235 таблицах единственным несущим инвариантом, который,
отпав на одной таблице, молча аннулирует её арендную стену без всякой ошибки. Сейчас FORCE есть на
176 из 239. Это чистая потеря аудируемости — обратное тому, что нужно истории про здравоохранение.

❌ **Внутреннее опасение верно: проверить права внутри тела definer-функции нельзя без исполнения.**
`plpgsql_check` проверяет идентификаторы, существование объектов и типы — **не ACL**, и его README
дословно гласит «этот инструмент нельзя использовать для аудита безопасности». Структурно: ACL
таблиц проверяются на старте исполнителя (`ExecCheckPermissions`), поэтому никакой анализ на этапе
разбора или планирования не выявит недостающий GRANT. https://github.com/okbob/plpgsql_check

✅ Но `plpgsql_check` **стоит** прогнать пакетно по всем 253 функциям: он ловит половину слепого
пятна — дрейф схемы (тело ссылается на таблицу или колонку, которых больше нет) — дёшево.

Единственная нереализованная идея, которую никто не опубликовал: соединить вывод
`plpgsql_show_dependency_tb()` с `has_table_privilege(<владелец функции>, relid, …)`.

**Названных институциональных внедрений не найдено.** «Так делают банки» — неподтверждённый фольклор
во всём прочитанном. Опубликованных данных о стоимости перехода к functions-only API или обратно —
ноль. **Оценка: избыточное усложнение на этом масштабе, притом снижающее аудируемую безопасность.**

**Защитимая середина, на которой реально живёт экосистема:** узкие явные GRANT на таблицы + RLS +
FORCE RLS как применяемая стена; `SECURITY DEFINER` только там, где политикой правило не выразить,
и в объёме, поддающемся ручному ревью; каталожные линты как гейты CI (`search_path` на каждой
definer-функции — здесь уже 0 нарушений; `EXECUTE` никогда для PUBLIC — уже 0; FORCE RLS на каждой
RLS-таблице — 176 из 239).

## Три находки, наиболее вероятно меняющие дальнейшие действия

### 1. `SET row_security = off` — детектор тихого нуля уже поставляется с Postgres

Механизм M3 выдумывался, чтобы вычислять выполнимость политик статически, и был опровергнут. База
**сама скажет** — настоящей ошибкой, на настоящей роли, через настоящий путь кода.

### 2. Место детекта — журнал ошибок Postgres, а два очевидных кандидата доказанно слепы

Каждый из десяти дефектов писал строку ERROR с текстом оператора, по умолчанию, месяцами.
Отгрузка журнала + алерт на класс SQLSTATE 42 покрывает все 2353 места вызова и все 9 пулов **без
единой правки кода**, ретроспективно, и это контроль, привязанный к CIS. При этом **pgaudit не
видит отказов**, а **спецификация OpenTelemetry предписывает отбрасывать обработанные ошибки** —
то есть ровно наши 177 мест гашения. Любой план на APM делает этот класс *менее* заметным.
Отдельно: отказ от «всегда бросать» не отменяет Result-типизированный порт — это другой механизм с
другим режимом отказа, и он заслуживает отдельного рассмотрения.

### 3. Конечное состояние (capability-only) — неверная цель, а инструмент, отвергнутый по ложной
посылке, стоит переоткрыть

**Первое:** ноль прав на таблицы + только EXECUTE — паттерн SQL Server на цепочке владения,
которой в Postgres нет; ни один авторитет Postgres его не одобряет; и поскольку definer-функция,
принадлежащая владельцу таблицы, обходит RLS без FORCE, это понизило бы сильнейший актив — 291
политику, применяемую движком, — до 244 императивных тел, которые ни один инструмент в мире не
проверит без исполнения. **Второе:** «Atlas не покрывает SECURITY DEFINER» — ложь.

**И хорошая новость, которую стоит сказать прямо:** `c5a` с двусторонним `expected EXCEPT actual` —
не местная самоделка, а паттерн pg_permissions, процитированный в стандарте CIS. Все семь находок
«EXPLAIN врёт» — поимённо каталогизированные ловушки RLS (в списке Bytebase из 16 присутствуют
все). Здесь сошлись на правильных примитивах и затем попытались масштабировать их единственным
способом, которым их не масштабирует никто, — перечислением поверхности запросов. Мир масштабирует
их **каталожным свипом**: шесть однострочных проверок «ноль строк» над `pg_class`/`pg_policies`/
`pg_roles` (RLS включена, FORCE выставлен, нет RLS-таблиц без политик, нет политик `TO PUBLIC`, нет
представлений без `security_invoker=true`, нет неожиданного `rolbypassrls`) плюс точечные
`table_privs_are`, управляемые из `pg_roles`. Это достаёт до всех 235 таблиц и всех 45 ролей уже
сегодня, а в pgTAP не хватает лишь трёх проверок, которые пишутся руками.

**Два меньших пункта на будущее:** колоночные GRANT заставляют `SELECT *` **падать громко** для
такой роли — это реальный проверяемый ответ на находку про новую колонку, молча втекающую в
существующие запросы. И проблема обхода девяти пулов (51 файл с сырым `pg.Pool`) — решённая
категория: `dependency-cruiser` позволяет задать **allowlist** разрешённых импортёров (ESLint
`no-restricted-imports` умеет только запрещать), это стандартная «architecture fitness function»
для принуждения к единой точке входа.
