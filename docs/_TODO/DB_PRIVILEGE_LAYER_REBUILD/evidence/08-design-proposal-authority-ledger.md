# Дизайн «Реестр полномочий» — предложение независимого архитектора (Opus)

**Дата:** 2026-08-08. **Записано в репозиторий:** существовало только в переписке.
**Статус:** частично опровергнуто последующим исследованием практики (см. §«Что не выдержало»).
Ценность — в проверенных живьём фактах и в двух механизмах, которые устояли.

## Находка, переформулировавшая задачу

Доказательства всех десяти дефектов **уже существуют** и лежали всё это время:

```
$ sudo -u postgres grep -c "ERROR:  permission denied" /var/log/postgresql/postgresql-16-main.log
141248
```

Один `grep` даёт полный живой инвентарь: роль, точный оператор, частота.

| Строк | Роль | Отказ |
|---:|---|---|
| 61 187 | `bcb_test_operational_scheduler_login` | функция `current_org_id` |
| 61 050 | `bcb_test_operational_scheduler_login` | таблица `operator_job_status` |
| 15 149 | `bcb_test_operational_delivery_login` | функция `current_org_id` |
| 1 306 | `bcb_test_operational_diagnostic_login` | функция `release_principal_context` |
| 720 | `bcb_test_staff_login` | таблица `saas_paid_period_policy` |
| 140 | `bcb_test_nonstaff_login` | функция `staff_user_has_password_credentials` |
| 34 | `bcb_test_operational_web_push_reminder_login` | **нарушение WITH CHECK политики `c4_web_push_reminder_status_restrictive`** |
| 16 | `bcb_test_operational_delivery_login` | `relation "projection_outbox" does not exist` (42P01, search_path) |

В списке присутствуют классы, которые статика поймать не может: `WITH CHECK` и 42P01 по search_path.

**Почему это структурно, а не везение.** Postgres пишет строку внутри серверного процесса, **до**
того как ErrorResponse пересечёт сокет. `try { await port() } catch {}` в Node выполняется позже.
Код Node не может стереть строку, которую сервер уже записал. Все ~177 мест гашения, все 577 форм
`.catch(() => default)`, все 9 пулов, все 51 сырой `new pg.Pool` и все 2353 места вызова —
**ниже по течению**, потому что говорят с одним и тем же постмастером.

**Это снимает главное противоречие v3.** M1 требовал, чтобы отказы *распространялись* — иначе
человек не узнает; fail-open пути требуют, чтобы они *не распространялись* — иначе рушится входящая
переписка. Конфликт был неразрешим, **пока видимость требовала распространения**. Она не требует:
запись сделана до того, как исключение стало объектом JavaScript.

**Отрицательный контроль, проверенный отдельно:** прямое чтение таблицы планировщиком **уже
исправлено в коде** (`operatorHealthDrizzle.ts:96-101`, с комментарием про этот самый 42501) — за
условием `getCurrentIntegratorTechnicalRuntimeRole() === 'app_operational_scheduler'`, которое
(`withClient.ts:56-66`) **угадывает роль в Node**, сопоставляя строку источника принципала с
захардкоженным множеством. На TEST догадка ложна, и код 17 тысяч раз в сутки идёт прямым путём.
Написанный комментарий, влитая починка и зелёный readiness-гейт этого не остановили. Знает только журнал.

## Механизм: две записи самой БД

- **Журнал** — какие полномочия *запрашивались* и получили отказ. Пишется сервером, клиентом не подавляется.
- **Каталог + живая проба** — какие полномочия *существуют*. Проверяется исполнением настоящих
  операторов под настоящими ролями с настоящим принципалом.

Один гейт читает обе, сверяет с зафиксированным эталоном, падает закрыто.

**Жёсткость, честно и асимметрично:**
- *Сторона каталога — превентивная.* Нельзя добавить таблицу без строки в `pg_class`, выдать право
  без записи в `relacl`, создать роль без `pg_roles`, добавить политику без `pg_policies`.
- *Сторона журнала — детективная, с задержкой в одно исполнение.* Агент может написать код,
  требующий права, которого никто не выдавал. Но при первом же исполнении — в тесте, смоуке, тике
  планировщика, вебхуке — сервер это запишет, и следующий прогон гейта красный.

**Чем можно сломать:** правкой `postgresql.conf` или удалением гейта из деплоя. Оба — root и
одиночный очевидный дифф. Проверено: `log_min_error_statement` и `log_min_messages` имеют
`context=superuser`, то есть сессия не может отключить логирование сама себе.

## Где доказывается авторизация: на ячейке, а не на месте вызова

v3 пытался доказывать на каждом из 2353 мест вызова, что требует покрытия кода — а покрытие ~0% и
структурно не поднимается (тики планировщика, ~40 типов задач воркера, вебхуки, компенсирующие пути
тестами не покрываются никогда).

Авторизация — свойство не места вызова, а тройки `(роль, объект, принципал)`. Это множество
конечно, перечислимо из `pg_class` × `pg_roles` и **покрывается на 100% без единого теста**.

**Замерено:** 11 ролей × 172 org-таблицы = **1892 ячейки за 1,5 секунды**.

`SET ROLE` из суперпользовательской сессии применяет и ACL, и RLS — проверено:
`SET ROLE app_patient; SELECT count(*) FROM public.system_settings` → `permission denied`;
та же роль на `public.platform_users` (RLS+FORCE) → `0` строк при реальных 278.

**Оговорка, требующая учёта:** `SET ROLE` **не применяет** `rolconfig` роли (у трёх ролей там
`search_path=public, integrator`), поэтому проба обязана выставлять `search_path` явно.

## Детект тихого нуля, частичной и избыточной видимости

Инвариант формулируется как **равенство фиксированному значению**, а не суждение о данных:

```sql
-- УТЕЧКА (избыточная видимость): обязано быть 0
SELECT count(*) FROM t WHERE organization_id IS NOT NULL AND organization_id <> :orgA;  -- под ролью
-- СЛЕПОТА (тихий ноль + частичная, одним уравнением): обязано быть равно
SELECT count(*) FROM t WHERE organization_id = :orgA;  -- под ролью
SELECT count(*) FROM t WHERE organization_id = :orgA;  -- под владельцем (эталон)
```

**Живой результат для `app_staff` по всем 172 org-таблицам, 0,8 секунды:**

```
ЧИСТО = 167     ЗАПРЕЩЕНО = 4     УТЕЧКА = 1     СЛЕПОТА = 0
```

167 из 172 удовлетворяют инварианту без всякой подгонки — это тест на доверие к правилу: оно
*верное*, а не флагующее всё подряд. Удалённый AST-детектор дал 0 верных срабатываний из 6; здесь —
1 находка на 172, и находка настоящая:

```
LEAKED_ROW: {"id":"d7779cf5-…","organization_id":"da6a96cb-8e94-4ec2-99da-2258bda0ce4d",
             "platform_user_id":"d4453e69-…","role":"owner","status":"active", …}
```

С установленным принципалом организации A роль `app_staff` читает запись о владельце организации B.
У `public.be_organization_members` `relrowsecurity = false`.

**По всем 11 ролям — 7 ячеек утечки**, включая межарендный биллинг:

```
app_platform_settings | public.saas_billing_invoices        | чужих строк = 4
app_platform_settings | public.saas_billing_subscriptions   | чужих строк = 2
app_platform_settings | public.saas_billing_provider_events | чужих строк = 2
app_platform_settings | public.saas_billing_accounts        | чужих строк = 1
app_platform_settings | public.admin_audit_log              | чужих строк = 1
app_platform_settings | public.be_organization_members      | чужих строк = 1
app_staff             | public.be_organization_members      | чужих строк = 1
```

**Спутник, не зависящий от данных** (ловит ту же форму, когда второго арендатора ещё нет):
таблица с `organization_id`, читаемая арендной ролью, обязана иметь RLS+FORCE.
**Живьём: 5 нарушений** — `appointment_records`, `be_organization_members`,
`outgoing_delivery_queue`, `patient_bookings`, `product_analytics_hourly`.

**Правило области требует объявления:** «своя организация» верно для staff-подобных ролей и неверно
для `app_patient`, чья стена — только свои данные. С неверным правилом `app_patient` даёт 65 ложных
срабатываний «тихого нуля». Отсюда единственный декларативный файл: **11 строк**,
`роль → область ∈ {ORG, OWN, GLOBAL, NONE}`.

## Почему записи именно две

| Группа | Матрица каталога | Журнал |
|---|---|---|
| 6 операционных ролей | ~100% «запрещено» на уровне таблиц — работают через definer-функции, матрица к ним **структурно слепа** | их реальный дефект: 60 613 отказов в сутки |
| `app_staff`, `app_patient` | утечка / слепота / чисто | **ни строчки никогда** — видимость не порождает ошибок |

Каждая запись слепа ровно там, где видит другая. Это разбиение пространства дефектов, а не
дублирование.

## Что не выдержало последующей проверки

Исследование мировой практики (файл `07-industry-practice-research.md`) опровергло два пункта:

1. **`row_security = off`** — Postgres умеет превращать тихую фильтрацию в громкую ошибку встроенным
   переключателем. Этот дизайн его не знал и строил детект через сравнение с эталоном. Сравнение
   остаётся полезным (оно ловит и *избыточную* видимость, чего переключатель не делает), но перестаёт
   быть единственным средством.
2. **Утверждение «журнал видит всё»** — неверно в части видимости: тихий ноль, частичная и
   избыточная видимость **не порождают строк журнала вообще**. Дизайн это признаёт в разделе о двух
   записях, но формулировка «полный инвентарь» относится только к отказам прав.

Устояли: журнал как место детекта отказов, доказательство на ячейке исполнением, необходимость
объявленного правила области, и вывод, что каталожная сторона превентивна, а журнальная —
детективна с задержкой в одно исполнение.

## Остаточный риск (из оригинала, сохранён)

1. **Ячейки «недоказано»** — таблица без строк арендатора-противника. Каждая новая таблица
   начинается отсюда; гейт должен падать при **росте** их числа. Нулём не станет никогда.
2. **Авторизация записи детектируется, а не предсказывается.** Задержка — одно исполнение.
3. **Гашение внутри сервера.** `EXCEPTION`-обработчик в plpgsql перехватывает ошибку до журнала.
   Проверено: `DO` с `EXCEPTION WHEN OTHERS THEN NULL` над несуществующей таблицей дал **0** строк
   журнала. Сегодня таких **4 из 253** функций `app.*` (`claim_unbound_patient_invite_email`,
   `install_signed_context`, `passkey_complete_registration`, `provision_specialist_owner`),
   **ни одна не использует `WHEN OTHERS`**, и 0 функций в `public`/`integrator` их несут.
4. **Семантическая правильность вне охвата.** Гейт доказывает, что БД исполняет объявленное. Если
   объявлена неверная гранулярность — гейт зелёный, продукт неверный.
5. **Ротация журнала** (65 МБ за ~6 дней): отказ, случившийся однажды, может выпасть из окна.
6. **`SET ROLE` ≠ вход по логину:** не проверяются `pg_hba`, `rolconfig`, `options` в строке
   подключения.
7. **Root может выключить.**
8. **Инструменты:** гейту нужен `sudo -u postgres`; агенты через Codex-порт до базы не достают.
