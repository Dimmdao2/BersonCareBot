# P0.5b-v2 / B5 — app_staff / app_patient table GRANTs

Status: dormant materialized ops artifact. No runtime role flip, no DATABASE_URL change, no RLS/policy
change. Closes cross-model audit finding #3 in `R2_MVP_MASTER_CHECKLIST.md` ("B5 under-grants runtime")
and the taskdb `#655` B5 checklist item, on top of the roles B4-roles-1 (`#662`) already created.

## Materialized artifact

Repeatable ops SQL: [`../../../deploy/postgres/p0-5b-grants.sql`](../../../deploy/postgres/p0-5b-grants.sql),
generated by [`scripts/p0-5b-grants-sql.mjs`](scripts/p0-5b-grants-sql.mjs). Requires
`deploy/postgres/p0-5b-role-split-staff-patient.sql` to have already created `app_staff`/`app_patient`
(fixed role names, LOGIN, NOBYPASSRLS, no credential — see `P0_5_DB_ROLE_SPLIT.md` sibling doc for that
role-creation step; this file is only the GRANT layer on top of it).

```
psql '<database-url>' -f deploy/postgres/p0-5b-grants.sql
```

Rollback: `-v p0_5b_grants_down=1` (revokes everything this script grants; does not drop the roles).

## app_staff — full runtime surface (219 tables)

Mechanically derived from `tiers-218.tsv` (`readTierRows()`): every SCOPED (157) + BOOTSTRAP (26) +
INFRA (18) + LEGACY (16) + TELEMETRY (2) table, **excluding 4 pure migration-bookkeeping tables**
(`drizzle.__drizzle_migrations`, `integrator.schema_migrations`, `public.schema_migrations`,
`public.webapp_schema_migrations` — touched only by the migrator role, never by a running process).

This closes the exact gap the cross-model audit flagged: the older single-role
`deploy/postgres/p0-5-role-split.sql` only grants SCOPED+BOOTSTRAP (183 tables), which is enough for
patient-wall RLS but NOT enough for the webapp/integrator/worker/scheduler/media-worker runtime, which
also reads/writes INFRA queues and outboxes every request (`projection_outbox`,
`integrator_push_outbox`, `outgoing_delivery_queue`, `delivery_attempt_logs`, `idempotency_keys`, …),
LEGACY Rubitime-era tables (still read by legacy sync paths), and TELEMETRY rollups. `app_staff` gets
`SELECT, INSERT, UPDATE, DELETE` uniformly on all 219 — it is the one role every non-patient session
(doctor/admin/system/worker) authenticates as, so it needs the same DML breadth the current single
shared app connection already has, just narrowed away from owner/migrator DDL privileges.

## app_patient — curated patient-only surface (111 tables)

**Not** mechanically derived. Candidate tables = the 102 patient-owned SCOPED tables (union of
`patientOwnedColumns` / `patientChainOwnedTables` / `patientConditionalOwnedColumns` /
`patientConditionalChainOwnedTables` / `patientPolymorphicOwnedTables` in `rls-descriptor-model.mjs`)
plus 9 BOOTSTRAP identity/settings tables the patient PWA reads/writes for its own account. SELECT is
the default privilege; INSERT/UPDATE/DELETE were added **only** where a 2026-07-11 code audit traced a
confirmed patient-authenticated route or repo performing that write. Every override is commented
in-line in `p0-5b-grants-sql.mjs`; the short version:

**Write-capable (38 of the 102 SCOPED tables + BOOTSTRAP as listed):**
- Booking: `be_appointments`, `be_appointment_cancellations`, `be_appointment_reschedules` (own
  create/cancel/reschedule, confirmed in `booking-appointment-lifecycle/service.ts` +
  `pgBookingAppointmentLifecycle.ts`, gated by `requirePatientBookingTrustedPhoneAccess`),
  `be_appointment_events`/`be_appointment_history_events`/`be_patient_timeline_events` (INSERT-only
  side-effect audit rows from that same request), `be_patient_booking_profiles`,
  `be_booking_form_submissions`.
- Support/chat: `support_conversations`, `support_conversation_messages`, `support_question_messages`,
  `support_questions` (`/api/patient/support`).
- Program discussion: `program_item_discussion_messages`/`_reads` (`/api/patient/messages*`, per-item
  discussion route).
- Diary/mood: `patient_diary_day_snapshots` (INSERT-only, idempotent side effect of a patient program
  action), `symptom_entries`, `symptom_trackings` (`/api/patient/diary/*`, `/api/patient/mood/*`).
- Online intake: `online_intake_requests`/`_answers`/`_attachments` (`/api/patient/online-intake*`,
  gated by `requirePatientApiBusinessAccess`); `org_enrollments` (**flagged**, see below).
- Media: `media_files`, `media_upload_sessions` (`/api/patient/media/program-submission`).
- Engagement: `patient_practice_completions`, `patient_daily_warmup_presentations`,
  `patient_daily_warmup_video_views` (`/api/patient/practice/completion`,
  `/api/patient/daily-warmup/video-viewed`).
- Content feedback: `material_ratings`, `patient_content_rating_feedback` (`/api/patient/material-ratings*`).
- `comments` (patient's own comment on its own program/lfk item — polymorphic wall, B4-core-4).
- `reminder_rules` (`/api/patient/reminders/{create,mute}`).
- LFK self-service diary: `lfk_complexes`, `lfk_sessions` (full write — patient can author its OWN
  complex, `origin` column distinguishes patient- vs doctor-authored, confirmed `pgLfkDiary.ts`),
  `lfk_complex_exercises` (UPDATE only — patient's local comment on an assigned exercise).
- `test_attempts`/`test_results` (patient takes a test).
- `program_action_log`/`treatment_program_events` (INSERT-only side-effect audit trail of the

- `product_analytics_events_recent` (`/api/patient/analytics/events` beacon; the hourly rollup

- BOOTSTRAP: `platform_users` (SELECT+UPDATE — own `calendar_timezone`/`reminder_muted_until`, NOT
  INSERT — the row is created at signup, a still-undecided B4-fanout boundary), `user_pins`
  (SELECT+INSERT+UPDATE — own login PIN), `user_channel_preferences`/`user_notification_topics`/
  `user_notification_topic_channels` (own notification toggles), `user_web_push_subscriptions`
  (SELECT+INSERT+UPDATE+DELETE — own browser push subscription).

**SELECT-only (the remaining ~64 SCOPED tables + 3 BOOTSTRAP read-only):** everything else in the
102-table patient-owned set defaults to SELECT — staff-authored clinical content
(`clinical_*`, `doctor_notes`, `doctor_patient_support`, `specialist_tasks`,

telemetry (`media_playback_*`, `product_analytics_user_hourly`), and every `integrator.*` patient-owned
table (see next section).

### `integrator.*` patient-owned tables — SELECT-only, deliberately

All 12 `integrator.*` tables in the patient-owned set (`contacts`, `content_access_grants`,
`conversation_messages`, `conversations`, `mailing_logs`, `message_drafts`, `question_messages`,
`user_questions`, `user_reminder_delivery_logs`, `user_reminder_occurrences`, `user_reminder_rules`,
`user_subscriptions`) are granted SELECT-only for `app_patient`. Their write side (Telegram/MAX message
ingestion, reminder scheduling) is currently performed by the **integrator service's own connection
identity** — a separate deployed process, not an authenticated webapp patient session. Whether the
integrator service itself will connect as `app_patient` for per-patient work (the roadmap note in
`R2_MVP_MASTER_CHECKLIST.md`'s B4-fanout item says patient sessions carry `app.integrator_user_id` too)
is an explicit **B4-fanout** connection-wiring decision, not made here. Granting INSERT/UPDATE
preemptively would risk conflicting with that undecided wiring; SELECT-only is the safe default and
does not block anything read-only (patient's own cabinet/profile views of its Telegram/MAX-side data).

### BOOTSTRAP tables explicitly NOT granted to app_patient (flagged, not an oversight)

`login_tokens`, `email_challenges`, `email_send_cooldowns`, `phone_challenges`,
`phone_messenger_bind_secrets`, `channel_link_secrets`, `user_email_setup_tokens`,
`user_oauth_bindings`, `user_password_credentials` — all are part of the **pre-session auth/challenge
flow** (login, OTP, OAuth linking, password reset). Several of these are structurally incompatible with
an "own row only" grant model: a login lookup by phone/email/token happens *before* the session knows
who the user is, so the query is not naturally scoped to `app.patient_user_id` the way every other
patient-owned predicate is — granting broad SELECT here would let an authenticated `app_patient`
connection query arbitrary other users' active challenge/token rows by phone/email. Which role
(`app_patient`, a still-undecided dedicated pre-auth service role, or something else) should own this
flow is exactly the kind of decision B4-fanout is scoped to make; excluding it now is the conservative,
intentional default this task asked for ("лучше не додать — поймаем в B4-fanout").

`be_organization_members` (staff roster — confidently staff-only), `system_settings` /
`system_settings_audit` / `integrator.system_settings` (global platform config; audit table is
staff-only, the base config table's patient-need is unconfirmed), `integrator.identities` /
`integrator.telegram_state` / `integrator.telegram_users` / `integrator.users` (integrator identity
plumbing; the patient's own integrator-side data is already reachable via the granted `integrator.*`
SCOPED tables above, keyed by `app.integrator_user_id`) are also excluded — see the generator's
comments for the identical reasoning per table.

## Flagged for extra review (owner/B4-fanout triage)

- **`public.org_enrollments`** — included with `SELECT, INSERT` on the strength of living in the same
  repo (`pgOnlineIntake.ts`) as the confirmed-write `online_intake_requests`, on the theory that a
  first-time online-intake submission can enroll the patient in an org in the same request. The exact
  call site inserting into `org_enrollments` was **not independently traced** (time-boxed audit) — worth
  re-verifying before the real B4-fanout flip.
- **`public.system_settings`** (non-audit) — excluded from app_patient on "no confirmed patient-session
  read path found," but it is plausible some authenticated patient screen wants a feature-flag/branding
  read from this table. If a permission-denied surfaces here during B4-fanout smoke, add it back with
  SELECT-only (never write — the audit table stays staff-only either way).
- **`public.user_channel_bindings` / `platform_user_contacts` / `user_phone_history`** — granted
  SELECT-only; if a patient-facing "manage my linked channels" write flow exists or is added later, it
  will need INSERT/UPDATE added here too.
- **Payment/package family** (`be_patient_packages`, `be_patient_package_items`, `be_package_usages`,
  `be_package_history_events`, `be_payments`, `be_payment_intents`, `be_payment_history_events`,
  `be_refunds`, `be_product_purchases`, `be_product_history_events`, `patient_payment`) — all SELECT-only.
  These are plausibly written as a direct side effect of a patient-initiated payment action (e.g.
  clicking "pay" for a booking), the same way the booking-cancel flow writes cancellation/event rows —
  but no confirmed patient-session INSERT/UPDATE call site was traced for this family specifically
  (time-boxed audit). If patients can trigger their own payment intents today, this whole family likely
  needs write grants before the real flip; the B4-fanout pre-flip process smoke should catch it as a
  hard permission-denied rather than a silent gap.
