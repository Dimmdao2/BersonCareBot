## app_staff — reviewed P0.5b runtime surface (213 tables)

Derived from `tiers-218.tsv` (`readTierRows()`): every table in the reviewed P0.5b snapshot across SCOPED,
BOOTSTRAP, INFRA, LEGACY, and TELEMETRY, **excluding 4 pure migration-bookkeeping tables**
(`drizzle.__drizzle_migrations`, `integrator.schema_migrations`, `public.schema_migrations`,
`public.webapp_schema_migrations` — touched only by the migrator role, never by a running process).

The generator also excludes post-snapshot tables whose dedicated overlays own their privilege contracts, so D3.5
regeneration cannot silently broaden the reviewed full-DML batch. These include organization invites; entitlement
tables; specialist signup and the function-only staff-security vault; immutable reference-catalog receipts;
SaaS-isolation diagnostics; and audience-aware runtime settings/audit. Moving any of them into P0.5b requires a
separate runtime-surface review rather than incidental regeneration.

The UP path also explicitly revokes stale `app_patient` table/column privileges on
`user_password_credentials` and `user_oauth_bindings`. Rehearsals therefore converge to the reviewed narrow
accessor model without manual grant cleanup.

This closes the exact gap the cross-model audit flagged: the older single-role
`deploy/postgres/p0-5-role-split.sql` only grants SCOPED+BOOTSTRAP (187 tables), which is enough for
patient-wall RLS but NOT enough for the webapp/integrator/worker/scheduler/media-worker runtime, which
also reads/writes INFRA queues and outboxes every request (`projection_outbox`,
`integrator_push_outbox`, `outgoing_delivery_queue`, `delivery_attempt_logs`, `idempotency_keys`, …),
LEGACY Rubitime-era tables (still read by legacy sync paths), and TELEMETRY rollups. `app_staff` gets
`SELECT, INSERT, UPDATE, DELETE` uniformly on all 220 — it is the one role every non-patient session
(doctor/admin/system/worker) authenticates as, so it needs the same DML breadth the current single
shared app connection already has, just narrowed away from owner/migrator DDL privileges.

`integrator.schema_migrations` remains deliberately excluded here as migration bookkeeping. Locked
integrator startup still needs to read that ledger, but the canonical grant for the TEST hard rehearsal is
separate and narrower: `deploy/host/deploy-test-saas.sh` discovers the actual `api.test` runtime login,
grants only `USAGE` on schema `integrator` plus `SELECT` on `integrator.schema_migrations`, and verifies
that same runtime login can select the ledger before restart. Do not broaden this P0.5b app DML grant set
to include migration ledgers.

## Column-level restrictions (app_patient)

RLS policies restrict which **rows** `app_patient` can touch; they never restrict which **columns** a
granted privilege applies to. A whole-table `UPDATE`/`INSERT` grant therefore lets the patient's own
session write **any** column of a row it owns — including staff-only fields living on that same row.
`platform_users.role` was exactly this class of bug (whole-table UPDATE + patient owns its own row +
`role` lives on that row = self-escalation to `'admin'`). Postgres supports
`GRANT UPDATE (col1, col2) ON table TO role` / `GRANT INSERT (col1, col2) ON table TO role` — these are
layered on top of a `SELECT`-only (or `SELECT, INSERT`) whole-table base grant. See
`appPatientColumnGrants` in `p0-5b-grants-sql.mjs` for the exact statements generated; rendered directly
into `deploy/postgres/p0-5b-grants.sql` (not through the bulk temp-table `\gexec` pipeline, since this
is a small, explicit, individually-reviewed list). `REVOKE ALL PRIVILEGES ON TABLE ... FROM app_patient`
(the rollback branch) already revokes column-level privileges too — no separate rollback SQL needed.

## Value-level residuals (pre-flip, not GRANT-fixable)

Postgres column `GRANT`s restrict which **columns** can be referenced in an `INSERT`/`UPDATE` target
list; they cannot restrict what **value** is written to a granted column. For a handful of tables, a
column that carries staff/actor/identity meaning is **structurally required** by the confirmed
patient-session call path itself (a shared repo function references it explicitly, with a currently
safe hardcoded value from the service layer) — excluding the column from the grant would break the
live patient flow, not just close an attack surface. These are explicitly **not** GRANT-fixable; they
need an RLS `WITH CHECK`, a `BEFORE INSERT/UPDATE` trigger, or a repo-level split before the real
B4-fanout flip. Tracked here so they are not silently dropped between now and that decision:

- **`be_appointment_cancellations` / `be_appointment_reschedules` / `be_appointment_events` /
  `be_appointment_history_events`** — `pgBookingAppointmentLifecycle.ts`'s `applyCancellation`/
  `applyReschedule` is a single SHARED repo function serving both the confirmed patient path
  (`patientCancel`/`patientReschedule` in `booking-appointment-lifecycle/service.ts`, which hardcodes
  `actorType:"patient"`, `actorId:input.userId`, `manualOverride:false`, `staffComment:undefined` ->
  `null`) and the staff path (`staffCancel`/`staffReschedule`, real `actorType:"specialist"|"admin"`,
  a real `staffComment`, `manualOverride:true`). Every one of `actor_type`, `actor_id`,
  `staff_comment`, `manual_override`, `notifications_sent`, `was_free`, `was_penalized`,
  `package_session_charged`, `prepayment_retained`, `prepayment_refunded`, `applied_policy_id`,
  `applied_policy_snapshot` is explicitly referenced by the INSERT for BOTH paths — none can be
  excluded from the grant without breaking the live patient cancel/reschedule flow. A
  raw-SQL-privileged `app_patient` session could otherwise forge `staff_comment` content,
  `manual_override=true`, `actor_type='admin'` (audit-trail impersonation), or `wasFree=true` (billing
  forgery) on its own row. **P2-C3 closes this before flip** with invoker-mode triggers: patient
  INSERTs must target an owned appointment/org, pin `actor_type='patient'`, `actor_id=current patient`,
  `staff_comment IS NULL`, and `manual_override=false`; patient UPDATEs on cancellation/reschedule rows
  are limited to owned latest-row `notifications_sent`. Events/history events are pinned to owned
  appointments, `actor_id=current patient`, and event types `created|cancelled|rescheduled`.
- **`program_item_discussion_messages`** (`sender_role`, `origin`) — `sender_role` (CHECK:
  `'patient'`/`'admin'`) and `origin` (CHECK: `'patient_observation'`/`'support_admin_reply'`) have
  **no DEFAULT** and are `NOT NULL`, so they must be explicitly referenced by every INSERT.
  `patient-program-actions.ts`'s confirmed patient call hardcodes `senderRole:"patient"`,
  `origin:"patient_observation"`, but `pgProgramItemDiscussion.ts`'s `insertMessage` is a SHARED
  function that also writes `senderRole:"admin"`/`origin:"support_admin_reply"` for the support-sync
  side. A raw-SQL-privileged `app_patient` session could forge `sender_role='admin'` — impersonating a
  support/doctor reply on the patient's own program item.
- **`support_conversation_messages`** (`sender_role`) — same class: `patientMessagingService.ts`
  hardcodes `senderRole:"user"` for the confirmed patient send-message path, but
  `appendWebappMessage` (`pgSupportCommunication.ts`) is shared with `doctorSupportMessagingService.ts`/
  `integratorSupportBridge.ts`, which pass `senderRole:"admin"`.

None of these are GRANT regressions introduced by this task — they were already present before the
2026-07-11 second-pass sweep (the `be_appointments.status`/`specialist_id` residual documented below is
the same class of problem, already known). This section makes the **full set** of them explicit for
B4-fanout triage, per this task's instruction to document rather than silently attempt (and fail) a
GRANT-only fix.

### `integrator.*` patient-owned tables — SELECT-only, deliberately

All 12 `integrator.*` tables in the patient-owned set (`contacts`, `content_access_grants`,
`conversation_messages`, `conversations`, `mailing_logs`, `message_drafts`, `question_messages`,
`user_questions`, `user_reminder_delivery_logs`, `user_reminder_occurrences`, `user_reminder_rules`,
`user_subscriptions`) are granted SELECT-only for `app_patient`. Their write side (Telegram/MAX message
ingestion, reminder scheduling) is currently performed by the **integrator service's own connection
identity** — a separate deployed process, not an authenticated webapp patient session. Whether the
integrator service itself will connect as `app_patient` for per-patient work (the roadmap note in
`R2_MVP_MASTER_CHECKLIST.md`'s B4-fanout item says patient sessions carry `app.integrator_user_id` too)
is an explicit **B4-fanout** connection-wiring decision, not made here. Granting INSERT/UPDATE
preemptively would risk conflicting with that undecided wiring; SELECT-only is the safe default and
does not block anything read-only (patient's own cabinet/profile views of its Telegram/MAX-side data).

### BOOTSTRAP tables explicitly NOT granted to app_patient (flagged, not an oversight)

`login_tokens`, `email_challenges`, `email_send_cooldowns`, `phone_challenges`,
`phone_messenger_bind_secrets`, `channel_link_secrets`, `user_email_setup_tokens`,
`user_oauth_bindings`, `user_password_credentials` — all are part of the **pre-session auth/challenge
flow** (login, OTP, OAuth linking, password reset). Several of these are structurally incompatible with
an "own row only" grant model: a login lookup by phone/email/token happens _before_ the session knows
who the user is, so the query is not naturally scoped to `app.patient_user_id` the way every other
patient-owned predicate is — granting broad SELECT here would let an authenticated `app_patient`
connection query arbitrary other users' active challenge/token rows by phone/email. Which role
(`app_patient`, a still-undecided dedicated pre-auth service role, or something else) should own this
flow is exactly the kind of decision B4-fanout is scoped to make; excluding it now is the conservative,
intentional default this task asked for ("лучше не додать — поймаем в B4-fanout").

For `user_password_credentials` and `user_oauth_bindings`, D3.5 keeps both tables excluded from app_patient
grants because they store password hashes or provider binding details. The authenticated patient tier gate reads
only boolean presence through the narrow SECURITY DEFINER helpers
`app.current_patient_has_password_credentials()` and `app.current_patient_has_web_oauth_binding()`. Both use
`app.current_patient_user_id()` and return no credential or provider row data. `app_staff` may execute the same
boolean helpers so shared platform-access resolution does not fail on doctor/admin paths; staff tier resolution
does not use the patient-only boolean result.

`be_organization_members` (staff roster — confidently staff-only), `system_settings` /
`system_settings_audit` / `integrator.system_settings` (global platform config; audit table is
staff-only, the base config table's patient-need is unconfirmed), `integrator.identities` /
`integrator.telegram_state` / `integrator.telegram_users` / `integrator.users` (integrator identity
plumbing; the patient's own integrator-side data is already reachable via the granted `integrator.*`
SCOPED tables above, keyed by `app.integrator_user_id`) are also excluded — see the generator's
comments for the identical reasoning per table.

`staff_security_profiles` is also excluded from both direct runtime-role surfaces. It contains staff MFA
secret ciphertext, recovery-code hashes and login-challenge state. The specialist-signup bootstrap overlay
revokes direct `app_staff`/`app_patient` table privileges and exposes only self-scoped `SECURITY DEFINER`
functions; the generated P0.5b grant script additionally repairs any stale `app_patient` table grant.
