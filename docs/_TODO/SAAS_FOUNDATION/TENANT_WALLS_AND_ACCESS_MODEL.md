# Модель стен и доступов (multitenant) — КАНОН

> Статус: канонический источник модели изоляции. При расхождении с другими доками — приоритет у этого файла.
> Владелец подтвердил модель 2026-07-12. Ключевые термины кода: роли `app_staff` / `app_patient`;
> хелперы `app.is_staff()`, `app.current_org_id()`, `app.current_patient_user_id()`,
> `app.current_integrator_user_id()`; запертая таблица контекста `app.principal_context`.

## 0. В двух словах

Изоляцию держит **сама база** (RLS), а не «на честном слове» приложения. Есть **ровно две стены**:

| Стена | Между кем | Кого защищает | Где живёт |
|---|---|---|---|
| **Клиническая (ORG)** | клиника ↔ клиника | персонал (специалисты/админы) | БД (RLS), только для персонала |
| **Пациентская (OWN)** | пациент ↔ пациент | пациенты | БД (RLS), «только свои строки» |

Клиника у **пациента** — это **НЕ стена в БД**, а **фильтр на уровне приложения** (какие данные показать в текущей сессии). Единственная стена пациента в БД — «видит только свои данные».

---

## 1. Специалист (тенант)

**Тенант = организация (клиника).** Каждый независимый специалист **сам регистрируется** → создаётся его организация (`be_organizations`), он становится её владельцем (`be_organization_members` role=owner + `be_specialists`), заводится workspace. Разные специалисты = разные изолированные организации.

**Как ходит в базу:** сессия персонала работает под ролью БД `app_staff`, с меткой клиники `app.org` (= его организация), выставленной запертым способом (см. §5).

**Что видит (клиническая стена):** только строки **своей** организации. Врач клиники А **не видит** клинику Б. Внутри своей клиники персонал видит данные **всех своих пациентов** (org-wide; решение владельца — вариант A, без пер-пациентных назначений на первом этапе).

**Предикат для персонала (в каждой политике):**
```
app.is_staff() AND organization_id = app.current_org_id()
```

---

## 2. Пациент

**Модель:** пациент — это **глобальный человек** (`platform_users`), который **записан (enrolled)** в одну или несколько клиник. Связка «человек ↔ клиника» — `org_enrollments`, уникальна по **паре** `(organization_id, platform_user_id)` → **один человек может состоять в нескольких клиниках**.

**Как ходит в базу:** сессия пациента работает под ролью БД `app_patient`, с запертой меткой личности `app.patient_user_id` (= кто он). Метку ставит только доверенный подписанный сеттер (см. §5).

**ЕДИНСТВЕННАЯ стена пациента в БД — «только свои данные»:**
```
row owned by app.current_patient_user_id()
```
Пациент **никогда** не видит чужие строки. Между клиниками **одного и того же** пациента стены в БД **нет** — его собственные строки и так лежат только в его клиниках, поэтому «только своё» уже закрывает и чужого пациента, и чужую клинику.

**Клиника у пациента = фильтр приложения, не стена:**
- либо сессия тянет данные **одной** выбранной клиники (приложение добавляет `WHERE organization_id = выбранная`),
- либо не фильтрует по клинике вовсе — тогда пациент видит **все свои** данные по **всем своим** клиникам.
В обоих случаях база всё равно вернёт только **его** строки.

### 2.1 Мультиклиника у пациента (продуктовая модель, поэтапно)

- **Экран-обзор (клиника НЕ выбрана):** все записи ко всем специалистам всех его клиник + все назначенные программы. Только просмотр и управление записями. Фильтра по клинике нет → видит своё по всем клиникам (стена «только своё» держит).
- **Работа в клинике (после выбора и входа):** программа, чат, комментарии и т.д. — по конкретной клинике; приложение фильтрует по выбранной клинике.
- **Первый этап:** пока клиника не выбрана — у пациента только **экран записей** + **экран выбора клиники**. Раскладку по экранам определим позже.
- Сегодня клиника одна → мультиклиника «спит»; модель включится сама, когда появится 2-я клиника (ядро не переделывать).

**Важно:** на уровне БД пациенту **не нужен** «резолвер клиники» и ответ «409 выбери клинику». Пациентский принципал = **только личность**. Выбор клиники — целиком на уровне приложения.

## 3. Итоговый предикат RLS (обе стены в одной политике)

Для каждой scoped-строки:
```
(app.is_staff() AND organization_id = app.current_org_id())   -- клиническая стена (персонал)
OR
(<строка принадлежит app.current_patient_user_id()>)          -- пациентская стена (только своё)
```
- Персонал: видит свою клинику целиком.
- Пациент: видит только свои строки (в любой из своих клиник).
- Никто не видит чужого пациента; персонал не видит чужую клинику.
- Запись (`WITH CHECK`) — тем же предикатом (нельзя записать в чужую клинику / за чужого пациента).

Материализовано в `deploy/postgres/phase4-locked-helper-rls-policies.sql` (генератор `docs/_TODO/SAAS_FOUNDATION/scripts/phase4-locked-policy-artifact.mjs`).

## 4. Что стена БД, а что фильтр приложения (явно)

| Что | Уровень | Механизм |
|---|---|---|
| Пациент не видит другого пациента | **БД (стена)** | RLS: `owns` |
| Клиника не видит другую клинику (персонал) | **БД (стена)** | RLS: `is_staff AND org` |
| Какую клинику показать пациенту сейчас | **Приложение (фильтр)** | сессия/`WHERE org=...`, выбор клиники |
| «Обзор» пациента по всем клиникам | **Приложение** | не фильтровать по клинике (БД всё равно = только своё) |

## 5. Неподделываемость меток (почему это «база держит», а не «на слово»)

Стены читают **запертые** метки через хелперы (`app.current_org_id()` / `app.current_patient_user_id()` / `app.is_staff()`), а **не** сырой изменяемый GUC. Метки лежат в таблице `app.principal_context`, писать в которую может **только** подписанный `SECURITY DEFINER`-сеттер `app.install_signed_context` (HMAC + привязка к backend_pid + одноразовый nonce + TTL ≤300с). Прикладная сессия **не может** сама подменить метку (`SET app.patient_user_id = чужой` игнорируется — хелпер читает не его). `app.is_staff()` — по членству в роли БД, не по GUC. Доказано на копии: попытка подделки не меняет видимость.

## 6. Рантайм: как метки попадают в каждый запрос

Механика — **два центральных места**, не «проверка в каждом файле»:

1. **Один auth-гейт** (`requireRole` / `requirePatientApiBusinessAccess`) — уже проверяет сессию на каждом запросе. После проверки он **кладёт личность** в контекст запроса (AsyncLocalStorage): персонал → staff + org; пациент → patient identity.
2. **Один порт БД** (`getDrizzle()` / `withClient`) — при каждом обращении к базе переключает роль (`app_staff`/`app_patient`) и ставит подписанный контекст; **fail-closed**: scoped-запрос без личности в боевом режиме **отклоняется** (не показывает пусто/чужое).

**Входы без сессии** (у них нет «юзер+клиника») получают явный принципал, а не «пусто»:
- пре-авторизация / публичное (логин, OTP, OAuth) → `bootstrap`;
- интегратор (Telegram/MAX/M2M) → `integrator` (+ org по пользователю);
- шедулер / медиа-воркер / кроны → `organization` (per-job) или `infra` (явно «можно видеть всё» — обосновывается точечно).

**Режимы** (`DB_PRINCIPAL_CONTEXT_MODE`): `legacy-guc` (по умолчанию, стены спят — как сегодня) → `shadow` (ставим контекст, логируем пропуски, не блокируем) → `locked` (боевой: enforce + FORCE + fail-closed). Флип — по кнопке владельца после репетиции на копии.
