## ВОПРОСЫ ВЛАДЕЛЬЦУ

1. Для `B4`, `C1`, `C3`, `C4`, `E1`, integrator runtime config и `T0` предлагается считать правилом
   матрицу «вид principal/capability → разрешённый transport/роль → обязательный pre-check/cleanup», а не
   буквальные имена функций и списки ветвей. Принимается ли такая матрица как следующий канонический
   контракт, от которого можно строить поведенческие или AST/call-graph проверки?
2. Для `P0.5 role split` предлагается считать правилом capability/ACL-матрицу ролей, а не закреплённый
   строкой перечень ролей и grants. Должен ли следующий гейт сравнивать нормализованный ACL inventory с этой
   матрицей?
3. Для `P0.11 storage/read/write` предлагается считать правилом org override + global `NULL` fallback +
   обязательную mirror-запись без обходных writers. Можно ли заменить часть source pins табличными
   read/write тестами и проверкой SQL-каталога, оставив текстовым только документальный гейт?
4. Для `new-table RLS`, `D1`, `P2-B/C1/C2/C3` и billing migration предлагается считать правилом реальные
   FORCE/RLS/policy/ACL свойства и негативные операции под соответствующими ролями, а не конкретную форму
   SQL predicate. Какие из этих свойств должны быть обязательным scratch-DB gate?
5. Для `C2`, `D3.4`, disposable dormant wrapper, hard migration protocol, TEST mode/finalizer и visual
   session предлагается считать правилом перечисленные fail-closed preconditions, порядок фаз и
   postconditions. Разрешено ли в следующем этапе заменить literal shell pins тестовым harness, который
   подменяет внешние команды и проверяет наблюдаемую последовательность/отказы?
6. Для public booking/slug resolvers и settings security предлагается считать правилом разрешённые и
   запрещённые bootstrap/request сценарии, а не имена текущих helper-функций. Какой набор негативных
   сценариев владелец считает минимальным каноном?
7. Для owner-ready/product-smoke/diagnostics предлагается считать правилом схему контракта плюс успешное
   исполнение зарегистрированного сценария; одно наличие строки в manifest остаётся лишь wiring-проверкой.
   Нужно ли разделить эти гейты на schema validation и отдельный executable smoke?
