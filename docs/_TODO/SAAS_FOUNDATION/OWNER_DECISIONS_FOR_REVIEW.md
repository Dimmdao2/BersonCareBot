## Часть Б — решения, которые ты уже принял, но нигде не собраны чек-листом

### Тарифы / магазин / entitlements (13.07, `store-tariff-entitlements-model.md`, taskdb `#724`/`#751`)

- **Модель:** тариф → entitlements (флаги механик) → клиника. Цены и состав тарифа — **данные, настраиваемые
  глобальным админом**, не хардкод.
- **Биллинг — БЕЗ реальных денег на старте:** _«start WITHOUT real money: build entitlements + tariffs, global
  admin manually assigns a tariff to a clinic; real PSP charging/invoices/subscription-lifecycle is a LATER phase»_.
- **Оверрайд:** тариф задаёт дефолтный набор механик, глобальный админ может переопределить точечно для конкретной
  клиники (как уже устроены per-org настройки).
- **Гранулярность:** строить **полный конструктор по механикам** (каждая механика — переключатель в тарифе), не
  2-3 грубых пресета — _«in agent-code the constructor is ~same effort»_.
- **Магазин упражнений:** пакеты — **только курируются глобальным админом** из платформенной библиотеки; свои
  упражнения клиники — отдельная существующая фича, НЕ часть магазина. **Файлы никогда не копируются** — грант на
  канонический `content_id`.
- Фазы (его же план): P0 фундамент entitlements → P1 гейт `requireEntitlement()` на каждую механику → P2 UI
  конструктора тарифов → P3 куррированные пакеты упражнений → P4 аналитика по клиникам → P5 биллинг (потом).
- **Плюс:** глобальному админу нужна **статистика/аналитика по каждой клинике** (не только по юзеру) — сквозной
  вид владельца платформы.

### Роли (13.07, `tenant-role-model-clinic-admin-capability.md`)

- Три уровня: **global_admin** (ты, вся платформа) / **clinic_admin** (владеет/управляет конкретной клиникой —
  соло-специалист сам себе clinic_admin; в команде один из докторов = clinic_admin) / **doctor/specialist** (без
  прав управления клиникой).
- Управление клиникой (настройки, локации, каталог) авторизуется **по членству в клинике**, НЕ по глобальной роли
  admin.
- Фронты **должны быть разделены** по этим трём уровням, не только admin/doctor (taskdb `#752` — сделано, но
  только на существующих shared/shadcn компонентах, без нового bespoke UI).

### Регистрация (13.07, `split-registration-staff-vs-patient.md`)

- Регистрация **разделена по входу**: лендинг «для врача» → staff-регистрация, «для клиента» → patient-регистрация.
  Один экран с переключателем режима, не полный редизайн.
- **Логин:** персонал — email + пароль; пациенты остаются на passwordless OTP (мессенджер/email).
- **Приглашение специалистов в клинику — email-инвайт со ссылкой, «стандартно, всегда»** (не по телефону). Владелец
  clinic_admin шлёт инвайт → специалист по ссылке логинится email → код → получает права внутри клиники.

### Пациентская стена (11-12.07, `patient-visibility-and-tenant-walls-decision.md`, `saas-patient-wall-is-own-data-only.md`)

- Пациент видит **только своё**, никогда чужое, ни при каких условиях — абсолютно, на уровне БД (RLS).
- Разделение клиник для пациента — **НЕ стена в БД**, а фильтр на уровне приложения (какую клинику показываем в
  текущей сессии).
- Доктор/персонал — **видимость по всей клинике** (variant A, без привязки «мои пациенты» в RLS). Запись
  «отложен, не строить сейчас» superseded решением 2026-07-15: UX-фильтр «мои пациенты» обязателен к работе,
  не меняя стену (`OWNER_RULINGS_2026-07-15.md:59-67`).

### Фоновые воркеры / рассылки (13.07, `walls-worker-infra-role-and-enqueue-filter.md`)

- Тенант-фильтр — **в момент постановки задачи в очередь** (сессия доктора/пациента, там уже работает RLS), не в
  момент отправки.
- Воркер-диспетчер не обязан знать, кто поставил задачу — ему нужна **узкая инфраструктурная роль** (`app_worker`),
  привязанная не к тенанту, с грантами только на нужные таблицы очереди/доставки/медиа — никогда bypass/«читать всё».

### Модель запуска — superseded запись (15.07)

- Всё доводится до боевого состояния **на тестовом сервере**: сколько угодно организаций, тестовые клиенты, все
  роли, админы, настройки — там же дорабатывается интерфейс и маршруты (лендинг, вход для специалистов, вход для
  клиентов).
- Дальнейшие копирование, переименование и домен **вне этого плана**. Канон заменён
  `OWNER_RULINGS_2026-07-15.md:87-104`: единственная плановая цель — полностью рабочая система на TEST.

### Внешняя среда — неприкасаема (15.07)

- Только получение свежего дампа допускается как источник для TEST-копии. Никаких живых флагов, отсечек
  провайдера, дропов таблиц, миграций или проверок вне TEST этот план не включает. Полная дословная запись —
  `OWNER_RULINGS_2026-07-15.md:95-104`.

### Абонементы (20.06, `subscription-system-already-exists.md`, ~80% уже построено)

- В кабинете доктора **уже есть** зрелая подсистема абонементов (`modules/memberships`,
  `be_subscription_packages`/`be_patient_packages`/`be_package_usages`) — создание с датой продажи, отметка в
  календаре, виджет на «Обзоре».
- Не хватает: bulk-кнопка «Пересчитать» (авто-списание прошедших визитов) и флаг абонемента на визите + связка с
  «Финансы» — это **достройка поверх существующего**, не стройка с нуля.

     подписанная платформенная роль, узкий `SECURITY DEFINER`-резолвер, или вообще убрать эту возможность);

   - интегратор: резолвер первого контакта (сейчас «одна активная организация» как заглушка) — оставить как
     временное решение под присмотром или сразу заменить явной привязкой канал→организация.

2. **Корень `system_settings`** — инженерная работа: таблица мешает в одну кучу секреты (ключи интеграций, OAuth, VAPID) и настройки,
   которые определяют интерфейс клиента. Стена сейчас висит на таблице целиком, поэтому пациентской роли закрыто и
   то, что приложению **обязано** быть доступно на чтение. Твои слова записаны в `SEQUENCE.md` (файл, зафиксированный
   15.07 по твоему прямому указанию): **«ПРИЛОЖЕНИЕ ДОЛЖНО ЧИТАТЬ НАСТРОЙКИ, КАК ИНАЧЕ ВООБЩЕ????»**. Решение:
   разделить секреты и клиентские настройки на два контура, дать приложению нормальный доступ ко вторым. Симптом
   сейчас виден живьём: роут `patient.program.item.discussion-summary` падает под стенами (файлы
   `.../discussion/summary/route.ts` и его тест сейчас в рабочих правках на ветке).

3. **Гранулярность ролей БД (O1)** — инженерная работа: сколько ролей Postgres нужно (сейчас построено и живо проверено `app_staff`/
   `app_patient`, пара), или нужна более мелкая нарезка (~12 ролей по типам принципала из старого черновика). Сам
   продуктовые уровни уже задал владелец: глобальный админ, админ организации, специалист, пациент, системные

   вопроса владельцу (`OWNER_RULINGS_2026-07-15.md:131-140`).

4. **`admin=doctor`** — снято: администратор организации может быть специалистом; интерфейс решает это
