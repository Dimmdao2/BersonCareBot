# Owner-ready TEST — требования владельца

Дата: 2026-07-15. Ветка: `feat/doctor-ui-rebuild`.

## Дословный смысл задачи

1. TEST нужен как среда обнаружения проблем: жёсткие стены базы включаются целиком, после чего код
   последовательно доводится по реально найденным падениям. На TEST нет живых пользователей, кроме владельца.
2. Жёсткие стены являются обязательным финалом migration/cleanup chain. Тестовые данные не являются миграцией:
   их создаёт отдельный повторяемый TEST-only seeder после миграций.
3. Seeder должен стать постоянным инструментом разработки интерфейса, а не минимальным A/B smoke fixture.
4. Нужны:
   - клиника с несколькими специалистами, где один участник — управляющий owner/clinic-admin;
   - solo-клиника;
   - пациенты в обеих клиниках и отдельные пациентские входы;
   - отдельный вход shared patient, состоящего в обеих клиниках, с проверяемым переключением контекста;
   - прошлые и будущие записи;
   - абонемент, остаток и история списаний;
   - назначенная программа и упражнения;
   - история выполнения с вариантами: подходы/повторы, вес, без веса, без количественных значений;
   - данные для графиков и содержательных экранов специалиста и пациента.
   - чистые public/login/registration экраны без сессии и публичная запись;
   - исполняемая locked read/write matrix между клиниками, shared patient и global admin.
5. SaaS-ошибки должны быть видны global admin в «Здоровье системы», а не только в технических логах.
   Нужны минимальный временной trend и достижимые TEST-сценарии okay/incomplete/critical.
6. Финиш инициативы — TEST развернут и проверен настолько, что следующий шаг принадлежит владельцу: войти
   разными ролями и вручную оценивать продукт и интерфейс.

## Ограничения

- PROD, `main` и `test` не изменяются.
- Никакой реальной доставки, внешнего S3 и реальных ПДн.
- Seeder меняет только зарезервированное fixture-пространство и сходится при повторном запуске.
- Стены не выключаются как способ восстановления.
- Секреты fixture не попадают в git, логи, скриншоты и отчёты.
- Финальная визуальная приёмка выполняется на TEST под настоящим global-admin профилем с включённым admin mode;
  DEV-сценарий является только предварительной проверкой.

## Решения владельца

- 2026-07-15: разрешено и требуется создать отдельный PostgreSQL login для SaaS-диагностики и отдельную runtime
