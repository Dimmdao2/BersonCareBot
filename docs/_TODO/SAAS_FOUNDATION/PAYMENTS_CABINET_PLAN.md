# Кабинет оплаты — план

Задача: довести оплату от «платёж проходит» до **рабочего кабинета**, где деньгами управляют, а не
только принимают. Владелец 01.08: «ЮKassa — надо сделать полноценный кабинет только: с возвратами,
статистикой, ручным и авто выставлением счетов, автосписанием и тд».

Соседние планы: [`SAAS_BILLING_PLAN.md`](SAAS_BILLING_PLAN.md) — приём оплаты и снятие моков (пункты
B0.x, доводится сейчас); [`TARIFFS_PAYMENTS_ADMIN_PLAN.md`](TARIFFS_PAYMENTS_ADMIN_PLAN.md) — тарифы и
механики. Этот план — про **управление деньгами после того, как платёж научился проходить**.

---

## 1. Решения владельца (актуальные, с цитатами)

- **Р-1 (01.08).** «ЮKassa — надо сделать полноценный кабинет только: с возвратами, статистикой, ручным и
  авто выставлением счетов, автосписанием и тд». Объём задан этим перечислением.
- **Р-2 (01.08).** «моки удаляй и делай полноценное апи для юкассы — на нём и проверишь». Мок-провайдер
  снят, проверка — прогоном через тестовый магазин.
- **Р-3 (01.08).** «цель — открыть кабинет и видеть рабочие экраны. Безопасность — единый порт, стены».
  Приёмка каждого этапа — экран, который открывается и работает, а не зелёные прогоны.
- **Р-4 (01.08).** «переводи руками через поиск всё, что размазано, на один порт — единые точки импорта,
  экспорта, доступа». Новых гейтов и списков исключений не заводить.
- **Р-5 (01.08).** «тесты нужны там, где они необходимы и без них никак… если для этого надо хуй знает
  что накрутить вокруг — то проще пойти и посмотреть». Правило: `AGENTS.md` §10a.

## 2. Открытый вопрос владельцу — от него зависит порядок этапов

⛔ **Чей кабинет делаем первым?** «Кабинет оплаты» — это две разные поверхности, и они не пересекаются
ни по правам, ни по данным:

- **(А) Кабинет клиники** — клиника видит платежи СВОИХ пациентов: возвраты пациенту, статистика выручки,
  счета пациенту, автосписание за абонемент. Деньги идут клинике, ключи эквайринга клиники.
- **(Б) Кабинет платформы** — мы видим, как клиники платят НАМ за тариф: счета клинике, автопродление
  подписки, статистика по клиникам, возврат клинике. Деньги идут нам, ключи наши.

Рекомендация: **начать с (А)**, потому что оплата пациентом уже доведена до конца и там есть что
показывать; (Б) упирается в checkout подписки, которого ещё нет. Пока ответа нет — этапы ниже
сформулированы так, что первые два одинаковы для обеих поверхностей.

## 3. Что уже есть (проверено 01.08, не переделывать)

- Адаптер ЮKassa ходит в REST API v3 напрямую: `POST /v3/payments`, `POST /v3/refunds`,
  `GET /v3/payments/{id}` — Basic-авторизация `shopId:secretKey`, заголовок `Idempotence-Key`.
  Официального SDK для Node у ЮKassa нет (официальные только PHP и Python), поэтому прямые вызовы —
  это и есть мировая практика, а не самодеятельность.
- Приём уведомлений: адрес отправителя сверяется со списком подсетей ЮKassa, платёж перезапрашивается
  по API, статус и сумма берутся из ответа. Подписи у ЮKassa нет — проверять нечего.
- Ссылка на оплату доходит до клиента, запись намерения её хранит, статус отдаётся во всех четырёх
  доменах покупки.
- Тестовый магазин рабочий (`shopId 1425962`), ключ в `system_settings`, платежи помечаются `test`.

## 4. Этапы

### К1. Список платежей — основа кабинета
- [ ] Экран со списком платежей: дата, сумма, статус, плательщик, за что, провайдер.
      Фильтры по периоду и статусу, поиск по плательщику.
- [ ] Данные берутся из НАШЕГО журнала платежей, не из ЮKassa: журнал — источник истины,
      провайдер — источник подтверждения.
- [ ] Стены: список org-scoped всегда. Чужой платёж не показывается и не открывается по прямой ссылке
      с чужим идентификатором — это отказ дорогой и молчаливый, здесь тест обязателен.

### К2. Возвраты
- [ ] Полный и частичный возврат с экрана платежа. Сумма возврата не превышает остаток по платежу.
- [ ] Возврат уходит в `POST /v3/refunds` с ключом идемпотентности; повторное нажатие не создаёт второй
      возврат — идемпотентность проверяется реальным повтором, а не только чтением кода.
- [ ] Статус возврата приходит уведомлением и обновляет журнал. Пока не подтверждён — «в обработке»,
      а не «возвращено».
- [ ] Право на возврат — отдельная способность, не «все, кто видит платежи». Кто именно — решает
      владелец при приёмке этапа.

### К3. Статистика
- [ ] Сводка за период: принято, возвращено, в обработке, не оплачено. Разрез по видам покупок.
- [ ] Сверка с провайдером: расхождение между нашим журналом и ЮKassa показывается явно, а не
      прячется. Тянется через `GET /v3/payments` списком за период.
- [ ] Выгрузка периода файлом для бухгалтерии.

### К4. Счёт вручную
- [ ] Выставление счёта из кабинета: сумма, за что, кому, срок действия. Уходит в
      `POST /v3/invoices`, ссылка на оплату возвращается в ответе и отдаётся получателю.
- [ ] Счёт живёт в нашем журнале со статусами: выставлен, оплачен, просрочен, отменён.
- [ ] Оплата счёта подтверждается уведомлением провайдера, а не открытием ссылки.

### К5. Счёт автоматически
- [ ] Правило выставления: за что и с какой периодичностью счёт выставляется сам (продление абонемента,
      продление тарифа).
- [ ] Выставление идёт фоновой работой через существующую очередь, а не по запросу пользователя.
      Фильтрация — на постановке в очередь, под принципалом (канон стен для фоновых работ).
- [ ] Повтор выставления в тот же период не создаёт второй счёт.

### К6. Автосписание
- [ ] При первой оплате запрашивается сохранение способа оплаты (`save_payment_method: true`);
      после успеха ЮKassa отдаёт `payment_method.id`, который мы храним привязанным к плательщику.
- [ ] Последующее списание — `POST /v3/payments` с `payment_method_id`, без участия плательщика.
- [ ] Согласие плательщика на автосписание — явное, хранится с датой и текстом, отзывается им же
      в один клик. Без этого автосписание не включается.
- [ ] Неудачное списание не молчит: плательщик и клиника узнают, и есть понятный следующий шаг
      (оплатить вручную по ссылке).

### К7. Фискализация — вопрос владельцу, не наша выдумка
- [ ] 54-ФЗ требует чек на каждый платёж. ЮKassa умеет пробивать чеки сама, если магазин подключён к
      их онлайн-кассе, и тогда в платёж передаётся объект `receipt` с составом покупки и признаками.
      **Нужно решение владельца:** чеки пробивает ЮKassa или у клиники своя касса. От ответа зависит,
      передаём ли мы состав корзины в каждый платёж.

## 5. Приёмка

Каждый этап закрывается **прогоном на тестовом магазине и открытым экраном**, а не отчётом и не
зелёными тестами: платёж тестовой картой, возврат, счёт, автосписание — по своему этапу. В план
пишется, что именно проведено и что видно на экране.
