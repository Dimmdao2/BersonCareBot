> следующим и почему**. Порядок меняется только владельцем. Агент, который хочет отклониться, — сначала

## Куда мы идём (слова владельца, 2026-07-15)

Всё доводится до боевого состояния **на ТЕСТОВОМ сервере**: сколько угодно организаций, тестовые клиенты, все
роли, админы, настройки. Там же дорабатывается интерфейс и маршруты — главный лендинг, вход для специалистов,
вход для клиентов. **Только после этого** система переносится на прод **копией**: копируется папка, проект
переименовывается с `bersoncare` на `therapysto`/`therapio`, поднимается на **новом домене**. К этому моменту
нужны интерфейс, оплата, магазин с пакетами упражнений и тарифная сетка — это то, что показывают инвесторам.

**Старый прод `bersoncare` — легаси, заморожен. Переключения прода не будет. Никогда.** Новый деплой рождается
со включёнными стенами. «На живом» = на тесте.

## Порядок

### Этап 1 — вырезать накрутку · план: `SAAS_R3_CUT_INVENTED_SCOPE.md` · СЕЙЧАС

Убрать код, который агенты построили против решений владельца, **и чекеры, которые его охраняют**. Система
должна стать меньше. Решений владельца не требует — техническая часть.

- [ ] 1.1 Медиа-воркер: убрать organization principal, вернуть модель владельца от 13.07 (infra/`app_worker`),
      снять требование из C4 и всех чекеров, которые его закрепили; добавить настоящий инвариант при захвате
      джоба (org непустой и совпадает у джоба и файла).
- [ ] 1.2 «Врач в двух клиниках»: вырезать ветку выбора клиники из резолвера членства. Больше одного активного
      членства персонала = громкая ошибка данных, не UX.
- [ ] 1.3 `be_organizations`: исправить классификацию (прецедент — `be_organization_members`), закрыть точечно:
      изменение/удаление — своя строка, создание — через функцию регистрации, кросс-клиничный список — отдельная
      роль.
- [ ] 1.4 Две таблицы (`organization_member_invites`, `saas_org_entitlement_overrides`) — внести в инвентарь
      чекера состояния БД.

**Выход:** накрутка удалена, охранявшие её чекеры сняты, `pnpm run check:saas-db-regression` зелёный,
независимый аудит подтвердил, что стены не ослаблены.

### Этап 2 — список решений владельцу · файл: `OWNER_DECISIONS_FOR_REVIEW.md` · ПАРАЛЛЕЛЬНО

Собрать из расшифровок сессий, что владелец **реально** решал, и отделить от того, что агенты приписали ему.
Владелец читает файл сам и вычёркивает чужое.

- [ ] 2.1 Проверить каждую атрибуцию «владелец решил/сказал» в SaaS-доках против его настоящих слов:
      подтверждено / искажено / выдумано.
- [ ] 2.2 Отдельно — вердикт по «одна кнопка туда-обратно» (`SAAS_ENFORCE_ROADMAP.md` строка 3, написана
      агентом). Главный подозреваемый: против неё построено двенадцать фаз.
- [ ] 2.3 Выбрать из сессий уже принятые решения по подпискам/тарифам/магазину/оплате/ролям/регистрации —
      владелец на эти вопросы уже отвечал, но их не зафиксировали чек-листами.
- [ ] 2.4 Владелец прошёлся по файлу и вычеркнул чужое.

### Этап 3 — прогон по тесту со скринами · ПОСЛЕ ЭТАПА 1

Агент ходит по тесту обеими демо-клиниками (A и B, вход по email+паролю, без OTP), снимает экраны, фиксирует
утечки и `Forbidden`. **Не вместо починки известного, а после неё** — чтобы увидеть то, чего в списке нет.

- [ ] 3.1 Пройти обеими клиниками все основные экраны, снять скриншоты.
- [ ] 3.2 Зафиксировать: где утечка между клиниками, где `Forbidden` там, где его быть не должно, где пусто
      вместо данных.
- [ ] 3.3 Свести в список находок против реальности, а не против документов.

### Этап 4 — зафиксировать чек-листами решения из этапа 2

Из вычеркнутого владельцем списка сделать этапы плана с чек-листами. Прежде всего — модель подписок/тарифов:
владелец на эти вопросы уже отвечал в других сессиях, но это не записано.

- [ ] 4.1 Модель подписок/тарифов/магазина → этапы с чек-листами.
- [ ] 4.2 Роли и регистрация → этапы с чек-листами.
- [ ] 4.3 Не мельчить там, где нюансы (интерфейс) ещё не проработаны с владельцем.

### Этап 5 — корень настроек · ЖДЁТ РЕШЕНИЯ ВЛАДЕЛЬЦА

**Не заплатка.** `system_settings` смешивает секреты (ключи интеграций, OAuth, VAPID) и настройки, которые
определяют интерфейс клиента. Стена повешена на таблицу целиком, поэтому пациентской роли закрыто и то, что
приложение **обязано** читать. Слова владельца: «ПРИЛОЖЕНИЕ ДОЛЖНО ЧИТАТЬ НАСТРОЙКИ, КАК ИНАЧЕ ВООБЩЕ????»

Флажков будут десятки, и это **не только** права из тарифа — это любые настройки, меняющие интерфейс клиента.
Аксессор с белым списком на каждый флаг — тупик, эту заплатку уже выкинули (коммит откатил роут
discussion-summary).

- [ ] 5.1 Разделить: секреты отдельно, настройки клиента отдельно; дать приложению читать вторые нормально.
- [ ] 5.2 Пока не сделано — роут `patient.program.item.discussion-summary` падает под стенами. Симптом
      оставлен видимым намеренно.

## Что НЕ делаем

- **F1/F2 — рубильник стен туда-обратно.** Переключения прода не будет; откат стен на живом мультитенанте =
  показать клинике А данные клиники Б. Помечено «не требуется» в роадмапе.
- **Rubitime R5/R6/R7** — живое отключение, отсечка провайдера, дроп таблиц. Только на старом проде, куда мы не
  едем. Трек остаётся non-live. Владелец 15.07: «ПРОДАКШЕН НЕ ТРОГАТЬ».
- **Чинить C4-чекер.** Он охраняет накрутку из этапа 1.1 и уходит вместе с ней.

## Правило провенанса

Атрибуция «владелец решил X» **без ссылки на то, где он это сказал** — догадка агента, а не решение владельца,
и должна быть подписана как догадка. Этот репозиторий уже дважды дорого заплатил за нарушение этого правила.
