## 5. ДЕФЕКТ (производительность). 30 запросов в пул размером 1

**Где:** `pgPlatformAnalytics.ts` (все методы) + `service.ts:93` + `infra/db/webappPoolProvider.ts:350`.

Точный счёт SQL-операторов на один рендер дашборда:

| метод | запросов | | метод | запросов |
|---|---:|---|---|---:|
| `countClinics` | 3 | | `videoVolumeExercises` | 1 |
| `countSpecialists` | 3 | | `videoVolumeCms` | 1 |
| `countPatients` | 3 | | `countCompletions` | 2 |
| `listPageViews` | 1 | | `countHomeWellbeing` | 1 |
| `countBookings` | 2 | | `programActivity` | 3 |
| `countProgramsAssigned` | 1 | | `videoPlayback` | 5 |
| `countClinicalVisits` | 1 | | `countCmsArticles` | 1 |
| `countExercises` | 2 | | **ИТОГО** | **30** |

`Promise.all` создаёт иллюзию параллельности: платформенный принципал ходит через `globalAdminPool`,
у которого `max: 1` (`webappPoolProvider.ts:350`). Все 30 операторов **сериализуются на одном коннекте**,
плюс установка принципала на чекаут. Параллельности нет ни на грамм, а латентность складывается.

Три отдельных подпункта внутри этого же места:

- **Неиндексируемый join.** `pgPlatformAnalytics.ts:295` и `:316` соединяют
  `${mediaFiles.id}::text = substring(url from '/api/media/(...)')`. Приведение PK к `text` убивает
  использование индекса по `media_files.id`; планировщик обязан протащить всю `media_files`.
- **Агрегация в Node вместо SQL.** `videoVolumeExercises`/`videoVolumeCms` (`:288-303`, `:309-324`) и
  медиа-запрос в `countExercises` (`:261-266`) тянут **по строке на каждый медиафайл** и складывают их
  в JS (`volumeFromRows`, `:466-476`). Сумма байт и раскладка по корзинам — это `sum()` + `count() filter`
  в один оператор; сейчас объём трафика растёт линейно с библиотекой.
- **Кэша нет.** Ответ роута без `Cache-Control`, каждое переключение периода — новые 30 запросов.
  Для платформенных агрегатов за сутки/неделю это дорого без причины.

**Цена.** Пока таблиц мало — незаметно; на реальных объёмах страница будет открываться секундами,
и её открытие будет занимать единственный коннект глобального админа, то есть блокировать другие
админские страницы.

Первое паинт не блокируется: серверная `page.tsx` отдаёт оболочку, данные тянет клиент. Это сделано верно.

## 7. МЕЛКИЕ дефекты счёта (проверить, но не срочно)

- `pgPlatformAnalytics.ts:428` — уникальные просмотры считаются как
  `count(distinct (user_id::text || ':' || media_id::text))`. Если `user_id` NULL, всё выражение NULL и
  строка не считается вовсе — анонимные просмотры входят в «всего» и исчезают из «уникальных».
- `pgPlatformAnalytics.ts:376-378` — знаменатель `patientsWithProgram` берётся по всем активным
  инстансам без окна, а числители (`visitDaysSum`, `markDaysSum`) — по выбранному периоду. Средние
  сравнимы между периодами только пока состав пациентов не меняется. План (GA-A-08b) допускает такое
  чтение, поэтому это оговорка, а не нарушение — но подписать на экране стоит.
- `hostingUrlKind.ts:21` — любой неизвестный `http(s)`-адрес классифицируется как `file`. Ссылка на
  чужой хостинг вне allowlist попадёт в «Видео-файлы».
- `pgPlatformAnalytics.ts:131-162` — «сейчас» фильтрует `is_archived = false`, а срезы за период нет.
  Числа из разных карточек считаются по разным правилам.
- `ports.ts:42` / `pgPlatformAnalytics.ts:415` — `patientsWithVisitDays` объявлен в порте, возвращается
  константой `0` и нигде не используется. Мёртвое поле контракта.

## Итог: насколько криво

Криво — в двух точках, и обе не про стиль.

1. **Страница, скорее всего, вообще не работает на TEST** — не потому что код плохой, а потому что
   к нему не заведены права роли. Это надо проверить первым же действием (команда в §1).
2. **Три цифры из показанных считаются не так, как задумано** (§2, §3, §6), и два пункта плана
   помечены сделанными, не будучи сделанными (§4).

Всё остальное — производительность, которая сегодня не болит (§5, §8), и вкусовщина (§9).
Архитектурных нарушений правил репозитория **не найдено ни одного**: слои, чокпоинт базы, порты,
расположение типов, переиспользование примитивов — всё по канону.
