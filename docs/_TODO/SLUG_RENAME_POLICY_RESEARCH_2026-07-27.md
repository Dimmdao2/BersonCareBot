# Можно ли менять slug клиники после регистрации — что делают взрослые платформы

> **SUPERSEDED — 2026-07-27.** Финальная one-way policy below is replaced by [`OWNER_PRODUCT_RULES.md` §12](../ARCHITECTURE/OWNER_PRODUCT_RULES.md): a former slug never goes to another organization, but the same organization may reclaim its own former name. Implemented by `d4d9a2771`.

> ✅ **РЕШЕНИЕ ВЛАДЕЛЬЦА 27.07 — ПОЛИТИКА ЗАКРЫТА, исследование ниже читать как обоснование.**
> Дословно: «старое имя не освобождается никогда - ок. Но менять имя можно один раз самостоятельно -
> дальше только по запросу в поддержку и рассмотрении причин (иначе начнут забивать себе домены).»
>
> **Итоговая политика:**
> 1. **Старое имя не освобождается НИКОГДА** — остаётся вечным псевдонимом, занять его не может никто,
>    включая саму клинику. Это уже реализовано: триггер в `0218_u6b_organization_slug_claims.sql` запрещает
>    удалять и менять записи `current`/`alias`, единый уникальный индекс закрывает повторный захват.
>    Строже, чем GitHub/Slack/Discord (там имя освобождается мгновенно — на этом и строится перехват ссылок).
> 2. **Смена имени самостоятельно — РОВНО ОДИН РАЗ** за всё время жизни клиники. Модель Shopify.
> 3. **Дальше — только через обращение в поддержку**, с рассмотрением причины. Причина ограничения названа
>    владельцем: иначе клиники начнут занимать имена про запас.
> 4. **Перенаправление на новый адрес обязательно** — и у нас оно не может сломаться, в отличие от
>    GitHub/Slack, где редирект живёт лишь пока старое имя свободно.
>
> **Что для этого не хватает в коде** (единственная дыра, найденная исследованием): порт
> `resolveCanonicalSlug` написан и покрыт тестами, но **его не зовёт ни один маршрут** — пациент по старой
> ссылке попадает в правильную клинику, однако браузер не получает HTTP-редирект на канонический адрес.
> Плюс нужен счётчик самостоятельных переименований (лимит 1) и путь обращения в поддержку.
> Задача: **#1050**.

Дата: 2026-07-27. Готовил research-агент по запросу владельца. Обязательное имя (slug) клиники при регистрации
уже решено владельцем — ниже только вопрос «что происходит ПОСЛЕ регистрации, когда клиника захочет
переименоваться». Каждое внешнее утверждение — со ссылкой. Где источник не даёт чёткого ответа — сказано прямо,
без додумывания (правило владельца «не изобретай»).

Важный контекст, не переоткрываем: владелец уже решил, что клиники стартуют на платформенных поддоменах,
свои домены — позже. Ниже речь только о changeable-части адреса (slug), не о домене верхнего уровня.

## 2. Доминирующий паттерн — и где расхождение

**Общее для всех платформ с self-service переименованием (GitHub, Slack, Shopify, Notion custom domain, Linear,
Discord):**
- Переименование — операция администратора/владельца, без модерации, доступна сразу.
- **Старые ссылки в момент смены не ломаются немедленно** — везде есть хоть какой-то механизм непрерывности
  (редирект или сохранение старого адреса как рабочего входа), кроме Discord.

**Главное расхождение — что происходит со старым именем:**
- **«Отпустить сразу» (GitHub, Slack, Discord).** Старое имя тут же становится доступным любому. Это и есть
  источник задокументированного риска захвата (ниже).
- **«Держать переадресацией, не отпускать» (Shopify — 1 раз и старый адрес навсегда редиректит; Linear —
  редирект добавлен отдельной фичей).** Здесь платформа не отдаёт имя в общий пул вовсе, а просто держит
  постоянный alias.
- **«Отозвать по усмотрению платформы» (Notion custom domain).** Домен не привязан к владельцу навечно —
  неактивность = потеря; смена — старое сразу мёртвое, без редиректа.

Ни одна из проверенных платформ явно не документирует политику «переименовывать можно N раз в M дней» —
там, где есть трение (Shopify, Discord), оно выражено не через cooldown, а через **разовость** или
**платный порог входа** (буст-уровень), а не временной лимит.

**Медицинские/бытовые бронирующие сервисы обходят проблему иначе, чем SaaS-инструменты:** ни один из
проверенных (Doctolib, Zocdoc, СберЗдоровье, Yclients) не даёт клинике/врачу самостоятельно выбираемый и
переименовываемый человекочитаемый URL-идентификатор вообще. Либо это внутренний ID (Yclients — числовой),
либо управление адресом целиком на стороне платформы/поддержки (СберЗдоровье), либо публично не описано
(Doctolib, Zocdoc). Это тоже сигнал: там, где на кону запись живого пациента к конкретному специалисту,
рынок предпочитает не отдавать пользователю контроль над идентификатором вовсе, а не решать задачу
«безопасного переименования».

**Документированная угроза, от которой все защищаются, — захват отпущенного имени (namespace hijacking).**
GitHub описывает это явно как «RepoJacking»: переименование освобождает старое имя → атакующий его
регистрирует → редирект на старый URL репозитория начинает вести на репозиторий атакующего, наследуя входящие
ссылки и доверие (в т.ч. цепочки поставок пакетных менеджеров). Источники:
[Checkmarx — GitHub RepoJacking Weakness Exploited in the Wild](https://checkmarx.com/blog/github-repojacking-weakness-exploited-in-the-wild-by-attackers/),
[Dark Reading — Millions of Repos Vulnerable to Hijacking](https://www.darkreading.com/application-security/millions-of-repos-on-github-are-potentially-vulnerable-to-hijacking),
[SecurityWeek — GitHub Account Renaming Could Have Led to Supply Chain Attacks](https://www.securityweek.com/github-account-renaming-could-have-led-supply-chain-attacks/).
Единственная задокументированная защита GitHub, не завязанная на разовость/деньги, — **постоянное списание
(retirement)** конкретно опасной комбинации старое-имя+владелец для «популярных» репозиториев (порог: Action
в Marketplace, либо >100 клонов/использований Actions за предыдущую неделю); для всех остальных — по-прежнему
«первый занял — забрал».

## 3. Рекомендация для нас — с учётом медицинской специфики

**Медицинский контекст поднимает планку выше типового SaaS.** У GitHub цена захвата — испорченная ссылка на
код или (в худшем случае) цепочка поставок для разработчиков, которые всё равно видят репозиторий и могут
заметить подмену. У нас цена ошибки — **пациент по старой (когда-то легитимной) ссылке `/book/{slug}` попадает
на бронирование к чужой организации** и в процессе записи вводит контактные данные и данные о состоянии
здоровья (см. постановку задачи владельца: «пациенты, бронирующие визит не в ту клинику и передающие health
data»). Здесь нет «пользователь заметит неладное в репозитории» — обычный пациент не сверяет юридическое лицо
клиники, он идёт по ссылке из мессенджера/визитки и заполняет форму. Это тянет политику в сторону самого
консервативного из увиденных вариантов — постоянного невозвратного alias (Shopify/Linear), а не «отпустить
сразу» (GitHub/Slack/Discord).

**Безопасный дефолт: переименование — self-service в любой момент после обязательной регистрационной slug,
без ограничения по количеству; старое имя не возвращается в оборот НИКОГДА** (не «через 90 дней», не «через
период неактивности», как временно допускают некоторые площадки) — оно навсегда остаётся привязанным к той
же организации как alias, и любой, кто когда-либо ходил по старой ссылке `/book/{старый-slug}`, обязан
попадать на ту же клинику постоянным редиректом, а не на 404 и не (что здесь недопустимо) на чужую клинику.
Ограничение по частоте (например, не чаще раза в 7–30 дней) можно добавить не как защиту от захвата (захвата
при таком дизайне структурно не существует — слаг никогда не освобождается), а просто как анти-спам от
метаний "передумал/передумал".

## 4. Что уже реализовано у нас — и что из рекомендации ещё требуется

Реализация уже есть, и она **строже**, чем у любой из процитированных платформ — по факту уже воплощает
рекомендацию §3, за одним технически не докрученным местом (редирект на публичном роуте).

**Уже сделано (проверено по коду и миграциям):**
- Сервис/порт `reserveSlug` → `claimReservedSlug` → `renameSlug` — переименование self-service, доступно
  организации-владельцу в любой момент (аудиторская проверка роли — `apps/webapp/src/infra/repos/pgClinicDirectory.ts:18-28`,
  `exactStaffOrganizationPrincipal`).
- Переименование — атомарная транзакция: новый slug становится `current`, старый — навечно превращается в
  запись `kind = 'alias'`, плюс append-only запись в аудит `organization_slug_rename_events`
  (`apps/webapp/src/infra/repos/pgClinicDirectory.ts:192-254`).
- **Старое имя никогда не освобождается — это гарантия на уровне БД, а не только приложения.** Триггер
  `app.guard_organization_slug_claim_mutation` жёстко запрещает удаление или изменение строк
  `kind IN ('current', 'alias')` (`apps/webapp/db/drizzle-migrations/0218_u6b_organization_slug_claims.sql:130-156`).
  Единый уникальный индекс `uq_organization_slug_claims_slug` действует по всем видам записей сразу
  (reservation/current/alias) без разделения по kind (`apps/webapp/db/drizzle-migrations/0218_u6b_organization_slug_claims.sql:67-68`),
  поэтому даже **сама организация не сможет позже повторно занять свой же прежний slug** — реализация даже
  строже, чем сформулированная выше рекомендация (там я предполагал только «чужой не заберёт», а не «никто,
  включая исходного владельца, не заберёт снова»). Это стоит явно подтвердить у владельца как осознанный
  выбор: переименование — билет в один конец, вернуть прежнее имя будет нельзя технически.
- Разрешение alias → организация уже поддержано на уровне резолвера: SQL-функция
  `app.resolve_public_organization_slug` резолвит и `current`, и `alias` в ту же организацию
  (`deploy/postgres/public-clinic-slug-bootstrap-resolver.sql:51-81`), это подтверждено тестом
  `apps/webapp/src/infra/repos/pgClinicDirectory.test.ts:121` («resolves aliases directly to the
  organization's single published current slug»). То есть **функционально старая ссылка `/book/{старый-slug}`
  уже не 404 и не чужая клиника — она резолвится в правильную организацию.**

**Чего не хватает, если фиксировать рекомендацию §3 как политику:**
1. **Публичный роут `/book/[slug]` пока не выдаёт канонический редирект.** `resolvePublicOrganizationBySlugRsc`
   (`apps/webapp/src/app/book/publicOrganizationBooking.ts:54-61`) вызывает `resolveOrganizationIdBySlug`,
   которая по цепочке идёт через `app.resolve_public_organization_by_slug` — «compatibility»-обёртку вокруг
   того же самого резолвера, но возвращающую только `organization_id`, без признака «это alias, отдай 30x на
   канонический slug». Разница между `resolveOrganizationIdBySlug` (используется на публичном роуте) и
   `resolveCanonicalSlug` (есть в порте, отдаёт `disposition: 'current' | 'redirect'`,
   `apps/webapp/src/modules/clinic-directory/ports.ts:32-37`, `apps/webapp/src/infra/repos/pgClinicDirectory.ts:77-92`)
   в том, что **вторую сейчас никто не вызывает вне тестов** — грепом по репозиторию `resolveCanonicalSlug`
   встречается только в самом модуле, репозитории и тестах, ни одного вызова со стороны роутов/UI не найдено.
   Итог: пациент по старой ссылке сегодня увидел бы правильную клинику, но URL в адресной строке остался бы
   старым (нет HTTP-редиректа на канонический), и поисковики/боты не получат сигнал о переезде. Это единственный
   зазор между «уже построено» и «практика зрелых платформ» — нужно на публичном роуте звать
   `resolveCanonicalSlug`/эквивалент и при `disposition === 'redirect'` отдавать постоянный (308) редирект на
   канонический slug.
2. **Лимита частоты переименований в коде нет** — ни в сервисе, ни в БД (грепом по репозиторию подтверждено:
   ни rate-limit, ни cooldown-колонки, ни счётчика попыток у `organization_slug_rename_events` нет — это чисто
   append-only лог, без каких-либо ограничивающих проверок при вставке). Раз риска захвата структурно нет
   (slug никогда не освобождается), это не блокер, а вопрос UX-гигиены — добавить не обязательно к релизу.
3. **UI/API-роут поверх сервиса ещё не подключён.** Грепом по `apps/webapp/src/app` подтверждено: `renameSlug`,
   `reserveSlug`, `claimReservedSlug` вызываются только из `service.ts`, `pgClinicDirectory.ts` и тестов — ни
   одного вызывающего API-роута или клиентской формы «Переименовать клинику» в коде нет. На TEST ни один slug
   не занят (сказано в задании), то есть менять правило сейчас — бесплатно в буквальном смысле, ничего не
   сломается ни для одной живой клиники.

## 5. Что не удалось установить

- **GitHub — нет подтверждённого лимита частоты** переименования username/организации в официальной
  документации (проверял `docs.github.com/en/account-and-profile/concepts/username-changes` и
  `docs.github.com/en/organizations/managing-organization-settings/renaming-an-organization`) — если лимит
  существует, он не задокументирован публично либо отсутствует. Отдельно: встречавшееся в непервичных
  источниках упоминание «90 дней» относится не к переименованию, а к **удалению аккаунта** — это разные
  политики, я их не смешивал.
- **Discord** — не удалось получить прямой доступ к `support.discord.com` (403 при фетче), вывод о поведении
  vanity URL (уровень буста 3/14 бустов, отсутствие редиректа) собран из вторичных источников
  ([replug.io](https://replug.io/blog/what-is-a-discord-vanity-url-and-how-to-create-one),
  [peakbot.pro](https://peakbot.pro/blog/how-to-get-discord-vanity-url-custom-invite-2026)), не из официальной
  страницы поддержки напрямую.
- **Tilda** — не нашёл документации именно про переименование платформенного alias/поддомена (только про
  привязку собственного домена); возможно, у Tilda такой сущности вообще нет в user-facing виде, но утверждать
  это не берусь без более прицельного изучения панели.
- **Doctolib, Zocdoc, СберЗдоровье** — не нашёл публичной документации, которая описывала бы (а) существует ли
  у них вообще пользовательски управляемый переименовываемый URL-идентификатор профиля/клиники и (б) что
  происходит со старым адресом при смене данных. Для СберЗдоровья это, по косвенным данным, объясняется тем,
  что карточка полностью шаблонная и не даёт клинике контроля над ссылкой — но это выведено из общих обзоров
  сервиса, не из официальной документации по этому конкретному вопросу.
- **Shopify** — точная формулировка «можно сменить только 1 раз» взята из синтеза поисковика по
  `help.shopify.com` и подтверждена форумом [community.shopify.com](https://community.shopify.com/t/how-can-i-change-my-stores-url-name-on-shopify/154171);
  прямую страницу `help.shopify.com`, дословно формулирующую это ограничение, зафетчить напрямую не удалось
  (страница по домену отдала общий раздел про primary domain, не про сам факт "1 раз").
- **Linear** — нашёл упоминание, что редирект со старого workspace URL был добавлен как фича в changelog
  (ноябрь 2022, [linear.app/changelog/2022-11-10-label-groups](https://linear.app/changelog/2022-11-10-label-groups) —
  дата совпала с записью про Label Groups, это может быть неточной атрибуцией поисковика к конкретному
  changelog-посту, а не сама фича редиректа задокументирована именно там); поведение «что со старым URL после
  многократных переименований» отдельно не описано.
