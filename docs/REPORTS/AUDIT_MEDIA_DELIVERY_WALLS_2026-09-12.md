## 1. Стена реальна — **PASS**

Все browser-facing пути идут через один из трёх резолверов, и ни один не умеет подписать сырой бакет:

- `resolveDeliverableMediaObject` (`apps/webapp/src/infra/repos/s3MediaStorage.ts:1200`) теперь
  отдаёт объект ТОЛЬКО для картинки с `standard_rendition_at != null`; для видео/аудио/документа →
  `null`. Ветка «рендишна нет → отдаём `s3_key`» удалена, `kind` из `MediaObjectLocation` убран.
- `resolveInlineMediaDeliveryUrl` (списочные/детальные payload'ы) отдаёт только стандартный WebP
  или same-origin HLS-прокси; raw в подпись не входит (`resolveInlineMediaDeliveryUrl.ts:11`).
- `resolveMediaPlaybackPayload`: не-картинка → 404 `inline_preview_unavailable`; картинка без
  рендишна → 409 `media_processing`; видео без готового HLS → 409; `progressive` навсегда `null`
  (`resolveMediaPlaybackPayload.ts:108-153`).
- Browser-facing S3-порт `infra/s3/deliveryClient.ts` жёстко зашивает `'hot'` во все вызовы и по
  сигнатуре не принимает `StorageKind` — `raw` через него недостижим.
- `/api/media/[id]`, `/preview/[size]`, `/brand/app-icon`, анонимная витрина
  `/[clinicSlug]/media/[mediaId]`, оба patient-files маршрута, playback/RSC — все переведены на
  `deliveryClient`/резолверы. `getMediaS3KeyForRedirect` и публичный каталог (`pgClinicPublicCard.ts`
  + `ports.ts`) протаскивают `standard_rendition_at`/`standardRenditionAt`, так что анонимная дверь
  больше не угадывает бакет по форме ключа.
- «Скопировать URL» в медиатеке (`MediaCardActionsMenu.tsx:81`) появляется только при готовом
  рендишне картинки или готовом HLS видео.
- Единственная сырая дверь — `/api/media/[id]/original` (М6): только загрузивший специалист
  (`rawOriginalDownloadRule.ts`), `attachment` + `application/octet-stream` + `nosniff`, поток без
  presign. Это в плане (М6), не обход.

Улики: `node scripts/check-media-delivery-chokepoint.mjs` → `exit 0`;
`node apps/webapp/scripts/check-media-upload-door.mjs` → `media upload door: OK`, `exit 0`. Гейт
расширен: `isHttpRoute` теперь ловит и `/app/[clinicSlug]/...` (не только `/api`), и запрещает
HTTP-GET-маршрутам (кроме `/original`) импортировать storage-kind-порт `s3Client.ts`; self-test
краснит обе инъекции. Для не-отрендеренного не-видео `/api/media/[id]` возвращает 404 (нет raw
fallback, `route.ts:100`).

## 2. Продукт сломан там, где стена не требовалась — **FAIL** (вопрос ведущему)

Подозрение ведущего подтверждено и шире, чем один тип файла.

**Файл, загруженный САМИМ ПАЦИЕНТОМ (PDF анализов, аудио):**
- `previewUrl` в обоих patient-files маршрутах теперь = `resolveInlineMediaDeliveryUrl(...)`
  (`files/route.ts:112`, `files/[fileId]/route.ts:66`), а он для документа/аудио возвращает `null`.
- В `PatientTabFiles.tsx` iframe-просмотр PDF удалён (был `file.previewUrl && isPdf`); кнопки
  «Скачать»/«Открыть» удалены; осталась одна ссылка на `/original`, видимая только при
  `canDownloadSource`.
- `canDownloadSource = isRawOriginalUploader({uploadedBy: f.uploadedByUserId, requesterUserId:
  session})` (`files/route.ts:112-116`). Для пациентской загрузки `uploaded_by` — это ПАЦИЕНТ, а
  правило `rawOriginalDownloadRule.ts` требует точного совпадения uploader==requester. Значит
  `canDownloadSource=false` для ЛЮБОГО специалиста, а сам маршрут `/original` закрыт
  `requireDoctorWorkspaceApiContext` — пациентская сессия туда не ходит.
- **Итог: PDF/аудио, загруженные пациентом, не может получить через продукт НИКТО** — ни лечащий
  врач (не он загрузил), ни пациент (маршрут только для doctor-workspace). До кандидата врач
  открывал PDF inline и имел «Скачать»/«Открыть».

**Аудио в медиатеке врача:**
- `MediaCard.tsx:106` рендерит `<audio><source src={item.url}/></audio>`, где `item.url =
  /api/media/:id`. После кандидата этот endpoint для аудио отдаёт 404 → инлайн-плеер не играет.
- `MediaLightbox.tsx` для не-видео/не-картинки показывает «Встроенный просмотр недоступен»; скачать
  аудио может только загрузивший (у медиатеки это работает, т.к. грузит специалист, — но
  проигрывание регрессировало).

**Почему это находка, а не работа:** решение владельца 11.09, под которое делался этап, дословно
про «картинку готовится / видео готовится» — то есть про изображения и видео в состоянии обработки.
Полное закрытие доступа к пользовательским документам и аудио (и особенно к файлам, которые загрузил
пациент) в плане владельца НЕ прописано; план М6 наоборот хотел отдавать скачивание «сотрудникам
организации, которая его загрузила», а реализованное правило сузилось до единственного загрузившего,
и для пациентских загрузок под него не подходит ни один специалист. Кроме того
`sourceStorageKindForKey` возвращает `hot` для любой не-`library` цели — файлы пациента М7 физически
не разделяет по бакетам, поэтому отказ им НЕ покупает никакой изоляции, это чистая регрессия доступа.

→ Ведущему: нужен явный owner-gate — оставить ли лечащему врачу способ получить пациентский
PDF/аудио, и вернуть ли проигрывание аудио медиатеки. Не чинил (граница: находки без пункта плана —
вопрос, не работа).

## 3. Бэкфилл `--reconcile-images` — **PASS с риском** (вопрос ведущему)

`mediaPreviewWorker.ts:369-396`. Завершается (ограничен `take`≤50) и идемпотентен для здоровых строк
(после успеха `standard_rendition_at` заполнен → кандидатом больше не выбирается). Но две проблемы,
ровно те, что поднял бриф:

1. **Requeue и обработка делят один бюджет `take`.** Requeue-транзакция помечает до `take`
   ready-картинок как `pending`, а последующий цикл `for (i<take)` обрабатывает `pending` — те же
   requeued строки конкурируют за те же `take` итераций с любыми органически-`pending` (свежие
   загрузки). Это by design (отдельный вызов крона), но при живой очереди новых загрузок бэкфилл
   и обычная очередь мешают друг другу.
2. **Нет терминального исключения → риск вечного churn.** Фильтр кандидата —
   `preview_status IS DISTINCT FROM 'pending'` + `standard_rendition_at IS NULL`. Строка, которая
   после обработки села в `'failed'` (5 попыток) или `'skipped'` (permanent error, напр. исходник
   удалён поведением 19.08 или битый файл), но осталась без рендишна, будет ВНОВЬ выбрана следующим
   прогоном reconcile — с `preview_attempts=0`. `ORDER BY created_at, id` означает, что одни и те же
   старейшие дохлые строки берутся первыми КАЖДЫЙ прогон, повторяют путь до fail/skip и никогда не
   пропускают вперёд здоровые строки за ними. Это и есть «крон зациклится на вечно падающей строке».

Улика (DEV, приведена в плане): `--reconcile-images --limit 10` → `{processed:10, requeued:10}`.
Здоровый путь работает; терминального стопа для неисправимых строк нет.

→ Ведущему: нужен ли предел (исключать `failed`/`skipped`, или счётчик reconcile-попыток), чтобы
неисправимые строки не жгли бюджет вечно.

## 4. Миграции `20260912T003000` и `...003100` — **PASS с замечаниями**

**Права/EXECUTE после DROP FUNCTION — OK.** `003100` делает `DROP FUNCTION
app.read_platform_media_row(uuid)` + `CREATE` (меняется набор OUT-колонок; `CREATE OR REPLACE` так не
умеет — верно). DROP снимает EXECUTE, но канонический entrypoint (`migrate-dev.sh` / `deploy-test.sh`)
после миграций выполняет полный owner/access reconcile в том же действии (AGENTS.md §миграции: «DROP+
CREATE меняет OID и требует reconcile после миграции»; «после миграций выполняет полный owner/access
reconcile»). `declaration.ts` обновлён в этой же ветке — добавлен `standard_rendition_at` и в объявленный
выход функции (`BUSINESS_SEAM_FUNCTIONS`), и в relation-access `public.media_files`. Значит reconcile
восстановит EXECUTE ДО живых вызовов; окна `permission denied` при штатном entrypoint нет (ручной
`psql`-накат запрещён каноном и здесь не рассматривается).

**BCB-MIGRATION-VERIFY.** `003100`: `-- BCB-MIGRATION-VERIFY: SELECT
pg_catalog.pg_get_function_result('app.read_platform_media_row(uuid)'::regprocedure) LIKE
'%standard_rendition_at%';` — формат по конвенции (`SELECT …`), семантически верно. `003000`:
`-- BCB-MIGRATION-VERIFY: pg_catalog.pg_get_functiondef(...) LIKE '%standardRenditionAt%'` —
**отклонение от конвенции**: нет префикса `SELECT` (AGENTS.md: «probe `-- BCB-MIGRATION-VERIFY:
SELECT …`»). Как раздельная проба этот SQL не выполнится. LIKE-цель `standardRenditionAt` в теле
присутствует (строка 154), т.е. смысл верен, но строку следует привести к `SELECT …`.

**Шапка `003000` скопирована у соседа — текст не о том, что делает миграция.** Основной объём шапки —
рассказ про #926 §17.R (`display_name`, «своя фамилия вместо названия организации»), который
фактически чинит СОСЕДНЯЯ миграция `20260911T235500_the_clinic_card_shows_the_name_the_cabinet_edits.sql`.
Данная миграция по сути добавляет `standardRenditionAt` в media публичной карточки; формула
`display_name` в ней лишь идемпотентно повторена (тот же `COALESCE(NULLIF(btrim(brand.display_name),
''), organization.title)`), поведение не меняется. Это находка качества документации, не корректности,
но заголовок вводит в заблуждение о скоупе. Оба файла несут OWNER/SCHEMA-CREATE/LANGUAGE-маркеры по
конвенции.

→ Ведущему: привести VERIFY `003000` к `SELECT …`; переписать шапку `003000` под её реальную работу
(М7 рендишн), убрав чужой §17.R-нарратив. (Правки миграций — за владельцем/ведущим; не трогал.)

## 5. `/api/media/[id]` для видео → 307 на `master.m3u8` — **PASS + явный флаг**

`route.ts:71-82`: если объект не отдаётся и mime — видео, маршрут резолвит playback и редиректит
307 на `/api/media/[id]/hls/master.m3u8`. **Этого поведения в плане владельца нет.**

Кто потребляет `/api/media/[id]` для видео в продукте: плеер `DoctorMediaPlaybackVideo` и
markdown-`embeddedLink` ходят на `/playback` и играют HLS, а не ставят bare `/api/media/:id` в
`<video src>`. Native `<source src={item.url}>` для видео в медиатеке убран (MediaLightbox теперь
`DoctorMediaPlaybackVideo`). Подтверждённого В ПРОДУКТЕ потребителя, который сломается, я не нашёл.

Но: любой потребитель, ожидающий БАЙТЫ от bare `/api/media/:id` (нативный `<video src>` вне нашего
плеера, инлайн-превью Telegram, `<img>`, мобильное приложение), получит плейлист m3u8 вместо
проигрываемых байт — для не-Safari нативных плееров это файл-плейлист, не воспроизведение. Латентная
ловушка, не активный баг. Называю явно, как требует бриф.

## Что сломано для пользователя (человеческим языком)

1. **Пациент прислал врачу PDF анализов или аудио — врач больше не может ни открыть, ни скачать его
   через продукт.** Раньше PDF показывался во встроенном окне и была кнопка «Скачать». Теперь окно
   пустое («Встроенный просмотр недоступен»), а единственная кнопка скачивания видна только тому, кто
   файл загрузил, — а загрузил его пациент, поэтому кнопки нет ни у кого. Файл фактически заперт.
   Это шире решения владельца (он говорил про «картинка/видео готовится»), поэтому — вопрос ведущему,
   не самовольная правка. **(п.2, блокер)**

2. **Аудиофайлы в медиатеке врача перестали проигрываться прямо в списке** — плеер обращается к
   адресу, который теперь отвечает 404. Скачать аудио может только загрузивший его специалист. **(п.2)**

3. **Старые картинки без готового рендишна.** Пока бэкфилл не догонит — вместо картинки «Картинка
   готовится» (это и есть задумка владельца). Риск: если у части старых картинок исходник был удалён
   старым поведением или файл битый, бэкфилл будет вечно пытаться их пересобрать, тратя бюджет и
   задерживая здоровые картинки за ними. **(п.3)**

4. **Видео по «голой» ссылке `/api/media/:id`** (если такую куда-то вставили вне нашего плеера —
   Telegram-превью, нативный тег, мобильный клиент) вернёт плейлист вместо видео. Внутри продукта
   таких мест не нашёл, но поведение новое и в плане владельца его нет. **(п.5)**

Стена как таковая (сырой файл наружу не уходит) держится: обходных путей выдачи raw не обнаружено,
кроме намеренной двери `/original` (только загрузивший специалист, только вложением). **(п.1, п.6)**
