# D39-F1 — M2M reminder-rule retry key

## Result

`postReminderRuleUpsertToIntegrator` now uses `reminder_rule:<rule.id>` when it receives no explicit idempotency key. This is the same scheme assigned by the database fallback-outbox. The explicit `existingIdempotencyKey` path is unchanged: `deliverIntegratorPushPayload` forwards `row.idempotencyKey` to the M2M sender at `apps/webapp/src/infra/integrator-push/deliverIntegratorPushPayload.ts:5-10`.

The new behavioral regression test sends the same reminder rule through both paths and reads each actual HTTP JSON body. Before the product change it failed because immediate delivery sent `rule_rule-a_<timestamp>` while fallback delivery sent `reminder_rule:rule-a`; after the change both bodies carry `reminder_rule:rule-a`.

## Receiver idempotency check

The receiver route dispatches `reminders.rule.upsert` through its write port at `apps/integrator/src/integrations/bersoncare/reminderRulesRoute.ts:161-187`; the write port calls `upsertReminderRuleDirect` at `apps/integrator/src/infra/db/writePort.ts:536-538`. That direct writer uses `INSERT INTO public.reminder_rules ... ON CONFLICT (integrator_rule_id) DO UPDATE` at `apps/integrator/src/infra/db/directPublic/writeReminderRulesDirect.ts:158-174`. Therefore a repeated delivery for the same `rule.id` updates the same rule's final state rather than appending a second rule.
