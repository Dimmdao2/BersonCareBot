Оракул: `docs/ARCHITECTURE/OWNER_PRODUCT_RULES.md` §34 (владелец, 19.08 + доп. 20.08 «не спрашивать —
согласен»). Проверяемое: ветка `wt/timezone-34-20260819`, коммиты `23e4ed4e7` и `b34abb0ae`. Отчёт
исполнителя `docs/REPORTS/TIMEZONE_RULE_34_2026-08-19.md` использован как заявление, не как улика — каждый
пункт ниже перепроверен живым прогоном на DEV (`bcb_webapp_dev`), отдельный `next dev` этого worktree на
`127.0.0.1:5311`, dev-bypass, headless Playwright/chromium, прямые SQL-запросы и HTTP-запросы мимо экрана.

## Вердикт: FAIL (1 подтверждённая находка), остальное — PASS

## Находка 1 — CONFIRMED: у пациента запись пояса идёт БЕЗ проверки «отличается ли значение», у сотрудника — С проверкой

**Требование (владелец, 20.08, дословно из §34):** «Записи в БД, когда они совпадают, нет — только сверка»;
из миссии: «Совпадает — записи в БД быть НЕ должно ни одной (проверь по `updated_at`, не по отсутствию
ошибки): иначе каждая загрузка экрана пишет в `platform_users`».

**Факт.** Для сотрудника (`syncPlatformUserCalendarTimezoneFromDevice`,
`apps/webapp/src/infra/repos/pgPlatformUserCalendarTimezone.ts:31`) `UPDATE` в `WHERE` несёт условие
`calendar_timezone IS NULL OR calendar_timezone <> candidate` — совпадающее значение не порождает запись.
Для пациента путь идёт через SECURITY DEFINER функцию `app.set_current_patient_calendar_timezone(text,
boolean)`. Её тело (снято живьём с DEV, `\sf`):

```sql
UPDATE public.platform_users AS platform_user
SET calendar_timezone = p_value, updated_at = now()
WHERE platform_user.id = v_patient_user_id
  AND platform_user.role = 'client'
  AND platform_user.merged_into_id IS NULL
  AND (NOT p_only_if_empty OR platform_user.calendar_timezone IS NULL);
```

При вызове с `p_only_if_empty = false` (это ровно то значение, которое шлёт
`syncCalendarTimezoneFromDevice`, `apps/webapp/src/infra/repos/pgPatientCalendarTimezone.ts:34`) условие
`NOT p_only_if_empty` истинно всегда — ветка `calendar_timezone IS NULL` не участвует, а сравнения со
старым значением в `WHERE` нет вовсе. Функция пишет `updated_at = now()` при КАЖДОМ вызове, даже когда
`p_value` совпадает с уже сохранённым.

**Живой прогон** (демо-пациент `00000000-0000-0000-0000-000000000001`, обе двери через реальный HTTP —
`dev-bypass` + CSRF-корректные заголовки, не напрямую в БД):

```
=== BEFORE ===
...0001|Europe/Moscow|2026-08-14 19:52:49.105604+03      (пациент)
...0002|Europe/Moscow|2026-08-19 23:34:03.916913+03      (сотрудник)

POST /api/patient/profile/calendar-timezone {"browserCalendarIana":"Europe/Moscow"}  → {"ok":true}
POST /api/doctor/account/timezone          {"browserCalendarIana":"Europe/Moscow"}  → {"ok":true}

=== AFTER (то же значение) ===
...0002|Europe/Moscow|2026-08-19 23:34:03.916913+03      ← сотрудник: updated_at НЕ изменился
...0001|Europe/Moscow|2026-08-20 00:16:57.612624+03       ← пациент: updated_at ИЗМЕНИЛСЯ
```

Повторил ещё дважды тем же запросом — `updated_at` пациента двигается на каждый вызов
(`00:16:57` → `00:17:09` → `00:17:10`), сотрудника — нет.

**Почему это не гасится клиентом.** `PatientCalendarTimezoneBootstrap.tsx:32` действительно шлёт `POST`
только когда `GET`-значение отличается от `Intl` браузера — в штатном UI-потоке лишней записи не будет. Но
гарантию владелец сформулировал как системную («записи быть не должно ни одной»), а не «UI не должен слать
лишний POST». Маршрут `/api/patient/profile/calendar-timezone` (POST) остаётся публичной дверью для
авторизованного пациента (требуется только своя сессия) и пишет безусловно при каждом вызове — вторая
вкладка, повтор запроса, будущий нативный клиент (сам канон §34 называет его «в планах», ограничение веба
явно временное) или просто медленная сеть с повторной отправкой одной и той же формы получат ту же лишнюю
запись, которую сотруднический путь уже умеет гасить на уровне БД. Асимметрия между двумя путями,
реализующими одно и то же правило, — сам по себе сигнал, что это недосмотр, а не намеренное решение: нигде
в каноне или отчёте нет объяснения, почему у пациента гарантия слабее.

**Не путать со «второй находкой».** Сам definer-аргумент `p_only_if_empty=false` НЕ открывает возможность
записать пояс чужому человеку — таргет всегда `v_patient_user_id := app.current_patient_user_id()`,
разрешается из attested port-context (`app_ext.accepted_port_contexts`), не из аргумента вызова. Это часть
мандата миссии (п.6, «убедись, что второй аргумент false не открыл постороннему принципалу...») —
проверено чтением тела функции и результатом `\df+`: `EXECUTE` есть только у `app_owner` (owner) и
`app_patient`; `app_staff` и `PUBLIC` явно отозваны (`deploy/postgres/e1-webapp-runtime-config.sql:118,233`).
**Эта часть требования — PASS.** FAIL — только про «нет записи при совпадении».

## П.1 — Никого не осиротили: PASS (подтверждено живым прогоном, не только чтением кода)

Утверждение отчёта проверено на РЕАЛЬНОМ сотруднике, а не на демо-аккаунте, который уже мог быть тронут
предыдущими прогонами: `d0000000-0000-4000-8000-000000000005` (`dev:doctor-isolated`), `role=doctor`,
`calendar_timezone IS NULL`, `created ~2026-08-14` — то есть создан до появления этой фичи, идеальный «сирота».

```
GET /api/doctor/account/timezone (до)  → {"ok":true,"timezone":null}
```

Двухшаговый headless-прогон канона (`dev-bypass` → `/app/account` тем же профилем, `--virtual-time-budget`
только на втором шаге) — реальная страница, реальный смонтированный `DoctorWorkspaceShell` →
`StaffCalendarTimezoneBootstrap`, реальный клиентский JS, не curl:

```
=== DB после захода на /app/account ===
d0000000-...05 | doctor | Europe/Moscow | 2026-08-20 00:19:41.353836+03
```

Пояс появился без единого ручного действия. Состояние демо-аккаунта восстановлено после прогона
(`calendar_timezone` вернул в `NULL`).

## П.2 — Дверей «поставить произвольный пояс» не осталось: PASS

- `PATCH /api/doctor/account/timezone` → `405`; `PATCH /api/patient/profile/calendar-timezone` → `405`;
  `PUT /api/doctor/account/timezone` → `405` (живой curl, не чтение кода).
- Оба `POST` игнорируют посторонний `userId` в теле: отправил `{"browserCalendarIana":"Asia/Tokyo",

- `grep -rn "setIanaForPatient|setPatientCalendarTimezoneIana|setPlatformUserCalendarTimezone\b"

- Остальные потребители `platformUsers.calendarTimezone`/`patientCalendarTimezone` в кодовой базе

## П.3 — Пояс филиала действительно доезжает: PASS

## Итог

Правило §34 в целом реализовано и проверено живьём по всем пунктам мандата, кроме одного: гарантия «нет
записи при совпадении» держится только у сотрудника на уровне БД, у пациента — только на уровне доверия к
одному конкретному клиентскому компоненту. Это конкретное, воспроизводимое расхождение с прямой цитатой
владельца от 20.08, не стилистическая претензия. Остальное — PASS, включая ранее нерабочий путь пояса
филиала (18/18 `Europe/Moscow` до этой ветки), отсутствие лишних дверей и отсутствие регрессий у читателей.
