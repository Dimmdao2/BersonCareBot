## Ф1 (блокирующая). Самостоятельная смена адреса падает 503 на живой базе: нет `INSERT (initiated_by)`

**Сценарий.** Любая клиника, у которой право ещё не потрачено, открывает «Настройки → Изменить адрес»,
вводит свободное имя, подтверждает. `reserveSlug` коммитит бронь, `renameSlug` доходит до записи события и
получает от PostgreSQL `permission denied`. Человек видит 503 «directory_unavailable», адрес не меняется.

**Почему.** Миграция `0048` добавила колонку `organization_slug_rename_events.initiated_by`. Репозиторий
пишет её явно (`pgClinicDirectory.ts:384`). Право на `INSERT` этой таблицы выдано **поколоночно**; табличный
`GRANT SELECT` на новую колонку распространяется автоматически, поколоночный `INSERT` — нет. В декларации
колонка добавлена (`relation-access.ts`, коммит `499f6ae1b`), в живой DEV — не приехала: шаг reconcile после
этого не гонялся.

**Живое доказательство** (dev-сервер этого воркдерева на `:5310`, сессия `dev:clinic-admin`, org
`d0000000-…-0004`):

```
curl -s -b /tmp/aud-cookies.txt -H 'Origin: http://127.0.0.1:5310' -H 'content-type: application/json' \
  -X POST http://127.0.0.1:5310/api/clinic/slug \
  -d '{"slug":"bcb-audit-step1","irreversibleRenameConfirmed":true}'
→ {"ok":false,"error":"directory_capability_unavailable"}   HTTP 503
```

журнал PostgreSQL в ту же секунду:

```
bcb_dev_webapp_staff@bcb_webapp_dev 42501 ERROR: permission denied for table organization_slug_rename_events
STATEMENT: insert into "organization_slug_rename_events" (... "initiated_by" ...) values (...)
```

замер прав:

```bash
sudo -n -u postgres psql -X -h /var/run/postgresql -p 5432 -d bcb_webapp_dev -c "
SELECT column_name, privilege_type FROM information_schema.column_privileges
 WHERE table_name='organization_slug_rename_events' AND grantee='app_staff'
   AND privilege_type='INSERT' ORDER BY column_name;"
```
→ шесть колонок, `initiated_by` среди них **нет**; в `SELECT` — есть.

Декларация же требует её:
`deploy/postgres/generated/privileges.bcb_webapp_dev.sql:15002`,
`deploy/postgres/generated/privileges.bersoncarebot_test.sql:15034`.

**Следствие для §16.3 плана.** Строка «Новых прав не выдано… у `app_staff` уже есть табличный SELECT на
события» — фактически неверна. Права ветка выдаёт (и правильно — генератором, не миграцией, §1 не нарушен),
но именно эта строка объясняет, почему шаг reconcile не был включён в приземление.

**Побочно (закрывает §16.2).** Расхождение, которым блокер был объяснён, после сведения `feat` больше не
воспроизводится: обе поверхности тела `app.resolve_public_booking_organization(uuid,uuid)` в декларации есть
(`privileges.bcb_webapp_dev.sql:3625-3626`). То есть reconcile, скорее всего, уже пройдёт — но его никто не
запускал, и до этого фича мертва.

## Ф2 (блокирующая). Миграция `0048` числится pending на DEV и TEST, а её бэкфилл безусловный

**Сценарий.** Следующий `bash deploy/host/migrate-dev.sh --execute` (или `deploy-test.sh`) увидит `0048`
в pending и выполнит её целиком, включая

```sql
UPDATE public.organization_slug_rename_events AS ev
   SET initiated_by = CASE WHEN EXISTS (SELECT 1 FROM public.be_organization_members …) THEN 'clinic'
                           ELSE 'platform_admin' END;
```

без `WHERE`. Все штампы пересчитываются **тем самым соединением с текущим членством**, ради устранения
которого миграция написана. Клиника, чей сотрудник менял адрес и с тех пор уволен (членство каскадно
удаляется от `platform_users`), получает `initiated_by='platform_admin'` — и вместе с ним **вторую
пожизненную смену**. Молча: ни клиника, ни поддержка этого не увидят.

**Замер.** `when` миграции `1800000060000`; водяные знаки: DEV `1800000056000`, TEST `1800000051000`; строки
леджера с этим `when` (и с хешем файла) нет ни в одной базе. При этом на DEV колонка и CHECK уже физически
есть — значит DDL накатили мимо wrapper'а (`AGENTS.md` §1 это запрещает прямо).

```bash
node -e "
const {readFileSync}=require('fs');const {execSync}=require('child_process');
const j=JSON.parse(readFileSync('apps/webapp/db/drizzle-migrations/meta/_journal.json','utf8'));
for (const db of ['bcb_webapp_dev','bersoncarebot_test']) {
  const rows=execSync(\`sudo -n -u postgres psql -X -h /var/run/postgresql -p 5432 -d \${db} -At -c 'SELECT created_at FROM drizzle.__drizzle_migrations'\`).toString().trim().split('\n').map(Number);
  const wm=Math.max(...rows);
  console.log(db,'watermark',wm,'pending:',j.entries.filter(e=>e.when>wm).map(e=>e.tag).join(', ')||'—');
}"
```
→ на обеих базах pending ровно `0048_a_lifetime_allowance_counted_by_join_is_not_lifetime`.


**ЗАКРЫТО фиксером `1462b777d` (19.08).** Безусловный `UPDATE` снят: бэкфилл существующих строк делает сам
`DEFAULT 'clinic'` в `ADD COLUMN` — это DDL, оно видит все строки независимо от RLS и переписать уже
проставленный штамп не может. Отдельно измерено, что снятый `UPDATE` и не работал: он идёт от
`app_object_owner`, а таблица под FORCE RLS без permissive-политики для этой роли (`SET ROLE
app_object_owner; SELECT count(*)` → 0, preflight печатал `UPDATE 0` при двух строках), плюс его отбил бы
append-only триггер. Потерь нет: у обеих строк DEV актор по-прежнему член своей организации, на TEST строк
нет вовсе. Состояние DEV приведено в честное штатным `migrate-dev.sh --preflight` → `--execute`: строка
леджера `created_at=1800000060000` есть, pending=0, содержимое таблицы до/после совпало. Свойство держит
`deploy/postgres/privileges/migration-backfill-idempotence.devDbProof.test.mjs`.

Комментарий в самой миграции («соединение здесь верно ровно один раз — сейчас») держится только при условии
«применяется ровно однажды», а этого условия ничто не обеспечивает: ни `WHERE created_at < …`, ни
nullable-колонка с последующим `SET`, ни запись в леджере.

## Ф4. Отказ по исключению оставляет бронь имени висеть

`setOrganizationSlug` (`service.ts:101`) коммитит бронь **отдельной транзакцией** до `renameSlug`. Отказ
по праву бронь снимает (`pgClinicDirectory.ts:328-337`) — это сделано и работает. А отказ **исключением**
(ровно случай Ф1, 42501; так же — падение процесса, обрыв соединения) откатывает только `renameSlug`;
строка `kind='reservation'` остаётся в базе.

**Сценарий и последствие.** Клиника вводит `nevskaya-klinika`, получает 503, уходит. Имя занято глобальным
`uq_organization_slug_claims_slug` и другой клинике не достанется — ни по сроку (владелец, §14.2: срока
годности нет), ни через админа (маршрута нет, Ф5). Освободится только когда та же клиника подаст следующую
заявку и перезапишет свою единственную строку брони.

Наблюдал живьём в этом аудите: после 503 из Ф1 строка `bcb-audit-step1 | reservation` осталась в
`organization_slug_claims`; исчезла лишь при следующей попытке той же клиники.

Класс не введён этой веткой (расщепление reserve/rename старше `499f6ae1b`), но правилом «слаг привязан
навечно» он сделан необратимым и потому виден именно сейчас.

## Что проверено и держится

### 1. «ОДНА смена за весь период жизни» — обходов не нашёл

Чем проверял: чтение кода + живая проба на DEV.

- **Считается по КЛИНИКЕ, не по актору.** `countSelfRenames` (`pgClinicDirectory.ts:53-67`) фильтрует
  `organization_id = $1 AND initiated_by = 'clinic'`. Актор в счёте не участвует вообще. Прежнее
  соединение с `be_organization_members` вырезано.
- **Смена через другого члена клиники** — не обход: тот же `organization_id`. Живьём: события, которые я
  подложил на org `d0000000-…-0004`, имеют `actor_platform_user_id = NULL` (то есть заведомо не тот
  человек, что сидит в сессии), и попытка сессионного админа всё равно получила
  `{"ok":false,"error":"self_rename_allowance_spent"} HTTP 409`.
- **Выход/повторный вход актора, удаление членства, удаление аккаунта** — не обход: признак стоит
  ШТАМПОМ на строке события в момент записи (`:381-386`) и ни от чего внешнего не зависит. Плюс таблица
  append-only на уровне БД: мой `UPDATE … SET initiated_by` от суперюзера отбит триггером
  `app.guard_organization_slug_rename_event_mutation` — «organization slug rename audit is append-only».
- **Гонка двух одновременных запросов.** По построению закрыта: решение и запись живут в ОДНОЙ транзакции
  `renameSlug` под `pg_advisory_xact_lock` по организации (`:39-44`, `:294`), замок держится до COMMIT,
  изоляция READ COMMITTED (`drizzleMutationTx.ts:29` — `db.transaction` без уровня), поэтому второй
  участник видит уже записанное событие первого. Предварительная проверка из сценарного слоя удалена
  осознанно (`service.ts:93-99`). **Живьём я гонку не переигрывал — упирается в Ф1**; автор гонял её
  17:42 и записал результат в тело коммита `499f6ae1b` (A→200, B→409).
- **Обход через «первое присвоение».** Ветка `claimReservedSlug` (без гейта и без события) достижима
  только при `currentSlug === null`, а потерять `current`-строку клиника не может:
  `app.guard_organization_slug_claim_mutation` запрещает DELETE строк `current`/`alias` и любой переход
  `current` кроме same-organization reclaim.
- **Обход через тело запроса.** `bodySchema` — `.strict()`, лишний `initiatedBy` даёт `invalid_body`;
  закреплено тестом «клиника не может объявить себя админом через тело запроса».

### 2. Админская смена лимит не тратит

Чем проверял: живая проба. На org `d0000000-…-0004` я оставил одно событие `clinic` и одно
`platform_admin`; лимит — один. Попытка самостоятельной смены вернула 409 → событие `platform_admin`

с join'ом), а штамп `initiated_by`.

### 3. Вечный редирект — держится, включая цепочку

Чем проверял: поведением на живой базе. Проиграл на DEV два последовательных переименования оператором
самой базы, повторяя ровно те же statements, что пишет `renameSlug` (две отдельные транзакции — в одной
отложенный триггер `assert_organization_slug_rename_complete` справедливо отбивает):
`race-clinic-start → aud-chain-b` (clinic) → `aud-chain-c` (platform_admin). Затем живьём:

```
race-clinic-start  card: 308 → /aud-chain-c   | booking: 308 → /aud-chain-c/booking
aud-chain-b        card: 308 → /aud-chain-c   | booking: 308 → /aud-chain-c/booking
aud-chain-c        card: 200                  | booking: 200
bersoncare-probe-l7 card: 308 → /dmitryberson | booking: 308 → /dmitryberson/booking
```

Самый старый адрес прыгает на текущий **за один хоп**, а не по цепочке: обе двери
(`app.read_public_clinic_card(text)`, `app.resolve_public_organization_slug(text)`) джойнят
`current`-строку организации напрямую, целевой slug в строке `alias` не хранится вовсе. Вечность подпёрта
и снизу: `guard_organization_slug_claim_mutation` запрещает удаление `alias`, а
`assert_organization_slug_alias_complete` не даёт завести alias без соответствующего события.

Состояние DEV после проб восстановлено побайтно к снимку (claims 4 строки, events 2, entries
`card_is_published=false` у всех трёх) — снимки лежат в `/tmp/aud-*-before.csv`.
