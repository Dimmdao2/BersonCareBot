## Находка

### F-A (BLOCKER, правило репозитория) — три миграции ветки меняют права

`AGENTS.md` §1, подраздел «⛔ Миграция не выдаёт и не отзывает права. Никогда» (в ветке с
`88b483d70`): запрет действует «полностью, без исключений и без „временно"», и второй абзац называет
ровно этот оператор — «Это касается и `REVOKE ALL ON FUNCTION … FROM PUBLIC` после `CREATE FUNCTION`».

Шесть таких строк в трёх миграциях ветки:

```
0053…:132  REVOKE ALL ON FUNCTION app.enroll_current_patient_in_public_booking_clinic(uuid,text)   FROM PUBLIC;
```

Это не спор о вкусе: генератор привилегий выдаёт ровно те же отзывы сам, и это видно в
сгенерированном артефакте —

```

    deploy/postgres/generated/privileges.bcb_webapp_dev.sql
4048, 4909, 7057, 7147   ← четыре из четырёх
```

То есть каждая из шести строк — второй источник того же права, а это ровно то расхождение, ради
которого правило и написано: права миграции применяются один раз в произвольной точке цепочки,
права генератора — целиком на каждом reconcile.

**Через живого человека.** Прямого вреда пользователю сегодня нет — оба источника пока говорят одно

разъезжались с ожиданием на живой базе (см. «Состояние DEV» ниже). Пока право живёт в двух местах,
такой разъезд читается как «кто-то из двух прав», а не как «источник один и он расходится с базой».

**Что нужно.** Удалить шесть строк. Ничего не сломается: `generate-cli.mjs --check` уже сходится
побайтно, а сами отзывы приезжают шагом reconcile.

## Замечания без статуса finding

- **Создание карточки клиента персоналом на DEV не работает вовсе** — `POST /api/doctor/clients`
  отвечает `409 create_failed`, под ним `permission denied for table platform_users` (INSERT).
  У `app_staff` на `platform_users` объявлены только `SELECT, DELETE`
  (`information_schema.table_privileges`), а маршрут всегда идёт в INSERT: человек, не состоящий в
  клиенте этой клиники, пациентскому SELECT персонала не виден, поэтому «уже существующий» не
  находится никогда. Дефект пред-существующий, к скоупу ветки отношения не имеет — но это значит,
  что путь персонала целиком проверить по HTTP сегодня нельзя ни в этой ветке, ни в любой другой.
- **Компенсация не покрыта тестом по существу.** `createVerifiedPublicBooking.unit.test.ts`
  проверяет только ПОРЯДОК (`['enroll','revoke']`) и аргумент; сама логика решения двери
  (провенанс, окно, живой приём) не закреплена ничем — в `devDbProof` четыре теста, ни один не
  трогает `revoke_public_booking_enrollment`. Отказ здесь дорогой и молчаливый по §10a («посетитель
  стирает карточку, заведённую клиникой»), так что тест уместен — но требования на него в плане
  владельца нет, поэтому это рекомендация, а не работа (§24.6).
- **Дверь компенсации не сверяет `accepted.organization_id` с аргументом.** Измерено: контекст с
  организацией A + аргумент B (и хеш аргументов на B) — дверь сработала по B
  (`{"effect":"deleted"}`). Недостижимо: приложение всегда ставит принципал по
  `intent.organizationId` и им же зовёт дверь, а тронуть можно только СВОЮ строку и только внутри
  15-минутного окна. Замечание об эшелонировании, не нарушение.
- **Провалившаяся запись оставляет аккаунт.** Проигравший гонку получил 409, клиентом не стал —
  но строка `platform_users` с его именем, телефоном и отметкой доверия к телефону осталась, и
  сессия ему выдана. §33.1 говорит «Несостоявшаяся запись КЛИЕНТА не создаёт», и клиент
  действительно не создан; фраза «ни аккаунта» стоит там в описании другого случая — человек ушёл,
  не начав запись. Формально не нарушено; называю, потому что грань тонкая и это вопрос владельца.
- **Вошедший человек молча привязывается к своей учётке при чужом телефоне.** В сессионном прогоне
  контакт записи (`+7999000991 3`) не совпадал с телефоном аккаунта (`+79990000006`), развилки
  «обновить профиль или создать постороннюю запись» (§33 п.5) не было — запись легла на вошедшего.
  Поведение пред-существующее: `git diff feat…HEAD -- identifyPublicBookingPayer.ts` показывает, что
  ветка добавила туда только поле `channel`. Незакрытый пункт §33, отдельная работа.
- **Постскриптум прежнего отчёта протух.** В `PUBLIC_BOOKING_WRITE_BLIND_AUDIT_2026-08-19.md`,
  раздел «Что с находками стало», написано «F1 — закрыта. Проверка квоты переехала в единственную
  функцию …, которую зовут ОБА создателя отношения», и про 0053 там нет ни слова. Читатель этого
  файла сегодня получит неверную картину продукта. План
  (`docs/_TODO/PUBLIC_BOOKING_TENANT_SERVICE_SEAM_2026-08-19.md:150`) помечен `SUPERSEDED` правильно
