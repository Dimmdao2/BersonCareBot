## 3. Журнал: кто прав — «добавила запись» или «удалила запись»?

**Правильное понимание — у `wt/invoice-reissue-20260819` («журнал заморожен, не трогать»), а не у
этой ветки.** Обоснование по действующему коду и канону, не по мнению:

- Заголовок `deploy/postgres/privileges/migration-order.mjs`: «`meta/_journal.json` is no longer
  read for order. It survives as the frozen historical `when -> tag` map used once per database to
  label ledger rows written before the tag column existed.»
- `check-drizzle-migration-order.sh`, финальное сообщение при провале: «meta/_journal.json is the
  frozen historical map; do not hand-edit it to reorder anything.»
- Прочитан весь механизм: `selectPendingMigrations` и `readMigrationFolder`
  (`migration-order.mjs:27-47`) журнал **вообще не читают** — pending/applied решается только по
  имени файла и по колонке `tag` в леджере. Журнал участвует ровно в одном месте —
  `renderLedgerBootstrapSql`, и там только для строк с `tag IS NULL` (легаси-бэкфилл один раз на
  базу).

Наша правка `dd1fa81a3` заменила существующую запись журнала (`tag: 0050_…, when: 1800000052000`)
на новую (`tag: 0054_…, when: 1800000090000`) — то есть **вручную отредактировала «замороженную»
карту**, ровно то действие, которое канон прямо запрещает («do not hand-edit it»). Это не то же
самое, что переупорядочивание (`переставить`), но по букве правила — то же семейство операции
(hand-edit журнала), и по духу правила («два места для одного факта расходятся молча») — лишнее:
новая запись не нужна ни одному потребителю в новой схеме, потому что `0054_…` получит свой `tag`
в леджере штатной вставкой при обычном применении, а не через бэкфилл.

**Функциональное последствие (проверено чтением, не гипотеза):** добавленная запись `idx 51` не
меняет исход pending/applied ни для одной базы, включая TEST, — код её не консультирует для этого.
Единственный канал, где она вообще что-то делает, — бэкфилл `tag IS NULL AND created_at = 1800000090000`;
это значение синтетическое (выбрано «выше обоих водяных знаков», не взято из реальной домиграционной
истории), поэтому шанс совпасть с настоящей легаси-строкой без тега — практически нулевой, и
исполнитель это на момент коммита проверил явно на DEV и TEST. **На TEST, где миграции `0054_…` ещё
нет вовсе, добавленная запись журнала не делает ровно ничего** — TEST применит `0054_…` штатным
pending-путём, журнал не участвует.

Итог: **это не блокер и не порча базы**, но это лишняя, канон-нарушающая правка, которую надо
откатить (убрать добавленную запись `idx 51` из `meta/_journal.json`), а не сохранять как образец.
Вопрос ведущему не требуется — правило уже написано текстом канона, выбор не альтернативный.
