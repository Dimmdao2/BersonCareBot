A2 — единственное непойманное с реальным последствием. По §10a оно не превращается в задачу автоматически:
отказ громкий (врач немедленно видит ошибку на своём действии), а не молчаливый, поэтому второго теста он по
критерию ступени 2 не требует. Решение — за ведущим и владельцем, не за аудитом.

### FAIL: тест пинит форму SQL, а не поведение

`pgTreatmentProgramItemRefValidation.platformLayer.unit.test.ts:105` и симметричная строка в отрицательном
случае проверяют ТЕКСТ отрендеренного запроса:

```js
expect(sql).toMatch(/"owner_kind" = \$\d+ and "\w+"\."organization_id" is null/);
```

Поведенчески эквивалентная перестановка операндов внутри `itemRefOwnershipPredicate`
(`and(isNull(organizationId), eq(ownerKind, 'platform'))` — тот же результат, тот же план запроса) красит
**4 случая из 8**. Это ровно то, что §10a запрещает: проверка внутренней формы, которая краснеет от
безопасного изменения и обесценивает красный цвет.

Проверено, что строки лишние, а не полезные: с ними снятыми (эксперимент аудитора, откачен)
инъекции B1 и B4 по-прежнему красят ровно те же случаи — их ловят соседние утверждения по параметрам
(`expect(params).toContain('platform')` / `not.toContain('platform')`), а эквивалентная перестановка B2
перестаёт быть красной. То есть удаление двух строк не теряет ни одной пойманной поломки.

Правка локализована до двух строк одного файла — по §24.1 её делает ведущий, не аудит. Приёмка этого теста
по §24.7 до неё блокирована.

## 6. Рефакторинг не изменил `exercise` и `lfk_complex` — доказано рендером SQL

Собран временный прогон (удалён после замера), который поднимает версию файла ДО `3b4c4c176` и версию после,
гоняет настоящий `switch` каждой из них через подменённый drizzle и сравнивает `toSQL()`:

| Тип | тариф | BEFORE == AFTER |
|---|---|---|
| `exercise` | вкл / выкл | **да, побайтно (sql + params)** |
| `lfk_complex` | вкл / выкл | **да, побайтно (sql + params)** |
| `clinical_test` | вкл / выкл | нет — в этом и правка |
| `recommendation` | вкл / выкл | нет — в этом и правка |

Живой контроль на ту же тему: `exercise` (и платформенное, и своё) после рефакторинга кладётся в этап `HTTP 200`
(п. 2.2).

### Одно изменение семантики, которое стоит назвать вслух

Для `clinical_test` и `recommendation` условие своей строки стало строже: было `organization_id = <своя>`,
стало `owner_kind = 'organization' AND organization_id = <своя>`. Сужение безопасно, и это проверено на живой
базе, а не выведено из типов:

```
tests_owner_check        | CHECK ((owner_kind='organization' AND organization_id IS NOT NULL)
                         |     OR (owner_kind='platform'     AND organization_id IS NULL))   convalidated = t
recommendations_owner_check | то же,                                                          convalidated = t
tests_violating   | 0     rec_violating | 0
```

То есть строки с непустой организацией и не-`organization` владением физически невозможны и в базе
отсутствуют. Зависимость односторонняя: если когда-нибудь уронят этот CHECK, свои строки с другим
`owner_kind` станут ненаходимыми молча. Это записано как риск, а не как дефект.
