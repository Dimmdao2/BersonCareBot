## FAIL — Ф1. Половина посеянных платформенных строк непригодна для живой проверки

**Что видит врач.** На карточке платформенного теста «Базовая библиотека: тест отведения плеча» и
платформенной рекомендации «Базовая библиотека: режим дня при боли в плече» поле «Регион тела» показывает
чип **«Значение недоступно»** вместо «Плечо». Снимок:
`/home/dev/s0b-shots/02-test-platform.png` (виден и баннер, и серые поля, и этот чип).

**Второе независимое проявление того же корня.** Фильтр каталога по региону не находит эти строки:

```
curl -s -b <докторская сессия> "http://127.0.0.1:5216/app/doctor/clinical-tests?region=knee"     → platform-строк 1
curl -s -b <докторская сессия> "http://127.0.0.1:5216/app/doctor/clinical-tests?region=shoulder" → platform-строк 0
```

То есть платформенный тест плеча существует, виден в общем списке, но по своему собственному региону
недостижим.

**Корень — измерено, не выведено.** `reference_items` существуют ТОЛЬКО в разрезе организации
(`organization_id NOT NULL`, платформенных строк в справочнике нет). Блок S0б выбирает элемент справочника
так:

```sql
JOIN public.reference_items AS item
  ON item.category_id = category.id AND item.code = seed.region_code
 AND item.is_active = true AND item.deleted_at IS NULL
ORDER BY seed.region_code, item.id      -- DISTINCT ON (region_code)
```

— то есть берёт элемент с наименьшим UUID **по всем организациям сразу**. Что из этого вышло на живой базе:

| строка | код региона | организация-владелец элемента справочника | эта организация существует? |
|---|---|---|---|
| тест «приседания у стены» | knee | `a0000000-…0001` | да (клиника врача) |
| тест «отведения плеча» | shoulder | `926a0000-…000a` | **нет** (`be_organizations` пуста для этого id) |
| рекомендация «нагрузки на колено» | knee | `a0000000-…0001` | да |
| рекомендация «режим дня при боли в плече» | shoulder | `926a0000-…000a` | **нет** |

У клиники врача СВОЙ элемент `shoulder` есть — `134cad21-7fc5-4156-a491-5f4e36f8bd99`; сеялка его не
выбрала только потому, что его UUID больше. Промах по knee не случился по чистому везению порядка UUID.

**Почему это дефект именно этого коммита, а не унаследованное свойство.** Комментарий в самом коммите
утверждает: «Регион берётся тем же способом, что и у упражнений: активный справочный элемент, который
каталог реально использует». Это неверно. Блок S0а (приземлён, `92f0f6732`) содержит якорь, которого в
блоке S0б нет:

```sql
AND EXISTS (SELECT 1 FROM public.lfk_exercises AS existing WHERE existing.region_ref_id = item.id)
```

Именно он привязывает выбор к организации, у которой каталог реально живёт. Проверка на живой базе: все
пять платформенных упражнений S0а указывают на элементы существующей `a0000000-…0001`, ни одного промаха.
Блок S0б заменил этот якорь на голое `is_active = true` — и промахнулся на двух строках из четырёх.

**Почему это блокирует приёмку.** Живая проверка S0б по плану — врач видит платформенный тест и
платформенную рекомендацию. Он их видит наполовину: название и описание читаются, регион — нет, по региону
строка не ищется. Владелец, проходя приёмку, упрётся в «Значение недоступно» и не сможет отличить дефект
фикстуры от дефекта платформенного чтения, ради которого этап и делался.

**Правка локализована** (одно условие в `deploy/postgres/dev-platform-lfk-demo-seed.sql`) — по §24.1 её
делает ведущий сам, аудитор продуктовый код не чинит. После правки строки надо пересеять и пересмотреть
карточку плеча живьём.

## Вопросы владельцу (не FAIL)

### Ф2. У `clinical_test_regions` и `recommendation_regions` нет owner-guard-триггера — и сообщение коммита утверждает обратное

Сообщение `4a7bc831b` говорит: «Дочерние ссылки на регионы несут владельца родителя — иначе триггер
`app.enforce_lfk_child_owner()` отбивает вставку». На живой базе этого триггера на этих таблицах **нет**:

```
триггеры на tests / recommendations / clinical_test_regions / recommendation_regions  → ни одного
app.enforce_lfk_child_owner стоит на: lfk_complex_template_exercises, lfk_exercise_load_types,
                                      lfk_exercise_media, lfk_exercise_regions
```

Доказано инъекцией в откатываемых транзакциях. Контроль на семействе ЛФК (там, где триггер есть) —
вставка ребёнка с чужим владельцем к платформенному родителю **отбита**: `ERROR: lfk_child_owner_mismatch`.
Та же инъекция в обе таблицы S0б — **принята**, `mismatched_child_rows_accepted = 1` в каждом случае.
Все три транзакции откачены, итоговые счётчики `clinical_test_regions|4` и `recommendation_regions|4`
не изменились.

Почему это вопрос, а не FAIL: план S0б требует для этой пары таблиц «колонку владения и CHECK по образцу
семейства ЛФК» — CHECK на месте, про триггер строки в плане нет (он назван только в S0в и только для детей
упражнений). По §24.6 находка без пункта в плане владельца работой не становится.

**Вопрос:** распространить ли `app.enforce_lfk_child_owner()` на `clinical_test_regions` и
`recommendation_regions`? Сегодня единственная защита — текст SELECT'а в сеялке; ничто в базе не мешает
привязать к платформенному родителю ребёнка организации, а такой ребёнок будет читаться организацией по
её собственной политике `rev10_saas_org_dormant_p0_8_3`.

Отдельно от вопроса: **фраза в сообщении коммита фактически неверна** и опирается на несуществующий
предохранитель. Это не меняет поведения кода, но искажает основание проектного решения для следующего
читателя.

### Ф3. Справочники регионов существуют только внутри организации — у платформенного слоя своего справочника нет

`public.reference_items.organization_id` — `NOT NULL`, платформенных строк в справочнике ноль. Значит любая
платформенная строка (упражнение, тест, рекомендация) вынуждена ссылаться на справочник **какой-то одной
клиники**. Сейчас это скрыто тем, что на DEV живая клиника одна; Ф1 — первое проявление проблемы, а не
её причина.

**Вопрос:** нужен ли платформенному слою собственный справочник регионов (владение `platform`,
`organization_id IS NULL`), или платформенная строка должна хранить код региона, а не UUID элемента?
Пункта в плане нет ни в S0б, ни в S0в; вопрос встанет в полный рост, как только платформенную строку увидит
вторая клиника.

## НЕ ПРОВЕРЕНО

- **Утверждение баннера «Материал доступен для назначения».** Текст скопирован из уже приземлённой карточки
  упражнения, но что платформенный тест или рекомендацию реально удаётся положить в набор, шаблон или
  программу пациента, я не проверял: эта дверь — server action редактора программ, а не докторский API
  каталога, и пункта про назначение в S0б нет. Если назначение платформенной строки не работает, баннер
  врёт врачу — это стоит проверить до приёмки владельцем.
- **Чтение чужой организацией.** Негатив «политика не отдаёт строки другой клиники» на продуктовом уровне
  не воспроизведён: в `be_organizations` на DEV существует **одна** организация (`a0000000-…0001`), вторую
  ради этого я не заводил. Ограничение доказано только текстом предиката и совпадением с артефактом.
- **Принципал без организации.** Ветка предиката `app.current_org_id() IS NOT NULL` живьём не проверялась:
  докторская сессия всегда несёт организацию, а поднимать сырое подключение `app_staff` мимо
  context-gate я не стал.
- **`pnpm run ci`, `typecheck`, `eslint`.** Не гонял. Коммит заявляет `typecheck EXIT=0` и чистый eslint;
  я это не перепроверял — вместо этого все четыре изменённых файла скомпилированы и отрисованы живым
  dev-сервером на шести экранах без единой консольной ошибки, что для условного рендера сильнее.
- **Мобильный viewport.** Все снимки сделаны на 1440×1000. Поведение карточки на узком экране не смотрел.
- **Поведение после refresh DEV.** Утверждение шапки сеялки «переживает обновление DEV» не проверялось:
  для этого нужно пересоздать базу из дампа, а Ф1 показывает, что выбор элемента справочника к составу
  данных как раз чувствителен.
- **Архивная платформенная строка.** Ветка `isReadOnly ? null : isArchived ? …` на архивной платформенной
  строке живьём не проверена — таких строк на DEV нет (0), а заводить их я не стал.
