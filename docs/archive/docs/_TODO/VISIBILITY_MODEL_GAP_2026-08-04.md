## 1. Связь «пациент ↔ специалист»

**Подтверждено: связи нет.** Владелец прав — это недоделка, не впечатление.

- Схема БД (`apps/webapp/db/schema/schema.ts`, 90+ таблиц; `bookingEngine.ts`; `bookingScheduling.ts`;
  `doctorPatientSupport.ts`) не содержит ни одной таблицы вида `patient_doctor`/`doctor_patient`/
  `assigned_doctor_id`/`primary_specialist_id`/`care_team`.
- Ближайшая по названию — `doctor_patient_support` (`apps/webapp/db/schema/doctorPatientSupport.ts:13-44`) —
  НЕ связь: уникальный индекс `uq_doctor_patient_support_patient` (строка 36) стоит на `patientUserId` ОДНОМ,
  колонки `doctor_id`/`specialist_id` в таблице нет вообще. Комментарий в коде прямо говорит:
  `/** Per-patient support profile (app-wide; not multi-doctor scoped in v1). */` (строка 13).
- `platformUsers.role` — плоский enum `'client' | 'doctor' | 'admin'` (`schema.ts:111,180-182`), без поля
  специальности/панели пациентов.
- Бронирования это НЕ заменяют: `beAppointments` (`bookingEngine.ts:519-597`) хранит `specialistId`
  (строка 526) + `platformUserId` (528) как атрибуты РАЗОВОЙ записи, без уникального ограничения пары и без
  накопления в постоянную связь. `patientBookings` (`schema.ts:2631-2722`) и `appointmentRecords`
  (`schema.ts:774-843`) колонки специалиста вообще не имеют.
- Миграции (330+ файлов в `apps/webapp/db/drizzle-migrations/`): по `patient_doctor|doctor_patient_assign|
  assigned_specialist|primary_doctor` — ни одна таблица-связь никогда не создавалась и не удалялась (кроме
  одноразовой seed-переменной `v_primary_specialist_id` в `0143_seed_staff_organization_members.sql:4` — не
  колонка схемы).

**Что на это завязано.** Список пациентов врача (`pgDoctorClients.ts:287-295`, п.3 ниже) сегодня строится не
из связи и даже не из истории записей, а из членства в организации — поэтому «свой пациент» нельзя выразить,
даже если понадобится: колонки, которую можно было бы отфильтровать, не существует ни в одной таблице.

## 3. Что видит врач сейчас

**`pgDoctorClients.ts:287-295` — не единственная точка, а представитель систематического паттерна.**
Пройдены все места, где врачу отдаётся список пациентов и медицинские данные — все идут через один шлюз
`getClientIdentityForOrganization(userId, organizationId)` (`pgDoctorClients.ts:1171-1193`), который проверяет
только `org_enrollments` (статус `invited`/`active`) — идентификатор специалиста нигде не сравнивается:

- Список пациентов: `pgDoctorClients.ts:287-295` (`listClients`) — только EXISTS по `org_enrollments`;
  `app/api/doctor/patients/route.ts:30` передаёт в него `organizationId`, `specialistId` не передаёт вообще.
- Дашборд-метрики: `pgDoctorClients.ts:1006-1158` (`getDashboardPatientMetrics`) — тот же org-only хелпер.
- Разбивка по контактам: `pgDoctorClients.ts:1425-1477` (`getClientContactBreakdown`) — тот же паттерн.
- Карточка пациента: `app/api/doctor/patients/[userId]/route.ts:40`.
- Клинические данные (жалобы/диагнозы/визиты): `.../[userId]/clinical/route.ts:25` → `pgPatientClinical.ts:139-254`
  — фильтр только по организации.
- Файлы пациента: `.../[userId]/files/route.ts:63,133` → `pgPatientFiles.ts:84-236` — только по организации.
- Коморбидности: `.../[userId]/comorbidities/route.ts:39,88` → `pgPatientComorbidities.ts` — только по организации.
- Заметки врача: `app/api/doctor/clients/[userId]/notes/route.ts:24,55` → `pgDoctorNotes.ts:28` — только по организации.
- Комментарии/история: `app/api/doctor/comments/patients/route.ts:41,52`, `.../appointments/route.ts:24-33` →
  `pgClientHistory.ts`, `pgDoctorClients.listPatientAppointments` — только по организации.
- Диалоги: `app/api/doctor/messages/conversations/route.ts:22-43` — тот же паттерн.
- Программы лечения: `pgTreatmentProgramInstance.ts` — все методы фильтруют строго по `organizationId`.

**Частичное исключение, не опровергающее вывод.** У доктора (без права `canManageAllSpecialists`) КАЛЕНДАРЬ
записей ограничен `appointment.specialistId === ctx.specialistId`
(`app/api/doctor/booking-engine/_resolveDoctorAppointmentAccess.ts:25`,
`_resolveDoctorScheduleScope.ts:58-112`) — но это ограничивает только «чей календарь», а не видимость списка
пациентов и медицинских данных: врач с этим ограничением всё равно видит полный список пациентов клиники и
их полную карту.

**Вывод:** `DoctorWorkspaceAccessContext` (`app-layer/guards/requireRole.ts:259-268`) уже несёт `specialistId`
в контексте запроса — техническая возможность фильтровать есть, но нигде на пути пациентских данных этот
`specialistId` не используется как предикат.

## 4. Админ клиники

**Роль «Менеджер» в коде отсутствует — подтверждено.** Enum ролей членства:
`apps/webapp/src/modules/organization-membership/ports.ts:1`:
```ts
export const ORGANIZATION_MEMBERSHIP_ROLES = ['owner', 'admin', 'doctor', 'assistant'] as const;
```
Четыре роли, `manager` нет. Поиск по «manager»/«менеджер» вне тестов даёт только не относящиеся к делу
совпадения (`requireBillingManager` — имя функции биллинга, `PushManager`/`ServiceWorkerManager` — Web Push
API, прозаический комментарий «clinic managers»).

**Складывается ли admin с doctor — да, механизм есть, но без переключателя.**
`app-layer/guards/workspaceCapabilities.ts:64-70`:
```ts
const canAccessClinicalWorkspace =
  facts.canAccessClinicalWorkspace ??
  ((facts.membershipRole === 'owner' || facts.membershipRole === 'doctor') &&
    facts.specialistId != null);
if (canAccessClinicalWorkspace) {
  capabilities.add('clinical.workspace');
}
```
Источник булева значения — `modules/organization-membership/service.ts:31-36`:
```ts
function canAccessClinicalWorkspace(membership: OrganizationMembership): boolean {
  return (
    (membership.role === 'owner' || membership.role === 'doctor') &&
    membership.specialistId !== null
  );
}
```
Вызывается безусловно в `toMembershipContext` (`service.ts:48`) при каждом резолве членства — никаких
настроек/флагов не читается. Потребитель — `app/app/doctor/layout.tsx:61-69`: если `canAccessClinicalWorkspace`
истинно, рендерится полная оболочка врачебных экранов.

**Переключателя «выключить врачебные экраны, оставить админ-экраны» не существует.** Поиск по
`doctorScreens|showDoctorUI|disableDoctor|hideDoctor|toggleDoctor` по `apps/webapp/src` — ноль совпадений;
поиск таблиц/полей вида `*organization*setting*`/`*membership*setting*` — ничего не найдено; в
`DoctorWorkspaceShell.tsx` и `accountContext.ts` нет полей `workspaceMode`/`activeWorkspace`/`preference`.

**Значение по умолчанию — включено, что ПРОТИВОРЕЧИТ модели владельца.** Единственное условие —
`specialistId != null` на строке членства. У owner, который одновременно врач (нормальное состояние по словам
владельца — «по умолчанию так и есть»), это условие истинно всегда → `clinical.workspace` выдаётся
безусловно → полная оболочка `/app/doctor/**` рендерится по умолчанию (`doctor/layout.tsx:61-69`). Шага
«скрыто, пока явно не включено» в коде нет — владелец требует обратного: «По умолчанию врачебные экраны
ВЫКЛЮЧЕНЫ, а не включены».

## 5. Стена между клиниками (RLS) vs фильтр внутри клиники (код)

**Сегодняшний код уже соответствует модели владельца на уровне доктрины и предикатов, конфликта с D15b/4 нет.**

- Рендерер RLS-политик `docs/_TODO/SAAS_FOUNDATION/scripts/rls-sql-renderer.mjs:154-161` — комментарий, уже
  исправленный 04.08 в этом же дне (снята ложная атрибуция «доступ org-wide — решение владельца»), дословно
  фиксирует актуальное решение владельца со ссылкой на `IDENTITY_AND_MERGE_SCHEME.md §2e`:
  > «межклиниковая стена остаётся в RLS, а видимость ВНУТРИ клиники («свои + переданные») фильтруется в
  > порту идентичности, не здесь»
  — это точное совпадение с формулировкой брифа («жёсткий блок между клиниками» = RLS, «фильтр внутри» = код).

## Оценка объёма

Модель владельца требует изменений минимум в четырёх слоях:

1. **Схема БД.** Нужна новая сущность связи «пациент ↔ специалист» (создание таблицы/колонки + миграция) —
   её нет вообще (п.1). Без неё невозможны ни «свой пациент», ни «передача пациента» (п.2), ни фильтр внутри
   клиники (п.5).
2. **Репозитории/порт идентичности.** Каждая точка из п.3 (list, dashboard, clinical, files, comorbidities,
   notes, comments/history, conversations, treatment-program-instances — минимум 10 файлов репозиториев)
   сегодня фильтрует только по `organizationId`; нужен единый предикат по назначению, применённый во всех
   местах разом (иначе разрыв повторится частично).
3. **Guards / capabilities.** `workspaceCapabilities.ts` + `organization-membership/service.ts` нужно
   переработать под «выключено по умолчанию» + добавить хранимый флаг-переключатель (новое поле в
   membership/organization settings, которого сейчас нет — п.4) — это новая настройка, не просто смена
   константы.
4. **RLS-слой.** Доктринально уже согласован с моделью (п.5, комментарий 04.08), но реализация фильтра
   «внутри клиники» полностью отсутствует и должна появиться в коде/порту идентичности, не в RLS —
   координация с идущей веткой `wt/d15b4-platform-users-rls` обязательна, т.к. она сейчас активно трогает
   RLS на смежной таблице `platform_users`.
5. **Экраны (не измерялось детально в этом проходе)** — UI переключателя «выключить врачебные экраны» в
   кабинете админа/owner не существует (п.4), потребуется новый UI-элемент и его persistence.

## Вопросы владельцу

1. Роль «Менеджер» в модели владельца упомянута («менеджер и админ клиники видят записи по всем») — в коде
   роли нет вообще, есть только `owner`/`admin`/`doctor`/`assistant`. Это будущая роль, которую нужно завести,
   или «менеджер» здесь = синоним `admin`/`assistant`?
2. «Фильтр на уровне кода» для видимости внутри клиники — где именно он должен жить: единый порт идентичности
   (как уже написано в комментарии рендерера RLS, `IDENTITY_AND_MERGE_SCHEME.md §2e`), или отдельный слой
   guards/capabilities? Комментарий фиксирует намерение, но самого порта с этой логикой в коде нет — нужно
   решение, прежде чем проектировать.
3. Переключатель «выключить врачебные экраны у admin+doctor» — это персональная настройка (на уровне
   membership-строки конкретного человека) или настройка организации (на всех admin+doctor сразу)? Модель
   владельца («он может отключить у себя в кабинете») читается как персональная, но не подтверждена явно.
