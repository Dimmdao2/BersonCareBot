### 4.2 Поведение ограничений на живой базе, мои значения

Артефакт: `AUDIT2_B4_DEV_PROOF_2026-08-23.sql` (rollback-only, значения выбраны независимо от круга 1).
`AGENTS.md` §1 прямо говорит, что голый SQL от `postgres` preflight не заменяет — поэтому этот файл
идёт **дополнением** к §4.1, а не вместо него. Круг 1 таким же способом проверил оба CHECK; **чего у
него не было и что добавлено здесь — три нижних пункта: посадка колоночных грантов на мигрированную
форму, покрытие новых колонок правами `app_patient` и живая проверка того, что RLS-политика пациента
ограничена `status = 'published'`.**

```
COLUMNS_BEFORE=0
VERIFY_PREDICATE=true
STAFF_INSERT_COLS=accent_token,created_by_platform_user_id,display_name,logo_media_id,organization_id,patient_app_name,status
PATIENT_TABLE_SELECT=SELECT
PATIENT_COLUMN_SELECT_ON_NEW_COLS=2
PATIENT_SELECT_POLICY_PUBLISHED_ONLY=true
ACCENT_REJECTED_10 = xxxxxxxxxx
NAME_REJECTED_4    = xx  NAME_ACCEPTED_UNEXPECTED['<TAB><TAB>']  x
LEGIT_ROW_ACCEPTED = Здоровье — кабинет / #a1b2c3
BOTH_NULL_ACCEPTED = true
COLUMNS_AFTER_ROLLBACK=0
```

Что это доказывает поведением, а не чтением файла:

- **Акцент вне `^#[0-9a-f]{6}$` отбивает БАЗА, а не только зод.** Отвергнуты все 10 значений:
  `#A1B2C3` (верхний регистр — нормализация в приложении несущая, не косметическая), `#12ab`,
  `#1234567`, `rgb(255,0,0)`, `#1234 56`, `var(--x)`, `＃123456` (полноширинная решётка),
  `#123456}body{display:none` и — важное — **`#123456\n` и `\n#123456`**: в Postgres `$` без
  newline-режима концом строки не считает перевод строки, значит вектор «пробить инлайновое
  кастомное свойство переводом строки» закрыт на уровне БД.
- **Пустое имя отбивает БАЗА:** `''`, `'   '` и 121 символ отвергнуты.
- **Колоночные гранты садятся на мигрированную форму без сюрприза.** Я применил в той же транзакции
  оба `GRANT` из отрендеренного артефакта привилегий: `app_staff` получил INSERT ровно на 7 колонок,
  включая обе новые. У `app_patient` грант **табличный** (`GRANT SELECT ON TABLE`), поэтому обе новые
  колонки покрываются автоматически (`PATIENT_COLUMN_SELECT_ON_NEW_COLS=2`) — известный капкан
  «колоночный список липнет к последней привилегии» здесь не срабатывает.
- **Вторая стена против утечки черновика стоит в самой БД.** Живая политика
  `rev10_org_brand_revision_select_129` содержит `status = 'published'` для `app_patient`
  (`PATIENT_SELECT_POLICY_PUBLISHED_ONLY=true`) — то есть даже если бы код в сервисе сломался,
  пациентский принципал физически не прочитает неопубликованную ревизию.

## 8. Неблокирующие находки

### `N-1`. Привязка Host-бренда к организации не закреплена ни одним коммитнутым тестом

Инъекция `J-8` снимает `resolvedSurface.organizationId === patientOrganizationId` в

уберёт эту строку, ни один тест не покраснеет, а последствие — пациент организации X на
брендированном Host организации Y увидит имя Y как заголовок СВОЕГО контекста заботы.

Сегодня недостижимо (`patient_branded` в проде не наступает, `NO_TENANT_SURFACE`), поэтому не блокер.
Закрывается одним `it` в `layout.branding.test.ts`: тот же сценарий, что «uses the Host brand», но с
`organizationId` другой организации и ожиданием, что заголовок — свой платный бренд.

### `N-2`. Проверка формы эффективного logo URL на границе поверхности не покрыта тестом

Инъекция `J-5` полностью удаляет регэксп `^/api/media/<uuid>$` из
`sanitizeEffectivePatientBrand` (`requestSurface.ts:98-106`) — **79/79 зелёные**. Ни один тест
`proxy.route.test.ts` не подаёт `logoUrl` вообще: в тесте `safeBrandWithInternalExtras` его нет, в
параметризованном 404-тесте — тоже. Значит поле, которое единственное из четырёх может стать
абсолютным внешним URL, проверяется только кодом без гейта.

Не блокер: значение в этот объект попадает только из `orgBrandLogoUrl(mediaId)`, который по
построению даёт `/api/media/<uuid>`, а шов арендатора ещё не подключён.

### `N-3`. Имя из одних табуляций проходит CHECK базы (подтверждает `N-7` круга 1)

`btrim(patient_app_name) <> ''` снимает только пробелы, поэтому `E'\t\t'` база принимает
(замерено выше: `NAME_ACCEPTED_UNEXPECTED['<TAB><TAB>']`). Через продукт недостижимо:
`normalizePatientAppName` использует JS `.trim()`, который табуляции снимает и отдаёт `null`.
Поведение дословно повторяет уже живущий `org_brand_revisions_display_name_check`, то есть это не
регрессия `B4`, а унаследованная форма. Правка этой строки в `B4` означала бы менять и соседний
check — этого в плане владельца нет.

### `N-4`. У двух новых значений нет ни одного писателя — их сегодня физически нельзя задать

`saveOrgBranding` (`app/app/settings/brandingActions.ts:33-42`) передаёт в сервис только
`displayName` и `logoMediaId`. Больше `saveDraft` не вызывает никто. Сервис при отсутствии ключей
корректно сохраняет удержанное значение — но удерживать нечего: записать `patientAppName` или
`accentToken` не может ни UI, ни action, ни API. То есть цепочка «БД → порт → сервис → поверхность»
собрана целиком, а вход в неё не открыт.

**Это не дефект против текста `B4`**: пункт просит расширить сервис и проекцию, форму ввода не
просит, а `B5a` прямо запрещает конструктор. Но фактическое положение стоит назвать вслух, чтобы
никто не принял «`B4` закрыт» за «клиника может задать имя приложения». **Вопрос владельцу, не
задача:** каким пунктом (`B5a`? `D1`?) открывается ввод этих двух значений.
