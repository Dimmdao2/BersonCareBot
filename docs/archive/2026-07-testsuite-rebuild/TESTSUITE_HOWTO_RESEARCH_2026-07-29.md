# Как пишут тесты во взрослых системах — свод двух независимых исследований (29.07.2026)

> Заказано владельцем: «принеси исследование, КАК ИМЕННО пишутся тесты во взрослых системах» + «моя идея
> (builders + fast-check-генераторы) где-то используется?». Два независимых веб-исследователя, каждый со своим
> углом (макро-архитектура / его связка), не видя друг друга. Ниже сведение со ссылками. Провенанс:
> `docs/_TODO/runs/testcut-how/` (агентские отчёты в транскриптах сессии).

## Прямой ответ: твоя идея реальна, ей 25 лет, и так делают те, кого ты уважаешь

- Называется **property-based testing (PBT)**. Заложена статьёй **Claessen & Hughes, «QuickCheck», ICFP 2000**
  (премия ICFP «самая влиятельная статья» 2010), портирована в ~40 языков.
- Для нашего TS — **fast-check** (github.com/dubzzz/fast-check): 10M+ загрузок/нед, встроен в тест-наборы
  jest, ramda, io-ts, fp-ts, js-yaml; ловил реальные баги в jest, React, io-ts.
- В проде у серьёзных: **AWS** — S3 ShardStore (40k строк Rust: исполняемая эталон-модель + PBT-сверка,
  **предотвратили 16 багов до прода**, SOSP'21); **Volvo** — критический AUTOSAR-софт машин (3000 стр. спеки →
  модели, **200+ дефектов**, Quviq QuickCheck); **Jane Street** — весь OCaml-core; **Ericsson** (протокол Megaco).
  Академ-подтверждение: **ICSE 2024 «PBT in Practice»** — PBT в проде у Amazon, Volvo, Stripe.
- Твоя «единая точка входа» существует как связка: **zod-схема → `zod-fast-check` → fast-check**. Одна схема
  служит И валидатором в проде, И генератором входов в тесте. Плюс **test data builders** (Fishery/thoughtbot,
  rosie) — «один валидный объект определён раз, тест меняет одно поле». Для API — **Schemathesis** (OpenAPI/
  GraphQL-схема → авто-property-тесты).
- **Честная поправка к твоей модели** (исследователь подчёркивает, не льстит): «слева допустимые, справа
  ожидаемые, остальное падает» звучит как белый список пар вход→выход. PBT работает не так: он роняет вход,
  нарушающий **ИНВАРИАНТ** — правило, верное для ВСЕХ входов пространства, — а не «не из списка». Правого
  «ожидаемого значения» нет: есть отношение, истинное для любого входа (`decode(encode(x))===x`, «результат
  всегда отсортирован», «выход подходит под схему»). Найти инвариант — и есть работа; пустой всегда-истинный
  инвариант = зелёный-но-бесполезный (ровно твой урок «зелёное врёт»). Поэтому PBT **не заменяет** примеры —
  их комбинируют (property на пространство + горстка примеров на конкретные бизнес-случаи и регрессии).

## Твоё «не верю, что человек пишет 30k тестов на треть кода» — подтверждено

- Единственный, кто публично гонит гигантский объём — **SQLite: 590:1** тест-к-коду (sqlite.org/testing.html).
  НО: **100% покрытие ветвей**, четыре независимых харнесса + фуззер на сотни млн мутаций/день. Обоснование их
  же словами: «широко развёрнутая инфраструктурная библиотека», БД «помнит прошлые ошибки» (баг = порча данных
  навсегда), должна выживать OOM/IO-сбой/краш на встраиваемых устройствах, **без возможности хотфикса**. Ни одно
  из условий к нашему continuously-deploy Next.js SaaS не применимо. SQLite цитируют как ЭКСТРЕМ, не норму.
- Норма прикладного кода — ~**1:1…1.5:1** (консенсус практиков, не жёсткий авторитет — цифру держать мягко).
- **Ключ не в отношении, а в KILL-RATE.** 2.3:1 сам по себе — не криминал. **2.3:1 + ~3% mutation score — приговор:**
  «покрыто, но следствия не проверены» (дословная формулировка Google). Это подпись сгенерированных тестов,
  набитых ассерциями, которые исполняют код, но не фиксируют поведение.

## Как на самом деле устроены взрослые наборы (первичные источники)

1. **Пирамида ~70–80% unit / 15–20% integration / 5–10% e2e** по числу тестов (SWE at Google, гл.11 — 80/15/5;
   Google Testing Blog 2015 — 70/20/10). База — быстрые unit по чистой логике; тонкий band integration; горстка
   e2e. Аргумент против перевёрнутой пирамиды конкретен: тяжёлый e2e = долгая обратная связь, флейк растёт с
   размером системы, отказ невозможно локализовать.
2. **Поведение через публичный интерфейс, не реализацию** (SWE at Google, гл.12): «Test via Public APIs»,
   «Test Behaviors, Not Methods», «Test State, Not Interactions». Kent Beck **Test Desiderata**: тест обязан быть
   **поведенческим** (краснеет ⇔ меняется поведение) И **нечувствительным к структуре** (не краснеет при смене
   только внутренностей). Это формальная запись «не тестируй реализацию».
3. **Забаненные анти-паттерны — ровно наши:** сверка вызовов заглушек (over-mock → change-detector); сверка
   ТЕКСТА исходника / снапшоты реализации (structure-sensitive, нулевая ловля); один-тест-на-метод (раздувает
   счёт, промахивает поведение). **3% mutation score — измеримый отпечаток именно этих анти-паттернов.**
4. **Покрытие — слабый прокси, и зрелые говорят это вслух:** Google — «покрыто, но следствия не проверены»;
   Microsoft Research — **незначимая корреляция** покрытия и пост-релизных дефектов на 100+ Java-проектах.
5. **Настоящий гейт на масштабе — мутации В КОД-РЕВЬЮ, не число тестов** (Petrović & Ivanković, «State of
   Mutation Testing at Google», ICSE-SEIP 2018; «Practical Mutation Testing at Scale», IEEE TSE 2021):
   **6000 инженеров, на КАЖДЫЙ дифф**, ~30% всех диффов; **diff-only** + подавление «arid»-строк (логи, тривиал);
   1.1M мутантов, 150k находок, полезность выросла 20%→80%. Урок: **СЕЛЕКТИВНОСТЬ, не объём** (у них 150M
   тестов/день на 2 млрд строк — и намеренно few мутантов на дифф).

## Что должен представлять собой НАШ взрослый набор

- **Форма — пирамида.** Основная масса — быстрые unit по чувствительной логике (права, квоты, overlap записей,
  таймзоны); band integration на **реальном Postgres с RLS** (доказать тенант-стены и границы definer-функций);
  горстка e2e на критические сценарии.
- **Объём честно — СИЛЬНО меньше 258k строк**, вероятно отношение МЕНЬШЕ 2.3:1, потому что каждый тест делает
  реальную работу. Число — следствие, никогда не цель. 27k ассерций с 3% ловли схлопываются в кратно меньше
  ассерций, ловящих большинство.
- **Гейт — mutation score на чувствительных модулях** (auth/права/RLS/квоты/booking), цель ~60–90%, не процент
  покрытия. Диф-мутации в ревью как у Google. 3% на самом чувствительном — число, которое взрослая команда
  отказалась бы катить.
- **Стек:** zod (единый источник формы) → `zod-fast-check` (генераторы) → fast-check (property на инвариантах)
  + builders (Fishery/rosie) для объектов, + горстка примеров, + Stryker как судья, что проверки не пустые.

## Честность по силе улик

- **Сильно** (первичка): PBT (репо/статьи/компании), SQLite, пирамида, поведение-канон гл.12, мутации Google.
- **Тонко/поправлено:** «Dropbox использует Hypothesis» — НЕ подтвердилось (наоборот: QuickCheck тестировал сам
  Dropbox-sync); финансировал Hypothesis **Smarkets**, не Stripe; конкретные адоптеры Pact — маркетинг-грейд;
  «удалили N% тестов» — цифр не нашли; целевые counts для нашего набора — рассуждение из принципов, не цитата.

## Куда это ложится в наш план

Подтверждает **гибрид** (не чистый снос, не бережный поштучный триаж): тонкий доказанный слой — переписать в
единый формат (`testsuite-rewrite-list.md`, порядок port-then-retire); важную поверхность построить
property+поведением на живой БД; гейт по мутациям на диффе в CI. Contract-testing (Pact) — пока N/A: он окупается
МЕЖДУ независимо деплоящимися сервисами; у нас аналог — тестировать роут-хендлеры против формы, которую реально
потребляет фронт.
