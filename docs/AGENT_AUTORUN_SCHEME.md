## 0. Принципы

- **Корректность + полнота > скорость > параллельность.** Строгость масштабируется по размеру задачи.
- **Атомарный шаг** — дробим до объёма, который: (фронтенд) доводится **до подтверждения скриншотом**; (не-фронтенд) агент безопасно делает за один проход, подтверждение = `curl`-воспроизведение или повторная детальная проверка в коде.
- ⛔ **Никогда git `main`.** Интеграционное (общее) дерево = **`feat`** (там dev-сервер `:5200`). Это НЕ `main`.
- **САМООЦЕНКА ИСПОЛНИТЕЛЯ НЕ ЗАСЧИТЫВАЕТСЯ.** Ни Миньон-воркер, ни aggregate agent `done`, ни общий audit
  `PASS` не закрывают пункт. Нужна построчная независимая проверка latest owner checklist по risk-sized режиму §4A;
  для явно high-risk/seal-gated scope дополнительно действует §4C. Корень прошлого провала: луп штамповал свои же ✅
  (заявил ~21 готовых — независимо подтверждено ~8).

## 3. Фаза планирования — УПРОЩЕНА (owner 2026-06-20, ретро процесса). ТОЛЬКО для БОЛЬШИХ инициатив; мелкие пункты её ПРОПУСКАЮТ (строгость по размеру §1)

> Старая цепочка 4–5 проходов имела осиротевший артефакт `plan-audit.md` — его не читал НИКТО. → Plan-auditor + Plan-revisor СЛИТЫ в один проход «Plan-critic». Итого 3 шага:
> **1) Planner (Opus):** первичный анализ + **подтверждение актуальности в коде** + **боли владельца ДОСЛОВНО → `REQUIREMENTS.md`** + `ROADMAP.md` (этапы `ST-NN`, первичная декомпозиция). Не упрощает/не обрезает «для удобства».
> **2) Plan-critic (Opus, НЕЗАВИСИМЫЙ ≠ Planner) — за ОДИН проход И критика, И усиление:** закрывает ли план ВСЕ боли, не обрезан ли; находит пробелы/вопросы И ТУТ ЖЕ усиливает ROADMAP + отвечает на вопросы. (Раздельные «найти» и «починить» нужны для КОДА — фиксер не оценивает свой фикс; для плана-документа один агент правит сразу, кривой план всё равно поймают Decomposer + весь аудит ниже.)
> **3) Decomposer (Sonnet):** атомарные пункты + непересекающиеся скопы + `acceptance-{ITEM}.md` по стандарту 🎯 (URL+логин+СЦЕНАРИЙ-ДАННЫХ+сид). По ходу видит дыру плана → флагает назад.
> **Requirements-lock (owner lesson 2026-07-22):** каждый owner-пункт из linked detailed plan становится отдельным
> checkbox. Roadmap summary только ссылается на этот checklist; worker и auditor читают/исполняют каждую строку linked
> authority. Новое уточнение сразу заменяет старое: прежний текст удаляется либо маркируется `SUPERSEDED` с
> датой/ссылкой; conflicting active text запрещён. Stage/taskdb/LOG не получают `done`, пока referenced checkbox
> открыт, кроме явного owner defer/cancel со ссылкой.
> **Замер пользы (§⚖️ инструментация):** на следующей живой инициативе включить логи «нашёл/изменил» по Plan-critic — если систематически «ничего не поменял», слить и его в Decomposer (decomposer сам флагает дыры).

## 4. Фаза исполнения

### 4A. Цикл на ЭТАП — risk-sized audit против полного linked checklist (шаги 6–11)

> Этапы — параллельно при непересекающихся файловых скопах (§5).

- **6. Executor** читает весь linked authority и работает по exact atomic checklist этапа; handoff = строка
  `status + code/test/runtime evidence либо deferred/blocker reason` на каждый checkbox, не общий `done`.
- **7. Code-auditor (Sonnet, ГЛУБОКИЙ трассировочный — НЕ «exists=PASS»)** — получает ТОТ ЖЕ exact checklist,
  supersession map и owner states/screenshots. Audit brief цитирует ID и полный текст linked checklist, не только
  roadmap summary. Отчёт = одна строка `PASS|FAIL|BLOCKED + code/test/runtime evidence либо точная
deferred/blocker reason` на каждый checkbox; missing/unclassified row запрещает общий PASS. Независимый код-ревью включает ошибки **и пропущенное** +
  трассировку исполнения + баги/уязвимости. ⛔ Шаллоу-grep-аудит «код есть → PASS» **ВЫРЕЗАН**.
- **8. Fixer — только если разрешён risk tier:** presentation/layout/text/mechanical стадия после одного аудита не
  входит в serial correction loop; её residual остаётся `FAIL/BLOCKED` и идёт по stop/owner-question правилам
  bindings. Для high-risk scope fixer закрывает точные checklist findings, не расширяя owner scope.
- **9. Opus-auditor — УСЛОВНЫЙ (ТИРИНГ ПО РИСКУ):** только сложное/безопасность/низкая уверенность/owner-flagged;
  mechanical/presentation stage §9 **ПРОПУСКАЕТ** и после единственного §7 не запускает re-audit. Ретро: на механике
  Opus-2 = 0 находок мимо Sonnet-1; **сигнал даёт ГЛУБИНА метода, не модель.**
- **10. Цикл аудит→фикс с КАПОМ+ЛЕСТНИЦЕЙ:** **≤2 круга** обычным исполнителем → не сошлось → **БОЛЕЕ СИЛЬНЫЙ** исполнитель (Opus, свежий контекст) → и он не смог → **ВЛАДЕЛЬЦУ**. Не шлифовать бесконечно.
- **10a. Тиринг модели = тиринг scope.** Сильную/дорогую модель запрещено тратить на узкий patch по одному finding:
  узкий фикс делает текущий оркестратор или дешёвый fixer. Если зовём сильную модель, ей дают цельный
  stage/convergence scope: перечитать план, diff и все аудиты, найти соседние причины, исправить систему целиком и
  сдать проверки. После повторных audit/fix провалов сначала проверить достаточность времени, контекста и scope;
  не заменять плохую постановку повышением reasoning/model.
- **11. Commit + push в СВОЁ дерево** (бэкап).

### 4B. Ревью + мерж на уровне ФИЧИ (шаги 12–15) — когда checklist закрыт

- **12. Risk-sized review и достаточный gate.** Full CI — только на milestone/merge/repo-level gate по правилам
  тестирования. После зелёного — **аккуратный мерж в `feat`** (⛔ НЕ `main`; `git pull --rebase`, без force — `feat` общий с SaaS-чатом).
- **13. Свежий рендер на `feat` (:5200):** сервер прогрет/перезапущен на текущем `feat` (§7), `health`-чек ДО съёмки.
- **14. Visual acceptance по каждой применимой строке:** mechanical/presentation = тот же **один** independent audit
  с runtime/screenshots; два независимых seal-reviewer используются только если это явно требует high-risk/owner
  acceptance (§4C).
- **15.** FAIL/BLOCKED обрабатывается по risk tier и потолку кругов bindings. Две печати требуются только для
  scope, чей acceptance contract явно включает §4C; они не заменяют closure matrix.

### 4C. 🔱 ПРОТОКОЛ ПЕЧАТИ (seal) — только для явно seal-gated scope

**SUPERSEDED — 2026-07-18/22:** blanket-правило «две печати = единственный сигнал приёмки любой фичи» заменено
risk-sized contract из `ORCHESTRATION_BINDINGS.md`. Этот раздел действует только когда linked checklist/owner gate
явно требует двух независимых visual seals; даже тогда печати не закрывают missing atomic checkbox.
**Режим ревьюера = «ДОЕБАТЬСЯ»:**

- Вердикт по умолчанию = **ОТКЛОНИТЬ**. Презумпция «НЕ сделано».
- Открыть КАЖДЫЙ требуемый скрин; проверить КАЖДЫЙ пункт требования по отдельности; прогнать ВСЕ состояния (ховер/клик/модалка/пустое/ошибка/рефреш/диплинк/мобилка если применимо).
- Список проверяемых пунктов берётся из latest atomic owner checklist, а не из roadmap summary. Печать без
  построчной матрицы `checkbox → screenshot/runtime evidence` недействительна.
- **Авто-FAIL при любом:** «—»/«Загрузка»/плейсхолдер/пусто там где должны быть данные; ошибка консоли / «N Issue»; утёкший dev/spec-текст в UI; непокрытое состояние; скрин отсутствует/старый/не та страница; UI визуально не изменился против требования.
- **ПЕЧАТЬ ставится ТОЛЬКО когда доебаться НЕ ДО ЧЕГО.**

**Журнал печатей** `round3/SEAL_LEDGER.md` (append-only). Запись печати = `✅ ПЕЧАТЬ <ITEM> | reviewer=<role/agentId> | пункты:[…] | скрины:[…пути, должны существовать] | "пытался сломать: …" | UTC`.

- Печать #1 — визуальный ревьюер; печать #2 — Главный Ревизор. Для явно seal-gated item две печати разными
  ревизорами закрывают seal-condition, но не заменяют atomic closure matrix. **РОЛЬ #2 ПЕРЕОСМЫСЛЕНА (owner
  2026-06-20, ретро): #2 — НЕ «второй штамп», а «ЛОВЕЦ ЛОЖНЫХ ОТКАЗОВ».** Его главная польза — опровергнуть
  НЕВЕРНЫЙ отказ #1 (data-gated / не тот URL / недостижимо), а не ловить пропущенные баги (за волну #2 ни разу не
  отклонил запечатанное #1, но опроверг 3 ложных отказа на QW-A3). Поэтому acceptance ОБЯЗАН нести URL+логин+
  СЦЕНАРИЙ-ДАННЫХ (иначе #1 жжёт отказы на «нечем срендерить»); 2 печати оставляем для явно seal-gated scope ради
  анти-самоштампа/независимости, но МОДЕЛЬ #2 тирим по риску.
- **Миньоны (воркер/оркестратор) журнал НЕ пишут** — только читают. Любая печать от Миньона = нарушение, контролёр откатывает.
- **Guard `verify-seals.sh`** (cron + перед закрытием seal-gated item): проверяет требуемые две печати и существующие
  screenshots. На обычном risk-sized stage closure определяется checklist matrix, а не искусственным добавлением seal gate.
- **Code-master** (§8) = верхний над печатями: на расхождение ревьюеров / повтор провала → нотификация владельцу (Telegram dev-redirect).

## 5. Параллельность и ОДИН сервер

- Параллелим **исполнителей** по непересекающимся файловым скопам. Лимиты: **≤3 воркера / ≤5 агентов всего**.
- **ОДИН Next-сервер `:5200`** (на `feat`) — воркеры своих серверов НЕ поднимают (ловили load 43 на 3 серверах). Визуал-ревью и тяжёлые Opus-аудиты — **сериализуем**.

## 6. Always-критерии (в КАЖДОМ плане и роль-промпте; канон — `.cursor/rules/*` + `AGENTS.md`)

- ⛔ Нет сырому SQL — только drizzle. ⛔ Предельная чистота архитектуры + изоляция слоёв; межмодульно только через DI.
- Нет дублированию при возможности переиспользования (shared-аналог / кандидат в shared / опенсорс — React, shadcn). Эталон UI — страница упражнений + `shared/ui/doctor/*`.
- Нет серверному поиску, если можно в UI. Нет избыточной fetch-подгрузке, если можно SSR. Шаблоны — смысловыми блоками (таб = блок) в общий контейнер; общий верхний шаблон («Сегодня»/«Расписание»).
- Тесты — только по своему коду; полный CI — контролёром перед пушем. По решению владельца от 2026-07-09 прямой запуск проверок разрешён; `run-tests.sh`/flock — опциональный throttling при высокой нагрузке или явной команде.
- Опциональное — оценить пользу+выполнимость В ЭТОМ проходе и делать сразу (или отдельным атомарным шагом). Ведение лога + синхронизация доков.

## 7. Оркестрация и governance (runtime) — ОПЕРАЦИОННАЯ ЗАКАЛКА (v3)

- **Единый launcher** `dev-orchestra start|pause|resume|status` — оркестратор + крон-скрипты + **единый PAUSE** (стоп всему; watchdog уважает PAUSE).
- **Liveness (разделение):**
  - **Governor (cron)** — АГРЕГАТ: снимок CPU/RAM, число агентов, **жив ли оркестратор**, **health :5200**, **ротация тиков**. Дёргает оркестратор если что-то не так.
  - **Orchestrator** — ПЕР-АГЕНТНО: раз в 15 мин тейлит логи агентов; **>20 мин без записи → подозрителен → проверка/реап**.
- **🩺 Health сервера (было: порт держит, а не отвечает):** Governor каждые ~5 мин `curl -m 5 :5200`; **таймаут/5xx → kill + чистый рестарт** dev-сервера. Не «жив ли порт», а «отвечает ли осмысленно».
- **🖥️ Жизненный цикл `:5200` (решение контролёра, v3):** держим **ОДИН ПОСТОЯННЫЙ** сервер (HMR подхватывает мержи) **+ чистый рестарт перед каждым батчем визуал-ревью И при разбухании `.next` кэша** (>~3–4 ГБ — ловили 22 ГБ-зависание). НЕ поднимаем эфемерно на каждый скрин (turbopack cold-start 30с–мин — дороже, чем рестарт-на-мерж). Свежесть рендера гарантируется рестартом+health-чеком на шаге 13.
- **🧟 Зависшие терминалы отработавших агентов:** на завершении воркера — **реап его процессов** (cwd под `.claude/worktrees/agent-*`, особенно осиротевший `next dev`) + `git worktree remove`. Governor добивает procs >30 мин stale.
- **🧟 Codex-субагенты, зависшие в UI/лимите:** если известный subagent-session UUID уже `completed`/`failed` через `wait_agent` или явно больше не нужен текущему этапу, чистить через CLI: сначала `codex delete --help`, затем точечно `codex delete --force <subagent-session-uuid>`. Удалять только известные UUID текущей оркестрации; не трогать основную Codex-сессию и системные `app-server`/`proxy`/`codex-code-mode-host`. После удаления проверить процессы `ps -eo pid,ppid,stat,lstart,cmd | rg 'codex|multi_agent|subagent|<plan-key>|vitest|tsx'`. Упоминание UUID в логе родительского чата `.codex` не считать живой сессией. Результат писать только в devlog/канонический план той работы, к которой эти агенты реально относились; taskdb-карточку narrative-отчётом не дополнять.
