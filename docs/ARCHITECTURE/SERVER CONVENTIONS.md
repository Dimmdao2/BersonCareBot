## ⛔ КРИТИЧНО: `deploy` НЕ СЧИТАТЬ БЕЗОПАСНО ОГРАНИЧЕННЫМ `sudo`

**Никогда не давать агенту команды с `sudo` для выполнения от имени `deploy` в SSH-терминале.**

Read-only проверка PROD `2026-07-19` через `sudo -n -l` показала: literal `NOPASSWD: ALL` отсутствует, но кроме
unit-specific rules разрешены широкие root-команды `/bin/systemctl`, `/usr/bin/sed`, `/usr/sbin/nginx` и
`/usr/bin/apt-get`. Это практически root-equivalent boundary и противоречит старому описанию «только строгий
whitelist». До закрытия `SEC-02` нельзя опираться на sudoers как на containment control. Обезличенный снимок:
[`../_TODO/RU_PRIVACY_AND_PRODUCTION_READINESS/CURRENT_PROD_BASELINE_2026-07-19.md`](../_TODO/RU_PRIVACY_AND_PRODUCTION_READINESS/CURRENT_PROD_BASELINE_2026-07-19.md).

**Практические следствия:**

- Не предполагать, что произвольная команда с `sudo` разрешена или запрещена: exact allow-list сначала проверяет
  root/operator; агент не экспериментирует на PROD.
- Если нужно почистить root-owned артефакты (например, `.next/` после `cp` от root) — это должен делать **root** в отдельной сессии, или задача должна быть переформулирована так, чтобы deploy-пользователь не создавал root-owned файлы изначально.
- Не предлагать `sudo install` для произвольных файлов вне unit-файлов сервисов.
- Никаких `sudo chown`, `sudo mkdir`, `sudo rm` в инструкциях для деплоя.

Если требуется root-операция (очистка `/opt/`, смена владельца, ручная правка `/etc/`): явно сказать «выполнить от root», не от deploy.

### Сетевой периметр (владелец, 19.08 — целевая политика прода)

**PROD, политика по умолчанию DROP.** Входящее пропускается только:

| Что                                                                 | Кто слушает        | Где                    |
| ------------------------------------------------------------------- | ------------------ | ---------------------- |
| tcp 22                                                              | `sshd`             | наружу                 |
| tcp 80, 443                                                         | nginx              | наружу                 |
| icmp (ping/MTU), петля `lo`, ответы на уже установленные соединения | —                  | —                      |
| 53                                                                  | `systemd-resolved` | только `127.0.0.53/54` |
| 323                                                                 | `chronyd`          | только `127.0.0.1`     |

Всё остальное входящее молча отбрасывается. Слушающие сокеты совпадают с правилами — лишнего наружу нет.
**Postgres на TCP не слушает вообще, только unix-сокет** — это отдельная проверка в приёмке хоста.

**TEST/DEV (`151.x`) — другая картина, замерено:** `ufw` inactive, `iptables -L INPUT -n` — политика
`ACCEPT` и ноль базовых правил. Web-поверхности TEST ограничены `allow/deny` в nginx. Для raw-портов
Jitsi/coturn дополнительно действует узкая additive-таблица nftables `inet bcb_jitsi_test`; она не меняет
политику и правила остальных сервисов.

**Что из этого следует для нового входящего пути** (прежде всего для подключения собственного домена
клиники, где чужое имя наводится на наш адрес): 80 и 443 на проде УЖЕ открыты миру, поэтому правки
файрвола такая работа не требует. Ограничением остаётся не сеть, а **поведение nginx на незнакомый
`Host`** и то, чем выдаётся сертификат. Замер открытости, сделанный на `151.x`, на прод не переносится
ни в какую сторону: probe прода запрещён, источник фактов о проде — только владелец и этот файл.

**Тонкость IP-замка теста (важно при отладке `403`):** трафик к собственным TEST-доменам приходит с **внутренним** адресом туннеля/NAT, а **НЕ** с публичного `151.241.228.122` (NAT-маскарад работает только для исхода во внешний интернет, поэтому `2ip` показывает `151.x`, а nginx видит другое). Поэтому nginx-allowlist теста разрешает:

- `10.9.0.0/24` — доверенная подсеть критичного PROD-релея `awg0`;
- `172.31.9.0/24` — заход владельца с **iPhone/Mac** через `awg1`;
- `172.17.0.0/16` — заход с **ноута** (wg-easy NAT-ит трафик в контейнерный `172.17.0.2` на docker0);
- `127.0.0.1` — loopback / health;
- всё прочее → **`403`** (в т.ч. публичный IP при заходе мимо VPN, и сканеры).

TEST-домены и endpoint `awg1` используют один публичный IP. Поэтому full-tunnel клиент исключает
публичный адрес endpoint из туннеля и без split DNS получает `403` от nginx. Каноническая схема: `dnsmasq` на
`172.31.9.1` отвечает для зон `test.bersoncare.ru`, `test.therapysto.ru` и `test.therapygo.ru` адресом
`172.31.9.1`, а профиль `awg1` использует `DNS = 172.31.9.1`. Применение
серверной части: `bash deploy/host/apply-test-vpn-dns.sh --apply`; nginx-allowlist применяется штатным
`bash deploy/host/apply-test-surface-domains.sh --apply` (старое имя `apply-test-nginx-webapp.sh` делегирует ему). Уже импортированные профили с публичным DNS не требуют
переимпорта: unit `bersoncare-test-vpn-dns-redirect.service` перенаправляет только входящие через `awg1`
UDP/TCP-запросы на порт `53` в этот split resolver. `awg0`, wg-easy и обычный host DNS unit не затрагивает.

Появился новый способ захода (другой VPN/девайс) — смотреть **реальный** source-IP в
`/var/log/nginx/bersoncare-test-webapp-access.log` (поле 1) и добавлять его подсеть, **не гадать**.

**Пользователи ОС:** `deploy` запускает сервисы; его sudo-boundary нельзя считать ограниченным или безопасным
(см. root-equivalent findings в начале файла). Рабочий пользователь — `dev`, его `$HOME` под `0700` →
`postgres`/`deploy` файлы из `/home/dev/` **не читают** (для обмена — `/tmp`, world-readable).

   становится тихой катастрофой:** ни кода входа, ни напоминания, ни одного сообщения пациенту —
   и НИ ОДНОЙ ошибки в логе, только `PRE_FORK_TEST_DELIVERY_SUPPRESS` уровня warn. Отдельным шагом
   cutover: снять `TEST=true` в обоих env-файлах, перезапустить `api`, `scheduler`, `webapp` и
   убедиться, что `PRE_FORK_TEST_DELIVERY_SUPPRESS` в логах больше не появляется.
6. **Свои же контейнеры ходят к вебаппу через nginx.** Пациентский корень переписывается на `/app` по
   публичному origin, поэтому в allow-list на время проб входят подсети мостов `172.30.0.0/24` и
   `172.31.0.0/24` — без них пациентский домен отвечает 403 при живом приложении.
7. 🔴 **КАПЧУ НЕ ПЕРЕНОСИМ. Ключ на новом проде создаётся заново — это отдельный шаг того, кто переносит**
   (решение владельца 14.09: «не надо тогда переносить капчу, просто надо чтобы агент, кто будет
   переносить, прочитал, что её надо создать»).

   Дамп физически тащит `public.system_settings` целиком, то есть строка ключа приедет сама — и именно
   поэтому её надо снять руками, а не надеяться, что «оно перенеслось». Порядок на проде, сразу после
   восстановления базы и до включения капчи:

   ```bash
   # ключ, поживший на TEST, на проде не живёт: обнуляем приехавший
   sudo -u postgres psql -d <база прода> -c \
     "UPDATE public.system_settings SET value_json = '{\"value\": \"\"}'::jsonb, updated_at = now()
       WHERE key = 'auth_altcha_hmac_secret' AND scope = 'admin' AND organization_id IS NULL;"
   ```

   Дальше — в кабинете администратора платформы: «Авторизация» → «Сгенерировать» → сохранить. Внешний
   сервис для нашей ALTCHA не нужен вовсе, ключ выпускается у нас одним нажатием.

   **Почему не переносим:** секрет, поживший на TEST, секретом прода быть не может — дампы TEST копируются
   на dev-бокс, разворачиваются в DEV и открываются агентами. Перенесённый ключ выглядел бы настроенным,
   а защищал бы ровно ничего.

   **Пустой ключ безопасен, это проверено:** дверь входа читает его как «капча выключена», а включить
   капчу без ключа нельзя ни галочкой, ни запросом мимо формы. Так что промежуток между восстановлением
   и генерацией нового ключа никого не запирает. Раньше было наоборот: пустой ключ из базового среза
   старого прода запирал учётную запись НАВСЕГДА, пока капча была жёстко включена в коде, — этот класс
   закрыт 14.09.

   **Ключи Яндекс SmartCaptcha — то же самое:** берутся в консоли Яндекс Облака под прод (клиентский —
   публичный, серверный — секрет), от TEST не наследуются. Схема целиком — `AUTH_AND_IDENTITY_CANON.md`,
   часть V, §25.

**Видео (развёрнуто 10.09.2026).** Jitsi/coturn на `meet.therapysto.ru` / `turn.therapysto.ru`,

Три вещи, которые пришлось узнать на живом хосте и которые ломали стек молча:

1. **Пакет не может жить в `/opt/therapysto/src`.** Дерево исходников — вход сборки: выкладка делает по
   нему `reset --hard` и `clean -fdx`, а пакет пишет рядом с собой проверенный по хешу апстрим. Отсюда
   отдельная копия, обновляемая тем же коммитом.
2. **`"no-new-privileges": true` в `/etc/docker/daemon.json` несовместим с образами на s6-overlay.** Они
   стартуют под root и сбрасывают привилегии через `s6-overlay-suexec` — это setuid, и под общесистемным
   флагом он падает, а контейнер уходит в бесконечный рестарт с «cannot create /run/test of writability».
   Четыре сервиса jitsi несут `security_opt: no-new-privileges:false`; это возврат к обычному поведению
   docker, а не новые права.
3. **Служебный пользователь внутри образов апстрима — фиксированный uid 1000.** На TEST он случайно
   совпадал с учёткой стека; здесь под 1000 живёт человек. Доступ выдан по группе (`group_add`) — тем же
   приёмом, что контейнеры приложения читают ключи mTLS.

Связь с приложением — `deploy/host/prod/link-video-settings.sh`: пакет принципиально не знает про базу
приложения, поэтому пять записей `system_settings` (URL, домен XMPP, id/issuer и секрет подписи JWT)
пишет отдельный скрипт. Секрет существует ровно в двух местах: env-файл и строка настроек.

**mTLS.** Приватный ключ CA лежит в `/etc/therapysto/postgres-mtls/authority/private/` (0700) и в
контейнеры не попадает; приложению монтируется только `/etc/therapysto/postgres-mtls/prod/` — публичная
часть CA и четыре клиентские пары. **CN каждой пары равен имени роли**, поэтому переименование логинов
(см. «База») обязано выпустить пары заново и отозвать старые в CRL: пара с прежним CN после
переименования не подойдёт ни к одной роли. Ключи ролей открыты группе `therapysto-app-prod`, и контейнер получает её
дополнительной (`group_add` в compose): это ровно тот же канон, что на dev/test, где группа ключа равна
учётке сервиса. Серверный сертификат выписан на имя `db.host`, под которым оба цвета видят хост; имя
указывает на шлюз своего моста, а не на docker-псевдоним `host-gateway` (тот ведёт на `172.17.0.1`, где
базы нет).

### Как устроен артефакт

`pg_dump -Fc` идёт ПОТОКОМ в `age` — открытого дампа на диске не бывает ни секунды, даже временно.
Рядом атомарный манифест `<файл>.sha256`. Имя — `unified_<база>_<YYYYMMDD>_<HHMMSS>.dump.age`:
«unified» потому, что `DATABASE_URL` webapp и integrator указывают на одну базу, и проход делается
один. Размер боевого дампа на 14.09 — ~10,1 МБ, база `therapysto_prod` — 499 МБ.

Скрипт **отказывается работать**, а не деградирует, если: нет `age`, нет или пуст файл получателей,
`age` не принял файл получателей, путь под `/opt/backups` содержит символическую ссылку, или не
заданы `BERSONCAREBOT_BACKUP_EXPECT_HOSTNAME` / `BERSONCAREBOT_BACKUP_EXPECT_IPV4`. Последнее —
защита от запуска боевого бэкапа не на той машине; строки cron задают обе переменные, поэтому
**ручной запуск требует их задать явно**:

```bash
runuser -u postgres -- env BERSONCAREBOT_BACKUP_EXPECT_HOSTNAME=therapysto-prod \
  BERSONCAREBOT_BACKUP_EXPECT_IPV4=135.106.187.95 BERSONCAREBOT_BACKUP_DATABASE=therapysto_prod \
  /opt/backups/scripts/postgres-backup.sh manual
```

`DATABASE_URL` уходит в `pg_dump`/`psql` только через libpq-переменную `PGDATABASE`, никогда через
argv — иначе строка с паролем светилась бы в `ps`.

### Расписание и сроки хранения

| Режим | Когда (UTC) | Держим |
|---|---|---|
| `hourly` | `17 * * * *` | 2880 минут = 48 часов |
| `daily` | `40 3 * * *` | 35 суток |
| `weekly` | `10 4 * * 0` | 84 суток |
| `pre-migrations` | перед каждой выкладкой, из `deploy-prod` | 20 последних всегда; сверх того — старше 30 суток удаляются |
| `manual` | руками | **по возрасту НЕ удаляется никогда** |
| `prune` | `50 4 * * *` | только чистка, дампа не делает |

`manual` не чистится по возрасту намеренно: ручной снимок делают перед чем-то опасным, и автоматика
не вправе его снести. Убирать его — руками, осознанно.

Чистка всегда сносит **поколение целиком** (`.dump.age` + `.sha256`) и отдельно — «сирот»: артефакт
без манифеста или манифест без артефакта восстановить нельзя, поэтому они удаляются независимо от
возраста (с минутным окном, чтобы не наехать на идущий прямо сейчас дамп).

Ёмкость: диск прода 69 ГБ, свободно 39 ГБ; установившийся объём всех окон — порядка 1,2 ГБ.

### Ключ и фраза — модель доступа (владелец, 14.09.2026)

**Замок и ключ — это ДВЕ ПОЛОВИНЫ одного ключа, а не два ключа.**

- **Замок** — публичная строка `age1…` в `/opt/backups/age-recipients.txt`. Ею только **запирают**.
  Она обязана лежать на проде открыто, иначе крон не сможет зашифровать дамп. Секретом не является.
- **Ключ** — приватная половина. Только он **отпирает**. На боевой машине его нет: иначе потеря
  машины уносит и бэкап, и ключ к нему разом.

Текущий замок — `age157zutylcuzyruwyf2ffzj8whp30cn52j2xzz20n46gruh4rpe9kqxvnq4p`.

**Что было до 14.09 и почему это чинили.** Стоял замок `age19d2srfx…`, а приватной половины к нему
не было ни у агентов, ни у владельца. То есть бэкапы снимались, были целы и **не открывались никем**.
«Бэкапы есть» и «бэкапы спасут» — разные утверждения, и держалось только первое. Владелец старые
артефакты списал, замок **заменён**, а не дополнен вторым получателем.

**Как сделана новая пара.** Генерировал ВЛАДЕЛЕЦ на dev-боксе, фразу вводил сам; агент фразу не
видел и видеть не должен:

```bash
umask 077 && age-keygen 2>~/recovery-pubkey.txt | age -p -o ~/recovery-key.age && cat ~/recovery-pubkey.txt
```

Приватная половина рождается и уходит в шифрование **по трубе** — открытой на диск не попадает,
поэтому «не забыть удалить незашифрованную копию» не требуется: её не существует. На выходе один
файл, запертый фразой (`scrypt`, work factor 18, права `0600`).

**Где лежит ключ** — три копии, сумма
`f4274af2792b76c50cf8293bf85b2dffbd631abee8b3382624415bc62940acfa`:

| Где | Путь |
|---|---|
| dev-бокс `151.241.228.122` | `~/recovery-key.age` (учётка `dev`) |
| `bcb-second` `81.26.183.196` | `/opt/backups/keys/recovery-key.age`, `0600 root:root` |
| компьютер владельца | отдан файлом 14.09 |

Файл можно хранить открыто: без фразы это мусор. **Фраза не записана нигде и знает её только
владелец.** Резервного замка нет — владелец выбрал один; значит, фраза и есть единственная точка
отказа всей схемы бэкапов.

**Проверено вживую 14.09, а не на словах.** Снят внеочередной боевой дамп уже под новый замок
(10 139 576 Б, `sha256` на проде и на dev совпали), владелец открыл его своей фразой:

```bash
age -d -i ~/recovery-key.age <файл>.dump.age 2>/dev/null | head -c 5   # → PGDMP
```

Черновые артефакты (ручной снимок на проде, копия дампа на dev) после проверки удалены.

**Смена фразы — пока старая ещё помнится.** Ключ при этом НЕ меняется, значит замок на проде
трогать не надо и старые бэкапы продолжают открываться. Спросит старую фразу, потом новую дважды;
открытый ключ на диск не ложится (проверено 14.09):

```bash
age -d ~/recovery-key.age | age -p -o ~/recovery-key-new.age
```

После этого — заменить все три копии и сверить, что новый файл открывается новой фразой, а старой
уже нет.

### ⚠️ ЕСЛИ ФРАЗА ЗАБЫТА — напоминание владельцу

Сделать нельзя ничего. Ни агент, ни хостер, ни перебор не вернут доступ: `scrypt` с work factor 18
существует ровно затем, чтобы перебор не работал. Остаётся снять новую пару и начать хранение
заново, а всё, что зашифровано прежним замком, списать.

**Пока фраза ещё помнится — её можно сменить** (команда в разделе выше). Ключ при этом остаётся тем
же, замок на проде трогать не надо, старые бэкапы продолжают открываться.

> Замок открыт и виден — он не тайна,
> он лишь запрёт, но сам не отопрёт.
> А ключ закрыт лишь фразой: не случайно
> её никто, помимо вас, не назовёт.
>
> Ни сервер, ни агент её не знают,
> нигде она не значится — и пусть.
> Пока вы помните — её меняют.
> Забыли — и останется лишь грусть:
>
> бэкапы целы, суммы их сойдутся,
> и каждый час прибавится ещё,
> но двери к ним вовек не отопрутся.
> Пока вы помните — сложите фразу в сейф.

### Миграции: webapp Drizzle (`public`) vs integrator

- **Симптом:** в логах webapp `column "…" does not exist` (например `publication_status` в `test_sets`) при открытии каталогов врача — **не накатили Drizzle-миграции webapp** на ту БД, что в `webapp.prod` (`DATABASE_URL`, схема **`public`**). Новый билд webapp без миграций оставляет схему старой.
- **`pnpm migrate` в корне репозитория** — по очереди: **integrator** (`pnpm --dir apps/integrator run migrate`), затем **webapp Drizzle** (`pnpm --dir apps/webapp run migrate`, каталог `apps/webapp/db/drizzle-migrations`). На production-host скрипт `scripts/migrate-all.sh` подгружает только точные канонические **`/opt/env/bersoncarebot/api.prod`** и **`/opt/env/bersoncarebot/webapp.prod`**, поэтому достаточно одной команды `pnpm migrate`; переименованный или произвольный env-файл не принимается. Только webapp без integrator: **`pnpm migrate:webapp`**.
- **Пример на production-хосте** (из каталога проекта, пользователь **`deploy`**; затем при необходимости перезапуск webapp):

```bash
cd /opt/projects/bersoncarebot
pnpm migrate
# при необходимости:
# sudo systemctl restart bersoncarebot-webapp-prod.service
```

Канон и backup перед миграциями: [`deploy/HOST_DEPLOY_README.md`](../../deploy/HOST_DEPLOY_README.md) (pre-migrations, состав `deploy-prod`).

**Исторические имена БД** (до unification, для старых отчётов; не считать текущим обязательным состоянием):

| Назначение (legacy)     | Было (пример)     |
| ----------------------- | ----------------- |
| Отдельная БД integrator | `tgcarebot`       |
| Отдельная БД webapp     | `bcb_webapp_prod` |

Подключение к psql на проде (под пользователем, у которого есть доступ к БД):

```bash
# Загрузить env и подключиться (значения не коммитить).
# Обязательно сначала source — иначе DATABASE_URL пустой и psql уйдёт в локальный сокет
# от имени пользователя ОС (часто root) → FATAL: role "root" does not exist.
# После unification оба варианта попадают в одну и ту же БД; для явного search_path:
set -a && source /opt/env/bersoncarebot/webapp.prod && set +a && psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -c "SHOW search_path;"
set -a && source /opt/env/bersoncarebot/api.prod && set +a && psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -c "SELECT current_schema();"
```

Если на хосте psql запускают от имени `postgres`: `sudo -u postgres psql -d <имя_базы>`. Имена баз и пользователей берут из соответствующих env-файлов (см. примеры в `deploy/env/.env.webapp.prod.example`; для api — корневой `.env.example`).

### Как узнать, чего не хватает, и вписать на сервер

Выполнять на **production-хосте** (под пользователем с доступом к env и при необходимости `sudo -u postgres`).

**1. Снять снимок баз и ролей (обновить раздел Database / backup facts):**

```bash
sudo -u postgres psql -At -F $'\t' -c "SELECT datname, pg_catalog.pg_get_userbyid(datdba) FROM pg_database WHERE datallowconn ORDER BY datname;"
sudo -u postgres psql -At -F $'\t' -c "SELECT rolname FROM pg_roles ORDER BY rolname;"
```

Результат вписать в этот документ (раздел «Database / backup facts») или в `deploy/HOST_DEPLOY_README.md`, чтобы не терять актуальные имена баз и владельцев.

**2. Проверить, какие переменные заданы в env (без вывода секретов):**

```bash
echo "=== api.prod (integrator) ==="
grep -E '^[A-Za-z_][A-Za-z0-9_]*=' /opt/env/bersoncarebot/api.prod 2>/dev/null | cut -d= -f1 | sort
echo "=== webapp.prod ==="
grep -E '^[A-Za-z_][A-Za-z0-9_]*=' /opt/env/bersoncarebot/webapp.prod 2>/dev/null | cut -d= -f1 | sort
echo "=== cutover.prod ==="
grep -E '^[A-Za-z_][A-Za-z0-9_]*=' /opt/env/bersoncarebot/cutover.prod 2>/dev/null | cut -d= -f1 | sort
```

**3. Чего часто не хватает и как добавить:**

| Чего не хватает                                | Как проверить                              | Как вписать                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ---------------------------------------------- | ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `INTEGRATOR_DATABASE_URL` для cutover-скриптов | Скрипт требует `cutover.prod`, а файла нет | Для **legacy** двух-БД: создать `cutover.prod` с `DATABASE_URL` = webapp и `INTEGRATOR_DATABASE_URL` = старая integrator БД. После **unification** оба URL часто **совпадают** — см. `DATABASE_UNIFIED_POSTGRES.md`.                                                                                                                                                                                                                                          |
| Имена баз для psql                             | Не знаете, к какой базе подключаться       | `source` нужный env и смотреть имя в `DATABASE_URL` (после последнего `/`). Для схем: `SET search_path TO integrator, public` или префиксы `public.` / `integrator.`.                                                                                                                                                                                                                                                                                         |
| Backup перед миграциями                        | Не уверены, что дампы создаются            | Канонический скрипт: репозиторий `deploy/postgres/postgres-backup.sh` → на хосте `/opt/backups/scripts/postgres-backup.sh`. **На новом проде голый запуск отказывает** — скрипт требует `BERSONCAREBOT_BACKUP_EXPECT_HOSTNAME`/`_IPV4` (защита от запуска не на той машине); точная команда и сроки хранения — раздел «Бэкапы и ключи — НОВЫЙ прод». Артефакт — зашифрованный `*.dump.age` + `*.dump.age.sha256` (не plaintext `.dump`); требует `age` + recipients file на хосте, иначе fail closed до `pg_dump`. При unified `DATABASE_URL` — одна пара файлов (`unified_…`); при двух разных URL — две пары. |

**4. После добавления переменных:** backfill/reconcile запускать с хоста (или с машины, где доступны те же env), см. `deploy/DATA_MIGRATION_CHECKLIST.md`.
