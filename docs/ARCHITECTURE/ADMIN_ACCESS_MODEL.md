## Правило в одну строку

**Права не берут — их выдают. Выдаёт только владелец, закреплённый вне приложения.**

## Два уровня, не один

|                             | владелец (суперадмин)            | администратор · поддержка           |
| --------------------------- | -------------------------------- | ----------------------------------- |
| откуда берётся              | закреплён в переменной окружения | **только по приглашению владельца** |
| может работать в панели     | да                               | да                                  |
| **может приглашать других** | **да**                           | **нет**                             |
| может отзывать доступ       | да                               | нет                                 |
| можно ли выдать через экран | **нет, никогда**                 | да, владельцем                      |

Владелец — один. Администратор, заведённый по приглашению, работает, но **круг доступа не расширяет**:
ни по ошибке, ни намеренно, ни если его учётную запись угонят.

## Самозапись в привилегию не существует

Стать администратором или поддержкой снаружи нельзя **никак** — ни регистрацией, ни паролем, ни кодом на
почту. Единственная дверь — приглашение.

## Поведение приглашения — все четыре свойства обязательны

1. **Срок** — ссылка сгорает.
2. **Одноразовость** — использовал, и она мертва.
3. **Именная привязка** — подходит только тому адресу, кому выслана; чужой её не применит.
4. **Отзыв** — владелец гасит ссылку до того, как ею воспользовались.

## Что видно после выдачи

Список всех, у кого есть доступ, и по каждому: **кто пригласил, когда**, и мгновенный отзыв. Отозвали —
доступ пропал сразу, а не после того, как человек сам выйдет.

## Опасные действия переспрашивают

Выдача прав, смена владельца, удаление клиники — требуют подтвердить личность заново, даже если вход был
час назад.

## Разные двери для разных ролей

У врача, клиента и администратора — свои экраны входа (задача **#1031**). Пришедший не по своей двери
видит понятное «этот аккаунт не зарегистрирован как специалист» и ссылку войти по своей. При этом дверь
**не сообщает, существует ли такой аккаунт** — иначе форма входа работает как справочник зарегистрированных.

## Осознанный размен

**Нет владельца — никто никого не добавит.** Владелец подтвердил это прямо 26.07: «это осознано».
Разблокировка всегда остаётся у него — доступ закреплён в настройках сервера, туда он попадает мимо
приложения.

## Что строим сейчас, а что потом

**Сейчас (в рамках C-4, это закрытие дыры):** убрать раздачу роли через списки, свести источник роли к
одному, закрепить владельца в переменной окружения.

**Потом (когда появятся вторые руки):** интерфейс приглашений, список доступов, отзыв. Владелец
26.07: «пока это не супер срочно строить детально, все равно я пока единственный. но запомнить надо».
**Не поднимать вперёд очереди безопасности.**

## Мировая практика, на которую это опирается

Первый администратор заводится **в обход собственных настроек приложения**: `createsuperuser` из
переменных окружения у Django, корневая учётная запись у AWS («заприте её и работайте под обычной»),
панель поставщика у Auth0 и WorkOS. Разделение «владелец против остальных» — GitHub organization owners,
суперадмин против делегированных ролей в Google Workspace, root против IAM в AWS. Участники организации
везде заводятся приглашением; самозаписи в привилегию не существует.

Ближайшая формальная классификация того, что было до этого решения, — **CWE-269, Improper Privilege
Management**. Отдельного расхожего названия у этой ошибки нет.
