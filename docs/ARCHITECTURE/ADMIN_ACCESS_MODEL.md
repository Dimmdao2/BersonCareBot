## Правило в одну строку

**Права не берут — их выдают. Выдаёт только владелец, закреплённый вне приложения.**

## Два уровня, не один

|                             | владелец (суперадмин)            | администратор · поддержка           |
| --------------------------- | -------------------------------- | ----------------------------------- |
| откуда берётся              | закреплён в переменной окружения | **только по приглашению владельца** |
| может работать в панели     | да                               | да                                  |
| **может приглашать других** | **да**                           | **нет**                             |
| может отзывать доступ       | да                               | нет                                 |
| можно ли выдать через экран | **нет, никогда**                 | да, владельцем                      |

Владелец — один. Администратор, заведённый по приглашению, работает, но **круг доступа не расширяет**:
ни по ошибке, ни намеренно, ни если его учётную запись угонят.

## Самозапись в привилегию не существует

Стать администратором или поддержкой снаружи нельзя **никак** — ни регистрацией, ни паролем, ни кодом на
почту. Единственная дверь — приглашение.

## Поведение приглашения — все четыре свойства обязательны

1. **Срок** — ссылка сгорает.
2. **Одноразовость** — использовал, и она мертва.
3. **Именная привязка** — подходит только тому адресу, кому выслана; чужой её не применит.
4. **Отзыв** — владелец гасит ссылку до того, как ею воспользовались.

## Что видно после выдачи

Список всех, у кого есть доступ, и по каждому: **кто пригласил, когда**, и мгновенный отзыв. Отозвали —
доступ пропал сразу, а не после того, как человек сам выйдет.

## Опасные действия переспрашивают

Выдача прав, смена владельца, удаление клиники — требуют подтвердить личность заново, даже если вход был
час назад.

## Разные двери для разных ролей

У врача, клиента и администратора — свои экраны входа (задача **#1031**). Пришедший не по своей двери
видит понятное «этот аккаунт не зарегистрирован как специалист» и ссылку войти по своей. При этом дверь
**не сообщает, существует ли такой аккаунт** — иначе форма входа работает как справочник зарегистрированных.

### Состав каждой двери (владелец, 04.08)

Три двери — **три разных дизайна**, не один экран с переключателем. Способы входа тоже разные:

| дверь | способы | сессия |
|---|---|---|
| **пациент** | пароля нет вообще: код, OAuth, мессенджеры, passkey | долгая |
| **специалист / админ клиники** | почта + пароль + код или 2FA | обычная |
| **глобальный админ** | почта + пароль + **обязательная** 2FA | обычная |

Два следствия, требующие работы:

- **PIN снимается** — владелец 04.08: «PIN — пока не надо. Можно снять. Думаю это лишнее». Заодно уходит
  дефект, где профиль предлагал задать PIN, которым нельзя воспользоваться.
- **У пациента не должно быть пароля.** Сейчас это не запрещено кодом — ограничения по роли нет, и клиент
  технически может завести пароль. Это расхождение с моделью, а не задумка.

### Passkey — доверенный вход, второй фактор поверх него не спрашивается (владелец, 04.08)

Владелец: «модель про passkey я принимаю».

**Почему один passkey — это уже два фактора.** В `modules/auth/passkeyAuth.ts:58-60,121` стоит
`userVerification: 'required'`: ключ не сработает без биометрии или PIN самого устройства. Внутри одного
действия — и **владение** устройством, и подтверждение, что это его хозяин. По NIST это уровень «пароль +
одноразовый код». Плюс главное: passkey **привязан к домену**, подпись создаётся только для нашего хоста, и
фишинговый сайт её не получит физически — а код на почту человек фишеру продиктует. Passkey не равен паре
«пароль + код», он **сильнее** её.

**Правило, из которого всё следует: вход стоит ровно столько, сколько самый слабый способ попасть внутрь.**
Если рядом с ключом висит «войти по коду на почту», весь вход равен этому коду. Отсюда резервные пути:

- **пациент** — код нужен, иначе потеря телефона равна потере доступа; это правильный размен;
- **специалист / админ клиники** — резерв почта + пароль + код;
- **глобальный админ** — резерв **только второй passkey или 2FA**, никогда не код на почту.

**Шаг-ап вместо второго фактора на входе.** Как у банков: не спрашивать ничего лишнего при входе, но
переспрашивать ключ на опасном действии — смена почты, выгрузка данных, доступ поддержки к чужой карте.

**Известный разрыв с кодом.** Сегодня passkey сотруднику полноценным входом не засчитывается:
`app/api/auth/passkey/login/verify/route.ts:88` зовёт `prepareVerifiedPrimaryLogin`, и при включённом втором
факторе ключ его всё равно потребует. Под принятую модель это место придётся менять.

**Что ещё мешает.** Завести ключ сегодня может только пациент — экран есть лишь в
`app/app/patient/profile/PasskeySection.tsx`, а в `passkeyAuth.ts:55` захардкожено
`userDisplayName: 'Пациент BersonCare'`. Кнопка *входа* по ключу на экране есть
(`shared/ui/patient/auth/AuthFlowV2.tsx:2477`) — не хватает именно регистрации ключа для персонала.

**Telegram Login** оставляем на будущее под тумблером админки — владелец 04.08: «телеграм теперь запрещён
законом, оставить можно на будущее, но тогда надо вывести его в настройки админки».

## Мировая практика, на которую это опирается

Первый администратор заводится **в обход собственных настроек приложения**: `createsuperuser` из
переменных окружения у Django, корневая учётная запись у AWS («заприте её и работайте под обычной»),
панель поставщика у Auth0 и WorkOS. Разделение «владелец против остальных» — GitHub organization owners,
суперадмин против делегированных ролей в Google Workspace, root против IAM в AWS. Участники организации
везде заводятся приглашением; самозаписи в привилегию не существует.

Ближайшая формальная классификация того, что было до этого решения, — **CWE-269, Improper Privilege
Management**. Отдельного расхожего названия у этой ошибки нет.
