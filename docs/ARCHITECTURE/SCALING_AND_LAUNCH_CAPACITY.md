## 1. Где система стоит сейчас (факт по метрикам)

Прод-бокс `2 vCPU / 4 GB / 50 GB` при **200 клиентах / 15 активных**:

- CPU **~1%** среднее (пики 5%), RAM **1.3 ГБ из 4** (~33%), диск **~0 IOPS**, сеть — килобиты/с.
- Загрузка бокса **~2–3%**. По средней нагрузке запас ~10–15×.

## 2. Почему «упадёт от N пользователей» — неверная модель

Три вещи снимают классические обрывы и превращают перегруз в **замедление, а не крэш**:

1. **FFmpeg (HLS-транскод) — отдельный systemd-воркер, one-time на загрузку видео, ВНЕ request-path.**
   Пациенты смотрят готовые сегменты из S3, не транскод на лету. Раздача видео боксу почти ничего не стоит.
2. **Пулы Postgres в вебаппе жёстко малы (хардкод): staff `max 3`, non-staff `2`, single-режим `5`.**
   Это предохранитель: сверх пула запросы **встают в очередь**, а не роняют базу. Перегруз = латентность.
3. **Пуши — web-push (HTTP POST), IO-дёшево.** ~50/день сейчас; ×100 — ерунда по CPU.

## 3. Что реально ограничивает (по порядку)

| #   | Стена                                      | Когда бьёт                                          | Симптом                                                                 |
| --- | ------------------------------------------ | --------------------------------------------------- | ----------------------------------------------------------------------- |
| 1   | Staff-пул 3–5 × тяжёлые доктор-дашборды    | много специалистов открывают аналитику одновременно | p95 дашбордов растёт до 1–3 с                                           |
| 2   | «Эффект толпы» от планового пуша           | синхронный залп будит сотни клиентов в одну минуту  | латентность пациентских страниц                                         |
| 3   | Аналитика по растущей event-таблице        | миллионы строк без rollup                           | дашборд держит коннект секундами → усиливает #1                         |
| 4   | **FFmpeg на 2 ядрах крадёт CPU у вебаппа** | врач(и) льют пачку видео                            | всё тормозит на время транскода; при совпадении с пушем — риск swap/OOM |
| 5   | RAM                                        | далеко; пулы кэпят конкуренцию                      | —                                                                       |

Практический потолок текущего `2/4` бокса: комфортно ~**30–60 специалистов и ~2–3 тыс клиентов** при
джиттере пушей и throttled FFmpeg. «Сложится» скорее не от headcount, а от совпадения **заливка видео + пиковый пуш** на 2 ядрах.

## 4. Сценарий: 200–300 специалистов сразу (клиенты — постепенно)

Это **более тяжёлый профиль**, чем рост клиентов: специалисты сидят на дорогой стороне (дашборды + загрузка
видео) и бьют в **маленький staff-пул**. Не крэш, но две конкретные боли волны онбординга:

- **Медленные дашборды** при одновременном логине (staff-пул 3 сериализует 20–50 запросов в полёте).
- **FFmpeg-бэклог от волны загрузок** + кража ядер — острое на 2 ядрах (очередь FIFO, без приоритетов).
- Плюс внешнее: провижининг тенантов (ок, если размазан) и **rate-limit email/OTP-провайдера** на волне регистраций.

### 4.1 Чек-лист подготовки к наплыву специалистов (PROD-PREP)

- [ ] **Поднять staff-пул** `3/5 → 10–15` (хардкод в `apps/webapp/src/infra/db/webappPoolProvider.ts`;
      у Postgres `max_connections ~100` есть запас). Лучше — сделать значение конфигурируемым через env. **Самый дешёвый точечный рычаг под этот сценарий.**
- [ ] **Убрать FFmpeg с боевых ядер:** `nice`/`cpulimit` на media-worker + окно обслуживания (ночь), ИЛИ вынести
      media-worker на второй бокс (см. §6). Приоритет свежих загрузок над bulk-backfill (в очереди сейчас общий FIFO).
- [ ] **На окно запуска — временно `4 vCPU / 8 GB`** (страховка под одновременные дашборды + провижининг + транскод).
- [ ] **Rollup/кэш доктор-дашбордов**, чтобы каждый специалист не бил по сырым событиям (снимает стену #3).
- [ ] **Разбить онбординг на волны приглашений** (нет thundering-login) — организационно, бесплатно.
- [ ] **Проверить лимиты email/OTP-провайдера** под ожидаемый темп регистраций/час.
- [ ] **Индексы горячих колонок** новых онбординг-таблиц — по `.cursor/rules/db-migrations-hot-column-indexes.mdc`.

С этими мерами 200–300 специалистов заходят спокойно; без них — заходят, но онбординг тормозной и есть шанс
залипания в дни массовых загрузок видео.

## 4.2 Модель стоимости выдачи видео (подтверждено кодом 2026-07-21)

Просмотр видео пациентами **почти бесплатен для бокса** при любом масштабе:

- `GET /api/media/[id]` = **307-редирект на presigned S3 URL** (`NextResponse.redirect(signed, 307)`); клиент
  качает байты **напрямую из S3** (307 сохраняет Range для перемотки). HLS: `/playback` отдаёт JSON с master-URL,
  сегменты клиент тянет из S3. Сервер на просмотр тратит только auth + presign + редирект (~мс), **не байты видео**.
  Стоимость просмотра не зависит от размера/длины ролика. (Метрики: 1065 выдач при сети в кбит/с, диск ~0.)
- **До готовности транскода играет исходник** (`isHlsAssetReady` в `playbackResolveDelivery.ts`): пока
  `status!=="ready"` или нет master-плейлиста → `delivery: "mp4"`, прогрессивный источник (тоже с S3, редиректом).
  Нюанс: это **оригинал до 3 ГиБ** без ABR — S3-egress, не CPU бокса. После готовности HLS исходный объект
  удаляется, прогрессивный путь для такой строки закрыт, и подмены обратно на MP4 больше нет.
- Оговорка: local/no-S3 (legacy) режим проксирует байты через Node; прод работает через S3 → не касается.

**Транскод — единственное, что реально грузит бокс в upload-волне, и он уже защищён:**

- `media-worker/src/main.ts` — **одна полоса на воркер**: claim 1 job (`ORDER BY created_at ASC FOR UPDATE
SKIP LOCKED LIMIT 1`) → обработал → `sleep(POLL_MS=5с)`. Один FFmpeg за раз; очередью бокс не перегрузить.
- Но: очередь сливается **последовательно и без приоритета** (свежая загрузка за backfill — README media-worker).
  Под волну 50–200 специалистов новейший HLS может ждать часы; playback при этом работает через оригинал.
- Даже один FFmpeg на 2 ядрах конкурирует с вебаппом → `nice`/`cpulimit` или отдельный бокс.
- **Слить очередь быстрее** = запустить **несколько инстансов media-worker** (`SKIP LOCKED` делает это безопасным),
  но только на боксе со свободными ядрами → аргумент дать media-worker отдельный бокс на время волны.

## 5. Рекомендуемая архитектура НА СТАРТЕ

**Один бокс `4 vCPU / 8 GB / 80 GB SSD`, все 5 юнитов co-located, Postgres остаётся loopback-only.** (D30 Ш9:
`worker` и `scheduler` — один резидентный процесс/unit, не два; счёт юнитов уменьшился с 6 до 5.)

Почему один, а не два:

- Сохраняет **security-инвариант loopback-only Postgres** (см. baseline) — без приватной сети и её сложности.
- 4 ядра: FFmpeg (`nice`, ≤2 ядра) оставляет ≥2 ядра живому вебаппу — снимает главный риск #4.
- 8 ГБ: комфортно под расширенные пулы + Node-хипы + `shared_buffers`.
- Проще всего в эксплуатации для маленькой команды. Диск — медиа в S3, 50 ГБ хватало; 80 ГБ — запас под рост БД/WAL/логов.

Что где крутится (все на одном хосте): `webapp` + `api`(integrator) + `scheduler` (резидентный scheduler+worker
процесс, D30 Ш9) + `media-worker` + PostgreSQL 16.

**Вертикальный апгрейд ПЕРЕД сплитом:** уперся — сначала `8 vCPU / 16 GB` одним боксом (проще, без сети). На два
бокса переходить только когда одному боксу физически не хватает ядер под FFmpeg+web одновременно, либо CPU БД доминирует.

## 6. Второй бокс и БД-масштабирование — что «потом» и что это значит

Все пункты ниже **аддитивны, делаются после запуска, кода почти не трогают.** Единый предохранитель: любой
многобоксовый вариант требует, чтобы Postgres принимал соединения по приватной сети (см. §7).

- **Вынос media-worker/scheduler на 2-й бокс.** Воркеры уже автономны (общаются с системой только через
  БД-очередь + S3). Переезд = env + systemd-юнит на 2-м боксе. Даёт изоляцию CPU/RAM (FFmpeg не ворует ядра).
  **Единственная причина сделать это ДО запуска специалистов** — если ждём большую волну загрузок видео.
- **Read-replica («зеркало для чтения»).** Streaming-реплика Postgres + отдельный read-only пул, тяжёлую
  аналитику роутить на реплику. У вебаппа уже мульти-пуловая архитектура (staff/non-staff/config-reader) —
  реплика ложится тем же паттерном (+1 пул). Снимает нагрузку чтения с primary. **В коде скаффолда пока нет.**
- **Rollup-таблицы аналитики** — предпосчитанные агрегаты вместо сканов сырых событий. Чистый код, когда события вырастут.
- **НЕ форсить:** физический раскол на отдельные write/read базы, шардинг. На обозримом масштабе не нужен;
  `primary + replica` закрывает потребность «разделить чтение и запись» без раскола базы.

**Ось для понимания:** Postgres — единый хребет, он не «делится». Второй бокс даёт изоляцию CPU/RAM, но
пул-стену и стоимость аналитических запросов снимает только реплика/rollup.

## 7. Единственное ops-решение с lock-in: приватная сеть до Postgres

Сейчас (по baseline) **PostgreSQL слушает только loopback, внешний 5432 закрыт** — намеренный security-инвариант
для одно-боксовой топологии. Следствия:

- На **одном** боксе приватная сеть не нужна никогда — loopback остаётся, инвариант цел.
- **Любой** двух-боксовый вариант (§6) требует, чтобы Postgres принимал соединения по **приватной сети между
  боксами** (`listen_addresses`, `pg_hba`, TLS, private subnet/firewall). Это НЕ переделка кода (пулы уже
  env-driven) — это день ops. Код не запирает; решение принимается в момент, когда реально нужен второй бокс.
- **WAL-репликация** (снять с primary read-реплику) сейчас в планах **отсутствует**; `pgbackrest`/WAL стоит
  только как _возможный_ backup-путь, отложенный в `DR-01`. Read-replica — это отдельное будущее решение, не запертое.

**Вывод:** заранее менять ничего не требуется. «Включить приватную сеть до Postgres» — это гейт, который
пересекаешь только при переходе на два бокса, и он ломает loopback-инвариант осознанно, а не по умолчанию.
