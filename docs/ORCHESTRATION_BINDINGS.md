## Обязательный anti-error checklist оркестратора

Перед запуском и перед закрытием каждого этапа оркестратор явно проверяет:

- **Не стартовать большую инициативу без планирования.** Нужны owner requirements, roadmap, этапные acceptance-чеклисты,
  final checklist и log. Для большой инициативы применять Planner → независимый Plan-critic → Decomposer; мелкая
  локальная задача может пропустить эту фазу.
- **Не запускать исполнителя без acceptance.** В промпте есть точные пути к плану, чек-листу, логу, правилам и
  релевантному контексту; файловые scope параллельных исполнителей не пересекаются.
- **Не дробить до микрофиксов и не отдавать непроверяемую мегазадачу.** Один проход = один цельный этап, который
  исполнитель способен полностью сдать, а аудитор — полностью проверить.
- **Не засчитывать самооценку исполнителя.** После worker обязателен независимый deep code-audit с трассировкой
  исполнения, крайними случаями, пропущенным scope и безопасностью; наличие файла/класса/теста не является PASS.
- **Развести FAIL path по риску.** Presentation/layout/text/mechanical stage после своего единственного независимого
  аудита фиксирует `FAIL/BLOCKED` и **останавливается**: automatic fixer/correction/re-audit запрещены, остаток
  возвращается владельцу/оркестратору как точный checklist residual или owner question по правилам scope. Только
  high-risk stage (`identity/auth/tenant/security/migration/money/data`) использует `FAIL → fixer → независимый
  re-audit`; после двух неудачных high-risk кругов расширить scope до convergence-stage и только тогда эскалировать
  модель. Исправивший код аудитор не может верифицировать собственный fix: high-risk auditor-fix всегда получает
  отдельную независимую проверку.
- **⛔ Аудит — ГЕЙТ ПРОТИВ ПЛАНА ВЛАДЕЛЬЦА, не источник работы (запрет аудит-разгона).** Находка аудитора, которой
  НЕТ соответствующего пункта в план-файле/owner-requirements, — ВОПРОС владельцу, НИКОГДА не новая задача.
  Оркестратор не заводит скоуп из находок аудита: план владельца — единственный источник И «todo», И «done», новую
  строку скоупа заводит только владелец (или оркестратор явным вопросом ему). **Автостоп:** 2 прохода подряд без
  закрытия ни одного пункта плана владельца (только рост кода / новый файл-модуль вне плана) → жёсткий СТОП +
  эскалация владельцу, а не следующий круг. «Готово» пользовательского milestone = пункты плана владельца + зелёный
  milestone full CI + живая проверка; для промежуточного этапа достаточно предписанного ему targeted gate, а full CI
  не повторяется после каждого слайса. «Аудит зелёный» сам по себе не «готово». Прецедент 17.07 (соседний проект «мозг»): аудит стал генератором скоупа —
  каждый FAIL против выдуманных требований становился новым кругом → 3 суток, ~5.3k строк машинерии, 0 задач владельца.
  Для многопроходной работы предпочитать детерминированный конвейер (фикс-последовательность стадий, СТОП на
  завершении/FAIL) — он физически не может выдумать скоуп.
- **Не запускать визуал без достижимого сценария.** Acceptance содержит точный URL, роль/логин, seed/data scenario,
  состояния и viewport; недостижимое состояние заранее помечено `code-only`.
- **Не закрывать визуальную фичу по одному общему скриншоту.** Каждый nuance проверяется отдельно в построчной
  runtime/screenshot matrix. Обычный presentation/mechanical stage делает это в **одном** independent audit и на
  `FAIL/BLOCKED` останавливается без correction/re-audit. Visual #1 + Chief #2 используются только если linked
  high-risk/owner acceptance явно помечает item как seal-gated; Chief сначала исключает ложный отказ из-за неверного
  URL или данных.
- **Не забывать process-audit.** После каждого второго этапа отдельный быстрый аудитор перечитывает этот файл и
  текущий план и отвечает только о корректности оркестрации. Это governance-check, не второй product/stage audit: он
  не переоткрывает presentation/mechanical findings, не создаёт correction и не обходит one-audit stop.
- **Не смешивать рабочие деревья и мержеров.** Проверить `pwd`, `git status -sb`, `git worktree list`; не копить три
  и более забытых worktree; один интегратор управляет общей веткой.
- **Не гонять full CI после каждого мелкого изменения и не пропускать его на крупном gate.** После локального фикса
  можно продолжить с упавшей части, если предыдущие части доказанно прошли на том же коде; перед финальной сдачей
  нужен полный достаточный gate.
- **Не принимать неполный handoff.** Каждый агент возвращает run_id, log/report path, проверенные пункты, exact files,
  команды и результаты, остаточные риски, а аудит/план-проход — также `НАШЁЛ/ИЗМЕНИЛ`; drift при re-audit требуется
  только в разрешённом high-risk multi-round path.
- **Не оставлять завершённые сессии и процессы.** Точечно проверить/удалить известные subagent UUID, проверить
  процессы и записать результат в taskdb.
- **Не закрывать этап до фактического final gate.** Чек-листы, предписанный risk-sized audit, high-risk фиксы (если
  применимо), тесты, commit/push, worktree/process cleanup и визуальные печати (если применимо) должны иметь
  проверяемые артефакты.

## Обязательная схема исполнения плана

Эта схема применяется к планам в `docs/_TODO/**`, если владелец не дал более узкое указание. Цель оркестратора — довести работу по плану до конца и сдать её по главному финальному чек-листу, а не просто запустить несколько агентов.

### Урок 2026-07-22: roadmap-summary не является заданием или приёмкой

Провал, который это правило предотвращает: подробный linked plan содержал десятки owner-пунктов, но исполнители
получали сокращённое описание stage из roadmap, а аудиторы — общий запрос «проверь реализацию». В результате
частичная реализация получила `PASS`, хотя полные owner requirements никто построчно не проверил. Это ошибка
оркестратора и постановки, не «невнимательность аудитора».

Обязательный contract для каждого этапа:

1. **Requirements lock до worker.** Оркестратор собирает latest owner addenda, screenshots/acceptance notes,
   roadmap stage и все linked detailed plans. Каждый in-scope owner-пункт существует как отдельный checkbox с
   устойчивым ID/ссылкой. Roadmap summary только маршрутизирует к detailed checklist и никогда его не заменяет.
   Worker и auditor обязаны прочитать и исполнить/проверить **каждый** атомарный checkbox связанного authority, а не
   выбирать пункты по краткому stage outcome.
2. **Supersession hygiene немедленно.** Новое уточнение владельца в тот же рабочий проход обновляет канонический
   checkbox. Противоречащий старый текст удаляется либо помечается `SUPERSEDED — <date>, replaced by <section/id>`;
   две несовместимые active-инструкции оставлять запрещено. То же правило применяется к style guides, taskdb blocks,
   acceptance и audit prompts.
3. **Worker brief содержит сами пункты.** Недостаточно написать «см. PLAN.md». В prompt вставляются exact checkbox
   IDs/формулировки выбранного этапа, protected/out-of-scope, evidence для каждого пункта и критерий закрытия.
   Worker handoff возвращает таблицу
   `checkbox → status → code evidence → test evidence → runtime evidence → deferred/blocker reason`. Неприменимое
   evidence помечается `N/A` с причиной; defer допустим только по явному owner ruling со ссылкой.
4. **Auditor brief изоморфен worker brief.** Аудитор получает тот же полный checkbox set, latest supersession map,
   owner screenshots/states и diff range. Brief **цитирует ID и полный текст** linked plan/checklist scope; ссылка или
   roadmap summary без этих строк недостаточны. Отчёт обязан иметь по одной строке на каждый checkbox:
   `PASS|FAIL|BLOCKED → code/test/runtime evidence либо точная причина deferred/blocker`. Общий `PASS`, выборочная
   проверка или «код похож» недействительны.
   Пункт вне owner checklist классифицируется только как regression/repo-rule, owner question или recommendation;
   он не становится новым scope автоматически.
5. **Closure matrix проверяет оркестратор.** Worker `done` и audit `PASS` — входные сигналы, не доказательство
   полноты. До статуса stage done оркестратор сверяет, что в матрице нет missing/unclassified checkbox, статусы
   detailed plan/roadmap/log/taskdb согласованы, нужные targeted/full gates прошли, а live-пункты проверены на
   достижимом сценарии. Непроверенный пункт остаётся `[ ]`, даже если stage summary зелёный. Stage status, taskdb и
   `LOG.md` **не могут** говорить `done/completed/PASS`, пока любой referenced checkbox открыт; единственное
   исключение — явный defer/cancel владельца, записанный на этой строке с трассируемой ссылкой и причиной.
6. **Debt-first reconciliation.** Если этап/план уже назывался завершённым без такой матрицы, сначала выполняется
   read-only reconciliation полного linked checklist. Найденные owner-residuals получают exact task/scope и
   закрываются до перехода к downstream stage; ранее доказанное не переделывается. Для текущего Doctor UI до полного
   закрытия атомарного UI checklist постоянно держится минимум один независимый UI workstream, если есть ready scope.

Эти шесть пунктов обязательны в каждом новом worker/auditor/correction brief: агент не может проверить то, чего
оркестратор не включил в acceptance contract.

### Единица прохода
- Один исполнительский проход = один полноценный связный этап плана: не микрослайс на одну мелкую правку и не
  бесконтрольная мегазадача. Агент получает достаточно широкий scope, чтобы понять и согласованно исправить всю
  картину этапа, а не две строки вокруг одного симптома.
- У каждого этапа должен быть свой чек-лист. Если чек-листа нет, оркестратор сначала добавляет или требует добавить его в план, иначе исполнителю нечего сдавать, а аудитору нечего проверять.
- После каждого второго этапа оркестратор запускает быстрого аудитора процесса с вопросом: "Корректно ли идёт
  оркестрация?". Этому аудитору обязательно дать перечитать этот документ и текущий план. Он проверяет только процесс
  и не является вторым audit/correction pass по результату presentation/mechanical stage.
- Планирование, исполнение, полный аудит и осмысленный checkpoint — границы работы. Не запускать повторные
  test/diff/commit циклы после каждой мелкой правки внутри этапа.

### Цикл этапа
1. **Исполнение:** запустить субагента `worker` через доступный spawn tool на один полноценный проход по выбранному
   этапу. В промпте дать не только ссылки, но и exact checkbox IDs/текст полного чек-листа этапа и финального
   чек-листа, supersession map, `AGENTS.md`, `.cursor/rules/*`, релевантные
   docs и этот документ. Исполнитель ведёт лог и сдаёт весь этап, а не произвольную короткую часть.
2. **Полный аудит:** отдельный независимый агент проверяет весь результат этапа против того же полного чек-листа и
   фактического кода/данных/документов. Аудит не ограничивается последним diff или одним finding. Для безопасности,
   tenant isolation, миграций, интеграций и сложной продуктовой модели нужен сильный reasoning; механическая проверка
   не получает xhigh «на всякий случай».
3. **Интегрированная коррекция — только high-risk:** если high-risk аудит нашёл связанные замечания, один correction
   owner получает весь этап, полный audit report, исходные требования и свободу исправить соседние причины
   согласованно. После этого проводится один полный **независимый** re-audit; correction owner/auditor, который менял
   код, не проверяет собственный fix. Для presentation/layout/text/mechanical stage этот пункт не применяется:
   единственный audit пишет `FAIL/BLOCKED` и останавливает stage без automatic correction/re-audit.
4. **Модель выбирается вместе со scope high-risk correction:** сильную/дорогую модель нельзя тратить на узкий patch
   по одному finding. В разрешённом high-risk path узкий локализованный фикс делает correction owner или дешёвый
   fixer, после чего fix проверяет независимый аудитор. Если зовём сильную модель, ей дают цельный
   stage/convergence scope: перечитать план, текущий diff, все audit findings, найти соседние причины, исправить
   систему целиком и сдать проверки. Повышенный reasoning effort не использовать как замену нормальной постановке.
5. **Классификация незавершённости:** до retry/escalation определить, что произошло: агент ещё работает; не получил
   достаточно времени; был прерван/ограничен; не получил контекст; получил слишком узкий scope; нашёл новый класс
   проблемы; либо завершил полноценную попытку и действительно не решил тот же класс ошибки. Только последний случай
   считается substantive failure.
6. **Эскалация после повторного содержательного провала high-risk stage:** два завершённых полноценных прохода должны провалить тот
   же класс проблемы при достаточных времени, контексте и scope. Сначала расширить постановку до цельного
   stage/convergence scope; затем дать её более подходящему сильному исполнителю. Если и полноценный сильный проход
   не закрыл проблему — записать blocked note с доказательствами и обратиться к владельцу. Таймаут или незавершённая
   попытка не засчитывается как один из двух провалов.

### Универсальный режим исполнения многоэтапного плана (обязателен для ЛЮБОГО плана — усиление 18.07)

«Цикл этапа» выше описывает ОДИН этап. Этот раздел — как вести весь план из многих этапов, чтобы не сползти ни в
аудит-разгон, ни в лишнюю сериализацию. Приоритет над общими формулировками при расхождении. Мотивирующий провал
(18.07): presentation-этап получил ~10 кругов worker→аудит→коррекция на правку в 2 файла — каждый круг находил
НОВУЮ косметику, поэтому предохранитель «2 содержательных провала» из «Цикла этапа» не срабатывал, а стадия стояла.

1. **Глубина аудита — по риску этапа, с жёстким потолком кругов.**
   - Presentation / вёрстка / текст / механика (рендер-матрица, перепись роутов, lint/format, тривиальный рефактор,
     docs) = worker + **ОДИН** независимый аудит. Серийные correction-раунды здесь запрещены.
   - Высокий риск (identity / auth / tenant-isolation / security / миграции / биллинг-деньги / данные / необратимое) =
     полный многораундовый адверсарный цикл из «Цикла этапа».
   - **Потолок независимо от риска:** >2 correction-раундов на ОДНОМ этапе без закрытия его чек-листа = ЖЁСТКИЙ СТОП,
     без 3-го круга, даже если каждый раунд ловит РАЗНУЮ мелочь. Это сигнал: требование неоднозначно или аудитор
     генерит скоуп. Неснятую дельту эскалировать владельцу одним вопросом (`owner_waiting` + `question` в taskdb), не
     открывать новый круг. Это отдельный предохранитель от «2 содержательных провала»: там ловится повтор ОДНОГО
     класса провала, здесь — суммарный косметический разгон на мелком этапе.
2. **Параллель на независимом file-scope.** Если план даёт слайсы/этапы с непересекающимися файлами — гнать их
   ОДНОВРЕМЕННО, каждый в своём worktree, ≤3 параллельно (лимит нагрузки). Сериализуется только конкуренция за общий
   ресурс: единый dev-сервер для живого скрина, heavy CI под mutex. Implementation / tests / typecheck общий ресурс не
   требуют. Не гнать заведомо независимое по очереди «для порядка» — это прямая потеря скорости.
3. **Приёмка владельца — В СЕРЕДИНЕ плана, не только в финальном гейте.** После каждого пакета пользовательски-видимых
   этапов (а не в самом конце) выкатывать накопленное туда, где владелец видит ЖИВО (web: code-only деплой на TEST без
   prod-дампа, `deploy/host/deploy-test.sh`), и передавать на клик-through. Это ловит неверное направление рано.
   **«Готово» пользовательского milestone = галочки чек-листа владельца + один зелёный full CI на накопленном точном
   SHA + живая проверка. Промежуточный слайс закрывает свой targeted gate и ждёт общего milestone CI; full CI после
   каждого мелкого слайса запрещён. «audit PASS» сам по себе — гейт, НИКОГДА не критерий завершения** (усиливает
   якорь из запрета аудит-разгона).
4. **Развилки владельца — заранее одним листом.** Перед этапами, зависящими от открытых продуктовых решений, свести
   ВСЕ pending owner-gates в ОДИН плейн-лист: по каждому — рекомендация + safe-default, простым языком. Владелец
   закрывает за присест, зависимые этапы едут без блоков. Не гадать развилку в середине этапа и не дёргать владельца
   по одному вопросу за раз.

### Документация и токен-дисциплина (код важнее прозы) — усиление 23.07

Мотивирующий провал (22–23.07): прогон потратил ~60% токенов на прозу (reality-audit эссе, evidence-матрицы на
167 строк, reconciliation-нарративы, provenance-заметки), а не на код. Верификация обязательна, но её артефакт
должен быть **дешёвым и по возможности исполняемым**, а не эссе. Приоритет над общими формулировками при расхождении.

1. **Verification ≠ documentation.** Проверять каждый owner-checkbox обязательно; превращать проверку в длинный
   markdown — нет. Там, где проверка механическая, доказательство = машинно-проверяемый артефакт:
   - предпочитать исполняемый gate прозе: contract-тест или census-скрипт (эталон — D0
     `docs/_TODO/SAAS_FOUNDATION/scripts/rubitime-r6-r7-static-inventory.mjs`). Сам скрипт + его зелёный прогон ЕСТЬ
     доказательство; отдельное эссе к нему не пишется.
   - зелёный targeted-тест закрывает свою строку матрицы ссылкой на имя теста, а не пересказом.
2. **Evidence — строка, не нарратив.** Одна строка на checkbox: `id → PASS/FAIL/BLOCKED → путь:строка | тест | SHA`.
   Без вводных абзацев, повторов требований и пересказа истории. Если evidence влезает в commit message / PR-описание —
   отдельный файл не заводить.
3. **Не плодить новые доки.** Отдельные файлы reality-audit / reconciliation / evidence-matrix допустимы ТОЛЬКО как
   заранее предусмотренный plan output или обязательный audit record. По умолчанию статус пишется В МЕСТЕ: checkbox в
   плане + одна строка evidence + SHA. Debt-first reconciliation (Урок 22.07) выполняется один раз read-only и не
   превращается в серию нарративных файлов.
4. **Оркестратор не пишет прозу своим контекстом.** Дорогая модель-оркестратор не тратит свой контекст на сочинение
   документов. Нужен write-up — делегировать дешёвой модели минимальным заданием, либо это ведёт worker в своём
   кратком логе. Логи агентов краткие (см. «Минимальный отчёт агента»), не эссе.
5. **Провенанс без театра.** Не переписывать в markdown то, что уже есть в git (diff, commit message) и taskdb
   (status / commit_ref / note). Owner ruling фиксируется ОДНОЙ строкой со ссылкой, не пересказом.
6. **Смелл-тест на границе этапа:** если этап произвёл больше строк документации, чем строк кода/тестов — это красный
   флаг разгона прозы. Спросить: документ реально нужен для старта следующего этапа или это самодокументирование? По
   умолчанию — не писать.
7. **Process-audit лог — коротко.** Вердикт процесс-аудита = несколько строк (verdict + конкретные corrections), один
   компактный append в ОДИН лог-файл, не новый файл на каждый прогон.

Цель: доминирующая доля токенов и коммитов — в коде и тестах. Документация обслуживает работу, а не заменяет её.

### Обязанности оркестратора
- Писать точные промпты: что делать, где план, exact checkbox IDs/текст, superseded map, какие правила читать, что
  считать готовым, куда писать лог, какие проверки запустить. Ссылка на roadmap/stage summary без атомарных пунктов
  является неполным brief. Audit brief обязан процитировать ID и полный текст linked checklist scope, а не только
  назвать roadmap stage или путь к detailed plan.
- Выбирать модель и reasoning effort оптимально под задачу. `xhigh` не запрещён, но не должен быть дефолтом "на всякий случай": обычно достаточно среднего или высокого effort в зависимости от риска, размера и неясности этапа.
- Если доступный spawn-интерфейс не предоставляет явного выбора model/effort, не делать вид, что override применён:
  компенсировать цельным scope, полным контекстом и достаточным временем, а ограничение записать честно.
- Оценивать длительность по объёму. Полная проработка или аудит могут занимать 5–20 минут и дольше; не ставить им
  короткий deadline и не интерпретировать рабочую тишину как провал. Технический mailbox wait/status check не должен
  прерывать агента, менять его scope или запускать дублирующий проход.
- Контролировать, что агенты пишут лог, не уходят от темы, не зависают и не остаются зомби-процессами или забытыми сессиями.
- Проверять coverage matrix `checkbox → worker evidence → auditor verdict → live/test evidence`; ни один missing или
  unclassified пункт не допускает stage done. Исполнитель сдаёт, а аудитор построчно проверяет один и тот же
  latest-checklist, не summary и не только слова исполнителя. Для каждой строки нужны code/test/runtime evidence
  либо точная трассируемая причина owner-deferred/blocker; агрегатные `done`/`PASS` не закрывают строки.
- Не допускать накопления трёх и более незамердженных и забытых worktree. Перед новым этапом проверять активные worktree/сессии; после завершения этапа мержить нужное, удалять ненужное, реапить процессы.
- Держать коммиты небольшими и осмысленными, регулярно бэкапить ветку пушем в интеграционную/текущую рабочую ветку. `main` и `test` не трогать без прямой команды владельца.
- Не гонять full CI на каждый мелкий чих, но и не давать накопиться длинной цепочке изменений без полного прогона. Практическое правило: targeted tests на каждом этапе, full CI на крупных гейтах, перед финальной сдачей и когда накопился существенный пакет коммитов.
- Если полный или длинный тестовый прогон упал в середине, а предыдущие шаги этого же прогона точно уже прошли на том же коде, после локального фикса можно начинать с релевантной упавшей части, а не обязательно с самого начала. Перед финальной сдачей всё равно нужен достаточный полный gate по риску плана.
- Обновлять существующие канонические документы, checklist и лог на границе содержательного этапа. Не создавать ad
  hoc файл с новой версией правил/решений, если уже есть канон: исправить его на месте или явно пометить старый текст
  историческим. Новый документ допустим только как заранее предусмотренный plan output или обязательный
  audit/evidence record.
- Разделять `owner ruling`, repository/current fact, recommendation, safe default и unresolved decision. Решением
  владельца считается только его явное трассируемое утверждение; вывод агента нельзя записывать как решение владельца.

### Очистка зомби-субагентов
- Если UI/лимит показывает зависшие Codex-субагенты, а `wait_agent` уже вернул по ним `completed`/`failed` или они явно больше не участвуют в текущем этапе, чистить их через CLI, а не оставлять "до потом".
- Сначала проверить форму команды: `codex delete --help`. Для точечных завершённых сессий использовать только точные UUID:
  ```
  codex delete --force <subagent-session-uuid>
  ```
- Удалять только известные subagent-session UUID текущей оркестрации. Не удалять текущую основную Codex-сессию, app-server/proxy/code-mode-host процессы и чужие процессы из других проектов без отдельного явного решения владельца.
- После удаления проверить, что не остались рабочие процессы по текущему плану:
  ```
  ps -eo pid,ppid,stat,lstart,cmd | rg 'codex|multi_agent|subagent|<plan-key>|vitest|tsx'
  ```
  В этой проверке отличать системные процессы Codex Desktop (`app-server`, `proxy`, `codex-code-mode-host`) от реально запущенных worker/audit/fixer процессов.
- Если `rg` по `.codex` всё ещё находит UUID только в основном логе текущей сессии, это не означает живую subagent-сессию: логи родительского чата сохраняют исторические упоминания. Живой проблемой считать отдельную сохранённую сессию или процесс.
- Результат очистки обязательно записать в taskdb через `{TASKDB}`: какие UUID удалены, что процессы проверены, запускались ли новые агенты после очистки.

### Минимальный отчёт агента
Каждый исполнитель, аудитор и фиксер должен вернуть:
- `run_id` / имя сессии или агента;
- путь к логу;
- какие пункты чек-листа проверены;
- какие файлы/модули реально смотрел или менял;
- какие проверки запускал и их результат;
- явные остаточные риски или блокеры.

### Финальный gate плана
Перед финальной сдачей оркестратор сверяет:
- все этапные чек-листы закрыты исполнителем и проверены аудитором;
- главный финальный чек-лист плана закрыт;
- фиксы по аудитам либо выполнены, либо явно deferred/cancelled владельцем с трассируемой ссылкой; обычный
  follow-up, recommendation или агентский `BLOCKED` не позволяет пометить исходный stage/taskdb/LOG как done;
- нет забытых worktree, зомби-процессов и неподтверждённых агентских веток;
- изменения закоммичены и запушены в разрешённую ветку;
- уровень тестов соответствует риску накопленных изменений.
